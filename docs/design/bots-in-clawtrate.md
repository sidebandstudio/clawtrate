# Bots in Clawtrate: what a bot knows about the app and what it can do there

How a bot that talks with its person in Clawtrate knows where it is, the tools it has to change things in Clawtrate (itself, its work, the conversation, other bots, the app), who decides each change, how a tool call becomes a change with a record and Undo, and how Clawtrate's own plugin reaches a person's gateway with nothing typed (issue #436, with #544's second half, #532's loop and #666). This is a design for sign-off: it builds nothing.

**Established** marks what the repository or OpenClaw's own source and documentation show today. **Proposed** marks this design's choice. **Not established** marks what could not be shown here, with what would show it (section 12). OpenClaw facts are from the published packages `openclaw@2026.10.6` and `openclaw@2026.11.10`, read only. `<1006>/…` and `<1110>/…` are paths inside each package. 2026.11.10's `dist/` is minified onto few lines, so for it the file and the function or schema are named instead of a line.

It builds on, and doesn't redesign:

- **The Main Bot design** (`main-bot-onboarding.md`): its `clawtrate-bots` plugin, the proposal records, the cards, the journal and Undo (its sections 5 to 9). This document narrows its section 6: the tools a bot sees are the ones in section 2 here, and its records, cards and journal carry them.
- **The first run** (the Main Bot design's first-run revision, #493): the first run's script and screens are that design's. This one gives it the tools it calls and says exactly when a person's answer there is the confirmation (section 4).
- **The guides** (`packages/core/src/guides.ts`, #544's first half): the section Clawtrate writes at the top of each bot's `AGENTS.md`. Section 7 adds one paragraph to it.
- **Tasks a bot starts** (#532's first three steps, on `main`: F-565, F-566, F-587), with the gateway's own `sessions_spawn`, `sessions_send` and `sessions_history`.

## The page to decide from

### What a bot will know and be able to do

A bot in a Clawtrate conversation knows it is in Clawtrate, and knows it from Clawtrate, not from a guess: one call, `clawtrate_here`, tells it whether this conversation is one its person is having in Clawtrate, which conversation it is, what its person can see of its work, what it may do here, and who decides each thing. It knows its tasks and which of them wait for its person. It knows the bots it can hand work to.

It can act on Clawtrate the way a person would ask an assistant to: take the name its person gives it, start a task and report back, open a task or its work panel beside the conversation, turn on its own check-ins, pause one of its routines, show its commands. For anything bigger it asks first, on a card that shows exactly what would change: a new routine, a change to its own instructions, its model or how freely it runs commands, a new bot, another bot's settings. No tool deletes anything, touches an account, or changes OpenClaw itself.

Every change lands in the record of changes and comes with Undo where it can be undone. A change only counts as the person's request when the person typed it in Clawtrate, in that conversation, on that device. A web page, a file, a tool's output, another bot, a routine or a chat-app message never counts.

Clawtrate installs the plugin that gives bots these tools by itself, on any gateway it has full control of, with nothing asked. Settings shows it, with Off and Remove.

### Four exchanges, and what the person sees

1. **"Call yourself Juniper."** By default the bot asks first. Under its reply, a card reads "Pip asks to be called Juniper", with **Rename** and **Not now**. One click on **Rename**: the sidebar, the header and the bot's settings say Juniper as soon as the gateway reads it back, and the card says "Renamed to Juniper" with **Undo**. With "Bots apply your requests to themselves at once" turned on under Settings → Advanced (off by default), there is no card: the name changes and the conversation shows one line, "Renamed to Juniper · Undo". In the first run, when the bot has just asked "What would you like to call me?" and the person types "Juniper", the name changes at once in the same way, with no card.
2. **"Put this in a task and tell me when it's done."** The bot starts a task under its own name. A "Started a task" card appears where it was asked, and the task appears in the sidebar with its work panel; the person can open it and step in at any point (this much is on `main`). When the task finishes, the gateway wakes the bot, and the bot tells its person what came back in a sentence or two (the guide on `main` asks it to). New here: if the task stops to wait for the person (an approval, a question), the bot says so in this conversation once, "The trail comparison is waiting for you to approve a command", and its own task list says "Waiting for you".
3. **"What can you do here?"** The bot calls `clawtrate_here` and answers from it, briefly: "I'm talking with you in Clawtrate. I can put work into tasks you can watch and step into, open a task or its work panel beside this chat, change my name or picture, turn my check-ins on or off, pause my routines, and show my commands. Bigger changes, like a new routine, my instructions or a new bot, I'll ask you about on a card first. I can't delete anything or change accounts."
4. **"Show me what the trail task did."** The bot opens that task's work panel beside the conversation at once. Had the bot offered it on its own, it would have been a card with **Open** instead.

### The decisions, with a recommendation and what each costs

1. **Who applies a change.** _Recommended:_ Clawtrate applies every change, with the person's own access, on both OpenClaw versions. The plugin records what the bot asked for and what started the run, and never writes a bot's settings itself. _Why:_ neither version gives a plugin a write it can bind to the bot it read (`agents.update` takes no precondition on either, section 5), and a tool's authority is its turn's connection, not the person's consent. _Cost:_ a change applies only while a Clawtrate with full control is connected. When none is, a request that would apply at once becomes a card, and the bot is told so.
2. **What counts as the person asking.** _Recommended:_ two independent checks, both required: the gateway's own record of what started the run (stamped by the plugin from the gateway's hooks: the gateway's own chat channel, the owner as sender, no message from another session or the system), and Clawtrate's own record that this device sent that very message in that conversation. Anything that fails either check, or that can't be checked, becomes a card. Nothing is refused for being unknown. _Cost:_ a message typed in the gateway's own web page or its command line never applies at once.
3. **The first run's answer.** _Decided by the first-run design:_ when the bot asks for its name in the guided first run and the person types it, that answer is the confirmation, applied at once with Undo. This design makes it exact (section 4): the first run is at its name step, the message is one this device sent there, and the name applied is text the person typed in it. _Recommended for the general case:_ the same rule (the value applied must be in the person's own words) is what keeps a change applied at once to what the person typed, so the Advanced setting can be on by default for a bot's name and picture once the first run has shipped. _Until the owner decides that, the 2026-11-23 decision stands:_ a card by default, the setting off.
4. **A routine a bot sets up for itself.** _Recommended:_ a card first, even when asked, because a routine is standing instructions that run when nobody is watching: a web page read in a turn the person typed could otherwise leave a routine behind that keeps acting on it. Pausing a routine and turning check-ins on or off apply at once. _Cost:_ "check my inbox every morning" takes one click on the card.
5. **Handing work to another bot.** _Recommended:_ letting Pip start tasks for Marlow always asks (it is more freedom). Once allowed, a hand-off the person asked for happens at once, because it changes nothing of Marlow: the task carries Pip's limits. _Cost:_ one card, once per pair of bots.
6. **Installing the plugin.** _Recommended:_ by default, with nothing asked, on any gateway Clawtrate has full control of, exactly the version and bytes the signed app names (section 6 says why that asks nothing, and the only cases that do). On the gateway's own computer it installs from a copy inside the app and needs no package registry, so it can ship first. On another computer the gateway downloads it from npm, which needs the project's npm scope and its publishing set up (section 6.9). _Cost:_ the plugin's own security review gates the first install on a real gateway.

### What ships first

Ten pull requests in section 10. **The first a person can see is the fourth:** on a gateway on the person's own computer, Clawtrate installs its plugin by itself, and a bot asked "call yourself Juniper" offers the rename on a card (or, in the first run, takes the name at once), and answers "what can you do here?" from what Clawtrate tells it. The three before it are the record of which messages a device sent, the plugin's reading of what started each run with the read tools, and the name tool with its record and Undo, each checked on development gateways of both versions. The fifth brings the same to a gateway on another computer, once the npm publishing is set up.

## 2. The tool surface

The class is who decides (section 3): **reads** change nothing; **at once**, **card first** and **always asks** are the three classes for anything that changes. "Exists today" says whether there is a gateway tool, a Clawtrate plugin method, or nothing, and on which version. Each Clawtrate tool is **Proposed**, in the `clawtrate-bots` plugin.

### Not offered to a bot

Deleting anything (a bot, a task, a routine, a file); signing an account in or out; installing, enabling or removing plugins; OpenClaw's config, its updates (`update.run`) and restarts; pairing and devices; another bot's instructions without a manager grant. Each stays in Settings, where the person does it. The managed policy keeps denying the gateway's own `gateway`, `plugins` and `openclaw` tools (`main-bot-onboarding.md` §12), and on 2026.11.10 the gateway tool's actions grew to `restart` and `update.cleanup` (`<1110>/dist/openclaw-tools-Dq3X7AxA.mjs`, `GATEWAY_ACTIONS`), which that denial covers.

### What the first run needs first

The first run (#493) needs, in order: `clawtrate_identity` for the name it is given (and the picture), applied at once under section 4's first-run rule; the gateway's `sessions_spawn` to start a small task the person watches appear (on `main`); a file handed over with `MEDIA:` (on `main`, 2026.10.6); an approval (on `main`). So of this design's tools it needs `clawtrate_identity` first, and `clawtrate_here` so the bot can say what it can do. Section 10 orders the pull requests that way.

## 3. Who decides

Three classes for anything that changes, and no others. Reads change nothing and return only what the person could see (section 8).

| Class           | When                                                                                                                         | What it means                                                                                                                                                                           | Tools                                                                                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **At once**     | Reversible, about the bot's own work or the person's own view, and asked for by the person in this conversation (section 4)  | Applied by Clawtrate as soon as it reads the request, written to the record of changes, shown with Undo. Not asked for (the bot's own idea, a check that can't be made): a card instead | `sessions_spawn` (own tasks, and within a hand-off grant), `sessions_send`, `clawtrate_show`, `clawtrate_checkins`, `clawtrate_routine_pause`, `clawtrate_view` |
| **Card first**  | The default for a bot changing itself (the owner's decision on #436, 2026-11-23), and for anything a bot proposes on its own | A card with exactly what would change; the person's click applies it with their access; then the record and Undo                                                                        | `clawtrate_identity` (with the two exceptions in section 4), `clawtrate_task_propose`, `clawtrate_routine_propose`                                              |
| **Always asks** | Another bot, permissions or freedom to run commands, accounts, spending, a bot's instructions after its first run            | A card, marked, whatever any setting says, needing full control to apply                                                                                                                | `clawtrate_change_propose`, `clawtrate_bot_propose`                                                                                                             |

The reason for each:

- **`sessions_spawn`, `sessions_send`, at once.** A task is the bot's own work, listed under it, and stopped or deleted by the person like any task. It never gets more than the bot that started it: on 2026.10.6 a started task carried its bot's denies, even under another bot, and permanently lost `sessions_send`, `cron`, `gateway` and the rest (run on a development gateway during #532). The hand-off to another bot rests on a grant that always asks.
- **`clawtrate_show`, `clawtrate_view`, at once.** They change what this device shows and nothing on the gateway.
- **`clawtrate_checkins`, at once.** The check-in's words stay the person's; the tool takes no prompt. Its interval is bounded (section 8), which bounds what it spends.
- **`clawtrate_routine_pause`, at once.** It makes the bot do less. Resuming restores what the person set up.
- **`clawtrate_identity`, card first.** The owner's decision. Its two exceptions are in section 4.
- **`clawtrate_task_propose`, card first.** It is the bot's own idea by definition.
- **`clawtrate_routine_propose`, card first.** A routine's prompt is standing instructions that run on a schedule with nobody watching, and in a routine's run an Ask rule is a refusal, not a question (`plugins/clawtrate-tool-rules/README.md`, "The card"). Text from a page the bot read in a turn the person typed must not be able to leave one behind.
- **`clawtrate_change_propose`, always asks.** Instructions: by the owner's decision on #436, a later change to a bot's own instructions asks first whatever the setting. Model and effort may cost more. Autonomy and rules are freedom. Account is an account.
- **`clawtrate_bot_propose`, always asks.** Another bot.

## 4. What counts as the person asking

**Exactly a message the person typed in Clawtrate, in that conversation.** Clawtrate establishes it with two independent records, and needs both.

### 4.1 What the gateway records about a run (both versions)

- **The run's origin, in the gateway's hooks.** Every run's prompt-building hooks get the run's `runId`, `sessionKey`, `trigger`, `channel` and `inputProvenance`, and the event carries `currentUserMessage` (Established: `<1006>/dist/config-contracts-C65kIjn4.d.ts:8790-8855`; `<1110>/dist/config-contracts-CmjbWZfI.d.ts:24608-24651`). `inputProvenance.kind` is `external_user`, `inter_session` or `internal_system` (`<1006>/…C65kIjn4.d.ts:717`; `<1110>/…CmjbWZfI.d.ts:654-666`). A plugin outside OpenClaw needs `plugins.entries.<id>.hooks.allowConversationAccess: true` for those hooks (`<1006>/docs/plugins/hooks.md:125-130`).
- **A tool call's run.** The `before_tool_call` hook gets the call's `runId`, `toolCallId` and `sessionKey`, and a `requester` with `channel`, `senderId` and `senderIsOwner` (`<1006>/…C65kIjn4.d.ts:9812-9848`; `<1110>/…CmjbWZfI.d.ts:25183-25206`, which adds `trigger`). The tool's own context gets `messageChannel`, `requesterSenderId` and `senderIsOwner` on both (`<1006>/…C65kIjn4.d.ts:40600-40615`), and on 2026.11.10 also `runId` and `inputProvenance` (`<1110>/…CmjbWZfI.d.ts:48269-48276`). OpenClaw calls these "facts for plugin-owned policy, not authority" (`<1110>/docs/plugins/tool-plugins.md`, "toolContext.inputProvenance").
- **What a message from Clawtrate looks like.** `chat.send` runs under the client's own `idempotencyKey` as its run id (`<1006>/dist/chat-send-handler-D_7lP5Io.mjs:4271`; `<1110>/dist/chat-send-handler-D686bqTH.mjs`, the same assignment), and an operator's send is on the gateway's own channel, `webchat` (`<1006>/dist/gateway-client-identity-E44CR5D-.mjs:63-80`, `message-channel-constants-B3vfipkP.mjs:3`; the same in 2026.11.10's `gateway-client-identity-DuRa4HsY.mjs`). Its first row is stored as `<run id>:user` (`docs/decisions.md`, the `chat.history` row of "Usage"). A message another bot sent with `sessions_send` carries `provenance: {kind: "inter_session", …}` (`docs/decisions.md`, "chat.history shows a bot's message to the recipient as an assistant row"). A client-supplied provenance or origin is accepted only from an admin or trusted caller (`<1006>/…chat-send-handler-D_7lP5Io.mjs:5428`).

**Proposed:** the plugin keeps, per run, `{runId, sessionKey, trigger, channel, inputProvenance.kind, senderIsOwner, the first 4,000 characters of currentUserMessage}`, for 24 hours or 512 runs, in its bounded store. On 2026.10.6 the tool learns its run from `before_tool_call` (by `toolCallId`); on 2026.11.10 from its own `runId`. The plugin calls a run **typed here** when: the channel is `webchat`, the sender is the owner, `inputProvenance` is absent or `external_user`, and the trigger, where given, is the person's (`user`).

### 4.2 What Clawtrate records (both versions)

**Proposed:** each Clawtrate device keeps the idempotency keys of the messages it sent, per gateway and conversation, with the text it sent, for 24 hours or 256 messages (registered in `owners.ts` and the documented totals). A device claims a request as the person's only when its run id is one of its own keys for that conversation.

### 4.3 The rule

A request is **the person asking** when the plugin says its run was typed here **and** the device that applies it sent that run in that conversation. Then an **at once** tool applies at once. In every other case, including when a field is missing, the hooks aren't allowed, the run id isn't the device's, or the gateway is a version whose fields this build doesn't know, the request becomes a card. A card is never refused for being unknown: the person can still apply it.

**The name and picture (`clawtrate_identity`) have one more condition:** the value applied must be in what the person typed. The name, with its spaces collapsed and compared without case, appears in the device's own copy of the message; a picture's avatar is named in it. "Call yourself Juniper" passes; "you choose" followed by the bot picking "Maple" does not, and becomes a card. This is what keeps a page, a file or a tool's output read in that same turn from choosing the bot's name.

### 4.4 The two exceptions to "card first" for a bot's own name and picture

1. **In the guided first run** (Decided, with the first-run design): the first run's record in the plugin is at its name step, for this bot and this conversation; the run is the person's (4.3); and the name is in their message. Then the answer is the confirmation: applied at once, read back, with "Named Juniper · Undo" and no card. Once per first run; a second change in it is a card. What the first run's record holds, and how the app opens and closes its name step, is the first-run design's.
2. **With "Bots apply your requests to themselves at once"** on, under Settings → Advanced (off by default, the owner's decision): the same three conditions without the first-run record. A later change to the bot's instructions still always asks.

### 5.1 What each version allows

| A plugin writing as the person            | No: a tool's gateway call carries its turn's connection, and the docs call run facts "not authority"                                                                            | The same; `api.runtime.gateway.request` acts as the current caller (`<1110>/docs/plugins/tool-plugins.md`, the guard paragraph) |

### 5.2 The choice: Clawtrate applies, for every class, on both versions

**Proposed.** The plugin records; Clawtrate applies with the person's own access.

1. **The bot calls a tool.** The plugin checks the input's bounds, takes the bot from the tool's own context, finds the run's origin (4.1), and writes a request into its ledger (the records `clawtrate-bots` already keeps: versions, ledger, journal) with the tool, the values, the class and the origin. It fires `plugin.clawtrate-bots.changed`.
2. **At once.** The device that sent that run (4.2) claims the request, checks 4.3 (and 4.4 for a name), reads the target afresh, writes with its own access and the write's own precondition where the gateway has one, reads back, and records the effect in the journal with a new admin method, `clawtrate-bots.changes.record`. The tool waits up to 15 seconds for that and returns what was read back.
3. **Not claimed in 15 seconds** (no Clawtrate with full control connected on that device, a read-only connection, the device closed): the request becomes a card for any of the person's devices, and the tool says so (5.4).
4. **Card first and always asks.** The tool returns at once. Every connected Clawtrate shows the card in that conversation and in the gateway menu's Proposals list. **Apply** on the card is the person's own edit: Clawtrate reads the bot again, checks it is the same bot with the values the card was drawn against, writes, reads back, and records it. This is what F-552's Rename card already does on `main`, so on 2026.10.6 the card applies directly instead of opening the editor (the Main Bot design gated a stored request applied later by the plugin, not a person's click that reads first).
5. **The record of changes.** Each confirmed effect is a journal entry on the gateway (`clawtrate-bots`' journal, retained 90 days), so every device shows it. **Undo** is a new edit by Clawtrate, written only when the field still holds the journaled result, under that read's precondition where the gateway has one; a field changed again since says so and offers its editor (the Main Bot design §8).

**Why not the plugin.** Neither version gives a rename that refuses a bot other than the one read, or a write bound to a bot's incarnation (5.1). A tool's gateway call acts with its turn's connection, which says nothing about what the person agreed to. And Clawtrate already writes every one of these fields with both versions' differences handled (check-ins differ on 2026.11.10, #616), so applying in one place keeps one path.

**What this guarantees.**

- **A bot can never widen its own permissions through a tool.** The plugin has no write path to bots, config or plugins. Clawtrate applies only the fields its class table names. Anything that adds freedom, an account or a cost is always asks, marked, and needs full control. No tool takes a tool policy, an exec mode, a plugin or a grant except `clawtrate_change_propose` and `clawtrate_bot_propose`, which only make cards.
- **Every change is in the record of changes,** with Undo where it can be undone: name, picture, check-ins, a routine's pause, a routine added from a card (removed by Undo), a hand-off grant, a view switch (kept on the device, with Undo in its line). A task started is shown, not journaled: the person stops or deletes it as any task.
- **On 2026.10.6 a name's Undo carries the race F-552 carries:** a change another admin makes between Clawtrate's read and `agents.update` can be overwritten without anyone being told.

### 5.3 The first run and the tools

The first run's name step uses step 2 with 4.4's first rule. Everything else in the first run is the gateway's own (a task, a file, an approval). The first-run design owns what the app does when the bot goes off script; this design guarantees only that nothing applies at once except the name the person typed, once.

### 5.4 What the bot is told

| Result                             | Words the tool returns                                                                                                                                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Applied                            | "Done: you're now called Juniper. Your person can undo it in Clawtrate."                                                                                                                                          |
| Became a card                      | "I've asked your person in Clawtrate. Nothing changes until they confirm it."                                                                                                                                     |
| No Clawtrate connected             | "Clawtrate isn't connected with full control right now, so this is waiting for your person as a request. Nothing has changed."                                                                                    |
| Not this conversation in Clawtrate | "This conversation isn't one your person is having in Clawtrate, so it's waiting for them there as a request. Nothing has changed."                                                                               |
| Refused                            | The reason, in words the bot can act on: "That name is longer than 40 characters.", "That isn't one of Clawtrate's pictures.", "You've made 3 changes to your name today. Ask your person to do it in Clawtrate." |

No result says a change happened before Clawtrate read it back.

## 6. How the tools reach a gateway

**Proposed: Clawtrate installs its plugin by itself on any gateway it has full control of, with nothing asked, and keeps it current with the app.** Settings → Bots shows "Clawtrate's tools for bots: On", with the version, where it came from, **Off** and **Remove**.

### 6.1 What is installed

One plugin, `clawtrate-bots`: the tools of section 2, its records (proposals, the ledger, the journal), the run-origin store of section 4, its gateway methods and its event. It runs inside the gateway, in-process and not sandboxed, with the same trust as OpenClaw's own code (`<1006>/docs/plugins/architecture.md:930`). What it is given, written by Clawtrate in the same change and shown in Settings:

- the install record (package, exact version, integrity, pinned);
- `plugins.entries.clawtrate-bots.enabled: true`;
- `plugins.entries.clawtrate-bots.hooks.allowConversationAccess: true`, which lets it read each run's origin and the text of the person's message (section 4);
- its name in `plugins.allow` when that list exists (the gateway adds it on install: `<1006>/dist/management-install-CiDYuS33.mjs:203`).

Its tools are required tools, offered to every bot whose tool policy allows them (`<1006>/docs/plugins/building-plugins.md:272-274`). A bot whose policy leaves them out shows "Pip can't use Clawtrate's tools" in its settings, read from `tools.effective` as `start-tasks.ts` does, and nothing is changed. The other plugins (`clawtrate-tool-rules`, `clawtrate-computer`, `clawtrate-memory`, `clawtrate-voice`) are not part of this default: each comes with its own feature's switch when its own review allows.

### 6.2 Why it asks nothing

1. **It adds no authority Clawtrate didn't hold.** Installing any plugin, and changing any config, already needs only the admin access the person gave Clawtrate in setup (`plugins.install` is `operator.admin`: `<1006>/docs/gateway/protocol/rpc-system-and-channels.md:100`; `<1110>/…:103`). That access is what applies every change in section 5. A question here would ask the person to approve code the app they installed already runs on their behalf.
2. **What runs is exactly what the signed app names** (6.3): an exact version, its SHA-512 integrity and its plugin id, fixed when the app was built and signed. The gateway installs those bytes or nothing.
3. **The plugin writes nothing to bots, config or plugins** (section 5). What it adds is tools that read and propose, and hooks that read each run's origin and the person's message, kept bounded in the gateway's own database and expiring in 24 hours.
4. **It is visible and reversible** (6.6), and a person's Off or Remove holds on every device.
5. **OpenClaw's own capability review is given only for what the app ships.** OpenClaw asks for consent before installing or enabling a third-party plugin, bound to the plugin's declared capabilities (`<1006>/docs/plugins/manage-plugins.md:137-181`; `<1110>/…:143`). Without it the install stops with a `reviewToken` (`<1006>/dist/capability-consent-BVhgMs_-.mjs:55-67, 150-169`). Clawtrate gives that token only after `plugins.inspect` shows the staged plugin declaring exactly the tools, hooks and methods the app's list names. Any difference installs nothing, and Settings says what differed.

**The cases where something is asked, and why each is unavoidable:**

- **OpenClaw's install policy warns** (`install_policy_warning_acknowledgement_required`). Clawtrate never acknowledges a warning by itself: Settings shows the gateway's words with **Install anyway**. The warning is the gateway owner's own policy speaking.
- **The person turned it off or removed it** (6.6): it stays so until they turn it on.
- **The connection hasn't full control:** nothing is installed, and Settings says "Needs full control" with the existing way to ask for it. That is setup's question, not a new one.

### 6.3 The trust chain

**Proposed, resting on Established checks:**

1. **The signed app.** Its release is signed (`docs/decisions.md`, "Updates and release signing"). Built into it: a list of Clawtrate's plugins, each with its package name, exact version, `sha512-…` integrity, plugin id and declared capabilities.
2. **On another computer, over the admin connection:** `plugins.install {source: "npm", spec: "<package>@<exact version>", pin: true, expectedPluginId, expectedIntegrity}` (both versions: `<1006>/docs/gateway/protocol/rpc-system-and-channels.md:100-116`).
3. **The gateway downloads it itself** from its own npm registry setting. It stops when the package's integrity is missing or differs from the expected one ("aborted: npm package integrity drift detected", `<1006>/dist/npm-integrity-C9ZL9MoY.mjs:3-27`; the same function in `<1110>/dist/npm-integrity-BhrqEmK0.mjs`), and when the plugin id differs (`<1006>/dist/install-TaW64_lP.mjs:60-66`). It installs with `--ignore-scripts` (`<1006>/dist/npm-managed-root-D5TGU8Tp.mjs:1094`). Clawtrate's plugins have no dependencies (`plugins/*/package.json`), so the one integrity covers all the code; a release check keeps it so.
4. **The capability review** (6.2, point 5), bound to the staged bytes.
5. **On the gateway's own computer** (a connection the gateway identifies as local, and a gateway Clawtrate's setup proved is on this computer): `plugins.install {source: "npm-pack", archivePath}` with the tarball inside the app. Only a local connection may name a local archive (`<1006>/dist/install-source-plan-CNjlQOX3.mjs:24-27`). Clawtrate checks the tarball's SHA-512 against its own list before naming it, and the gateway records the archive's integrity (`<1006>/dist/management-install-CiDYuS33.mjs:626-640`). No registry is involved.

**What a compromised package registry could do:** refuse or delay a download (the install fails, and Settings says so with the gateway's words); see which gateways download which version. **What it couldn't:** make the gateway run other bytes (integrity, step 3); move an installed copy to another version (the pin: `openclaw plugins update --all` keeps exact pins, `<1006>/docs/plugins/manage-plugins.md:380-384`, and an OpenClaw update's plugin step stops on an integrity difference, `<1006>/dist/update-command-plugins-DecR6wrq.mjs:547-557`). **A stolen publishing credential** could publish a new version that no Clawtrate pins; a person who updated the plugin by hand to it would see Settings say "Not the version this Clawtrate ships", with **Use Clawtrate's**.

### 6.4 `plugins.allow` and `plugins.deny`

- An install adds the plugin to a non-empty `plugins.allow` and **takes it out of `plugins.deny`** (Established: `<1006>/dist/management-install-CiDYuS33.mjs:203-204`; the same two calls in `<1110>/dist/management-install-DE7uCVdo.mjs`). So Clawtrate reads `config.get` first, and by default never installs a plugin named in `plugins.deny`, nor one that a non-empty `plugins.allow` no longer names after Clawtrate installed it. Each of those is the gateway owner's choice; Settings shows "Turned off in the gateway's settings".
- Removing it from `plugins.allow` disables it at once (#544). Clawtrate never adds it back by itself.

### 6.5 Updates, and a gateway two Clawtrates talk to

- **With the app.** A Clawtrate connected with full control updates the plugin when the installed copy is one of Clawtrate's own (its record matches a version and integrity Clawtrate shipped) and older than its own list's: `plugins.install {mode: "update", …}` as in 6.3. It never moves it backwards.
- **Two versions of the app on one gateway.** The plugin reports a protocol version in `clawtrate-bots.status`, and keeps the previous one working for at least two releases. The newer app updates it; the older one uses it when it knows the protocol, and otherwise says "Update Clawtrate on this device to use Clawtrate's tools for bots" and leaves it alone.

### 6.6 Off and Remove

- **Off** disables it: `plugins.setEnabled {enabled: false}`. `plugins.entries.clawtrate-bots.enabled: false` is the record every device reads, and none turns it back on by itself.
- **Remove** uninstalls it (`plugins.uninstall`) and adds its name to `plugins.deny` in the same config change, so no device installs it again by default. Turning the switch on again is the person's action, and the install takes the name out of `plugins.deny` (6.4).
- With it off or removed, bots have none of the tools of section 2, the guide's paragraph about them says "when you have them" (section 7), and the gateway's own tools work as before.

### 6.7 A gateway on another computer, a connection without full control, and a plugin installed by hand

- **Another computer:** the npm route. The gateway needs to reach its npm registry; when it can't, Settings shows the gateway's own error with **Try again**. Clawtrate itself contacts no host for this: the gateway does, and Settings names the package and the registry it came from.
- **Without full control:** nothing is installed or changed. Tools a gateway already has keep working.
- **Installed by hand** (a linked checkout, another source, another version): Clawtrate leaves it. Settings shows its source and version, and **Use Clawtrate's** replaces it with the app's own copy on the person's click. Its tools work when its protocol is one the app knows.

### 6.8 Both versions, and the development gateway

- `plugins.install`, `plugins.setEnabled`, `plugins.uninstall`, the consent token and the allow and deny handling read the same on 2026.10.6 and 2026.11.10 (the two `rpc-system-and-channels.md` files, the same functions in both `dist/`). 2026.11.10's answer adds a `catalogId`.
- **The development gateway** keeps loading the plugins from the checkout as a snapshot (`--with-plugin`, `tools/dev-gateway/src/dev-plugins.ts`). Proposed: a second way, `--install-plugin <name>`, which packs the plugin from the checkout and installs it through `plugins.install {source: "npm-pack"}` on a local connection, so the install, the consent token and the allow and deny handling are checked on both versions with no registry.

### 6.9 Publishing, which the owner sets up

The gateway on another computer needs Clawtrate's plugins on npm. What the owner creates:

1. **An npm organization for the project's scope** (its name is the owner's choice, subject to npm's availability), with two-factor authentication required to publish.
2. **The package** `@<scope>/clawtrate-bots`, published only from this repository's release workflow.
3. **Publishing from CI with npm's trusted publishing** (GitHub Actions' OpenID Connect), configured on the package for this repository, the release workflow's file and a protected environment, so no long-lived npm token is stored anywhere. Whether npm needs a first version published by a person before trusted publishing can be set up is not established here (section 12).

What the release process needs from it:

- The release builds each plugin's tarball with `npm pack` from `plugins/<name>` at the release commit (its `package.json` no longer `private`, with a `files` list), computes the SHA-512, and writes the list of 6.3 into the app **before** the app is built and signed.
- It publishes the tarball with provenance, then reads the registry's `dist.integrity` back and compares it. A difference, or a failed publish, fails the release: no app ever names a version that isn't on the registry as built.
- A published version is never reused. A plugin that didn't change keeps its version and its integrity.

### 7.3 "What can you do here?"

The bot calls `clawtrate_here`, whose answer already sorts its tools by who decides, and says it in its own voice in a few sentences, as in exchange 3 on the first page. In a conversation that isn't in Clawtrate, `clawtrate_here` says so, and the bot says it can do these things when its person talks with it in Clawtrate.

## 8. Limits

**Inputs** (Proposed; a call past any of them is refused whole, with the reason, and changes nothing):

| Tool                        | Bounds                                                                                                                                                               |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `clawtrate_identity`        | name 1 to 40 characters after trimming, no control characters or line breaks (as `bot-names.ts`); picture one of Clawtrate's avatar ids; reason up to 200 characters |
| `clawtrate_show`            | an id of one of this bot's tasks, of a file in this conversation, or this bot's own computer; nothing else                                                           |
| `clawtrate_checkins`        | every 30 minutes to 24 hours                                                                                                                                         |
| `clawtrate_routine_pause`   | one of this bot's own routines                                                                                                                                       |
| `clawtrate_routine_propose` | name up to 64, prompt up to 4,000 characters (as check-ins' `MAX_CHECKIN_PROMPT_CHARS`); schedule no more often than hourly; at most 20 routines per bot             |
| `clawtrate_task_propose`    | label up to 80, brief up to 8,000 characters                                                                                                                         |
| `clawtrate_change_propose`  | instructions up to 64 KiB with the hash read; values from the lists the gateway gives                                                                                |
| `clawtrate_bot_propose`     | as New bot's fields; for "change", only a bot the person made this bot a manager of                                                                                  |
| `clawtrate_tasks`           | `limit` up to 50                                                                                                                                                     |

**How often** (Proposed): per bot, at most 30 change calls an hour and 120 reads an hour; at most 3 at-once applies per run; at most 3 name or picture changes a day; at most 5 open cards per bot, after which the oldest is replaced. A call past a rate is refused with when the bot may try again.

**What a tool returns** (Proposed): never more than the person could see in Clawtrate, and only about this bot: its own tasks and the ones it started, never another bot's; its own settings and rules; other bots by name and purpose only. No device names, addresses, tokens, account credentials or other conversations' text. Each answer is at most 8 KiB of text.

## 9. On each OpenClaw version, without the plugin, and on the iPhone

- **2026.10.6:** everything in this design. The tool learns its run from `before_tool_call`. `cron.remove` has no precondition, which this design doesn't use (no tool removes a routine).
- **2026.11.10:** everything, and the tool's own context carries `runId` and `inputProvenance`. A routine removed by Undo is bound to its revision. Files handed over wait for #661. Check-ins rest on #616.
- **A version this build doesn't know:** the plugin still offers its tools. A run whose origin can't be read in the fields this build knows becomes a card (4.3).
- **A gateway without the plugin:** none of these tools. The bot still has the gateway's own (tasks, follow-ups, history, questions), the guide, and F-552's rename card. `clawtrate_here` doesn't exist, so the guide's paragraph is conditional ("when you have tools whose names start with `clawtrate_`").
- **The iPhone app** (`apps/mobile`, another thread's; nothing there changes here): it would need the record of the messages it sent (4.2) to apply anything at once from a message typed on the phone, the cards of section 3 with Apply and Undo, the one-line applied state, and `clawtrate_show` and `clawtrate_view` acting on its own panes and switches. Without them a message typed on the phone becomes a card on the desktop, and the tools' answers say "waiting for your person".

## 12. Not established, and what would establish it

- **Whether the run id the hooks report is the `chat.send` idempotency key.** The handler stores the client run id as the run's (`chat-send-handler-D_7lP5Io.mjs:4271`), but the same file also keeps a separate runtime run id (`:1727`). A run on a development gateway of each version: send with a known key, read `runId` in `before_prompt_build`, `before_tool_call` and (2026.11.10) the tool's context. If they differ, 4.1 keys on `currentUserMessageId` instead, matched to the `<run id>:user` row; that too needs the same run.
- **What each field holds for each origin.** `senderIsOwner`, `channel`, `trigger` and `inputProvenance` for a Clawtrate send, a `sessions_send` from another bot, the command line, a routine, a check-in and a channel message, on both versions. The fields' existence is read from the types; their values need the same scenario (pull request 2). #666's research covers part of it.
- **Whether a plugin sees a task's approvals and questions** and can put a notice into the conversation that started it (C5): `enqueueSystemEvent` with an explicit session is read from the docs, not run, and reading approvals from a plugin was not tried.
- **How `clawtrate-bots` reads a bot's tool rules** from `clawtrate-tool-rules` (a gateway method through `api.runtime.gateway.request`, or a shared store). Until then `clawtrate_here` says rules exist and a refusal names them.
- **The npm route end to end.** That `plugins.install {source: "npm"}` with `expectedIntegrity` refuses other bytes was read from the source, not run: running it needs a registry, and this design ran none. A run against a registry of the project's own for tests would show it.
- **The capability check.** That `plugins.inspect` of a staged install lists the declared tools, hooks and methods in a form the app can compare, on both versions. A run of `--install-plugin` (pull request 4) shows it.
- **Whether a gateway counts Clawtrate's connection on the same computer as local** for `npm-pack` in every way setup connects (loopback direct; through Clawtrate's connector). The same run.
- **Whether npm needs a first publish by a person** before trusted publishing can be configured for a new package.
- **The prompt cost** is counted from the text here, not measured in a prompt. The scripted model's request log on a development gateway would measure the directory entries.
- **How a real model acts** on the paragraph, the descriptions and the cards. The scripted model only does what it is scripted to.
