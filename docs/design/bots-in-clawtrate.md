# Bots in Clawtrate: what a bot knows about the app and what it can do there

How a bot that talks with its person in Clawtrate knows where it is, the tools it has to change things in Clawtrate (itself, its work, the conversation, other bots, the app), what happens when it uses them or the tools it already had, how a change keeps a record and a real Undo, and how Clawtrate's own plugin reaches a person's gateway with nothing typed (issue #436, with #544's second half, #532's loop and #666). This is a design for sign-off: it builds nothing.

It follows the product's rule (`docs/decisions.md`, "Doing, not asking", and `docs/design/doing-not-asking.md`): Clawtrate does the thing, shows what it did, and offers Undo. A card, a confirmation or any other "read this and approve" step stays only before something destructive. A change that can't be shown to be the person's own request is never presented as theirs: it is done with a visible note and Undo when the worst case is small and fully reversible, and otherwise it is not done, and Clawtrate says so.

**Established** marks what the repository or OpenClaw's own source and documentation show today, or what a run on development gateways of both versions showed (said so where it is). **Proposed** marks this design's choice. **Not established** marks what could not be shown here, with what would show it (section 12). OpenClaw facts are from the published packages `openclaw@2026.10.6` and `openclaw@2026.11.10`. `<1006>/…` and `<1110>/…` are paths inside each package. 2026.11.10's `dist/` is minified onto few lines, so for it the file and the function or schema are named instead of a line.

It builds on, and doesn't redesign:

- **The Main Bot design** (`main-bot-onboarding.md`): its earlier revision's `clawtrate-bots` plugin, records, journal, tool list and proposal cards are this document's now (section 2 here, and changes that are applied and shown); that design keeps the first run and the Main Bot's three-tool deny (its section 2).
- **Doing, not asking** (`doing-not-asking.md`): the rule, and what Undo means, are written there once; where both documents say the same thing, the words are the same.
- **The first run** (#493): the first run's script and screens are that design's. This one gives it the tools it calls.
- **The guides** (`packages/core/src/guides.ts`, #544's first half): the section Clawtrate writes at the top of each bot's `AGENTS.md`. Section 7 adds one paragraph and changes one sentence.
- **Tasks a bot starts** (#532's first three steps, on `main`: F-565, F-566, F-587), with the gateway's own `sessions_spawn`, `sessions_send` and `sessions_history`.

## The page to decide from

### What a bot can do, with nothing asked

A bot in a Clawtrate conversation knows it is in Clawtrate, from Clawtrate rather than a guess: one call, `clawtrate_here`, tells it whether this conversation is one its person is having in Clawtrate, which conversation it is, what its person can see of its work, and what it can do here. It knows its tasks and which of them wait for its person, and the bots it can hand work to.

It acts on Clawtrate the way a person expects an assistant to, at once: it takes a new name or picture, starts a task and reports back, opens its task beside the conversation, hands work to another bot, sets up a routine or check-ins for itself, pauses a routine, shows its commands, changes its own instructions, model or effort, makes a new bot, or changes another bot when its person asks. Each change is shown where it happened, in one line with **Undo**, and kept in the bot's record of changes on every device. A change made through a tool the bot already had has Undo only when its journal entry was written (section 5.2); otherwise it shows as "Changed outside Clawtrate · Open".

### What holds it

- **A silent check on every change.** Clawtrate decides, without asking, whether a change was the person's own ask: typed by them in Clawtrate, in this conversation, on this device, with nothing read from outside first. A change that was is shown as done. A small one that wasn't is done and shown as the bot's own doing, never as the person's: "Pip renamed itself after reading a web page · Undo". One that would keep acting afterwards, or reach another bot or the person's settings, is not done when it didn't come from the person, and the bot says so plainly. A routine or check-ins a bot sets up in its own words, with nothing read first, are made at once, and their first run waits until their line has been on one of the person's screens.
- **The same check on the tools a bot already has.** A bot doesn't need Clawtrate's tools to change itself: OpenClaw already gives it file tools that can rewrite its instructions, a scheduler tool, messages to other bots, its check-in notes, and tools that change OpenClaw. Clawtrate's plugin holds each of those calls to section 3.3's rule, which keeps what OpenClaw already lets its owner do.
- **What is assumed about commands.** With nothing set, both OpenClaw versions run a bot's commands without asking, and a bot made in Clawtrate gets that today. A bot that runs commands freely can change any of this with a command, and nothing here stops it. For such a bot the checks make sure that nothing it did is shown as the person's ask, and that an instruction it read is handed no easier, sanctioned way to act. They are a boundary only for a bot whose commands ask or are denied. To keep "nothing acts unseen" true on the command route too, a change to a bot's name, instructions, routines, check-ins or reach that Clawtrate didn't make is shown as "Changed outside Clawtrate · Open". The command question itself is decided in `doing-not-asking.md` §3.5: Clawtrate writes no command mode, so the bot follows the gateway's policy.

### What a bot someone brings in keeps

**Installing Clawtrate's plugin takes away nothing a bot does for its owner when the owner asks in a chat app with nothing read first.** A person whose bot lives in a chat app and who says there "remind me every morning at eight" gets the reminder at once, the day after the plugin is installed as the day before, without opening Clawtrate. What OpenClaw already treats as its owner's request keeps working as before: Clawtrate journals it and shows it as what it is ("Pip set up Morning reminder, asked in Discord · Undo"). The holds are for the attack: a call after the bot read something from outside in that run, from a sender who isn't the owner, from another bot, or from an unwatched run (a routine's or a check-in's own). There a tool the bot already had never gets more than Clawtrate's own tool would: a routine is not made. The owner's own request in a chat app after the bot read something is the one exception: the routine is stored turned off, and starts when the owner tells the bot to start it there or turns it on in Clawtrate, never by merely being seen; what can't wait is not done (section 3.3). After the bot has read something in that run, the owner there also loses changes to the bot's instructions, to an existing routine, and messages to bots out of its reach; and on a gateway with no owner list, OpenClaw can't tell its owner in a chat app from anyone else there, so neither can Clawtrate (section 3.3). Two of OpenClaw's own kinds of change ask through OpenClaw's own approval, in the chat it came from: deleting a routine, and changing OpenClaw itself (section 3.3).

### What still asks, and why each is destructive

| What                                                                                                              | Why it is destructive                        |
| ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Deleting one of its tasks or routines                                                                             | Deleting                                     |
| Changing the account a bot runs on                                                                                | Accounts                                     |
| A bot changing OpenClaw itself with the tools OpenClaw gave it (`openclaw`, `gateway`, `plugins`), from its owner | Changing OpenClaw itself                     |
| Removing Clawtrate's plugin (in Settings)                                                                         | Deleting: its record of changes goes with it |

A routine that ends itself from its own run is not among them: it is reversible, so it is done and shown with Undo (section 3.3).

A bot can't sign anything in or out, spend money, loosen a rule its person set to Ask or Never, change how freely it runs commands, install anything through Clawtrate's tools, or update OpenClaw without OpenClaw's own approval.

### Four exchanges, and what the person sees

1. **"Call yourself Juniper."** The sidebar, the header and the bot's settings say Juniper as soon as the gateway reads it back, and the conversation shows "Renamed to Juniper · Undo". The same in the first run, when the bot has just asked what to call it. Had the bot picked a name from a page it read, the line would say "Pip renamed itself to Maple after reading a web page · Undo".
2. **"Put this in a task and show me."** The bot starts a task under its own name and opens it beside the conversation. A "Started a task" card stays where it was asked (on `main`). If the task stops to wait for the person, the bot says so once: "The trail comparison is waiting for you to approve a command".
3. **"Check my inbox every morning."** The routine exists at once, in a session of its own: "Set up Morning inbox, every day at 8:00 · Edit · Undo", with the person's own words as its instruction. Every run of a routine a bot set up shows one line in its main conversation.
4. **"What can you do here?"** The bot answers from `clawtrate_here` in a few sentences: "I'm talking with you in Clawtrate. I can put work into tasks you can watch and step into, hand work to Marlow or Otto, set up routines and check-ins for myself, open a task beside this chat, change my name, picture or instructions, and make you a new bot. Everything I change shows up here with Undo. I'll check with you before I delete anything or change the account I run on."

### Decided since the first version of this design

- **No cards, and no setting for applying at once.** The three choices this design once left to the owner are settled by the rule: name and picture at once with no setting, a routine made at once whether the person asked or the bot proposed it, and a hand-off to another bot with no grant first.
- **The run id is settled:** on both OpenClaw versions the run id the plugin's hooks report is the `chat.send` idempotency key Clawtrate sent (ran on development gateways of both versions during this design's review), so the device's record can be matched to the gateway's.
- **Removed:** the "card first" and "always asks" classes, the proposal cards, the Advanced setting, the tool that offered a task on a card, and the hand-off grant card. A person clicks 0 times for every change here except the four in the table above.

### What is new, and the owner's to know

- **Without a connected Clawtrate** a change waits up to 24 hours until a Clawtrate with full control connects, and the bot is told so (section 5.3).
- **Where this is weakest.** Something a bot read earlier in a conversation stays in its context, so a page read three turns ago can still shape a change in a later turn the person typed. A routine runs in a session of its own, its instruction is the person's own words when the person asked, and in the bot's own words its first run waits until seen. That narrows it; it doesn't remove it (section 4.6).
- **Installing:** Clawtrate installs its own plugin by itself only once the gateway has staged it without running it and Clawtrate has checked it is the exact package the signed app names (section 6.2). It never installs over a person's deny.
- **Publishing:** the npm organization `@clawtrate` exists. One first publish has to be done once, by the owner with their own two-factor sign-in, before trusted publishing can be set (section 6.9).

### What ships first

Six steps in section 10. **The first a person can see is the third:** a bot asked to put work in a task opens its own task beside the conversation, a bot asked "call yourself Juniper" takes the name with Undo, and a bot tells its person once when a task waits for them. It reaches a real gateway with the fourth and fifth, which land together: Clawtrate's plugin installed by itself, from the app on the gateway's own computer and from npm on another.

### Not offered to a bot through Clawtrate's tools

Signing an account in or out, or letting a device in; spending money; installing, enabling or removing plugins; OpenClaw's config, its updates and restarts; how freely a bot runs commands, and loosening a rule a person set to Ask or Never (what a bot may do on the person's machine is `doing-not-asking.md` §3, with its own security review); deleting a bot or another bot's tasks. ### What the first run needs first

The first run (#493) needs, in order: `clawtrate_identity` for the name it is given (and the picture); the gateway's `sessions_spawn`, to start a small task the person watches appear (on `main`), with `clawtrate_show` to open it beside the conversation; a file handed over with `MEDIA:` (on `main`, both versions). So of this design's tools it needs `clawtrate_identity` and `clawtrate_show` first, and `clawtrate_here` so the bot can say what it can do. Section 10 orders the pull requests that way.

## 3. What happens, per tool, and the tools a bot already has

Every change has one of three outcomes and no fourth:

- **Done, shown, with Undo.** Shown as the person's ask only when section 4 says it was (**A** below). Otherwise shown as the bot's own doing, with what prompted it when known.
- **Not done, said plainly**: to the bot in the tool's answer, and to the person in one quiet line where it would have appeared ("Pip tried to set up a routine after reading a file. Nothing was changed."). For a change that would keep acting afterwards, reach another bot or the person's settings, or be hard to notice, when it didn't come from the person.
- **Asks** (destructive), with the kind named: a single plain confirmation, the same however it is reached.

Section 4 sorts each call into one of three origins:

- **A, the person's ask:** typed by the person in Clawtrate, in this conversation, on the device that applies it; the run read nothing from outside before the call; and for a name or picture, the value is in their words.
- **B, in the person's conversation but not their ask:** the run is the person's, but the bot chose the value itself, or it read something from outside first (section 4.3 says what counts).
- **C, not from the person:** another bot's message, a chat-app message, a routine's or check-in's run, the gateway's own web page or command line, a started task's brief, or an origin that can't be read.

**An instruction a bot writes itself.** `clawtrate_change` instructions, and a routine's or check-in's instruction in the bot's own words, write into **one block of the bot's own**, at most 2 KiB, marked as the bot's, shown whole in the change's line. A tool never rewrites the person's text, in `AGENTS.md` or anywhere else.

**What replaces the hand-off grant.** A bot can reach another bot when two things hold: the other bot is one the person sees in their sidebar (not hidden, not the gateway's own bot, not another tool's), and the person asked, once, for work or a message to go to it (A). That first ask writes the name into `agents.entries.<bot>.subagents.allowAgents` at once (with `config.patch {baseHash}`), shown as "Pip can now hand work to Marlow, on Marlow's account · Undo", and listed in the bot's settings under "Can hand work to", each with a switch. Nothing else widens a bot's reach. The gateway checks `allowAgents` when the task starts, so for the first hand-off the plugin holds the call in `before_tool_call` until Clawtrate has written the name, then lets it through; with no Clawtrate connected it is not done (5.3). What a hand-off reaches (established by runs on both versions during this design's review, and in `<1006>/docs/tools/subagents/tool-reference.md:65, 190, 266`): the task runs in **Marlow's workspace**, loads Marlow's bootstrap files and runs on Marlow's model, so on Marlow's account; it carries Pip's tool denies (run during #532). So a write to Marlow's own files from a task Pip started is a change to Marlow (3.3). Whether Pip's command freedom carries into a task under Marlow is not established (section 12). A message to another bot's main conversation is held the same way: OpenClaw's own docs warn that a message is permission to ask the other bot to act (`<1006>/docs/gateway/config-tools/sessions-and-subagents.md:100-104`).

### 3.2 Routines and check-ins a bot sets up

- **Where a routine runs.** A routine a bot sets up with `clawtrate_routine` runs in a session of its own (`sessionTarget: "isolated"`, a fresh session for each run, with no conversation history: `<1006>/docs/automation/cron-jobs/payloads.md`, "Main session vs current vs isolated vs custom"), never in the main conversation, so nothing read earlier in a conversation rides into its runs.
- **Its instruction.** When the person asked (A), the instruction stored is the device's own copy of the person's message, with the bot's wording beside it, and the line shows both. When the instruction is the bot's own words (B), it goes into the bot's own block (3.1).
- **Its first run, in the bot's own words.** It is made at once, with Edit and Undo, and stored turned off. Clawtrate turns it on as soon as its line has been on screen on one of the person's devices: seen, not clicked. Nothing is asked. Until then the line says "Starts once you've seen this". A routine the owner asked for in a chat app is section 3.3's: with nothing read it doesn't wait, and after the bot read something it never starts by merely being seen.
- **Check-ins** run in the main conversation, with its whole history, and are the least protected standing change (OpenClaw's check-in, `<1006>/docs/gateway/heartbeat.md`). Check-ins a bot turned on itself (B) take the first-run-seen rule above. Undo of check-ins restores the setting **and** the check-in's notes (below), because the notes survive check-ins being turned off ("Its monitor scratch is retained for when you re-enable the cadence": `heartbeat.md:101`).
- **The check-in's notes.** OpenClaw lets a bot replace its own check-in notes from inside a check-in's run (`heartbeat_respond {scratch}`, a full replacement: `<1006>/docs/gateway/heartbeat.md:486-498`), and with no notes "the model decides what to do" (`:506`). Clawtrate's check-in words are the check-in's prompt (`agents.*.heartbeat.prompt`, `check-ins.ts`), not the notes. **Proposed:** a notes write is held as the bot's own block: done, journaled with the previous notes and shown ("Pip updated its check-in notes · See · Undo"), when the notes are empty or were last written by this bot through a journaled write, and at most 2 KiB; not done when the notes hold anyone else's words (a person's, or an imported `HEARTBEAT.md`). The reason: a bot keeping its own checklist is what check-ins are for, on plain OpenClaw too, and replacing a person's notes is the thing to stop.

### 3.3 The tools a bot already has

A bot doesn't need Clawtrate's tools to change itself. With nothing set, a bot's tool profile is `full`, which filters nothing (`<1006>/docs/gateway/config-tools/tool-policy.md:39`), and even the `coding` profile has the file tools, the session tools and the scheduler (`:37`). New bot on `main` writes no tool policy (`packages/core/src/accounts-engine.ts`), and the Main Bot design's deny (its section 2) is not built yet. So each Clawtrate check has a side door, and the plugin's `before_tool_call` hook holds each one, for every bot the plugin serves.

**What the hook can do** (Established, both versions): see the call's `runId`, `toolCallId`, tool name, parameters, `sessionKey` and `agentId`, and a `requester` with `channel`, `senderId` and `senderIsOwner` (`<1006>/dist/config-contracts-C65kIjn4.d.ts:9812-9848`; `<1110>/dist/config-contracts-CmjbWZfI.d.ts:25183-25206`); refuse it with a reason (`block`, `blockReason`); rewrite its parameters (`params`); or hold it for OpenClaw's own approval (`requireApproval`) (`:8888-8899` and `:24802-24815`; `<1006>/docs/plugins/hooks/tool-policy.md:43-80`). No conversation-access setting is needed for `before_tool_call` (`tool-policy.md:85-86`).

**Whose request it is, in a chat app** (Established, read in both versions). OpenClaw counts a chat-app sender as its owner when the sender is on `commands.ownerAllowFrom` (`<1006>/dist/command-auth-Dl8IkZ5H.mjs:362, 439-443`; the same rule in `<1110>/dist/command-auth-Ch_q0NQN.mjs`), which the command line's pairing fills with the first owner (`<1006>/docs/tools/slash-commands.md:139-148`); that is what `requester.senderIsOwner` says. `requester.senderIsOwner` is not the command rule's "owner": with no owner list on a channel that doesn't enforce owners, OpenClaw lets every sender the channel admitted use commands (`isOwnerForCommands`, `<1006>/dist/command-auth-Dl8IkZ5H.mjs:444`), but `senderIsOwner` stays false for them and is what OpenClaw itself uses to withhold the scheduler, `gateway`, `plugins`, `openclaw` and its other owner-only tools from a run (`<1006>/dist/agent-tools-BcX3RaIU.mjs:325-331`, `dangerous-tools-fofvrQTg.mjs:20-58`; the same in `<1110>/dist/dangerous-tools-Bm_fma95.mjs`). Clawtrate uses `senderIsOwner` and never recomputes the command rule. So on a gateway with no owner list nobody in a chat app is the owner: a stranger in a shared channel is never shown as the person asking, and the owner's own requests there are held as a non-owner's. Plain OpenClaw already withholds the scheduler from them, so a reminder asked there is unchanged; what they lose is editing the bot's instruction files or `IDENTITY.md` from the chat app. On the gateway's own chat channel `senderIsOwner` is true for any admin connection, another bot's message included (ran during this design's review), so there it decides nothing, and only the device's record does. A chat-app message was not run (the development gateway has no channel).

**The rule for the tools a bot already has** (Proposed). The origins are section 3's, plus one:

- **O, the owner in a chat app:** the channel is a chat app (not the gateway's own channel and not none), there is no message from another session or the system, and `requester.senderIsOwner` is true.

**A tool a bot already had never gets more than its Clawtrate row gives the same origin. The one addition is O.**

**A routine that ends itself.** OpenClaw gives a routine's own isolated run a narrow self-cleanup grant: it may remove only its own job (`<1006>/docs/automation/cron-jobs/how-it-works.md:31`; `<1110>/docs/automation/cron-jobs/how-it-works.md:42`), and bots people bring in use it. So it keeps working, and it is not a delete. Before the call goes through, the plugin journals the routine's whole definition as `cron.get` returns it (name, schedule, instruction, session target, delivery), up to 64 KiB. The line says "Morning check ended itself · Undo", and Undo makes the routine again from that definition with `cron.add`. What Undo doesn't bring back: the routine's id (the routine made again has a new one) and its record of earlier runs, which isn't attached to the new routine; whether the gateway keeps the old runs after a removal is not established on either version (section 12). A definition over 64 KiB can't be kept, so its removal couldn't be undone; then it is not done, said plainly, because nobody is there to ask. Only that same routine, and only from its own run: anything else from an unwatched run stays not done.

The hook decides a write to a bootstrap file by its path, resolved against the bot's workspace (with the host's `derivedPaths` for `apply_patch`), and journals the file as it was before the write (Proposed). The gateway tool's reads (`config.get`, `config.schema.lookup`) are not changes and pass.

**Asking through OpenClaw's own approval** (Established, read in both versions, and seen for Clawtrate's rules plugin on 2026.10.6). A `before_tool_call` hook can hold a call for OpenClaw's plugin approval (`requireApproval`). That approval reaches the Clawtrate device whose message started the run and admin connections (`plugins/clawtrate-tool-rules/README.md`, "The card"), and, for a request that came from a chat app, that same chat, which can answer with `/approve` by default under the channel's own rules (`<1006>/docs/tools/exec-approvals-advanced.md:304-314`; `<1110>/…:308`). A routine's run, a check-in's run and a run another bot's message started have no one to ask, and the plugin refuses the call itself before asking: on 2026.10.6 the gateway would refuse such a request too, but on 2026.11.10 it sends the card to admin connections (both run during #606), so the hold never relies on the gateway to refuse. Whether the request reaches a chat app on 2026.10.6 was read, not run (section 12); where it doesn't, the gateway blocks the call ("Plugin approval required (gateway unavailable)", `<1006>/dist/agent-tools.before-tool-call-B71Yo63P.mjs:985`), and the owner can't delete a routine or change OpenClaw from that chat app on that version. So a bot someone brings in loses nothing on the `openclaw`, `gateway` and `plugins` route and on deleting a routine (a routine ending itself from its own run is not a delete: above): its owner answers in the chat where they asked, which by the rule is the one place a destructive change may ask. What it loses is the same change from an unwatched run or another bot, which is refused with the reason ("Changing OpenClaw needs your person, and nobody is here to ask").

**Each hold gets its own scenario check, failing with the hold undone, in the pull request that adds the hook** (section 10, step 2).

**For bots Clawtrate makes,** Clawtrate also denies OpenClaw's `gateway`, `plugins` and `openclaw` tools on the bot's own entry, as the Main Bot design §2 does for the Main Bot, so those bots never have those tools, and the table's last row above (`openclaw`, `gateway`, `plugins`) applies only to a bot someone brings in, which keeps its tools and is covered by the hook.

**A change Clawtrate didn't make.** Clawtrate already reads every field these tools change. When a read finds a bot's name, instructions, routines, check-ins or reach changed with no journal entry behind it (a command did it, or a client without the plugin), the bot's conversation and settings show "Changed outside Clawtrate · Open", with the field and the time. Nothing is undone by itself.

## 4. Whose ask it was: the silent check

**A message the person typed in Clawtrate, in that conversation, is their ask.** Clawtrate establishes it with two independent records and needs both. The check runs on every change and is never shown as a question.

### 4.1 What the gateway records about a run (both versions)

Established by runs on development gateways of both versions during this design's review, and by reading the types:

- **The run id.** The run id the hooks report (`before_prompt_build`, `before_tool_call`, `agent_end`, and on 2026.11.10 the tool's own context) is the `chat.send` idempotency key the device sent (`<1006>/dist/chat-send-handler-D_7lP5Io.mjs:4271`). On 2026.10.6 the tool's own context has no `runId`; `before_tool_call` carries `runId` and `toolCallId`, and the join is made there. A key sent again with different text is refused. A steer has no run id of its own in the hooks: its words join the running run.
- **The message's text is not in the hooks' fields.** `currentUserMessage` is absent from `before_prompt_build` on both versions for every origin; the text is only inside `event.prompt`. The value check uses the device's own copy (4.2), never the plugin's.
- **What the plugin's fields tell apart:**

| Origin                               | `trigger` | `channel` | `inputProvenance`                                  | `senderIsOwner` | Sent by a Clawtrate device? |
| ------------------------------------ | --------- | --------- | -------------------------------------------------- | --------------- | --------------------------- |
| Clawtrate `chat.send`                | user      | webchat   | none                                               | true            | yes                         |
| Another bot's `sessions_send`        | user      | webchat   | `inter_session`                                    | true            | no                          |
| A task one bot started under another | user      | webchat   | none on 2026.10.6; `inter_session` on 2026.11.10   | —               | no                          |
| A task's report back                 | user      | webchat   | `inter_session`                                    | —               | no                          |
| The command line (`openclaw agent`)  | user      | none      | none                                               | true            | no                          |
| A routine's run                      | cron      | none      | none on 2026.10.6; `internal_system` on 2026.11.10 | none            | no                          |

So `trigger` and `senderIsOwner` tell none of these apart, `channel` rules out the command line and a routine, and `inputProvenance` rules out another bot. On 2026.10.6 a task's run looks exactly like a typed run to the plugin, and only the device's record tells them apart. The two records are not a belt and braces: on that version the device's is the only check against a task's run.

**Proposed:** the plugin keeps, per run, `{runId, sessionKey, agentId, trigger, channel, inputProvenance.kind, requester, readOutside and what set it}`, for 24 hours or 512 runs, in its bounded store. On 2026.10.6 a tool learns its run from `before_tool_call`, keyed by session key and tool call id together (tool call ids come from the model provider, and some repeat them); on 2026.11.10 from its own `runId`. The plugin calls a run **typed here** when the channel is `webchat`, `inputProvenance` is absent or `external_user`, and the trigger is `user`; that is necessary, not enough.

### 4.2 What Clawtrate records (both versions)

**Proposed:** each Clawtrate device keeps, per gateway and conversation, the idempotency key and text of each message it sent, for 24 hours or 256 messages, in the host's storage so a restart keeps them (registered in `owners.ts` and the documented totals). **A steer is filed under the run it joined:** Clawtrate already records that run's id when it steers (`OutgoingMessage.runId`, `packages/core/src/client.ts`, the send path), so "call yourself Juniper" sent while the bot was working is matched to the run it joined, and the value check reads every message the device sent into that run. A message the person steered into a check-in's run is C: the run is the check-in's, not theirs.

### 4.3 The rule

The A, B and C cases below describe the proposed plugin. F-552's shipped rename rule is in the next section.

A call is **A** when the plugin says its run was typed here, the device that applies it sent that run in that conversation (as its first message or as a steer), and:

- the run's `readOutside` is off before the call, for every tool. A run that read something from outside first can be steered by it, whatever the person typed, so nothing done in it is shown as their ask;
- for a name or picture, also, the value is in what the person typed into that run: the name, spaces collapsed and compared without case, appears in the device's own copy of the messages, or a picture's avatar is named in them ("call yourself Juniper" passes; "you choose", followed by the bot picking "Maple", doesn't).

**What counts as read from outside** (`readOutside` turns on, and records its source): every tool result except Clawtrate's own tools, `ask_user`, `progress_card`, and `sessions_spawn`'s acceptance. That includes the session tools: a `sessions_send` that waits for the other bot's reply, `sessions_history` (a task may have read a page), `sessions_list` (labels bots wrote) and `subagents` (results). It also turns on for a message that arrived with attachments (a file's contents aren't the person's words) and for a run that took in a steer no Clawtrate device sent. The source is kept so the line can name it: "after reading a web page", "after reading Marlow's reply", "after reading a file you sent". Reading the bot's own IDENTITY.md counts as reading a file, including when the bot reads it before editing its name.

**What Clawtrate's own read tools return.** What a Clawtrate tool returns is the person's only where the person set it. Any other text a bot wrote that a read tool returns is outside content: returning it turns `readOutside` on, with its source ("after reading Marlow's name, which Marlow chose"). The plugin knows which is which from the journal: each field the journal records the person setting (typed in Clawtrate as A, or set in Settings) is the person's; a field already there before the plugin's record began, and unchanged since, is the person's; a field the journal records a bot choosing (B or C), or one Clawtrate's last read found changed outside Clawtrate since, is outside content. Clawtrate's own fixed words (a state, what a tool does) are never outside content.

| `clawtrate_here`  | The bot's own name and picture, by `clawtrate_bots`'s rule; this conversation's title, by `clawtrate_tasks`'s; routines' instructions the person typed or set; the check-in's prompt; the bot's tool rules; what each tool would do | A routine's name or instruction in the bot's own block; the check-in's notes; anything else by the rules above                          |

**`clawtrate_bots { find? }`.** Given the name the bot was told (`find`), it returns only the bots whose current name matches it, by id, with their person-set fields and whether that name is the person's, and returns no name text, so nothing it returns is outside content. Without `find` it lists every bot, and a name a bot chose taints the run.

**The main case still works.** The person types "hand this to Marlow". The bot calls `clawtrate_bots {find: "Marlow"}` and gets Marlow's id. Nothing it returned was written by a bot, so `readOutside` stays off and the hand-off is A, done, and adds Marlow to reach the first time. With a name the person gave, the same holds when the bot lists every bot. What breaks: a bot that lists every bot, without `find`, while some bot's name is one it chose itself. Then the run has read outside content, the hand-off is B after reading, and it is not done. The person sees "Pip tried to hand this to Marlow after reading a name a bot chose itself. Nothing was changed.", and the bot can ask again with `find`; its tool description tells it to.

The name check alone doesn't prove the person asked for the rename: a page could pick a word the person happened to type ("Summarize this page" → a bot named Summarize). That is why A also needs `readOutside` off. A run that read nothing can still name itself after a word of the person's on the model's own, so A means "the person's ask, as far as Clawtrate can tell", and the change is still shown with Undo.

A call is **B** when the run is typed here and sent by the device but one of those two fails, and **C** otherwise, including whenever a field is missing, the hooks aren't allowed, or the gateway is a version whose fields this build doesn't know. Section 3 then decides. A call is never presented as the person's ask unless it is A. If a later version broke the match (its run id no longer the key), every call would be C: names done as the bot's own, everything standing not done. That errs toward doing less, and section 10's first scenario catches it.

#### Shipped rename behavior (F-552)

**Who can cause a rename** (F-552's rename, `docs/decisions.md`). Only the owner's own turn, and only a name change that run made: the run's own message is one the gateway stored as the owner's (`senderIsOwner`, as OpenClaw itself reads a row's origin), and one of the run's own writes put a name on the `Name:` line of `IDENTITY.md` other than the one Clawtrate read when it started; a write of another line while someone else changed the name doesn't count. Where the sender can't be established (history that can't be read, an older row, a version whose fields this build doesn't know) or the start wasn't read, nothing is done. **Bots made outside Clawtrate are eligible on exactly the same rule:** a person who tells their own bot to take a name has asked for it, whoever made the bot, since what makes a rename the person's is their own turn, not the bot's origin. The gateway's default bot stays excluded.

**Which device applies a rename, and what each device shows** (F-552's rename, `docs/decisions.md`). The device that sent the run has five seconds to claim the rename; then the first eligible device applies it; if a device other than the sender applied it, every device shows it as the bot's own change.

### 4.4 The first run

The first run's name step is A by the rule above, with nothing special: the bot asks for a name, the person types it, and it is applied at once with "Renamed to Juniper · Undo". What the first run does when the bot goes off its script is the first-run design's.

### 4.6 Where this is weakest, and what is done about it

What a bot read earlier in a conversation stays in its context. A page read three turns ago can still shape a change in a later turn the person typed, where `readOutside` is off and the call is A. Tainting a whole conversation once it has read anything would make every standing change impossible in most real conversations, so it isn't done. What narrows it, without asking:

- a routine runs in a session of its own, with no conversation history (3.2);
- when the person asked, the routine's instruction is their own words; in the bot's own words, its first run waits until seen (3.2);
- instructions a tool writes go into the bot's own bounded block, shown whole, and never rewrite the person's text (3.1);
- every run of a routine a bot set up leaves one line in its main conversation with **Pause** and **Edit**, and its runs carry the bot's own limits, where a rule set to Ask is a refusal, not a question (`plugins/clawtrate-tool-rules/README.md`, "The card").

### 5.2 Clawtrate applies, for every tool, on both versions

**Proposed.** The plugin records; Clawtrate applies with the person's own access. For a call through a tool the bot already had, the gateway's own tool makes the change and the plugin records it from the hook (`before_tool_call` with the field's value before, `after_tool_call` with the result); the steps below are for Clawtrate's own tools.

1. **The bot calls a tool.** The plugin checks the input's bounds, takes the bot from the tool's own context, finds the run's origin (4.1), and writes a request into its ledger (the records `clawtrate-bots` keeps: versions, ledger, journal) with the tool, the values and the origin. It fires `plugin.clawtrate-bots.changed`. A call section 3 says isn't done is refused here, and recorded as tried.
2. **Applying.** For A, the device that sent the run claims it. For B and C, any connected Clawtrate with full control does. It sorts the call by 4.3 and reads the target afresh. Then it **claims** the request in the plugin's ledger, in one `compareAndApply` transition from `waiting` to `committing` (the same transition the plugin's README describes for a claim), recording the value it read, the value it will write, its device and the time. Only one device can win that transition, so a change is never applied twice, and a request that ended (applied, not applied or expired) can't be claimed. It writes with its own access and the write's precondition where the gateway has one, reads back, and records the effect with a new admin method, `clawtrate-bots.changes.record`, which attaches the journal entry and moves the request to `applied` in the same transition. If that call fails while the claiming device is still connected, the device retries it, with a growing pause, for as long as it stays connected; until it succeeds, the change's line says "Saving the record of this change". If it never succeeds (the device disconnects first, and step 3 then recovers it), the next read shows the change as "Changed outside Clawtrate · Open" (3.3), so a change is never unseen. The tool waits up to 15 seconds and returns what was read back.
3. **A write whose record didn't follow.** A request in `committing` is recovered only once the claiming device's connection to the gateway has gone and it has been in `committing` for more than 120 seconds, longer than the client's own 60-second request timeout (`REQUEST_TIMEOUT_MS`, `packages/core/src/client.ts`). Each connected Clawtrate with full control sets a timer for the moment the oldest such request becomes eligible, so recovery doesn't wait for another event. Then one device claims the recovery (one ledger transition, as for the request) and reads the field once. A matching value doesn't prove this request wrote it, since someone else may have written the same, so nothing recovered gets Undo, and no read can show whether the write happened, so a recovered request always becomes `unconfirmed`. Its line says what the read found: '<field> is still <value>' when it holds the value read before, or "Couldn't confirm Clawtrate made this change" with what Clawtrate now reads, and in both cases **Open** for that setting. A write still in flight that lands after recovery has no journal entry, so the next read shows it as "Changed outside Clawtrate · Open" (3.3): it is shown at the first read that finds it, and never as the person's ask; a write someone else overwrites before that read is not seen.
4. **Shown.** Clawtrate draws the line for the change in the conversation from the journal entry, not from the tool's arguments: as the person's ask for A, as the bot's own for B and C, and as "asked in <app>" for O.
5. **Asks.** For `clawtrate_delete` and an account change, Clawtrate shows its one confirmation in the conversation instead of applying. **Delete** or **Change account** applies it; **Keep** ends it.

### 5.4 Undo

What `doing-not-asking.md` §1 says Undo is holds here. For this design's changes:

**What is kept.** Each confirmed change is one journal entry in the plugin's retained store on the gateway, with what Undo needs: the previous name and picture; the previous bootstrap file in full (up to 64 KiB) and its hash; the previous model, effort, rule or check-in setting and the check-in's previous notes; a routine's previous definition and revision, or, for one just set up, its id; for reach, the `allowAgents` list before it; for a new bot, its id and creation record. A view switch is the device's own and is kept in the host's storage.

**Where it is offered.** In the change's own line in the conversation, and in the bot's settings under "Recent changes", on every device connected to that gateway, because the journal is on the gateway. A restart of Clawtrate or of the gateway keeps it. A view switch's Undo is on the device it changed.

**For how long.** Undo is offered for 7 days, or until the next change to the same field. The journal itself is kept for 90 days (the plugin's README), so after the 7 days the line and "Recent changes" still say what changed, without Undo.

**What Undo does.** Clawtrate reads the field once. If it still holds what the change wrote, Clawtrate writes the previous value back under that read's precondition where the gateway has one. If it changed again since, nothing is written, and the line says so with the two side by side and **Open** for that setting. On both versions a name's Undo carries the race F-552 carries: a change another admin makes between Clawtrate's read and `agents.update` can be overwritten without anyone being told.

**Something that has already acted:**

- **A routine set up, then run.** On 2026.11.10, Undo removes the routine with `cron.remove {expectedConfigRevision}`, so a routine someone edited since isn't removed. On 2026.10.6, `cron.remove` takes no precondition, so Undo instead turns it off with `cron.update {id, patch: {enabled: false}, expectedConfigRevision}`, bound to the revision the change left, and the line says "Turned off Morning inbox"; removing it after that is deleting a routine, with its one confirmation. Either way, what its runs already did stays: their lines and history stay in the conversation ("Its 3 runs stay in its history"). Undo is not a delete in the rule's sense: it restores the state before the change. A routine edited since gets **Open routine** instead of Undo.
- **A routine changed, then run.** Undo puts the previous definition back with `cron.update {…, expectedConfigRevision}`; runs made under the changed one stay.
- **Check-ins.** Undo restores the setting and the notes as they were.
- **A hand-off the other bot already started on.** Undo stops the task's run (the gateway's own stop) and, when this hand-off was the first to that bot, takes the name out of `allowAgents` again. What the task already did in the other bot's workspace stays; a write it made to that bot's own files has its own journal entry and its own Undo (3.3). The task stays under the other bot; deleting it is the person's, with the one confirmation.
- **A new bot that has already been used.** Undo is offered only until the new bot has a conversation the person wrote in. After that, removing it is deleting a bot, in Settings, with its confirmation.
- **Instructions, then a turn under them.** Undo restores the file; turns already answered stay.
- **A name other devices and chat apps already showed.** Undo restores it from now on.

## 6. How the tools reach a gateway

**Proposed: Clawtrate installs its own plugin by itself on any gateway it has full control of, and keeps it current with the app.** By the rule this needs no question once it is Clawtrate's own pinned code, and the sequence in 6.2 is what makes it so before any of its code runs. Afterwards Settings → Bots shows "Clawtrate's tools for bots: On", with the version, where it came from, its integrity, "Installed by Clawtrate", and each config key it wrote (its entry, `hooks.allowConversationAccess`, its `plugins.allow` entry), with **Turn off** and **Remove**. The gateway's record of changes shows "Installed Clawtrate's tools for bots <version>".

### 6.1 What is installed

One plugin, `clawtrate-bots`: the tools of section 2, the hooks of section 3.3, its records (the ledger, the journal), the run-origin store of section 4, its gateway methods and its event. It runs inside the gateway, in-process and not sandboxed, with the same trust as OpenClaw's own code (`<1006>/docs/plugins/architecture.md:930`). What it is given, written by Clawtrate when it enables it (6.2) and shown in Settings:

- the install record (package, exact version, integrity);
- `plugins.entries.clawtrate-bots.enabled: true`;
- `plugins.entries.clawtrate-bots.hooks.allowConversationAccess: true`, which lets its prompt hooks read each run's origin (section 4);
- its name in `plugins.allow` when that list exists.

Its tools are required tools, offered to every bot whose tool policy allows them (`<1006>/docs/plugins/building-plugins.md:272-274`). A bot whose policy leaves them out shows "Pip can't use Clawtrate's tools" in its settings, read from `tools.effective` as `start-tasks.ts` does, and nothing is changed. The other plugins (`clawtrate-tool-rules`, `clawtrate-computer`, `clawtrate-memory`, `clawtrate-voice`) are not part of this: each comes with its own feature when its own review allows.

### 6.2 How it is installed, checked before it runs

**What OpenClaw's own consent does over the connection** (Established by runs on both versions during this design's review, and read): nothing that Clawtrate can use as a check. The connection's install handler gives the gateway's own review token back to itself (`<1006>/dist/plugins-mutations-ClrWTX5-.mjs:72-80`; the same in `<1110>/dist/plugins-mutations-MjAXEDgk.mjs`), so a plugin installed with no acknowledgement was enabled and ran, and `plugins.setEnabled` enabled one with no token and with a wrong one. `npm-pack` installs take neither an expected integrity nor an expected plugin id (refused at the schema on both versions: `<1006>/dist/sessions-B6HQw2nf.mjs:829-833`).

**What does work, on both versions, and is the sequence** (Proposed, each step established by the same runs):

1. **Stage it without running it:** `plugins.install {…, enable: false}`. No code runs, no config entry is written, and `plugins.allow` and `plugins.deny` are left as they are.
2. **Read what was staged:** `plugins.inspect {pluginId}`, which returns the source's integrity (equal to the archive's SHA-512), its version, its plugin id, its declared surface (its tools and hooks among it) and a review token.
3. **Compare** integrity, version, plugin id and the declared tools and hooks with the list built into the signed app (6.3).
4. **Only if all match, enable it:** `plugins.setEnabled {pluginId, enabled: true, acknowledgeCapabilities: {reviewToken}}` (the token changes nothing today, and binds if a later version enforces it), writing `hooks.allowConversationAccess` and any `plugins.allow` entry with `config.patch {baseHash}` in the same step.
5. **On any difference,** `plugins.uninstall`, and Settings says what differed. Nothing of it ran.

The same sequence for an update (`mode: "update"`). Clawtrate reads `config.get` just before step 1 and again before step 4: if the plugin was turned off or put in `plugins.deny` meanwhile, by any device, it stops, uninstalls what it staged, and Settings says why. A Remove interrupted partway leaves the plugin disabled, and the next Clawtrate with full control finishes it.

**Why that asks nothing.** Installing any plugin already needs only the admin access the person gave Clawtrate in setup (`plugins.install` is `operator.admin`: `<1006>/docs/gateway/protocol/rpc-system-and-channels.md:100`; `<1110>/…:103`), which is what applies every change in section 5. The rule asks before installing into OpenClaw anything that isn't Clawtrate's own pinned code, and steps 1 to 4 make sure nothing else is enabled.

**When it isn't installed, said plainly in Settings, with nothing asked:**

- **OpenClaw's install policy warns** (`install_policy_warning_acknowledgement_required`). Clawtrate never acknowledges a warning by itself. Settings shows the gateway's words, and the switch stays off until the person turns it on.
- **The person turned it off or removed it**, or the gateway's settings exclude it (6.4).
- **The connection hasn't full control:** "Needs full control", with setup's existing way to get it.

### 6.3 The trust chain

**Proposed, resting on Established checks:**

1. **The signed app.** Its release is signed (`docs/decisions.md`, "Updates and release signing"). Built into it: a list of Clawtrate's plugins, each with its package name, exact version, `sha512-…` integrity, plugin id, declared tools and hooks, and the commit it was packed from (the lock of 6.9).
2. **On another computer:** `plugins.install {source: "npm", spec: "@clawtrate/clawtrate-bots@<exact version>", pin: true, expectedPluginId, expectedIntegrity, enable: false}` (both versions: `<1006>/docs/gateway/protocol/rpc-system-and-channels.md:100-116`). The gateway downloads it from its own npm registry setting, stops when the integrity is missing or differs ("aborted: npm package integrity drift detected", `<1006>/dist/npm-integrity-C9ZL9MoY.mjs:3-27`; the same function in `<1110>/dist/npm-integrity-BhrqEmK0.mjs`) and when the plugin id differs (`<1006>/dist/install-TaW64_lP.mjs:60-66`), and installs with `--ignore-scripts` (`<1006>/dist/npm-managed-root-D5TGU8Tp.mjs:1094`; also ran). Clawtrate's plugins have no dependencies, so the one integrity covers all the code (#676 refuses a package with any dependency field). That the npm route refuses other bytes was read, not run: running it needs a registry.
3. **On the gateway's own computer** (a direct loopback connection, which the gateway counts as local: ran during the review; Clawtrate's connector path was not tested): `plugins.install {source: "npm-pack", archivePath, enable: false}` with the tarball inside the app. Only a local connection may name a local archive (`<1006>/dist/install-source-plan-CNjlQOX3.mjs:24-27`). The bytes are checked by 6.2's step 2 and 3 before anything runs.
4. **Enabled** by 6.2's step 4.

**What a compromised package registry could do:** refuse or delay a download (the install fails, and Settings says so with the gateway's words); see which gateways download which version. **What it couldn't:** make the gateway run other bytes (integrity, step 2, and 6.2's comparison); move an installed copy to another version (the pin: `openclaw plugins update --all` keeps exact pins, `<1006>/docs/plugins/manage-plugins.md:380-384`, and an OpenClaw update's plugin step stops on an integrity difference, `<1006>/dist/update-command-plugins-DecR6wrq.mjs:547-557`). A compromised release workflow could publish bytes, but no app enables them until a signed release names their integrity: the signed release is the root of trust. A person who updated the plugin by hand to another version would see Settings say "Not the version this Clawtrate ships", with **Use Clawtrate's**.

### 6.4 `plugins.allow` and `plugins.deny`

- An install that enables a plugin adds it to a non-empty `plugins.allow` and **takes it out of `plugins.deny`** (Established: `<1006>/dist/management-install-CiDYuS33.mjs:203-204`; the same two calls in `<1110>/dist/management-install-DE7uCVdo.mjs`; ran: a denied plugin was taken out of deny, enabled and run). So Clawtrate reads `config.get` first and never installs by itself a plugin named in `plugins.deny`, nor one that a non-empty `plugins.allow` no longer names after Clawtrate installed it. Each is the gateway owner's choice, and Settings shows "Turned off in the gateway's settings". Only the person's own switch overrides it.
- Removing it from `plugins.allow` disables it at once (#544). Clawtrate never adds it back by itself.

### 6.5 Updates, and a gateway two Clawtrates talk to

- **With the app.** A Clawtrate connected with full control updates the plugin by 6.2's sequence when the installed copy is one of Clawtrate's own (its record matches a version and integrity Clawtrate shipped) and older than its own list's. It never moves it backwards.
- **Two versions of the app on one gateway.** The plugin reports a protocol version in `clawtrate-bots.status`, and keeps the previous one working for at least two releases. The newer app updates it. The older one uses it when it knows the protocol, and otherwise says "Update Clawtrate on this device to use Clawtrate's tools for bots" and leaves it alone.

### 6.6 Turn off and Remove

- **Turn off** disables it: `plugins.setEnabled {enabled: false}`. `plugins.entries.clawtrate-bots.enabled: false` is the record every device reads, and none turns it back on by itself. Turning it on again is the same switch, by 6.2's step 4. Nothing is lost.
- **Remove** is two calls: `plugins.uninstall`, then `config.patch` adding its name to `plugins.deny`, so no device installs it again by itself. Uninstalling leaves `plugins.entries.clawtrate-bots.enabled: false` and adds nothing to deny by itself (ran on both versions). It removes the plugin's managed files, and with them its records (the journal and its Undo), so it is destructive: it asks once, "Remove Clawtrate's tools for bots? Their record of changes and its Undo go with them." Turning the switch on again is the person's action: the install takes the name out of `plugins.deny` but leaves the entry disabled, so 6.2's step 4 sets it.
- With it off or removed, bots have none of the tools of section 2, the hooks of 3.3 don't run (so the tools a bot already had work as on plain OpenClaw), the guide's paragraph about the tools says "when you have them" (section 7), and Clawtrate still shows "Changed outside Clawtrate" for what it reads.

### 6.7 A gateway on another computer, a connection without full control, and a plugin installed by hand

- **Another computer:** the npm route. The gateway needs to reach its npm registry; when it can't, Settings shows the gateway's own error with **Try again**. Clawtrate itself contacts no host for this: the gateway does, and Settings names the package and the registry it came from.
- **Without full control:** nothing is installed or changed. Tools a gateway already has keep working.
- **Installed by hand** (a linked checkout, another source, another version): Clawtrate leaves it. Settings shows its source and version, and **Use Clawtrate's** replaces it with the app's own copy by 6.2's sequence. Its tools work when its protocol is one the app knows.

### 6.8 Both versions, and the development gateway

- `plugins.install` with `enable: false`, `plugins.inspect`, `plugins.setEnabled`, `plugins.uninstall` and the allow and deny handling behave the same on 2026.10.6 and 2026.11.10 (ran during the review; the two `rpc-system-and-channels.md` files). 2026.11.10's answer adds a `catalogId`. On neither version does the consent token check anything over the connection (6.2).
- **The development gateway** keeps loading the plugins from the checkout as a snapshot (`--with-plugin`, `tools/dev-gateway/src/dev-plugins.ts`). Proposed: a second way, `--install-plugin <name>`, which packs the plugin from the checkout and runs 6.2's sequence with `source: "npm-pack"` on a local connection, so the install, the comparison and the allow and deny handling are checked on both versions with no registry.

### 6.9 Publishing

The gateway on another computer needs Clawtrate's plugins on npm. **Established:** the project's npm organization exists, with the scope `@clawtrate`, two-factor authentication required for the organization, and public packages. No publishing token exists. The package is `@clawtrate/clawtrate-bots`.

**Publishing is from CI only, with npm's trusted publishing** (GitHub Actions' OpenID Connect), so no long-lived npm credential exists anywhere. What npm's documentation says (read on 2026-11-26):

- A trusted publisher can only be configured on a package that already exists: "**Package must exist**: The package you're configuring must already exist on the npm registry." (`docs.npmjs.com/cli/v11/commands/npm-trust`, last edited 2026-06-02). The website's setup also starts from the package's own settings: "Packages → YOUR_PACKAGE → Settings → Trusted publishing" (`docs.npmjs.com/trusted-publishers`, last edited 2026-10-06). So a first version has to be published once by a person (below).
- "A newly created trusted publisher configuration must complete its first successful publish within 2 days", or "it expires and can no longer be used or edited" (`docs.npmjs.com/trusted-publishers`).
- The workflow needs "the `id-token: write` permission", npm "CLI version 11.5.1 or later and Node version 22.14.0 or higher". The workflow filename is entered without its path and "must exist in .github/workflows/". The environment name is optional, and "all fields are case-sensitive and must be exact" (`docs.npmjs.com/trusted-publishers`).
- From a public repository, for a public package, "npm automatically generates and publishes provenance attestations" (`docs.npmjs.com/trusted-publishers`).
- Afterwards npm recommends "Settings → Publishing access" → "Require two-factor authentication and disallow tokens" (`docs.npmjs.com/trusted-publishers`).

#### On the repository's side (as #676 builds it)

- **The workflow** `.github/workflows/plugins-publish.yml`, started only by `workflow_dispatch` on `main`, with one input, `mode` (`publish` or `bootstrap`). It packs and publishes at **its own commit**, `main`'s head when it was dispatched, and runs its packing and publishing helper from that same commit, so an older commit can't bring older checks with it. Just before publishing it checks again that its commit is still on `main`. It has `contents: read`; only the Publish job gets `id-token: write`, and it runs in the `npm` environment. Every action is pinned by commit, it uses no secrets, and Node and npm are pinned exactly, above npm's minimums. Provenance therefore names the commit that was packed.
- **The environment** `npm` exists: deployments from the `main` branch only, no secrets, no reviewers, and no tag rule, for the reason the `github-pages` environment has none (`docs/development/releases.md`).
- **`mode: publish`:** packs the plugin (a copy of its `package.json` without `private`, with a `files` list and no dependency field, which the helper refuses otherwise), checks the tarball is the bytes it hashed, publishes a version the registry hasn't got with `--provenance --access public`, reads `dist.integrity` back and fails unless it is the same, succeeds without publishing when the same version is already there with the same integrity, and fails when it is there with another.
- **The lock** (`plugins.lock.json`, the `plugins-lock` artifact): for each plugin, `name`, `version`, `integrity` (SHA-512, base64, as read back from the registry), `pluginId`, the declared tools and hooks, and `commit`, each read from the packed tarball's own `package.json` and `openclaw.plugin.json`. The app's list (6.3) holds exactly these, and 6.2's comparison checks `plugins.inspect` against them: integrity, version, plugin id, and the tools and hooks the manifest declares (`contracts.tools`, `hooks`), which `clawtrate-bots`'s manifest must therefore list; the commit is the release's own check. The integrity is what binds the code.
- **`mode: bootstrap`:** packs the placeholder `@clawtrate/clawtrate-bots@0.0.0` (a `package.json` with no `openclaw` entry and a README line, so it can't be installed as a plugin), uploads it, prints its file name and integrity, publishes nothing and gets no OpenID token.
- **The plugin's own `package.json`** keeps `private: true`, so nobody can publish it from a checkout by accident; only the workflow's packed copy drops it.

#### The app's release

Betas are built and signed on the release machine by `pnpm release:beta`, run by the hourly release. The release dispatches `plugins-publish.yml` with `mode: publish` at `main`'s head, using **the release machine's existing GitHub login, which can dispatch workflows** (`pnpm release:beta` already starts the Site workflow with it: `docs/development/releases.md`, "Publish it"). It waits for the run, downloads `plugins-lock`, and packs each plugin itself from its own release commit with the same helper. An unchanged plugin packs to the same bytes and keeps its version, so the two integrities match, and the release writes the lock's entries into the app before the app is built and signed. It dispatches rather than calls the workflow: npm's trusted-publisher check matches the calling workflow's file, so a release workflow calling this one would not match.

**When they don't match** (the plugin changed on `main` after the release commit, or a version was published that the release commit doesn't have): the release stops before building, names both integrities and both commits, and ships nothing. No app ever names a version that isn't on the registry as its own commit packs it. The next hourly release, from a commit where they agree, goes ahead.

#### The one-time first publish

It publishes the placeholder, which has no plugin code, so no person's computer ever builds or publishes plugin code. The real first version comes from the workflow. It is done once, by the owner, with their own two-factor sign-in, and leaves no token behind:

1. After #676 is on `main`, run the workflow with `mode: bootstrap`. Its summary shows the placeholder's file name and its `sha512-…` integrity.
2. Download the run's artifact and check it before publishing: `openssl dgst -sha512 -binary <file>.tgz | openssl base64 -A` must print the summary's value after `sha512-`.
3. Sign in to npm in the terminal (`npm login`, in the browser, with two-factor). Publish exactly that file: `npm publish ./<file>.tgz --access public --tag bootstrap`. Then `npm deprecate @clawtrate/clawtrate-bots@0.0.0 "Placeholder: install a released version"`.
4. Check it after: `npm view @clawtrate/clawtrate-bots@0.0.0 dist.integrity` prints the summary's value.
5. On npmjs.com: the package → **Settings** → **Trusted publishing** → GitHub Actions: organization or user `sidebandstudio`, repository `clawtrate`, workflow filename `plugins-publish.yml`, environment `npm`, publishing allowed. Save.
6. Same page → **Publishing access** → "Require two-factor authentication and disallow tokens" → **Update Package Settings**.
7. `npm logout`, which ends the terminal's sign-in.
8. Within 2 days, run the workflow with `mode: publish`. That first successful publish validates the trusted publisher. From then on, releases publish with no credential stored anywhere.

Whether `--tag bootstrap` keeps `latest` off the very first version a package ever has is not established. It is harmless either way: the placeholder has no `openclaw` entry, so no gateway can install it as a plugin, it is deprecated, and every Clawtrate names an exact version.
