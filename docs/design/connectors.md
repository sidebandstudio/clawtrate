# Connectors

How a person finds and adds apps for their bots (the catalog, "Connect apps"), what a connector's page says about it and its sign-in, how a sign-in is started from that page and from a card in the conversation, how a tool server is added by its address or as a command, how each is removed, and the first-run question "What do you use every day?". This part of the design follows `visual-language.md`, `conversation.md`, `bots.md`, `work-pane.md`, `setup.md` and `controls.md`, in the same language and with the same tokens.

What must be true is in `docs/parity.md`, rows F-004, F-217 to F-221 and F-380 to F-383; the rail button that opens it is F-030. What the gateway does is in `docs/research/connectors.md` (cited as R§n). Every state below names the fact it rests on, and section 17 lists them. Section 18 lists the rows. Section 19 is for builders.

One rule sits above the rest: **a connector's page says what the gateway reported, and when, and nothing else.** The gateway reports a plugin's state, and a sign-in it holds for a plugin's own server; for a server added by address or command it reports neither a sign-in nor accounts, only the gateway's tool listing for the selected task, as read. So the page says "Not reported" where the gateway is silent, and never draws "Connected" from a call that once worked.

Five facts from the research shape the design:

- **The catalog is ClawHub's.** Categories, Recommended, search and everything that can be added come from ClawHub, fetched by the gateway. When the gateway cannot reach it, the catalog shows only what is already on the gateway, and a full-catalog request takes about 14 seconds to say so (R§2).
- **Adding a connector installs code on the gateway's machine.** It downloads a package, installs its dependencies there and runs it inside the gateway. It can apply changes to the running gateway. Use the reply's `restartRequired` and warnings. It needs admin, and the gateway can stop first with an install-policy warning (R§3).
- **A tool server's tools show only in the gateway's tool listing for a task, as of when it was read.** A save is confirmed by reading the gateway's settings back; a listing names what the gateway has discovered for one task, not a run, a time of use or every bot (R§5).
- **A sign-in from a page needs a connection that comes from a browser.** Both apps reach the gateway through their host as the same client, with no browser origin, and Clawtrate does not present itself as a browser; so both give the gateway's own sign-in steps instead, and the gateway keeps the tokens (R§7).
- **What the gateway keeps, it does not encrypt.** A header's value is kept by the gateway in its settings file, and a sign-in's tokens in its state, not encrypted there; a removed server's sign-in stays (R§6).

The prototype walks every path to its outcome: `prototype/connectors.html`, with the state in the address (`prototype/README.md`). The styles are in `prototype/css/connectors.css`, the behaviour in `prototype/js/connectors.js`, and `prototype/tools/checks/connectors.mjs` clicks through every walk and asserts each state's words and structure.

### The drawn initial, and no other marks

A connector is shown by its name and its initial, never by a picture. The catalog offers an icon and an image address (`catalog.icon`, `catalog.imageUrl`); Clawtrate never fetches or draws either (R§2), as the decision on addresses requires (`docs/decisions.md`, "Addresses a gateway hands the client": an address it does not list, in an event, a reply or a tool result, is never fetched or opened). `plugins.list`'s `hasIcon` is not a reason to fetch one either. No product's logo, icon or colour appears in Clawtrate or in this design; the prototype's connectors have invented names.

### Access

| What                                                                              | Tier                                   | Fact                                                                                                                                       |
| --------------------------------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Browse, search, a catalog page, On this gateway, a connector's or a server's page | Read                                   | `plugins.catalog.*`, `plugins.list`, `plugins.inspect`, `skills.search`, `config.get`, `tools.effective` are `operator.read` (R§2, §5, §8) |
| Add, Turn off, Turn on, Remove a connector                                        | Admin                                  | `plugins.install`, `plugins.setEnabled`, `plugins.uninstall` (R§3, §4)                                                                     |
| Add, change or remove a tool server                                               | Admin                                  | `config.patch` (R§5)                                                                                                                       |
| Sign in from a page                                                               | Admin                                  | None from Clawtrate: the gateway's own steps, on its machine or in its Settings (section 10)                                               |
| Copy a live requester sign-in address                                             | Any tier that receives the tool result | Copies text from the live structured result.                                                                                               |
| Tick apps in "What do you use every day?"                                         | Any                                    | Kept on this device                                                                                                                        |

Admin is asked for only when the person chooses an action that needs it, never on opening the window. On the read and interactive tiers the action's place holds the access bar of `bots.md` §2: "**Read-only.**" (read) or "**Admin access needed.**" (interactive), then the screen's words, and "Request admin access". The words: "Adding apps needs admin access." (Browse, a catalog page), "Changing connectors needs admin access." (a connector's page), "Changing tool servers needs admin access." (a server's page), "Adding a custom connector needs admin access." (the form). The request, its waiting, denied, expired and granted states are that bar's, unchanged. What the screen held (a typed address, the arguments) is kept through the request. Values are shown at every tier; controls that change them are absent, not disabled, below admin. When the gateway's settings are read-only, its note (section 4) takes the bar's place, with no request.

### Writing and reading back

Every change is written, then read back, and the screen says what the read-back shows, step by step:

- **A connector** (add, turn off, turn on, remove): the gateway's answer gives the plugin's new state; Clawtrate then reads `plugins.list` and shows that row. After any failure, and after a request that got no answer, it reads `plugins.list` before it says anything about what is on the gateway.
- **A tool server**: `config.patch`, then `config.get`. The page shows the entry as `config.get` returns it.
- **Busy.** "Another plugin or config operation is already running" (R§4) is shown as "The gateway is busy with another change. Try again in a moment." with "Try again"; nothing is retried by itself.
- **No answer** (the connection dropped or the call timed out): "Checking what the gateway has…", then the read-back's result. A write is never sent twice before that read.

### Input

- The window is a modal dialog: Tab stays inside, Escape closes it (an open confirmation first), focus returns to the control that opened it.
- The section list is a `nav`; a section's title takes focus when it opens.
- The category chips are a radio group with one tab stop; Left and Right move and choose.
- The search field is a `search` landmark; typing filters as it is typed, Escape clears it.
- A confirmation puts focus on Cancel. In the window and in a confirmation, Tab and Shift-Tab stay inside; closing it returns focus to the control that opened it.

### Announcements

One polite live region for the window announces, each only once it is read back: "Loading the catalog", "Showing what's on this gateway", "12 apps", "No apps match", "Adding Quillnote", "Added Quillnote", "Couldn't add Quillnote", "Turned off Ledgerkin", "Turned on Ledgerkin", "Removed Quillnote", "Added notes-work", "Couldn't add notes-work", "Removed notes-work", "Asking the gateway", "Admin access granted", and the copy results. Nothing is announced on a click alone.

## 4. Browse: search, categories, Recommended

**When the gateway's settings are read-only.** `plugins.list.mutationAllowed: false` means the gateway's configuration is read-only (R§3). Show "**This gateway's settings are read-only.** Plugins and tool servers can't be changed here." on Browse, On this gateway, catalog and connector details, tool server details and the custom server page. Omit Add, Turn on, Turn off, Remove, Add another account and the admin request for those writes. Keep reads available. An account row may still explain the gateway's sign-in steps where eligible. This is the gateway's own state, not this device's access: a read-only device on a writable gateway still sees the access bar.

**Opening.** Browse asks `plugins.catalog.browse {}` (with no query, ClawHub's overview with its categories) and, at the same time, `plugins.catalog.browse {intent: "featured"}` (R§2).

| State                        | It shows                                                                                                                                                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Loading                      | The search field, a chip row of three grey pills, and four grey rows, `aria-busy`. After 4 s, under them: "Still loading. The gateway is asking the catalog."                                                |
| Loaded                       | The search field "Search across apps and skills"; the chips, "All" first, then the categories in their `order`; "Recommended for you" with the featured rows; then "All apps" with every row of the overview |
| The catalog can't be reached | Section 5                                                                                                                                                                                                    |
| The gateway refused          | A `--danger-soft` note: "**Couldn't load the catalog.**" and the gateway's message, with "Try again"                                                                                                         |

**A row** has the initial, the name, the summary, and at its end:

| The row's `local`             | Its end                                                 |
| ----------------------------- | ------------------------------------------------------- |
| `action: "install"`           | "Add" (a default button, 28 px); below admin, no button |
| Installed, `state: "enabled"` | the pill "Added"                                        |
| `state: "disabled"`           | "Turned off"                                            |
| `state: "needs-setup"`        | "Needs setup" (warn)                                    |
| `state: "error"`              | "Not working" (danger)                                  |
| `action: "unavailable"`       | "Not available" in faint text, no button                |

Choosing a row opens its page (section 6); "Add" goes straight to the confirmation of section 6.

**"Recommended for you"** is the gateway's featured list (`intent: "featured"`), the same for everyone on this gateway. Its line says so: "Featured in the catalog." When a person ticked apps in "What do you use every day?" (section 15), a group "You picked" comes first, with those rows. With neither, the group is absent.

**Categories.** A chip shows its category's `label`; choosing it asks `browse {category: <slug>}` and lists the rows under the chip's label. "All" returns to the overview.

**Search** asks `browse {query}` and `skills.search {query}` as the person types, after 300 ms without a key. Results come in two groups, "Apps" and "Skills". A skill row has the initial, the skill's name and description, and opens the skill in its own page, which is not designed here (section 20). The chips and Recommended are hidden while a query is in the field.

- **Each group says which source answered.** When `browse` comes back with `remoteError`, its rows are the gateway's own, under "On this gateway", and the group says "The catalog didn't answer this search." When `skills.search` fails, the Skills group says "Skills search didn't answer." A source that failed never reads "No match".
- "No apps or skills match "<query>"." only when both answered and both are empty; "No apps match." or "No skills match." for one group whose source answered.

**More.** When the gateway returns `nextCursor`, "Show more" at the foot of the list asks the next page.

## 5. When the catalog can't be reached

When `browse` comes back with `remoteError`, or `categories` and `featured` fail, the gateway answered with what it has itself (R§2). Browse then says so and shows that, carefully:

- A note at the top, neutral: "**The catalog can't be reached from the gateway.** You can still see and manage what's on this gateway. Apps to add come back when the gateway can reach the catalog." with "Try again". Under it, the gateway's message as given, in `--text-faint`, folded behind "Details".
- No chips and no Recommended: "Categories and recommendations come from the catalog." in the place of the chips.
- The rows the gateway returned, under "On this gateway", each with its state pill. None has "Add".
- The search field reads "Search what's on this gateway". A search lists the gateway's own rows that match; the Skills group says "Searching skills needs the catalog."
- The window does not ask again by itself. "Try again" asks once more; it takes as long as the first time ("Asking the catalog… This can take up to 15 seconds.").

## 6. Add

**A catalog page.** Choosing a row opens its page in the section, with Back. It shows the initial at 56 px, the name (20/500), "by <author>", "Official" when `catalog.official`, and the summary; then, from `plugins.catalog.get` (R§2):

- "What it adds": its servers (`mcpServers`, with "signs in with OAuth" where `auth: "oauth"`), its skills by name, and the settings it needs (`configuration`, marked "required").
- "About": the readme as plain text (the first 12 lines, "Show all" for the rest), its version, and the verification and security summary as given.
- At the foot, "Add" (primary), or the access bar below admin.

Everything the catalog and a plugin give (a name, a summary, an author, the readme) is text, escaped, never markup: the readme is shown as plain text, not rendered Markdown. So an address in it, and the catalog's `repositoryUrl`, `documentationUrl`, `author.imageUrl` and the like, are text that is never fetched or opened (`docs/decisions.md`, "Addresses a gateway hands the client", its last row). A connector's resources, pictures and app views (`mcp.app.*`) never load by themselves. Render gateway strings with text insertion or context-appropriate escaping in every position, including names, headings, row and control labels, metadata, settings fields, tool results and notices. Values used in attributes and local navigation parameters are encoded for that context. Only the controls and addresses classified in the address decision can open a destination.

**The confirmation** (role `alertdialog`, focus on Cancel):

> **Add Quillnote to the gateway?**
> Package: `@quillnote-labs/quillnote`, from ClawHub. Version 2.4.1, the release reviewed here.
> The gateway installs this package and can run it with the gateway's access. The gateway will tell you if it needs a restart.
> [Cancel] [Add]

**The request** is the gateway's own: `plugins.install` (R§3). If the catalog row has `local.install`, use its source and identifier. For an installable remote ClawHub row with no `local.install`, use `source:'clawhub'` and the gateway's `catalog.packageName`. An "Official" label does not select the `official` request. Use `source:'official'` only when `local.install` gives it and names the `pluginId`. For ClawHub, use `detail.selectedRelease.version` when the detail reply supplies it. Omit `expectedIntegrity` in this catalog flow. Without a reviewed version say "The gateway picks the release." If the gateway supplies no install source and identifier through these paths, omit Add.

The install RPC supplies its own capability acknowledgement in OpenClaw 2026.10.6. An explicit refusal is shown with the gateway's reason. Do not promise a second capability review or automatically retry. If the gateway returns an acknowledgeable install-policy warning, show its actual findings and require a new click for `acknowledgeInstallPolicyWarning:true` on that same request.

**Then the gateway may ask first** (R§3), before anything is written:

| The gateway answered      | The screen                                                                                                                                                                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An install-policy warning | "**The gateway's install check found something.**" with each finding (its severity in words, its message, the file and line when given), "Add anyway" and "Cancel". "Add anyway" is a new click that sends the same request with `acknowledgeInstallPolicyWarning: true`. |
| A ClawHub trust error     | The refusal result below ("Couldn't add Quillnote:" and the gateway's message). Nothing to acknowledge.                                                                                                                                                                   |

**While it installs**, a step list from `plugins.install.progress` (R§3), each step started, done or failed: "Finding the release", "Downloading", "Unpacking", "Writing files", "Installing what it needs", "Starting it on the gateway". Cancel is absent: the gateway has no way to stop an install.

**How it ended**, after `plugins.list` is read back:

| The answer                            | The read-back                           | The result                                                                                                                                                                                         |
| ------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ok`, `restartRequired: false`        | `installed: true`, `enabled`            | "**Added Quillnote.** The gateway lists it as installed and turned on." and "Open Quillnote" (its page). Whether a bot is offered its tools is that bot's tool rules' business (`controls.md` §4). |
| `ok`, `restartRequired: true`         | `installed: true`                       | "**Added Quillnote.** The gateway lists Quillnote as installed and says a restart is required." Clawtrate does not restart the gateway.                                                            |
| A refusal before anything was written | not listed                              | "**Couldn't add Quillnote:** <message>. The gateway lists nothing new." with "Try again"                                                                                                           |
| A failure with `persistence`          | listed, `error`                         | "**Quillnote was installed but didn't start:** <message>." with "Open Quillnote" (its page, where Remove is)                                                                                       |
| No answer                             | as read                                 | "Checking what the gateway has…", then one of the above                                                                                                                                            |
| Any                                   | unreadable, or not what the answer said | "Couldn't confirm the install." with "Check again", which reads `plugins.list` again                                                                                                               |

Either installed outcome needs `installed: true` in the read-back. A recorded install and the restart flag alone say nothing about whether its tools work.

## 7. On this gateway

Every plugin `plugins.list` returns as installed, then every entry of `config.get` `mcp.servers` (R§2, §5). A search field filters both.

- **Plugins**, in two groups, "Turned on" and "Turned off", each row with the initial, the name, its description and its state pill. Plugins that come with OpenClaw are many (64 on a fresh gateway of this version), so they are folded behind one more group, "Comes with OpenClaw (64)", which opens in place.
- **Tool servers**, under that word, each row with the server's name in mono, its address or its command, and "Added by address" or "Runs a command". There is no state pill: the gateway reports none (section 9).
- "Add a custom connector" at the foot opens section 12.

## 8. A connector's page

A plugin's page: the initial at 56 px, the name, "by <author>" or, only for `origin: "bundled"`, "Comes with OpenClaw", the version, the state in words, the description; then "Tools", "Accounts", and the actions. It reads `plugins.list` (the row), `plugins.inspect {pluginId}` and, when it came from the catalog, `plugins.catalog.get` (R§8).

**Tools** lists what the plugin gives, from `inspect`'s `components`: each server ("quillnote, a tool server"), each skill, each command. Under the list: "Which bots may use these is in each bot's settings." linking to `controls.md` §4.

**The state**, from `plugins.list` and `inspect`:

| The gateway reports                              | The page says                                                                                                                                                                                                                 | Its actions      |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| `enabled`, `runtime.state: "active"`, no sign-in | "Added"                                                                                                                                                                                                                       | Turn off, Remove |
| `enabled`, `runtime.state: "unloaded"`           | "Added. The gateway reports it is not loaded."                                                                                                                                                                                | Turn off, Remove |
| `disabled`                                       | "Turned off."                                                                                                                                                                                                                 | Turn on, Remove  |
| `needs-setup`                                    | "Needs setup. Open Settings on the gateway to finish setup." When `inspect` reports credential fields with `status: "missing"`, their labels follow: "The gateway reports missing: Account address." No other field is named. | Remove           |
| `error`, or `runtime.state: "service-failed"`    | "Not working:" and `runtime.error` or `error`, as given                                                                                                                                                                       | Turn off, Remove |
| `removable: false`                               | (any of the above), with no Remove. When `origin: "bundled"`, also "Comes with OpenClaw, so it can be turned off but not removed."                                                                                            | no Remove        |

Editing a plugin's settings is not designed here (section 20); "Needs setup" says where to finish it, and names only fields the gateway reports missing.

**Accounts.** For every `plugins.inspect.mcpAuth` row, show the reported `serverName`, "Shared by everyone on this gateway", and the reported state. A server independently known to be declared with OAuth but missing from this reply shows its name and "Sign-in status not reported." Show no shared-account claim or sign-in action on that fallback. A turned-off plugin can show the turn-on requirement if the gateway reported that state. Read again after the user returns, and date a status only when read.

| `mcpAuth.state`                                    | The row says                                                                                                    |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `unauthenticated`                                  | "Needs sign-in." (warn)                                                                                         |
| `requires-authorization`                           | "Needs sign-in again." (warn)                                                                                   |
| `pending-authorization`                            | "Sign-in pending."                                                                                              |
| `authorized`                                       | "Signed in. The gateway reports saved sign-in tokens." and, under it, "Whether they still work isn't reported." |
| No row for a server the plugin declares with OAuth | "Sign-in status not reported."                                                                                  |

For an eligible reported row show "Open Settings on your OpenClaw gateway to sign in to <server>." Show "Check again" for the inspection (section 10). The gateway's terminal command cannot find a plugin's own server, so it is not offered here (R§7). There is no "Connected": `authorized` means the gateway holds tokens, not that they work (R§8). A plugin with no sign-in has no Accounts group. When the plugin is turned off, `inspect` reports no sign-in, and the group says "The gateway reports sign-ins only while Quillnote is turned on."

"Add another account" is not offered for a plugin: the gateway keeps one sign-in per declared server, and no method adds a second (R§8). For a server added by address it is section 9's.

**Turn off and Turn on** write `plugins.setEnabled`, then read back. Turning off says first, in the confirmation: "Turn off Quillnote? Its settings and any saved sign-ins stay." with "Cancel" and "Turn off". Turning on needs no confirmation. Runs already going may keep the runtime state they started with (`controls.md`). After either, the result states the read-back's explicit fields; what follows from them is not reported as read.

**Sign-in: "Not reported."** Under it, always: "The gateway doesn't report whether it's signed in to this server, or for whom." Offer "Sign in" only for an enabled shared HTTP OAuth entry without an auth-profile override (section 10). For an existing per-requester entry: "Uses the gateway's requester sign-in. Set up and use it in a channel where the gateway identifies each sender." There's no sign-in action on this server page (section 11).

**Accounts.** The gateway keeps one shared sign-in per server name and address (R§6). So a second account at the same address is a second server under another name. "Add another account" is offered only for a shared HTTP OAuth server whose credentials the gateway stores for that entry ("Sign in with OAuth"); with an external auth-profile override the page omits the second-account promise and the logout directions; its line says "A second name for the same server, with its own sign-in. Bots tell them apart by name." It opens section 12 with the address and the header names filled in, the header values and the name left empty, and under the headers: "Enter any header values this server needs. Saved values are hidden." The label a person types is the name.

What the page can never say: that the server is signed in, for whom, until when, or that it works now.

## 10. Signing in from a page

"Sign in" on a server's page, and on a plugin's account row (section 8). It needs admin; below admin the access bar takes its place (section 2).

**The rule.** The gateway starts a browser sign-in (`mcp.authLogin`) only for a connection that comes from a browser (R§7). Clawtrate never presents a connection as a browser to be given what the gateway withholds from its own kind of connection. Both apps reach the gateway through their host, the desktop app's main process or the web preview's host, as the same client: `gateway-client` in `ui` mode, with no `Origin` (R§7). In the web preview the viewer's browser shows Clawtrate's page, but it is not the gateway's client. So both apps sign in the same way: neither calls `mcp.authLogin`, and both give the gateway's own sign-in steps.

**Which sign-in a page gives** depends on where the server is defined, because the gateway's terminal command reads only its own settings (R§7):

| The server                                                                                                                                                              | The page gives                                                                                                                            |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| An entry in the gateway's settings (`mcp.servers`) that is enabled, has an HTTP URL and `auth: "oauth"`, is shared (not per-requester) and has no `oauth.authProfileId` | The command-line sign-in, below, with the entry's exact configured name                                                                   |
| A plugin's own server (an account row of section 8, named by the gateway's `mcpAuth[].serverName`)                                                                      | For an eligible reported row show "Open Settings on your OpenClaw gateway to sign in to <server>." Show "Check again" for the inspection. |
| Any other entry (per-requester, an auth-profile override, not OAuth, turned off)                                                                                        | No sign-in from Clawtrate                                                                                                                 |

**The command-line sign-in:**

1. "On the gateway's machine, run:" and `openclaw mcp login notes-work` in the command block. The name is rendered from the reviewed entry, shell-quoted when necessary, with the gateway's profile option when the host knows the gateway runs under a named profile.
2. "If it prints an address, open it in a browser and sign in."
3. "If the terminal is listening for the callback, it waits up to five minutes. Follow the terminal's instructions to finish with a code if the callback cannot reach it."
4. "It may also find a saved sign-in and say so without printing an address."

Under the steps: "Or sign in from Settings on the gateway's own web page." For the gateway's Settings flow, the gateway's page says "Sign-in response received. Return to OpenClaw for the sign-in result." The terminal flow may use its own loopback callback or finish with a code. On return to Clawtrate, a raw entry still reads "Not reported."

## 11. A sign-in in the conversation

**"Each person signs in" is not offered for Clawtrate chat.** For a server with `oauth.identity: "per-requester"` the gateway keeps one sign-in per requester, told apart by channel, account and sender, with no device in it (R§7). For a client like Clawtrate the sender is the client's own id, `gateway-client`, the same on every device of this app. Two people who use one gateway from Clawtrate are one requester to it, and would share one sign-in. So the form of section 12 offers no per-requester choice, and an existing per-requester entry says on its page: "Uses the gateway's requester sign-in. Set up and use it in a channel where the gateway identifies each sender."

**A live connect result.** If a bot in a Clawtrate task calls such a server's `<server>__connect` tool anyway, the call's live result can carry `details.mcpConnect {serverName, authorizationUrl}` (R§7). Only then is the action card (`conversation.md` §8.3) a connect card, and it says what the gateway can and cannot tell apart:

| The call's result                                                                       | The card                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `details.mcpConnect {serverName, authorizationUrl}`, observed live for this call        | Initial, "**team-notes asks for a sign-in**", "The gateway sees every device using Clawtrate as one sender, so this sign-in is shared by everyone who uses this gateway from Clawtrate.", the sign-in address in full as text (below) with its copy button, and under it "After you sign in, ask Pip again." |
| "MCP server "team-notes" is connected. Its tools become available on the next message." | The ordinary card, with the gateway's words as its result                                                                                                                                                                                                                                                    |
| `details.status: "error"` (no public address)                                           | "**team-notes can't ask for a sign-in here:**" and the message as given ("… gateway.publicOrigin is not configured. Ask the operator to set the public Gateway HTTP(S) origin.")                                                                                                                             |

- **The address is text, with no button that opens it.** The decision on addresses lets a person open a link in a tool's result only for the kinds it names (a link card, web search results, an MCP `resource_link`, a T3 Code thread); any other address in a tool result is never fetched or opened and may appear as text (`docs/decisions.md`, "Addresses a gateway hands the client"). `details.mcpConnect.authorizationUrl` is not among them, and in Clawtrate chat the gateway cannot say for whom the sign-in is (above). So the card shows the address in full, its host in medium weight on the first line and the whole address under it in mono, with "Copy sign-in address", and the line "To sign in, copy this address into a browser." Opening it from the card would need the decision to name it (section 20).
- The gateway tells the client nothing when the sign-in finishes, so the card never says it did.
- If a used or expired attempt reaches the gateway's callback, the gateway can show "This sign-in link expired or was already used. Ask the bot to connect again." The card reports no link status. Under the address show "Anyone with this address can complete this shared sign-in." In a task more than one person can read, show that line as a warning.

**From history, never a connect card.** `chat.history` keeps a call's tool name and its result text, and omits `details.mcpConnect` (R§7). A call read back from history is therefore the ordinary action card, with the tool name as recorded (`team-notes__connect`) and its result as text; an address in that text is shown in full, as text, and never opened (`docs/decisions.md`, "Addresses a gateway hands the client"). Nothing is inferred from a tool name's prefix, from the tools the gateway lists today or from the result's words: a card made that way could name the wrong server or offer an old link again.

**A shared server says nothing in the conversation.** A shared OAuth server that is not signed in is left out of the bot's tools; the bot gets no connect tool and the gateway sends no card (R§7). The server's page (section 9) is where its sign-in starts.

## 12. Adding a server by address

"Add a custom connector", Type "Remote HTTPS". It needs admin.

| Field      | Rule                                                                                                                                                                                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name       | Required. Letters, digits, hyphens and underscores. The name bots see in tool names (`notes-work__…`). A name already on the gateway: "There's already a server named notes-work."                                                                                |
| Server URL | Required. "Enter the server's URL." when empty. Not a URL: "Enter a URL that starts with https://." A URL that is not `https`: "Use the server's https:// URL." Nothing is saved until it is `https`. (Clawtrate's rule; the gateway itself accepts `http`, R§5.) |
| Headers    | Optional, name and value rows, "Add a header". The value field is a password field. Under them: "Kept by the gateway in its settings file, not encrypted there. Clawtrate can't read a value back once it's saved."                                               |
| Sign-in    | A radio group: "None" and "Sign in with OAuth". There is no "Each person signs in" (section 11).                                                                                                                                                                  |

There is no Client ID and no Client Secret: the gateway has no field for either and refuses them (R§5). The gateway handles OAuth registration and credentials.

**The write.** Every write to a server entry follows one contract (R§5):

1. **The revision reviewed.** When the form opens (and when "Add another account" fills it in), Clawtrate reads `config.get` and keeps its `hash`. That read is also where a name already on the gateway is found: "There's already a server named notes-work."
2. **The patch.** `config.patch` (admin) with `raw: JSON.stringify({mcp: {servers: {[name]: entry}}})` and `baseHash` set to that `hash`, never a hash read later. The entry is exactly:

   | Kind                               | `entry`                                                                                                                                                                                                 |
   | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | Remote HTTPS, Sign-in "None"       | `{url, transport: "streamable-http", headers?}`                                                                                                                                                         |
   | Remote HTTPS, "Sign in with OAuth" | `{url, transport: "streamable-http", headers?, auth: "oauth"}`                                                                                                                                          |
   | Command (section 13)               | `{command, args, cwd?}`, with `args` always an array, `[]` when there are none                                                                                                                          |
   | Removal (section 14)               | `null`. Include in `replacePaths` the exact paths of every array field removed under the reviewed entry, including `args`, `toolFilter.include`, `toolFilter.exclude` and `codex.agents` where present. |

3. **A changed revision.** If the reviewed hash is stale, show "The gateway's settings changed. Review the current entry before trying again." Read current settings without retrying the write. If the name now exists, show "There's already a server named <name> on the gateway." Keep the draft, show the gateway's current entry separately, and require another name before adding. A removal can be sent again only after reviewing the current entry and confirming again. The hash read when the form or confirmation opened is the one kept through submission.
4. **The read-back.** After an accepted write, after a refusal and after no answer, Clawtrate reads `config.get` and compares the fields the person reviewed: the address, the transport, `auth` and the header names (remote), or the command, every argument and the working folder (command). Header values cannot be compared: the gateway hides them (`__OPENCLAW_REDACTED__`), so their names are the most that can be verified.

| The reply, then a fresh read                                                         | The section shows                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The gateway accepted the write and a fresh read matches every visible reviewed field | "**Added notes-work.** The gateway lists this server." and "Open notes-work", and under it "The gateway hides saved header values." when there were headers; for a command server also "The gateway can start this program when it needs this server." With "Sign in with OAuth": "Sign in" as the next step. Nothing is said about bots or runs. |
| Read succeeded, entry differs                                                        | "**Couldn't confirm the change.** The gateway lists a different entry." and the entry's visible fields as read                                                                                                                                                                                                                                    |
| Read failed                                                                          | "**Couldn't confirm the change.** The gateway's settings couldn't be read back."                                                                                                                                                                                                                                                                  |
| A lost or refused reply, and a matching entry                                        | "The gateway lists an entry with these settings. Couldn't confirm this save." The visible match cannot identify the writer or establish which hidden values won.                                                                                                                                                                                  |
| A lost reply, and a read showing absence                                             | "The gateway's settings have no entry named notes-work."                                                                                                                                                                                                                                                                                          |
| A refusal, with absence confirmed                                                    | "**Couldn't add notes-work:**" and the actual error as given ("mcp.servers.notes-work.url: Expected http:// or https:// URL"), the field it names marked.                                                                                                                                                                                         |

"Check again" repeats the read only, and can still fail.

## 13. Adding a server started by a command

"Add a custom connector", Type "Command". Only an admin connection reaches it; below admin the access bar takes the form's place, and on a gateway whose settings are read-only its note does.

| Field          | Rule                                                                                                                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name           | As section 12                                                                                                                                                                                  |
| Command        | Required: "Enter the command." Clawtrate refuses an empty command; the gateway would accept one and do nothing with it (R§5). Spaces at its start and end are removed.                         |
| Arguments      | One per line. Each line is one argument: spaces at its start and end are removed, spaces inside it stay part of that argument, and a line left empty is dropped. Nothing goes through a shell. |
| Working folder | Optional. Spaces at its start and end are removed; left empty, the entry has no `cwd`.                                                                                                         |

Under the fields: "The gateway can start this program on its own machine, as the user it runs as, when it needs this server. The program has that user's access to files, programs and the network." and "The gateway can show saved commands and arguments to operators who can read its settings." (a command and its arguments are read back in full, R§6; no secret belongs in them). "Continue" opens the confirmation.

**The confirmation**, before anything is written (role `alertdialog`, focus on Cancel). It shows the reviewed values, and those same values, no others, are what the write sends (section 12's contract):

> **Run this command on the gateway's machine?**
> On Home gateway's machine (`studio.example`):
> Program: `/opt/example/bin/search-server`
> Arguments: `--stdio`, `--index ./notes`, each on its own line, or "No arguments"
> Working folder: `/srv/notes`, shown only when one was given
> The gateway can start this program on its own machine, as the user it runs as, when it needs this server. The program has that user's access to files, programs and the network.
> [Cancel] [Add command server]

Each argument is shown on its own line, in mono, never shortened, so an argument with spaces in it reads as one. The machine is the gateway's address as this device knows it, or "the gateway's machine" when that is all it knows.

- Keep the untouched form in memory until the operation ends or the person leaves it. On Continue, trim the command and working folder, split the textarea on newlines, trim each line and drop empty lines. Cancel or Escape restores the untouched form and puts focus on Continue. The confirmation, patch and read-back comparison all use the resulting program, argument array and optional working folder. Show them independently in the resulting server page. Do not put a draft, header value, program, argument or working folder in a navigation address.
- Tab and Shift-Tab stay inside the confirmation, as in every dialog here. Cancel and Escape close it and put focus back on "Continue", with every field as it was typed.
- "Add command server" writes `{command, args, cwd?}` and reads back by section 12's contract; the result compares the command, every argument and the working folder with what was confirmed.

## 14. Removing

Every removal is a confirmation that says exactly what goes and what stays, then a result in the same two lists, each item marked by what was read back (the removal list, section 2).

**A connector** (`plugins.uninstall {pluginId}`, admin, R§4). The gateway removes a plugin by the package that owns it, which can hold several plugins:

> **Remove Quillnote from the gateway?**
> The package `@quillnote-labs/quillnote`, with: Quillnote, Quillnote sync. (the plugins `plugins.list` shows with that package; when the inventory doesn't establish them: "The gateway removes the package that owns Quillnote, and any other plugins in it.")
> Goes: the package's files on the gateway's machine; its settings on the gateway; its tools.
> Stays: Any saved MCP sign-ins in gateway state. The gateway stores these unencrypted. The gateway keeps an off marker for the removed plugin.
> [Cancel] [Remove]

Any credentials a plugin manages outside MCP state are unreported. Use the gateway's `removed` and a fresh `plugins.list`. For each plugin named by the receipt or established before confirmation, show "No longer installed" if a fresh list omits it or says `installed:false`, and "Still installed" if it remains installed. If the affected package membership was unknown, say "Other affected plugins weren't confirmed." If the list is unavailable, show "Couldn't confirm the removal." The list confirms installed status. It gives no separate read-back of files, settings or credentials. "Check again" reads `plugins.list` again, and can fail again. `removable` alone decides whether Remove is offered (section 8).

**A tool server** (section 12's contract: `null`, with `replacePaths` for a command's arguments, and the `hash` read when the confirmation opened, R§5):

> **Remove notes-work from the gateway?**
> Goes: the server's entry in the gateway's settings, with its headers; its tools.
> Stays: "Removing this entry leaves any saved MCP sign-ins in the gateway's state. The gateway keeps them unencrypted." The gateway finds them again if a server with the same name and URL is added.
> To clear them, run `openclaw mcp logout notes-work` on the gateway's machine before removing the entry, or remove it there with `openclaw mcp unset notes-work`, which clears them too.
> [Cancel] [Remove]

The sign-in lines are for an OAuth entry only. The commands render the name from the reviewed entry, shell-quoted when necessary, and carry a known profile option on `login`, `logout` and `unset`. For an existing per-requester entry `logout` refuses, so the line is: "To remove it and clear them, run `openclaw mcp unset team-notes` on the gateway's machine instead." (R§6). For an entry without an OAuth mode, omit the Stays sign-in line. Then `config.get` is read. Write "Removed notes-work. The gateway's settings no longer have it." only when a fresh read finds absence. If it remains, say "notes-work is still in the gateway's settings." Append the gateway's reason only if one was received. When the settings changed since the confirmation opened: "The gateway's settings changed. Review the current entry before trying again."; the removal can be sent again only after reviewing the current entry and confirming again. When the read fails: "Couldn't confirm the change. The gateway's settings couldn't be read back." "Check again" repeats the read only and can still fail.

### What the engine supplies

- A catalog store that keeps the last overview, its time, and whether it came with `remoteError`.
- Gateway strings are text in every position (section 6): text insertion or context-appropriate escaping for names, headings, labels, metadata, settings fields, tool results and notices; attribute and navigation values encoded for their context.
- One write at a time per window: a second change waits for the read-back of the first.
- A server write carries the `config.get` `hash` read when the person reviewed it, and the exact entry of section 12; its result comes only from the read-back's comparison.
- The command and the profile option for `openclaw mcp login`, `logout` and `unset` come from the host, as the approve command does (`bots.md` §2).

### Order

1. On this gateway and a connector's page, read-only (rows F-218 in part).
2. Browse, its states without ClawHub first (F-217, F-380).
3. A tool server's page and adding one by address and by command (F-221, F-381).
4. Add, with its confirmations and results (F-217).
5. Sign-in from a page: the gateway's own steps, the same in both apps (F-220, F-382).
6. The connect card (F-220).
7. The picker (F-004).

### Prototype states

`connectors.html?screen=<id>`, one per state; the README lists the parameters. The prototype draws the Settings frame and the confirmation again (`.c-window`, `.c-frame`, `.c-confirm`) so that its one-pane layout follows the prototype frame's width; in the app they are `bots.md`'s. The walks the check clicks: Browse to a catalog page to Add, through the review, progress and each ending; the catalog unreachable and Try again; a search with results and with none; On this gateway to a connector's page in every state, Turn off and on, and Remove; a server's page in every state of its last run, "Add another account", and Remove; adding a server by address with each error and each ending; adding a command through its confirmation; the gateway's sign-in steps for a tool server and for a plugin's server; the connect card with its address as text, read from history, and its error; the picker, ticked, then Browse with "You picked"; and each admin action on a read-only connection, through the request.
