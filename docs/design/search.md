# Search

What Cmd/Ctrl+K opens: one palette over the bots, task names, messages, files, links, routines and settings, and on the iPhone the same search with scopes. It shows only what matched, and it opens each result that can be opened in the place where it already lives. It builds on `visual-language.md` and `conversation.md`, in the same language and with the same tokens.

What must be true is in `docs/parity.md`, rows F-033, F-240 and F-268. What the gateway does is in `docs/research/search.md`, from OpenClaw's source and a development instance. This document decides appearance, wording and input, and for every state it names the gateway fact behind it. Section 13 lists those facts. Section 14 lists the parity rows whose wording changes, and the one that needs a decision. Section 15 is for builders.

One rule sits above the rest: **the palette shows what matched, and nothing else.** A group is drawn only when it found something, and a group that found nothing is neither drawn nor listed. A search that finds nothing says so in one plain line: No results for “ephyr”. The palette carries no panel explaining what search looks in; what each source covers, and what it can't find, is written down here (sections 5, 6 and 8) rather than in the interface. A source that failed still says so, with "Try again" (section 10), and the live region says only what the screen says.

The prototype shows all of it: `prototype/search.html` is the app with the palette added, and its address picks any state (section 15). The styles are in `prototype/css/search.css` and the behaviour in `prototype/js/search.js`. `prototype/tools/checks/search.mjs` checks them. The prototype predates the plain palette (#793): it still draws a panel before anything is typed, groups that found nothing and a list of the sources with no match. Where it differs, this document and the app decide.

## 1. How search works

The palette is a dialog over the whole window. Its field is a combobox; under it, one list holds the results in groups, one group per source. Typing filters what the device already holds at once (bots, task names, links, settings) and asks the gateway for the rest (messages, routines, files) when typing pauses (section 6). Each group fills in when its source answers, so a slow or failed source never holds the others back.

Enter opens the active result where it lives: a bot in the rail, a task or a message in its conversation, a setting in Settings. A file result is its name only (section 9). Opening reuses those views and changes none of them. The palette closes, and the query goes with it: it is never written to a log, kept, or offered again (section 2).

On the iPhone, and in a desktop window narrower than 688 px, search is a full screen with scopes: All, Messages, Bots, Group Chats, Files and Routines (section 11).

### Tokens

No new token. The palette is `--bg-raised` with `--shadow-pop` and an 18 px radius; rows use the 10 px radius and `--bg-selected` when active; group names are 13 px medium `--text-muted`, a group's failure or status line 13 px `--text-faint`, row first lines 14 px `--text`, second lines 13 px `--text-muted`, the key hint 12 px `--text-faint`, the status line under the results 13 px `--text-muted`. Where the device itself found the query in a name, those characters are drawn in medium weight and `--text` against the rest in `--text-muted`: weight, not colour, since colour belongs to the bots and to the person (`visual-language.md` §1, principle 5). Message snippets carry no marks (section 7).

### The query

- It lives in the palette's state while the palette is open, and on the iPhone while the search screen is in the navigation stack. Closing the palette, Cancel on the phone, or switching gateways clears it.
- It is never written to the host's log, to the device's storage, to the address, to `users.prefs`, or anywhere else. There is no list of recent searches. Requests carry it to the person's own gateway and nowhere else; on the development gateway, the log records a search's method, time and size, not its words (research §8).
- It is trimmed. It is at most 4,096 characters, the gateway's limit; the field stops there.

### Content, not interface

Everything a row shows that came from the gateway is text: bot names and labels, task titles, snippets, file names and paths, routine names, link addresses. Nothing in a snippet is a link, a picture or formatting: the snippet is drawn as the gateway sent it, with runs of white space shown as one space. A bot's picture follows `docs/decisions.md`, "Addresses a gateway hands the client", as everywhere else on the platform: a `data:` picture is drawn only after the core decoded it as PNG, JPEG, WebP or GIF of at most 2 MiB; an `https` one is never fetched, and the bot's character is drawn instead ("Doing, not asking"; until that conversion is built, the desktop draws it after the person allowed that exact address); anything else is the bot's character. A link's address is shown as text: its host first, then its full canonical serialization (scheme, host, port, path, query and fragment) on a line that breaks anywhere. That same serialization, and nothing else, is what is handed to the system, with no lookup, fetch or preview before or after (section 9).

### Access

Every source is read tier: `agents.list`, `cron.list`, `sessions.search`, `sessions.files.list`, `agents.workspace.list` and `chat.history` all answered a connection holding only `operator.read` (research §12). The palette never asks for more access and writes nothing, so on a read-only connection it is the same in every state and needs no access bar.

### Announcements

The palette has its own polite live region. It is drawn from the same state as the list, so it never says more than the screen: it speaks once nothing in view is pending (section 12). Moving through results is announced by the screen reader from the active option, not by the live region.

**Why the scope matches the task list.** `excludeCron` and `excludeSubagents` are the task list's own filters (`packages/core`, `SESSION_LIST_PARAMS`), and `scope` leaves archived tasks out by default. The search requests these two filters. The device applies its own task list rules and 500-task limit separately. The result opens only if its matching task and message are available, as in section 9. Searching archived tasks (`archived: "all"` finds them, research §9) is not offered: the app lists no archived task, so their results would lead nowhere.

**Why task names are their own group.** Tasks searches titles in this device's loaded task list. The device keeps up to 500 tasks. A cut-short or unavailable list says so under the group's heading when a title matches; with none matching, the group isn't drawn. The gateway's search does not match a task's title (research §1), and a person remembers a task by its title; the titles are already on the device, so matching them costs no request, and finds "Heat pump vs. gas furnace" for "furnace", which the message search would not. On the iPhone the group sits inside the Messages scope.

## 6. When the gateway is asked

A search costs the gateway little: on about 400 tasks it took 10 to 20 ms, the first after a start 2 s, and it reads an index, not files (research §8). A files search walks up to 5,000 entries per bot. So:

- Bots, Tasks, Links and Settings are filtered on every change to the field.
- Messages and Routines are asked 250 ms after the last change. Files are asked at the same moment, once the query has 2 characters or more: a single character is in nearly every path, and the walk would stop at its 500-name cap; with one character Files isn't asked and isn't drawn.
- **Every change to the text starts a new generation at once**, before the pause: the gateway's groups are emptied of the previous answer's rows and the status line says "Searching…" (section 10), and the actions on those rows go with them. Every reply, retry, open and announcement carries the generation it started in, and is dropped on arrival, before it changes anything, when that generation is no longer current.
- One request per source is in flight. While one is out, only the latest query waits, with the generation that queued it, and it is sent when that reply arrives or after 8 seconds, whichever comes first, and only if its generation is still current; a request not answered in 8 seconds is given up (section 10). "Search each bot for more" and Files each run one batch at a time, with at most 4 requests in flight (sections 8 and 7). Files has one lane and one pool for the whole source: a batch, a single bot's retry and the latest query's batch all go through it, so a new query or a retry never puts more than 4 Files requests in flight; each request sent has the same 8-second deadline, work not yet sent is dropped as soon as the text changes, and the next batch and each retry are offered only once the current batch has settled.
- A result opened before the pause (one of the device's own) is not cancelled when the gateway is then asked.
- Nothing is asked for an empty field.
- **A change of connection starts a new generation too**: when the connection drops, reconnects, or comes back with other scopes, the gateway's groups are cleared and the status line says they were not searched (section 10), anything still out from before is dropped, and an open link confirmation is cancelled. When it is connected again, the latest query is asked once. On a change of gateway or of access, the previous authority's cached search inputs (its bots, task titles and loaded links) are cleared; an ordinary disconnect from the same gateway, with the same access, still filters that connection's cache.

## 7. Results: groups, rows, Show all

**A group** has a heading row (not an option): its name and, after a dot, its count of results shown ("Messages · 25"). Under the heading there is no line about what was searched: the palette shows results, not how search works. A line appears there only for something a person acts on or something that changes what the results mean: a failure with its "Try again", a list that is stale, or messages still being indexed (the table below). A group is drawn only when it has results, or when it failed or has an action that searches further ("Try again", "Search the next 8 bots' files"); such a group without results shows its heading and its action, and its line only when it failed. A group with no results is not drawn and not named anywhere, and no heading ever shows a count of 0. A group shows its first 5 rows, then the action row "Show all 25 messages", which shows the rest in place and leaves the other groups as they are.

## 8. Messages: what the gateway returned, and searching each bot

`sessions.search` has no cursor, no offset, no time range and no time order: it returns at most `limit` matches, at most 25, chosen by its relevance score in each bot's index, and says `truncated` when that index holds more matches than it sent (research §3, §5). `indexing` and `archivedTranscriptsExcluded` say that part of the index was not searched. So the palette can never page back, and never says "recent messages". A narrower search can return matches a wider one left out: across all bots, the 25 came from two bots of four, and a search per bot returned 25 more for each of the other two (research §7). It does not promise more: a bot's own search may return the same matches, and a second query reads the index as it is then.

**The first search** asks across all bots. The palette shows what came back newest first, since the gateway's scores of two bots are not on one scale (research §3) and time is what a reader can follow. Only `indexing` and `archivedTranscriptsExcluded` give the group a line, because each makes a short list, or "No results", possibly untrue. `archivedTranscriptsExcluded` counts listed tasks whose older transcript content is in the gateway's cold archive (research §4), not archived tasks, hence its words. "Search each bot for more" is offered whenever the reply is incomplete, with or without matches; with no match, Messages is drawn as its heading and that action, under the nothing-found lines. A per-bot search uses the same scope, so whether it reaches cold-archived content is not established; the line says what was left out, and the action says only what it does:

| What came back                   | Line                                                                                                                                   | Action row                                          |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| No `truncated`, no other flag    | none                                                                                                                                   | none                                                |
| `truncated`                      | none                                                                                                                                   | "Search each bot for more", with or without matches |
| `indexing`                       | "Some messages are still being indexed." under Messages' heading; with no match, as a status line under "No results" (section 10)      | as above, with or without matches                   |
| `archivedTranscriptsExcluded: 4` | "Older messages in 4 tasks weren't searched." under Messages' heading; with no match, as a status line under "No results" (section 10) | as above, with or without matches                   |

The palette knows the index is catching up only from the reply: `sessions.search` returns `indexing: true` when a task whose index needs rebuilding was left out of the search and its rebuild started in the background (research §4 and §8), the core maps it to `MessageSearch.indexing`, and each new search reads it again, so the line goes once a reply comes without it.

**Search each bot for more** asks again once for each bot, with `scope.agentId`, 25 each, in the rail's order: at most 24 bots per action, 4 requests at a time. While it runs, the first search's rows stay and the status line says "Searching…"; nothing says Messages found nothing meanwhile. Then the rows are shown bot by bot. No line tallies the bots or names those not asked; a line appears only for:

| A bot's reply                                 | Its line                                                                                                          |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Failed or timed out                           | "Pip · couldn't search: <the gateway's message>", with "Try again for Pip"                                        |
| `indexing` or the archive count, with matches | "Juniper · Some messages are still being indexed." and/or "Juniper · Older messages in 2 tasks weren't searched." |

A bot that found nothing isn't named. With more than 24 bots, "Search the next 6 bots" asks the rest; the prototype's `bots=30` draws it. A new query starts again from the first search.

**What it cannot find.** Inside one bot, matches beyond what that bot's search returns. The gateway would return some of them for a narrower set of that bot's tasks (research §7), but nothing reaches all of them, and the palette does not walk a bot's tasks in batches to collect a list it still could not call complete. More words narrow a search to what a person wants. It also cannot find text the gateway does not index (section 5) or messages in archived tasks.

## 9. Opening a result in its place

Opening uses the identity the reply returned, all of it together: the task's `sessionKey` and `sessionId` and the message's `messageId`. A link keeps the identity of the message it came from. ## 10. Nothing found, partial, failed, offline

**Nothing found.** Once nothing is pending and no group has a result, the status line says "No results for “ephyr”." and nothing else: no list of the sources that found nothing, and no explanation of what each covered. The gateway's rules on what a message search matches (research §2: "ephyr" finds nothing in "Zephyrine") and each source's coverage are in sections 5, 7 and 8. The exceptions are what the message search says it left out: when it found nothing and its reply says `indexing` or `archivedTranscriptsExcluded`, quiet lines follow, "Some messages are still being indexed." and "Older messages in 4 tasks weren't searched.", since "No results" may then be untrue, and Messages is drawn as its heading with "Search each bot for more" (section 8). The same holds for `truncated`, with the action and no line. The lines show the same way when another group found something but Messages found nothing, and go with the next reply that doesn't carry the flag. With nothing found, the status lines come first, above any group drawn for its action. A failed source is still drawn, with its line and "Try again", beside "No results".

**Still searching.** While any source asked has not answered, a "Search each bot for more" or a routine page included, the status line says "Searching…". No group is drawn for a source until it has a result; the device's own groups show theirs at once, and a group that has results keeps them while it searches further. The palette has no skeleton rows.

**Failed and timed out.** A source that fails shows its heading and one line on `--danger-soft`: "Couldn't search messages: <the gateway's message>." with the action row "Try again", which asks that source again. A request that has not answered in 8 seconds is given up the same way: "Couldn't search messages: the gateway didn't answer in 8 seconds." The other groups are not touched. For Files, a failure is per bot, in the line under Files' heading.

**Offline or reconnecting.** The gateway's sources are not asked and no group is drawn for them. The status line says "Messages, files and routines weren't searched: Home gateway isn't connected.", after "No results for “ephyr”." when nothing matched. The device's groups still filter what was loaded before, and the latest query is asked again once the gateway is connected.

## 11. The phone: scopes

On the iPhone, and in a desktop window narrower than 688 px, the search button at the top right opens search as a full screen.

- **The top.** The field as a pill, 44 px, with "Search" as its placeholder and focus on opening, and "Cancel" (a quiet button) to its right, 12 px from the edges.
- **The scope bar** under it: six segments, All, Messages, Bots, Group Chats, Files, Routines, in a row that scrolls sideways when it does not fit. All is chosen first. The bar is a tab list; the results under it are its panel.
- **All** shows every group in section 5's order, 3 rows each, then "See all 25 messages", which chooses that group's scope. **Messages** shows Tasks, Messages and Links. **Bots**, **Files** and **Routines** show their group. Settings shows only in All, and since it has no scope of its own, All shows every Settings row.
- **A scope asks only for what it shows.** All asks every gateway source; Messages asks the message search (Tasks and Links are the device's own); Files asks files; Routines asks routines; Bots and Group Chats ask nothing. Choosing another scope asks the sources it shows for the current text, if they were not asked yet.
- **A link row has an "Open link" option** under it, a touch target of its own, under the same address rule as ⇧↵ (section 9). Its name says where it opens: "Open <address> in your browser", on the iPhone "Open <address> outside Clawtrate". The row itself goes to the message.
- **Files are names only**, as on the desktop: a file row says "Opening a file from search is unavailable until the gateway can bind the read to the workspace searched." and opens nothing.
- **Group Chats** shows one line: "Group chats aren't part of Clawtrate yet." It is true, and it keeps the scope's place for when they are.
- Rows are at touch sizes: 56 px or more, 32 px avatars, 17 px first lines. A group's failure and status lines, "Search each bot for more" and every line of section 9 are the same, except where a link opens: the iPhone says ‘Opens outside Clawtrate’. Desktop and web preview say ‘Opens in your browser’, the narrow desktop window included.
- **Opening.** On the iPhone a result pushes its place onto the stack (Home, Search, then the chat); Back returns to Search with the query, the scope, the results and the chosen scope's scroll position as they were. Cancel clears the query and returns to Home. In the narrow desktop window, opening closes the search screen and shows the one-pane detail; Back to bots returns to the list, and search opens empty again.
- The software keyboard's return key reads "Search", hides the keyboard and opens nothing; the gateway was already asked on the pause. A hardware keyboard's Enter opens the active result, as on the desktop.
- Scroll and focus survive a group filling in: the list keeps its position, and a focused scope stays focused.

## 16. Not covered here

- **Group chats.** Their own design is not merged. A place is kept in the palette's order (between Bots and Tasks) and the phone's Group Chats scope says they are not part of Clawtrate yet.
- **Several gateways.** Their own design is not merged. The palette searches the connected gateway; how results from several would be grouped and named is left to that design.
- **Loading earlier messages in a conversation.** `chat.history {messageId}` returns a page that starts at a message, with a cursor forward (research §4). With it, the conversation could show an older match in place; until the conversation design adds earlier pages, the palette says the message can't be shown in place.
- **Searching inside one bot's tasks in batches** to go past what its own search returns (research §7).
- **Searching reasoning, tool calls or tool results.** The gateway does not index them; a plugin would have to.
- **A task's own folder or repository.** Files search covers bots' workspaces; the Work pane's filter (`work-pane.md` §3) searches one task's files.
- **Archived tasks.** The gateway can search them; the app lists none, so nothing would open.
