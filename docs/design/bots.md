# Bots, accounts and T3 Code

How a bot is created with the account it runs on, how accounts are connected, what a bot's settings say about its account, model and lock, and how the optional T3 Code integration is set up. This is the third part of the design, after `visual-language.md` and `conversation.md`, in the same language and with the same tokens.

What must be true is in `docs/parity.md`, rows F-472 to F-490, and the bot setup rows F-034 to F-052 that the same screens carry. What the gateway can do is in `docs/research/provider-accounts-and-t3-code.md`, above all its Part C. This document decides appearance, wording and input, and for every state it shows it names the gateway fact the state rests on. Section 20 lists those facts with their sources. Section 21 lists the parity rows whose wording has to change. Section 22 is for builders.

One rule sits above the rest: **no state claims more than the gateway establishes.** The app knows which account a bot is bound to; it never knows which account served a turn. It knows a sign-in it started finished; it does not know that a sign-in someone else made is still valid. Where the gateway says nothing, the screen says that it cannot see, and never fills the gap.

The prototype shows all of it: `prototype/bots.html` is the app with these screens added, and its address picks any state (`prototype/README.md`). The styles are in `prototype/css/bots.css` and the behaviour in `prototype/js/bots.js`. `prototype/tools/checks/bots.mjs` checks them.

## 1. How the pieces fit

```
"+" menu, New bot (⌘N)          New bot: picture and name, then Account, then Create

    Connect another account        the connect component, inside the same dialog
gateway menu, Settings (⌘,)     Settings: Accounts, Integrations

    Connect an account             the same connect component
  Integrations                     the T3 Code switch, off by default
Work pane, Settings tab          a bot's settings
  Account                          bound or locked, the lock command, changing it
  Model and effort                 side by side, from the account's provider
  Tools                            tools that come with the account; T3 Code for this bot
transcript                       event lines and the turn error, as conversation.md has them
rail                             a bot's line two carries an account notice
```

Grok Bot creates a bot in one sheet: a large picture, a name, shapes, colours, Create. Clawtrate keeps that sheet and adds one step after it, Account, which Grok Bot does not have. Everything else a bot has lives where Grok Bot keeps a bot's profile: the panel that opens from the title pill, here the Work pane, under a Settings tab.

### Access: the admin tier

Creating a bot, changing its settings, connecting an account and adding T3 Code all need `operator.admin`, and the gateway's sign-ins check it again inside their handlers (section 20, rows 1, 6, 7). `conversation.md` §3 says the admin tier is "requested the first time such a screen is opened, never by the conversation". Here that request is the access bar of `conversation.md` §3, in the place of the screen's primary action, with this screen's words. One component, one set of states:

| State            | The bar says                                                                                                                                                                                               | Actions                          |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| Read tier        | An eye, "**Read-only.** <what this needs>"                                                                                                                                                                 | "Request admin access" (primary) |
| Interactive tier | An eye, "**Admin access needed.** <what this needs>"                                                                                                                                                       | "Request admin access" (primary) |
| Asking           | "Asking the gateway…"                                                                                                                                                                                      | none                             |
| Requested        | "**Waiting for the gateway's owner.** Approve this request on the gateway's machine:", the command the host supplies with its copy button, "Request 3f9a2c71" with its copy button, "checking again in 4s" | "Check now", "Cancel request"    |
| Denied           | "**The request was denied.** Nothing changed. This device keeps the access it had."                                                                                                                        | "Request again"                  |
| Expired          | "**The request expired** before it was approved."                                                                                                                                                          | "Request again"                  |
| Couldn't ask     | "**Couldn't send the request.**" and the reason                                                                                                                                                            | "Try again"                      |
| Granted          | "**Admin access granted.** You can change this now." for 4 seconds, announced, then the screen's own action takes the bar's place                                                                          | none                             |

The words after the first sentence, by screen: "Creating a bot changes the gateway's settings, which needs admin access. What you chose stays here while you ask." (New bot); "Connecting an account needs admin access. The gateway lets only admin connections start a sign-in." (Connect); "Connecting and changing accounts needs admin access." (Accounts); "Changing <Bot>'s settings needs admin access." (a bot's settings); "Adding T3 Code needs admin access." (Integrations).

- The command and the request id come from the host, as in pairing and in `conversation.md` §3. The design never writes that command.
- What a screen holds (a draft bot, a chosen account, a typed label) is kept through the whole request, and survives leaving the screen and coming back.
- Everything else on the screen can still be read: values are shown, controls that change them are absent or disabled, and nothing that would do nothing is offered.
- On the read tier the "+" button is absent (`visual-language.md` §7), so New bot is not reached at all.

### Input

- Every dialog is modal: what is behind it is inert, Tab stays inside, Escape closes it, focus returns to the control that opened it. Escape inside an open menu closes the menu first.
- A radio group (shapes, colours, accounts) has one tab stop; arrows move and choose; Home and End go to the ends.
- Shortcuts: ⌘N opens New bot where the "+" menu offers it; ⌘, opens Settings.
- Copy follows `conversation.md` §9: a check for 1.4 s and "Copied code"; when the clipboard refuses, the text is selected and the announcer says so.
- One polite live region for the page announces: "Creating the bot", "Created Viral", "Could not create the bot", "Connected to xAI", "Sign-in cancelled", "Key saved", "Label saved", "Asking the gateway", "Access requested", "Admin access granted", "Locked", "Lock checked", and the copy results.

## 3. New bot

The "+" menu's "New bot" and ⌘N open the New bot dialog (F-034). On a phone it is a sheet that covers the screen, as Grok Bot's is.

**The picture and the name.** Title "New bot". In the middle, the character at 104 px, drawn live from the chosen body and colour (`visual-language.md` §5). Under it the name field: a 52 px pill on `--bg-inset`, centred text at 17/500, placeholder "Name", a visually hidden label "Name", focused when the dialog opens. Then "Shape" (13, faint, centred) and the eight bodies in two rows of four, "Colour" and the eight colours. One primary button at the foot: "Next". Enter in the name field is Next. (F-034, F-035)

- An empty name is allowed; the bot is then called "New bot". (F-036)
- The shapes and colours are radio groups named "Shape" and "Colour"; each body's name is its accessible name, each colour's is a plain word ("Pink").
- Closing the dialog keeps what was entered until the app quits; Create clears it. The picker here is the one `visual-language.md` §5 leaves to a later flow; the editor for an existing bot's picture is still later (section 23).

**Account.** Next replaces the content with the Account step (section 4). Its Back returns to the picture with everything kept.

**Create.** The primary button at the foot of the Account step.

| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Ready                     | "Create", primary, full width                                                                                                                                                           |                                                 |
| Creating                  | "Creating…", disabled                                                                                                                                                                   | The gateway creates the bot (section 20, row 2) |

**What Create writes.** The bot with its model and account, and an empty list of model fallbacks, in that order and in one action from the person's point of view: `agents.create` with the model reference `<provider>/<model>@<account id>`, then the bot's model object with `fallbacks: []` (section 20, rows 2 and 3). If the second write fails, the bot exists without its empty fallback list; its settings then show the difference (section 10, "Checks"), and Create does not report success until both are written. A bot created with nothing chosen is created with no model of its own.

## 4. The Account step

Title "Account", Back to the picture, Close. At the top, the character at 56 px and one sentence: "Choose the account <Bot> runs on. The sign-in stays on your gateway." (F-472)

**The list.** Every account the gateway reports, in groups, each a choice list:

| Group                | What is in it                                                                               | Rows   |
| -------------------- | ------------------------------------------------------------------------------------------- | ------ |
| Subscriptions        | Accounts made by a subscription sign-in that Clawtrate started (section 5)                  | First  |
| API keys             | Accounts made from an API key, and OpenRouter's sign-in, which saves a key billed per token | Second |
| Added on the gateway | Accounts Clawtrate did not create, whose kind it cannot tell                                | Last   |

A row: the provider and its label as the title ("OpenAI · Work"), and under it the kind, the state when it needs attention, and the bots that use it: "Subscription · Expires in 3 days · Pip", "API key · Juniper", "Subscription · Not used yet". The state words, from the gateway's status (section 20, row 5): nothing when it is `ok` or `static`; "Expires in 3 days" in `--warn` when `expiring`; "Expired" in `--danger`; "Needs sign-in" in `--warn` when `missing`.

- **Nothing is chosen at first**, and the step says what that means, in a neutral note under the list: "**No account chosen.** <Bot> would use the gateway's default model, OpenAI gpt-5.5, and the gateway would pick one of OpenAI's accounts for each run." If the gateway's default model names an account, the sentence names it instead: "…OpenAI gpt-5.5 on OpenAI · Work." The gateway has a default model, not a default account, so with no account in the default the step never names one (section 20, row 4). Create stays available: a bot with nothing chosen is the gateway's default bot, by choice.
- **Choosing an account** replaces the note with the model and effort, side by side (section 9): "Model" with the provider's first model as the gateway lists it, "Effort" with Medium, and "<Provider> models, as the gateway lists them. Change either later in <Bot>'s settings." A chosen account that expires soon or is expired adds a `--warn-soft` note: "OpenAI · Home expires in 3 days. Sign in again before then, or <Bot>'s runs will fail."
- **"Connect another account"**, a row with a plus at the end of the list, opens the connect component inside this dialog (section 5). When it finishes, the step returns with the new account chosen. The bot being created is never lost: the picture, the name, the choice, the model and the effort are all kept through a sign-in, a failed one included.
- The list is a radio group named "Accounts"; one tab stop, arrows move and choose. Each row's accessible name is its title and its line.

**No account at all.** The list is replaced by an empty state: the 44 px mark with a lock, "No accounts yet", "Sign in with a subscription you already have, and <Bot> runs on it." Under it the default model's note, as above. The foot has "Connect an account" (primary) and "Create without an account" (quiet).

**Loading and failing.** While the gateway's accounts load, the list is three grey rows that pulse (still when motion is reduced), with `aria-busy`. If they cannot be loaded: "Couldn't load the gateway's accounts." with "Try again", and Create stays available with the default model's note, since creating without an account needs no list.

**Below admin.** The rows are shown but cannot be chosen (`aria-disabled`), "Connect another account" is disabled, and the access bar takes Create's place (section 2).

## 5. Connecting an account

One component, in two places: inside New bot (title "Connect an account", Back to the Account step) and in Settings, Accounts (section 7). It starts the gateway's own sign-in; Clawtrate never receives, stores or copies the provider's lasting credential (F-474).

### Choosing how

A sentence: "Sign in with a subscription you already pay for. Your gateway does the sign-in and keeps it; Clawtrate never sees your password and never keeps the sign-in." Then the sign-in methods the gateway can start, in two groups (section 20, row 6):

| Subscriptions    | xAI; ChatGPT (a code); ChatGPT in the browser; Sign in with ChatGPT (on the gateway's machine); GitHub Copilot; GitHub Copilot Enterprise; MiniMax |
| Billed per token | OpenRouter (its sign-in saves a key, billed per token)                                                                                             |

Each row's title is the gateway's label for the method, with its hint after a middle dot; the line under it is what the person will do, from the method's kind: "Open a page and enter a code", "Open a page, then paste a code back here", "Finishes in a browser on the gateway's machine", "Your company's GitHub address, then a code". The provider is named in text; no provider's logo is drawn. Methods the gateway cannot start (Anthropic's sign-ins, local servers) are not listed.

**The API key path** sits under the list, closed: a disclosure "Use an API key instead" (F-475). It is never open by default and never preselected. Open, it holds:

- "With an API key, the provider bills each request by the tokens it uses, apart from any subscription you have. Most people don't need one."
- "Provider", a select of the providers that accept a key, and "Key", a password field with no autocomplete and no spellcheck.
- When the gateway already has a key for that provider, a `--warn-soft` note: "This replaces the <Provider> key your gateway already has. Bots that use it switch to the new key. To keep both, add the second on the gateway's machine." The gateway's key method replaces the provider's key; a second named key is only possible on the gateway's command line (section 20, row 8).
- "The key goes to your gateway, which keeps it. It is not kept on this device, and Clawtrate can't read it back."
- "Save key" (default, not primary). Saved, the field is cleared at once and the component goes to the label step with "Key saved".

Two more states belong to every kind:

- **The connection dropped.** A sign-in belongs to the connection that started it and ends with it (section 20, row 6). After a reconnect the component shows "The sign-in ended", "The connection to the gateway dropped, and a sign-in ends with its connection. Nothing was saved." with "Start again". It never claims the sign-in may have finished.
- **The gateway is busy.** It runs one sign-in or setup at a time. "The gateway is busy", "It is already running a sign-in or a setup, and does one at a time. Try again when that one finishes." with "Try again".

GitHub Copilot Enterprise asks first for "GitHub Enterprise address" in a field, with "Continue", then follows the link-and-code stages.

- The pasted code is a one-time authorization code. It is sent once to the gateway in the sign-in's next step and not kept: the field is cleared when it is sent, and nothing writes it to storage or logs (F-474).
- "Open <Provider>'s page" opens the system browser at the link the gateway's step gives. Nothing is fetched before it is chosen.
- The waiting line is a live region; the code has the accessible name "Code QK4F 7PZD", spaced so it is read in parts.
- The 25-minute limit on a sign-in, and a code's own expiry, both end in Expired.

## 6. Labels, and two accounts of one provider

**Naming an account.** When a sign-in or a key is saved, the component shows the result with a check, "Connected to <Provider>" (or "Key saved") and "Your gateway keeps the sign-in.", then a field "Label", focused, placeholder "For example, Personal". Under it: "Shown wherever this account is, so you can tell accounts apart." "Done" (primary) saves it and returns to where the component was opened.

- **When the provider already has an account**, the label is required: the placeholder is "For example, Home or Studio", the line under the field reads "You have another <Provider> account, OpenAI · Work. A label tells them apart everywhere.", and Done is disabled until there is a label.
- **A label already used by that provider** is refused: under the field, in `--danger`, "Another <Provider> account is called Work. Choose a different label.", and Done stays disabled. Labels are compared without case.
- **When the sign-in was the same account again**, the gateway refreshes that account rather than adding one. The component compares the gateway's list before and after; when no new account appeared it says "This was OpenAI · Work again, so your gateway refreshed that sign-in." and skips the label.
- **When a locked bot's provider gained an account**, a sign-in can add the new account to that bot's lock (section 10). Clawtrate checks every locked bot of that provider after any sign-in it started, and the label step says what it found, in a neutral note with a lock: "Clawtrate checked Otto's lock after this sign-in. It still allows only OpenAI · Work." or, on `--warn-soft`, "This sign-in added the new account to Otto's lock. Lock Otto again in its settings." with "Open Otto's settings".

Labels are the gateway's display names for accounts, written with admin access and returned only to admin connections (section 20, row 9). Below admin no label is available, so an account is its provider and its id on the gateway, in mono ("OpenAI openai:work"), which is what tells two accounts apart there. Every list, every row and the Account step use the label wherever there is one.

**Changing a label** is on the account's page in Settings (section 7): "Edit" beside the label turns it into a field with "Save" and "Cancel", the same rules apply, and a refused label marks the field invalid and announces why.
