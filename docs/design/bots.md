# Bots, accounts and T3 Code

How a bot is created with the account it runs on, how accounts are connected, what a bot's settings say about its account, model and lock, and how the optional T3 Code integration is set up. This is the third part of the design, after `visual-language.md` and `conversation.md`, in the same language and with the same tokens.

What must be true is in `docs/parity.md`, rows F-472 to F-490, and the bot setup rows F-034 to F-052 that the same screens carry. What the gateway can do is in `docs/research/provider-accounts-and-t3-code.md`, above all its Part C. This document decides appearance, wording and input, and for every state it shows it names the gateway fact the state rests on. Section 20 lists those facts with their sources. Section 21 lists the parity rows whose wording has to change. Section 22 is for builders.

One rule sits above the rest: **no state claims more than the gateway establishes.** The app knows which account a bot is bound to; it never knows which account served a turn. It knows a sign-in it started finished; it does not know that a sign-in someone else made is still valid. Where the gateway says nothing, the screen says that it cannot see, and never fills the gap.

The prototype shows all of it: `prototype/bots.html` is the app with these screens added, and its address picks any state (`prototype/README.md`). The styles are in `prototype/css/bots.css` and the behaviour in `prototype/js/bots.js`. `prototype/tools/checks/bots.mjs` checks them.

## 1. How the pieces fit

```
"+" menu, New bot (⌘N)          New bot: picture and name, then Account, then Create

    Connect another account        the connect component, inside the same dialog

  Accounts                         every account: label, kind, state, the bots on it
    Connect an account             the same connect component
  Integrations                     the T3 Code switch, off by default
Work pane, Settings tab          a bot's settings
  Account                          bound or locked, the lock command, changing it
  Model and effort                 side by side, from the account's provider
  Tools                            tools that come with the account; T3 Code for this bot
transcript                       event lines and the turn error, as conversation.md has them
rail                             a bot's row's name carries an account notice
```

A bot is created in one sheet: a large picture, a name, shapes, colours, then one more step, Account, before Create. Everything else a bot has lives in the panel that opens from the title pill, the Work pane, under a Settings tab.

### Access: the admin tier

Creating a bot, changing its settings, connecting an account and adding T3 Code all need `operator.admin`, and the gateway's sign-ins check it again inside their handlers (section 20, rows 1, 6, 7). `conversation.md` §3 says the admin tier is "requested the first time such a screen is opened, never by the conversation". Here that request is the access bar of `conversation.md` §3, in the place of the screen's primary action, with this screen's words. One component, one set of states: One thing here needs less: the T3 Code switch is the person's own preference and needs only the interactive tier (section 15); everything it reveals that writes to the gateway needs admin.

| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| Read tier        | An eye, "**Read-only.** <what this needs>"                                                                                                                                                                 | "Request admin access" (primary) |
| Interactive tier | An eye, "**Admin access needed.** <what this needs>"                                                                                                                                                       | "Request admin access" (primary) |
| Asking           | "Asking the gateway…"                                                                                                                                                                                      | none                             |
| Requested        | "**Waiting for the gateway's owner.** Approve this request on the gateway's machine:", the command the host supplies with its copy button, "Request 3f9a2c71" with its copy button, "checking again in 4s" | "Check now", "Cancel request"    |
| Denied           | "**The request was denied.** Nothing changed. This device keeps the access it had."                                                                                                                        | "Request again"                  |
| Expired          | "**The request expired** before it was approved."                                                                                                                                                          | "Request again"                  |
| Couldn't ask     | "**Couldn't send the request.**" and the reason                                                                                                                                                            | "Try again"                      |

The words after the first sentence, by screen: "Creating a bot changes the gateway's settings, which needs admin access. What you chose stays here while you ask." (New bot); "Connecting an account needs admin access. The gateway lets only admin connections start a sign-in." (Connect); "Connecting and changing accounts needs admin access." (Accounts); "Changing <Bot>'s settings needs admin access." (a bot's settings); "Adding T3 Code needs admin access." (Integrations).

- The command and the request id come from the host, as in pairing and in `conversation.md` §3. The design never writes that command.
- What a screen holds (a draft bot, a chosen account, a typed label) is kept through the whole request, and survives leaving the screen and coming back.
- Everything else on the screen can still be read: values are shown, controls that change them are absent or disabled, and nothing that would do nothing is offered.
- On the read tier the "+" button is absent (`visual-language.md` §7), so New bot is not reached at all.

### Input

- Every dialog is modal: what is behind it is inert, Tab stays inside, Escape closes it, focus returns to the control that opened it. Escape inside an open menu closes the menu first.
- A radio group (shapes, colours, accounts) has one tab stop; arrows move and choose; Home and End go to the ends.
- Shortcuts: ⌘N opens New bot where the "+" menu offers it; ⌘, opens Settings.
- Copy follows `conversation.md` §9: a check for 1.4 s and "Copied code"; when the clipboard refuses, the text is selected and the announcer says so.
- One polite live region for the page announces: "Creating the bot", "Created Viral", "Could not create the bot", "Connected to xAI", "Sign-in cancelled", "Key saved", "Label saved", "Asking the gateway", "Access requested", "Admin access granted", "Locked", "Lock checked", and the copy results.

The "+" menu's "New bot" and ⌘N open the New bot dialog (F-034). On a phone it is a sheet that covers the screen.

A fresh dialog shows a blue Clawling as an example only: if the picture is left as it is, Create sends no picture and the new bot gets the Clawling its id gives, the same on every device. Under it the name field: a 52 px pill on `--bg-inset`, centred text at 17/500, placeholder "Name", a visually hidden label "Name", focused when the dialog opens. 4. "Use your own picture", a quiet button that takes an image file (PNG, JPEG, WebP or GIF, under 25 MB), crops it to its centre square and shows it in place of the creature; "Use the creature" goes back. A file too large or not an image says so under the button and changes nothing.

- An empty name is allowed; the bot is then called "New bot". (F-036)
- Every group is a radio group named by its label, with one tab stop: arrows move and choose, Home and End go to the ends. Each option's accessible name is a plain word: "Shellfolk", "Fiddler claw", "Pink".
- Closing the dialog keeps what was entered until the app quits; Create clears it.

**What the picture is.** The gateway keeps one picture with a bot, in its identity (`agents.create` and `agents.update`, `avatar`, a PNG data URL of at most 32,768 characters). A creature is sent as a 128 px PNG of its still pose with the choice written into a `tEXt` chunk under the keyword `clawtrate-avatar`, so any other client shows a picture and Clawtrate reads the choice back and draws the creature, moving. The person's own picture is sent as it is, at most 128 px, and is shown cropped to a circle. A picture without the chunk is the person's own.

**The choice's fields**, which a bot editing itself (#292) sets the same way: `family` (`clawling`, `shellfolk`, `lantern`) and `color` (`green`, `blue`, `orchid`, `violet`, `yellow`, `pink`, `sky`, `lime`), and the family's parts: for `clawling`, `body` (`dome`, `tall`, `wide`, `round`), `eyes` (`pair`, `splayed`, `short`, `single`) and `claws` (`even`, `fiddler`, `big`); for `shellfolk`, `shell` (`spiral`, `turret`, `dome`, `spotted`); for `lantern`, `body` (`round`, `bell`, `oval`, `box`), `lure` (`hook`, `flick`, `wave`, `reach`) and `eyes` (`two`, `one`). `parseAvatarChoice` in `packages/core/src/avatar.ts` accepts exactly these and nothing else; the text in the chunk is the same fields as `v=1&family=…&…&color=…`.

## 4. The Account step

Title "Account", Back to the picture, Close. At the top, the character at 56 px and one sentence: "Choose the account <Bot> runs on. The sign-in stays on your gateway." (F-472)

**Which accounts.** A bot can use the accounts in the gateway's shared store, which every bot inherits, and the accounts in its own store. A bot that does not exist yet has no store of its own, so the step lists the shared accounts only. An account kept in another bot's own store is never offered here, because the new bot could not use it (section 20, row 10).

**The list** is one radio group, "Accounts", in up to four blocks:

| Block                | What is in it                                                                                      | Order                    |
| -------------------- | -------------------------------------------------------------------------------------------------- | ------------------------ |
| Subscriptions        | Shared accounts made by a subscription sign-in that Clawtrate started (section 5)                  | First                    |
| API keys             | Shared accounts made from an API key, and OpenRouter's sign-in, which saves a key billed per token | Second                   |
| Added on the gateway | Shared accounts Clawtrate did not create, whose kind it cannot tell                                | Third                    |
| (no heading)         | One more choice, in words: **"Let the gateway choose"**                                            | Last, set apart by 12 px |

An account's row: the provider and its label as the title ("OpenAI · Work"), and under it the kind, the state when it needs attention, and the bots bound to it: "Subscription · Expires in 3 days · Pip", "API key · Juniper", "Subscription · Not used yet". "Used by" means bound in a bot's settings, not every run that may reach the account. The state words follow the gateway's status for the account (section 20, row 5): nothing for `ok` and `static`; "Needs sign-in" in `--warn` for `missing`; for `expiring` and `expired`, "Expires in 3 days" or "Expired" in `--warn` only when the account is a kind the gateway cannot renew by itself (a `token`); a sign-in the gateway renews by itself (`oauth`) shows no state word, because an expired access token is refreshed when it is next used (section 20, row 32).

**"Let the gateway choose"** has the title in medium weight and one line: "No fixed account. The gateway picks one of OpenAI's accounts for each run, as its account order allows, with its default model, gpt-5.5." The provider and model are the gateway's default model's. It is a real choice with a stated outcome, and it makes the third account state (section 10).

**What is chosen at first.**

- If the gateway's default model names an account (`<provider>/<model>@<account>`), that account is chosen, and the line under the list says why: "Chosen because the gateway's default model names it."
- Otherwise nothing is chosen. Create is disabled, and the line in its place (13, faint, centred) reads "Choose an account, or let the gateway choose." Nothing is created by not choosing.
- With nothing chosen, the radio group's first row is its one tab stop, so Tab reaches the list; arrows move and choose; Space or Enter on a row chooses it, and focus stays on that row.

**Once a choice is made**, the model and effort follow, side by side (section 9): "Model" with the gateway's default model when it belongs to the chosen account's provider and otherwise the provider's first model in the gateway's list; "Effort" with the model's own default level when the gateway reports one, else the middle of its levels, and "Not offered" when it reports none. Under them: "OpenAI's models, as the gateway lists them. Which ones this account may use is OpenAI's decision." "Let the gateway choose" shows the same pair for the default model's provider.

**"Connect another account"**, a row with a plus under the radio group ("Connect an account" when there is none), opens the connect component inside this dialog (section 5). When it finishes, the step returns with the new account chosen if the gateway's list shows it. The bot being created is never lost: the picture, the name, the choice, the model and the effort are all kept through a sign-in, a failed one included.

**No account at all.** The account blocks are replaced by an empty state: the 44 px mark with a lock, "No accounts yet", "Sign in with a subscription you already have, and <Bot> runs on it." with "Connect an account" (primary). "Let the gateway choose" stays below it: with no account, the gateway's default model still runs on whatever credential the gateway has for its provider, and the row says so: "No fixed account. The gateway uses what it has for OpenAI, with its default model, gpt-5.5."

**Loading and failing.** While the accounts load, the account blocks are three grey rows that pulse (still when motion is reduced), with `aria-busy`; "Let the gateway choose" is shown and can be chosen. If they cannot be loaded: "Couldn't load the gateway's accounts." with "Try again", and "Let the gateway choose" stays available.

**Below admin.** The rows are shown but cannot be chosen (`aria-disabled`), "Connect another account" is disabled, and the access bar takes Create's place (section 2).

## 5. Connecting an account

One component, in two places: inside New bot (title "Connect an account", Back to the Account step) and in Settings, Accounts (section 7). The gateway starts the sign-in and keeps the credential (F-474). An API key or Claude setup token the person enters passes through Clawtrate once to reach the gateway. Clawtrate clears the field at submission and keeps neither value in app state, logs or disk.

**Which store a sign-in lands in.** The gateway saves a sign-in in the store of the bot it is started for. That store is the shared one, which every bot inherits, only when the bot's resolved folder is the gateway's shared-main folder; a bot with a folder of its own configured, or a gateway with no `main` bot, keeps the sign-in in that bot's store (section 20, row 33). Naming a bot does not make a sign-in shared, so Clawtrate says where an account landed only from what the gateway reports after the sign-in:

- **Which bot it is started for.** For `main` when the gateway lists a `main` bot with no folder of its own configured (`config.get`, `agents.entries.main.agentDir` absent); otherwise for the bot the person is working on: the bot whose Change account opened the connect component, or, from Settings, the gateway's default bot.
- **Before it starts**, when it is already known that the account cannot be shared (no `main` bot, or `main` has a folder of its own configured), the first screen of the connect component says so, in a neutral note, before any method is chosen: "This gateway keeps this sign-in for <Bot> only. Other bots, and a bot you are creating, won't be able to use it." In New bot that note adds: "To give <new bot> an account of its own, create it with 'Let the gateway choose', then connect from its settings."
- **After every sign-in**, whatever its target and however it ended, Clawtrate reads `models.authStatus {agentId, refresh: true}` for the target bot and for one other bot, and finds the new account by its id. Sharing is decided only from refreshed answers: an answer from the gateway's prepared view can list a shared account as `saved`, so it does not establish that an account belongs to one bot. It calls the account shared, and offers it to every bot and to New bot, only when another bot's view lists it with `source: "inherited"`. When only the target bot's view lists it (`source: "saved"`), the result says "Saved for Juniper only. Other bots can't use it.", the account is listed under "Kept by one bot", and New bot does not offer it. When the gateway has a single bot, there is no second view to read: the account is shown as kept by that bot until a later read, with another bot present, shows otherwise.

### Choosing how

A sentence: "Sign in with a subscription you already pay for. Your gateway does the sign-in and keeps it; Clawtrate never sees your password and never keeps the sign-in." Then a grid of providers, one tile per provider the gateway can sign in to (section 20, row 6): its logo and its name, two columns and one at phone width, read left to right, row by row. A tile says "Connected" when the gateway already has an account of that provider, and OpenRouter's says "Billed per token" (its sign-in saves a key). Claude's tile comes second, after OpenAI, and opens to its ways, the plan first: "Paste a setup token", under it "Your Claude plan, with a token from Claude Code", then "API key", under it "Billed per token", which opens "Use an API key instead" with Anthropic chosen and focus on the key field. A gateway whose hello doesn't list it has the key alone: there Claude's tile says "API key · Billed per token" and opens the key's fields at once. If admin access is lost while Connect is open, the tile still opens its ways: the plan's says "Your Claude plan · needs full control" and can't be pressed, the key's stays, and the request for full control is under them. **A Claude plan's setup token (#932).** Its steps screen is titled "Connect your Claude plan" and says the one step outside the app plainly: "In a terminal on a computer where Claude Code is signed in, run `claude setup-token`. The token passes through Clawtrate to the gateway in one `wizard.next` answer so the gateway can connect the plan. Connect reads it from a masked input and clears the field before sending. The Electron and web hosts forward the command without logging or persisting its payload. The accounts engine keeps only a temporary copy in memory to remove echoes from gateway replies before publishing state or logging. It clears that copy when the sign-in settles or the connection ends. On both versions the gateway then does this, in order (by reading `system-agent-setup-wizard-*.mjs`, `setup-inference-*.mjs`, `setup-inference-credentials-*.mjs` and `setup-model-selection-*.mjs`; a gateway run here stops before a token is sent, because the gateway's check would reach Anthropic):

1. It checks the token's form (`sk-ant-oat01-`, at least 80 characters) and asks again for one that isn't; the screen says "That isn't a setup token. Paste the whole line it printed."
2. It saves the token for the bot as an inactive `token` sign-in, `anthropic:setup-<id>`, in the bot's sign-in store.
3. It sends one test request to Anthropic with it ("Testing your AI connection…").
4. If the bot already had an Anthropic connection it asks "Activate this saved sign-in?"; Clawtrate answers yes, since the person chose the plan for this bot.
5. It activates the sign-in and writes, in one config change: the sign-in's entry under `auth.profiles`, the bot's model (`agents.entries.<bot>.model.primary`, an Anthropic model on that sign-in), and an empty entry for that model under the bot's own per-model settings (`agents.entries.<bot>.models`) and, when it has any, the gateway's (`agents.defaults.models`). An existing API key stays.

The model change can't be left out on either version (2026.11.10's `selectModel` only takes `true`), so it is said: "<Bot> now uses <model>." with **Put back <earlier model>**, which writes the bot's earlier model back, its fallbacks kept, only while the bot still has the model the sign-in gave it (`docs/design/gateway-settings.md`, section 6); Put back uses the revision of the config it checked, so a concurrent edit is kept. The empty per-model entries change nothing a person sees and are not put back. The account is removed as any account is, with Disconnect (`models.authLogout`). A sign-in that doesn't connect leaves the bot's model as it was: the screen says "The gateway didn't connect your Claude plan. The bot's model wasn't changed." and reads the accounts again; the inactive token the gateway may have kept is removed with `models.authLogout`, so nothing of it stays. The gateway runs one setup at a time: a second one is refused as busy, said as for any sign-in. The setup session isn't tied to the connection that started it, so Clawtrate ends it itself: Cancel and closing Connect send `wizard.cancel`; a connection lost on the way sends it once the connection is back, then reads back the account and config. Cleanup runs only on the gateway that started the session and leaves any account already activated in config alone. A session that connects is ended by the gateway itself.

Four more states belong to every kind:

- **The connection dropped.** A provider sign-in started by `models.authLogin` ends with its connection. A setup session started by `openclaw.setup.auth.start` survives the drop. - The pasted code is a one-time authorization code. It is sent once to the gateway in the sign-in's next step and not kept: the field is cleared when it is sent, and nothing writes it to storage or logs (F-474).
- "Open <Provider>'s page" opens the system browser at the link the gateway's step gives. Nothing is fetched before it is chosen.
- The waiting line is a live region; the code has the accessible name "Code QK4F 7PZD", spaced so it is read in parts.

What was found belongs to the dialog or page that asked, like "View more"'s answer, and is dropped on the same changes. **The config's model list:** when the gateway's config names the models every bot may use (`agents.defaults.modelPolicy.allow`, or the old `agents.defaults.models` while the config is unmigrated, and no bot has a `modelPolicy.allow` of its own, so the list is the same for every bot and a new one) and doesn't leave the provider whole with `<provider>/*`, the result says "The gateway's config names which of OpenAI's models it lists and lets a task switch to; a bot's own model can still be one it doesn't name." With a wildcard in the list, a bot set to a model the list doesn't name runs on the first one it allows, so it says "…; a bot set to another model runs on one it names." instead. What a wildcard is follows the version the gateway reports: on 2026.10.6 an entry ending in `/*`, on 2026.11.10 also a prefix such as `openai/gpt-*`; on any other version the broader reading decides whether "type its id" is said. It is the line's reason when nothing new was found, since it is what keeps a model out of the menu then, and in the panel otherwise. With a list of a bot's own, which list a menu's bot has isn't said, so nothing is. It is said only when the gateway reports a version where that was established (2026.10.6 and 2026.11.10), and nothing on any other. Research: `docs/research/model-catalog.md` section 8.

**The chosen model always has a checked row.** When neither the picker nor the dialog's answer has it, it is pinned first, checked, by its id; no answer that arrives, is dropped or fails removes or changes it. The effort is resolved once from the model's row in either list, and that one result is what Effort shows and what Create or Save sends: a level the row offers, kept when it offers the level chosen before; "Not offered", and none sent, when the row offers none or no row has the model.

**A model id typed in.** The menu's last row is "Use another model…", with "Type its id" under it. It closes the menu and opens a field under the pair, "Model id", focused, with "As OpenAI names it." under it, and "Use" (primary) and "Cancel". Enter is Use; Escape is Cancel and closes the field alone. A leading `openai/` is the provider's own and is dropped. Nothing typed says "Type a model id."; a space or an `@`, which would name an account, says "A model id has no spaces and no @." A control character says "A model id can't hold control characters." These are the bridge's own rule for every model id (`modelIdProblem`), so the field never takes an id the save would refuse. An id that a row of either list has is that row, chosen as if from the menu; one the picker disables is refused where it is typed with the row's own "Not available", and the field stays open. Any other id is chosen, pinned as the chosen model's row, with one line under the pair: "gpt-6.2-sol was typed in." Focus returns to the select. No row has such a model, so Effort reads "Not offered" and none is sent; once the dialog's "View more" answer has it, its row's level is shown and sent, as for any model (above). Choosing another provider's account clears the field, its error and the line.

**A newer OpenClaw.** When the gateway's own update check reports a newer OpenClaw than it runs (`hello-ok` `snapshot.updateAvailable`, kept current by the `update.available` event), a neutral note follows the pair: "Your gateway runs OpenClaw 2026.10.6, and 2026.11.6 is out. Updating the gateway is how newer models get listed.", with a link, "OpenClaw's update instructions", to OpenClaw's own page on updating (docs.openclaw.ai/install/updating). It names no command: the step differs by install, and `openclaw update` skips container installs. Only something shaped like a version counts as one; a report of a word such as "unknown" says nothing. When the report's channel isn't the stable one, the note names it, so a beta never reads like a stable release: "…and 2026.11.10-beta.1 is out on its beta channel, not as a stable release." With no report, nothing is said: the gateway gives no way to tell which models a newer OpenClaw would add (research: `model-catalog.md` 7).

**Changing account** to another account of the same provider keeps the model, one from "View more" included. Another provider's account clears it: Model reads "Choose", with "Choose one of xAI's models for Marlow.", and Save waits for a model. In New bot, an account chosen before the gateway's picker arrives gets its first model (section 4) when it does, unless the person has chosen one, and Create waits for a picker read already under way before it writes anything. Research: `docs/research/model-catalog.md`.

**Effort** lists the levels the gateway reports for the chosen model (`thinkingLevels`), for example "Off", "Low", "Medium", "High". When the model changes, the effort keeps its level if the new model offers it, and otherwise takes the model's own default level, or the middle of its levels; the line under the pair says so for 4 seconds: "Effort is now Low: gpt-5.5-mini doesn't offer High." A model with no levels shows "Not offered", disabled.

- A bot set to "Gateway chooses" has its own model and effort like any other.
- A bot on the gateway's default model shows that model, read-only, with "The gateway's default model. Choose an account to pick another."
- A save the gateway refuses puts the select back to its saved value, with "Couldn't save the model: <the gateway's reason>." under the pair, and focus stays on the select. A save that crossed another person's change shows what the gateway now has.
- On a phone the two stack, Model first.

When the provider has no other account, the bound sentence reads "…the gateway may use another <Provider> account, if one is added, for that run." The words are plain and the tone neutral: a bound bot is the gateway's ordinary behaviour, not a fault (F-476, F-480).

**What "bound" and "locked" are.** Bound is the bot's model reference carrying its account, `<provider>/<model>@<account>`, with an empty fallback list. The gateway puts that account first among the provider's accounts and moves on to the others when it fails (section 20, rows 11 and 15). Locked adds the gateway's stored order for that bot and provider, holding the bound account alone. In the research's words, the order is "a fence for the bot's ordinary runs on its provider. It does not stop a run that is started with another account named, and it can be widened or repaired by sign-ins and removals." The Locked sentence says the first part on the page itself, not only in the folded list.

**What the empty fallback list stops.** It stops the gateway moving a run to the next model in a fallback list. It does not stop the providers' own reroutes inside a request: OpenAI's Codex runtime escalating to another model, and Anthropic's refusal fallback on a direct API key (section 20, row 22). The ways-round list says so.

**Locking.** Under "Lock to this account" (13, faint):

1. "To keep this bot on this account alone, run this on the gateway's machine. A sign-in can also leave a bot limited to one account; Clawtrate shows the limit it finds, however it was made:"
2. The command, in the pairing screen's command block, with a copy button named "Copy lock command": `openclaw models auth order set --provider openai --agent marlow openai:work`. It is built from the bot's id, its provider and its account's id on the gateway, in the gateway's own command-line form; when the host knows the gateway runs under a named profile, it adds that profile's option, as it does for the approve command. The command never breaks inside a word.
3. The evidence line and "Check now" (below).
4. When the gateway's order matches, the page becomes Locked. If focus was on "Check now" it moves to the page's title; otherwise it stays where it was. The announcer says "Locked. The gateway confirmed it.", and the account row reads "Locked".

**On a gateway that changes orders only while stopped.** From OpenClaw 2026.10.10 the gateway's command line refuses `models auth order set`, `clear` and `get` while the gateway runs, and changes nothing; it says to stop the gateway, wait for it to release its state, and run the command again (section 20, row 12). **What a lock doesn't cover**, folded, the same on bound and locked, said as facts and without alarm, in the research's terms:

- A task or conversation set to another account, by another app or with the model command in chat. Clawtrate never does this.
- A routine, or a helper bot, whose model names another account.
- A message from another bot into a conversation that already uses another account.
- A run that uses another model than <Bot>'s own, set in a task or a routine: it doesn't carry <Bot>'s account, so the gateway's own provider settings or order choose one.
- A new <Provider> sign-in on the gateway can add itself to the order. Clawtrate checks after every sign-in it starts.
- Removing <account>: the gateway then repairs the order to <Provider>'s other accounts.
- Commands run on the gateway's machine itself.
- A lock is about accounts. An empty fallback list keeps <Bot> off other models in the gateway's fallback list, but some providers can still switch the model inside a request.

**What this cannot see**, on the bound state only, one line under the command: "What this cannot see: if <account> is pausing after a failure, a run can start on another <Provider> account without leaving a record Clawtrate can read." (F-489)

**Checks.** Clawtrate keeps every bot it manages that has an account on its model with that account and an empty fallback list (F-490). When such a bot's model on the gateway lists fallbacks, the Account page says so on `--warn-soft`: "**<Bot> can move to another model.** Its model on the gateway lists fallbacks (anthropic/claude-sonnet-5.5), so the gateway can move a run to them when this one fails." with "Remove fallbacks". When its model has lost its account suffix without Clawtrate removing it, the page shows a note on `--warn-soft`: "The gateway's model for <Bot> has no account. It now uses the gateway's choice of <Provider> account." with "Choose an account". A bot set to "Let the gateway choose" is neither: it is reported as "Gateway chooses".

## 12. Served by another account

When the gateway's log shows that a bot's run moved off its bound account, Clawtrate says so afterwards and never silently (F-489, F-479). The log establishes two things: which account failed, as a hash Clawtrate matches against the bot's accounts, and that the gateway rotated to another account of the provider. It does not say which account served the run (section 20, row 16). The notice says those two things and no more, and uses only what the conversation and the rail already have.

**In the task**, a grey event line (`visual-language.md` §8) where the run's reply begins, aligned with the bubbles' text. It is the opening event line of `conversation.md` §9: a `summary` with a chevron.

| The log                                                                                          | The line                                                                             |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| A `rotate_profile` record for the run whose hash matches the bound account                       | "OpenAI · Work failed (rate limited), and the gateway tried another OpenAI account." |
| The same, when exactly one other account of the provider was eligible for the bot at that moment | "…tried another OpenAI account, likely Home."                                        |
| A `rotate_profile` record whose hash matches no account the bot has                              | "An OpenAI account failed (rate limited), and the gateway tried another one."        |

The reason is the gateway's failure reason in words: "signed out" (auth), "out of credit or quota" (billing), "rate limited", "provider busy" (overloaded), "timed out", otherwise "an error". Whether the run then finished is what follows in the transcript: the reply or the run's error card. The line never says "finished on", and never names a serving account as fact.

"Likely" is a marked inference, made only from the bot's own view of the gateway's accounts (`models.authStatus {agentId: <bot>}`): the provider's accounts other than the bound one whose state is usable (not `missing`, not excluded by the order) number exactly one. With two or more, or none, there is no "likely".

**Opened**, the line shows a card: "The gateway's log for this run says OpenAI · Work failed after a rate limit and the gateway moved on to another OpenAI account. It doesn't say which account served the run." With "likely": "**Inferred:** OpenAI · Home was the only other OpenAI account <Bot> could use, so it is likely. The gateway doesn't confirm it." Then "Lock <Bot> to <account>, in its settings, to have a failure stop the run instead.", "Open <Bot>'s settings" and "Raw", which shows the log record as the gateway wrote it (the failed account appears there as a hash).

**On the bot's row**, which is its picture and its name with no line of words (#790, `conversation.md` §20), when the bot is otherwise calm (done, stopped or idle): the row's name adds ", the gateway tried another account". No new mark and no badge. A pinned tile shows nothing extra.

**It clears**, and only on something Clawtrate observes:

- the person opens the task that has the line (the notice is news, like unread);
- the bot is locked, confirmed from the gateway's order (section 10);
- the bot's account is changed in its settings.

It does not clear on a later run, because nothing the gateway reports shows that a later run used the bound account again. The line in the transcript stays.

**In settings**, the Model group carries a note on `--warn-soft`, "The gateway tried another <Provider> account in <Bot>'s last run with a notice. See Account.", and the Account page a neutral line with a clock: "**4:58 PM:** OpenAI · Work failed (rate limited) and the gateway tried another OpenAI account." Both go when the row's warning clears.

**When the log cannot be read.** The notice depends on the gateway's diagnostic log, which is the operator's configuration and not a protocol (section 20, row 16). Clawtrate says what it cannot see, in the bot's Account page under "What this cannot see", and nowhere else:

| The log                                                                      | The line                                                                                                   |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `logs.tail` is refused or not offered                                        | "Clawtrate can't read the gateway's log, so it can't tell you when the gateway tries another account."     |
| The log holds no failover records at all while runs fail and recover         | Nothing: an empty log is not evidence.                                                                     |
| The follower lost its place (the file rotated, was cut, or the cursor reset) | "Clawtrate missed part of the gateway's log, between 4:10 and 4:30 PM; a switch then would not show here." |
| A record that cannot be read as the fields above                             | Skipped; it is never shown as a switch.                                                                    |

What it never says: "this turn was answered by <account>". The turn record of F-044 names the bound account as "bound to OpenAI · Work", never "served by".

A run that fails on its account ends with the turn error of `conversation.md` §17. The gateway's error names the provider, the model and the kind of failure, not the account (section 20, row 18), so the card names the bot's bound account as bound, and names it as the failed account only when the gateway's log says so:

Otto is bound to OpenAI · Work; the gateway's log names it as the account that failed." When Otto is locked: "Otto is locked to it, so the gateway didn't try another account." | Signed out (auth)                               | "OpenAI didn't accept the sign-in. Otto is bound to OpenAI · Work; the gateway's log names it as the account that failed." and, locked, the same second sentence                                                                                                                                                                                      | "Sign in again" (primary), "Change account" |

- When the log does not name the account, the second sentence reads "Otto is bound to OpenAI · Work. The gateway didn't say which account failed." The card never says "Otto's account is out of quota" as a fact it has not read.
- When the bot is bound, not locked, and the log shows a rotation, the line of section 12 sits above the card.
- "Copy request ID" and "Raw" stay as in `conversation.md` §17.
- "Sign in again" opens Settings on the connect component, starting the same provider's sign-in. "Change account" opens the bot's Settings tab on Change account.
- **The bot's row** uses its failed state: the failed badge, and its name says "a run failed".
- **The bot's settings** add, in the Model group, a note on `--danger-soft` with the same cause and the two ways forward in words.
- **Settings, Accounts** shows the account's own state as the gateway reports it. The gateway does not report a pause or a billing failure there, so the account can read "Connected" while its runs are refused; when the log named it as the account that failed, its page adds "Otto's last run failed on it: refused for quota, 5:58 PM."

## 14. Tools that come with a provider

Some providers' plugins bring tools: xAI's brings "Search posts on X" and "Run code" (F-481). What decides whether a bot is offered them is the gateway, not the account: the plugin must be loaded, its sign-in usable and the bot's tool policy must permit them, and then they are offered when the bot's model is xAI's, or for any model when the gateway's xAI settings switch the tool on explicitly (section 20, row 19). So the place shows what the gateway's inventory lists, not what an account implies.

**Where.** In the bot's Settings, in the Tools group, after "Permissions", one block per plugin that brings tools, headed "From xAI" whatever the bot's provider. One row per tool, with the rule that applies to the bot today:

| The bot's tool policy        | The row's value |
| ---------------------------- | --------------- |
| Nothing denies it            | "Allowed"       |
| The bot's deny list names it | "Denied"        |

Under the block: "From the gateway's tool list for <Bot>'s latest task. xAI bills these per call." The names are Clawtrate's plain words for the gateway's tool names (`x_search`, `code_execution`), shown in the row's tooltip and its accessible name.

- **"Ask"** is not offered and not shown: asking before a tool runs needs Clawtrate's rules plugin. With the plugin, the row gains it; without, the block's line adds "Asking first needs Clawtrate's rules plugin."
- **Before the bot's first task** the inventory has nothing to say: "Tools that come with a provider appear here after <Bot>'s first task."
- **The list is the gateway's last listing**, not a live check: it can be stale until the bot runs again.
- **Changing account.** When the new account's provider is not xAI and the gateway's xAI settings do not switch the tools on for every model, Change account says "Search posts on X and Run code come with xAI here, and may leave <Bot>'s tools." When they are switched on for every model, it says nothing: they stay.
- Choosing and changing those rules is the tool permissions screen, a later task; this section fixes only where they appear and what they say.

## 15. T3 Code: the switch

T3 Code integration is optional (F-487). Settings, **Integrations**, has one row: "T3 Code", "Let bots start and follow threads in T3 Code, a coding app you run. Off by default; nothing else in Clawtrate needs it.", and a switch, off.

**What the switch is.** It is the person's own preference, stored with the gateway so that their desktop and phone agree (section 20, row 30). It changes only what Clawtrate shows that person. Flipping it never writes anything to the gateway by itself: the server, each bot's T3 Code and the skill are the gateway's, shared by everyone who uses the gateway, and change only through the admin actions of sections 16 to 18.

| This device may    | Flipping the switch                                                                                                                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Only read          | Not possible: the switch is disabled, and the access bar asks for the interactive tier, the same request as `conversation.md` §3 ("Request access"), not admin: "**Read-only.** This is your own preference; saving it needs this device to be able to send." |
| Send (interactive) | On: shows the server, the sign-in and the bots, read-only, with the admin request where they change. Off: hides them again, for this person.                                                                                                                  |
| Administer         | The same, and the actions behind it work.                                                                                                                                                                                                                     |

- **Off** is the whole of it for that person. Nothing else about T3 Code appears anywhere: no server, no sign-in, no per-bot switch, no limits, no prompt to set it up. One exception, by design: a "Messaged T3 Code" card in a transcript (`conversation.md` §11) records what a bot actually did and is drawn whenever a bot's own tool events show such a call, on or off. "Has no setting for it" in that section means the card depends on no setup, not that the integration has no settings.
- **Other people.** The switch is per person; the bots are shared. When the switch is off for this person and some bots have T3 Code on at the gateway, the switch's line says so and nothing more: "Off for you. Otto and Viral have T3 Code on at the gateway; this doesn't change that."
- **On** reveals, under the row, the server (section 16), the gateway's sign-in, and the list of bots that have it on; and each bot's Settings gains its own T3 Code switch (section 17).
- The switch has role `switch` and the name "T3 Code integration"; changing it is announced ("T3 Code is on").

## 16. T3 Code: the server and the gateway's sign-in

**The server.** With no server on the gateway: "Add your T3 Code server to the gateway. Copy its address from T3 Code's settings.", a field "T3 Code address" (placeholder `https://code.example.net`), "T3 Code signs in only over https, or on the gateway's own machine (localhost).", "Adding it turns T3 Code off for every bot first, so no bot gets its tools until you turn it on for that bot.", and "Add to gateway" (primary).

- A plain-http address that is not localhost is refused under the field, in `--danger`: "T3 Code signs in only over https, or on localhost. Use its https address." An empty field: "Enter T3 Code's address." The field is marked invalid, described by the message, and keeps focus.
- "Add to gateway" writes, in one `config.patch`, a deny of the server's tools on every bot and the server itself, named `t3code` (section 20, rows 23 and 27). Then it reads the configuration back and shows what is there.

| The write                                                                                      | The section shows                                                                                                  |

**Signing the gateway in.** T3 Code has no key for outside apps: the gateway signs in with T3 Code's own sign-in, the person approves it on T3 Code's page (or types a pairing code from T3 Code there), and the gateway keeps the sign-in (section 20, row 24). There are two ways to start it, and the section shows the one this connection has.

_When this connection can start it_ (a desktop connection the gateway treats as coming from its own page, with admin): "The gateway signs in to T3 Code and keeps the sign-in. You approve it on T3 Code's page." and "Sign in" (primary). Then, in the forms of section 5:

| Starting                   | "Asking the gateway to start the sign-in…", "Cancel"                                                                                                                                                                                                          |

_When it cannot_ (Clawtrate's connection as it is today), the whole of the gateway's own command-line sign-in, as the gateway runs it (section 20, row 34):

1. "On the gateway's machine, run:" and `openclaw mcp login t3code` in the command block, with the gateway's profile option added when the host knows it runs under a named profile.
2. "It prints an address. Open it in a browser and approve the gateway on T3 Code's page, or enter a pairing code from T3 Code there."
3. "If that browser is on the gateway's machine, T3 Code returns to the command by itself; it waits 5 minutes. When it prints 'MCP OAuth credentials saved', the gateway is signed in."
4. "If the browser is on another computer, the page it returns to won't open. Copy the code from that page's address (the part after `code=`) and run this on the gateway's machine:" and `openclaw mcp login t3code --code <code>` in a second command block.

- After "Refused", "Sign in again" is primary.

## 17. T3 Code for one bot

With the integration on, a bot's Settings has a block "T3 Code" with one switch row: "T3 Code", "Start and follow threads in T3 Code.", off by default for every bot, Clawtrate's new bots included (F-483).

- **Before the server is added** the switch is disabled and the line reads "Add T3 Code in Settings first." with "Open Settings". It does not wait for a confirmed sign-in: the first call is how the sign-in is learned (section 16). While the sign-in is not yet observed, the line reads "Start and follow threads in T3 Code. Whether the gateway's sign-in works shows with the first call."
- **Turning it on** removes the bot's deny of the server's tools, in one `config.patch`, and gives the bot Clawtrate's T3 Code skill (below). Then Clawtrate reads the bot's latest tool listing. A tool policy above the bot can still withhold the tools (a restrictive profile, a sandbox, a session's overrides); when the listing shows that, the line reads "On, but the gateway doesn't offer Otto the T3 Code tools:" and the gateway's notice as given.
- **Turning it off** adds the deny back and removes the skill where Clawtrate added it.
- A write that is refused leaves the switch as it was, with "Couldn't change T3 Code for Otto: <reason>." and the switch focused.
- Turned on, a row follows: "Limits", with a summary ("All projects, asks first"), opening the **T3 Code** page.

**The skill, as a contract.** The skill explains how to choose a project, start a thread with a provider and model, follow up and read the result.

- It ships inside Clawtrate's gateway plugin, which lists its skills folder in its manifest; the gateway loads a plugin's skills when the plugin is enabled (section 20, row 35).
- Which skills a bot sees is decided by one list: its own `agents.entries.<id>.skills` when it has one, which replaces any default; otherwise the gateway's default list, `agents.defaults.skills`; with neither, every loaded skill (section 20, row 35). Turning T3 Code on and off works from that:
  - **The bot has a list of its own.** Turning it on adds the skill's name to that list; turning it off removes only that name, nothing else.
  - **The bot inherits the gateway's default list, and that list does not name the skill.** Turning it on writes a list of the bot's own, equal to the default list as it is now plus the skill. It is turned on at once ("Doing, not asking"), and the switch's line says what changed, in plain words: "Otto now has a list of skills of its own: today's default list plus T3 Code. A skill added to the default later won't reach Otto." with **Undo**, which writes back Otto's earlier setting exactly: no list of its own. Clawtrate keeps the list it wrote with the switch's record. Turning it off removes the skill; if the bot's list is otherwise still the one Clawtrate wrote, the whole list is removed and the bot follows the default list again; if the person has changed it since, only the skill is removed and the list stays the bot's own.
  - **The bot inherits the default list, and it already names the skill**, or **there is no default list** (every loaded skill is visible): nothing is written for the skill. The bot sees the skill whether or not its T3 Code is on, and the skill itself tells it to use T3 Code only when the T3 Code tools are offered.
- Writing a shorter list needs the gateway's explicit permission to remove entries: the turn-off write names the list's path in `replacePaths`; removing the bot's own list is a `null` for that key (section 20, row 37).
- **The enable step reads back before it says the skill is in place.** After the write, Clawtrate reads the configuration and checks the bot's effective list (its own list, or the default) for the skill. Only then does the switch's line drop its caution; when the read-back does not show it, the line reads "On. Clawtrate couldn't confirm the T3 Code skill for Otto." with "Try again".
- Without Clawtrate's plugin there is no skill. The switch then gives the tools only, and its line says "Without Clawtrate's plugin, Otto gets the T3 Code tools without Clawtrate's instructions for them."

**Limits** (F-486). "What <Bot> may do in T3 Code. A thread outside these is refused on the gateway, before it reaches T3 Code, and its card reads Not sent."

| Group                | Control                                                                                                                                                                                                           | Default      |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| Projects             | A radio group with one tab stop: "All projects", "Only these"; with "Only these", a checkbox per project. With none checked: "Choose at least one project, or allow all." and nothing is saved until there is one | All projects |
| Providers and models | A checkbox per provider and model, "As T3 Code lists them for the gateway's sign-in." With none checked: "Choose at least one model." and nothing is saved                                                        | All          |
| Approval             | A switch: "Ask before starting a thread", "On: a card asks you first, in the conversation." The card is the approval card of `conversation.md` §12.                                                               | On           |

Each valid change is saved at once and announced; an invalid one is never saved, and the last saved limits stay in force. A limit applies to follow-ups that could change a thread's project, provider or model as well as to starting one.

**The plugin, as a contract** for its builder (section 20, rows 29 and 31). Clawtrate detects it from the gateway's `hello-ok.features.methods`.

| Method                    | Scope            | Takes                                                                                              | Returns                                                                                                                                                                                                                                                                                           |
| ------------------------- | ---------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `clawtrate-t3.catalog`    | `operator.admin` | `{agentId}`                                                                                        | `{projects: [{projectId, title}], providers: [{instanceId, label, models: [{model, label}]}], fetchedAt}`, made by calling T3 Code's `t3_project_list` and `orchestrator_capabilities` through the gateway's `t3code` server; or `{code: "not-signed-in" \| "unreachable" \| "refused", message}` |

The page's states: the catalogue loading (three grey rows, `aria-busy`); it failed ("Couldn't load T3 Code's projects:" and the message as given, with "Try again"; the saved limits still apply and are listed by their ids); a saved project T3 Code no longer lists ("website, no longer in T3 Code"); a save that conflicted ("Someone else changed these limits. They now show the saved ones." and the current limits).

**Without Clawtrate's plugin.** The page says, in a note: "**Limits need Clawtrate's plugin on the gateway.** Without it, <Bot> can use any project, provider and model its T3 Code sign-in allows, and starting a thread doesn't ask first." and "T3 Code itself limits an outside app only by the access level approved at sign-in." The Limits row's summary reads "None". There is no install button: the plugin is not built.

### Order

Three things come before any screen that writes, because every later step depends on them:

1. **Where accounts live and where a sign-in lands.** On the development gateway, with the research's probe pattern: a sign-in started for `main` lands in the shared store and is offered to every bot; an account in one bot's own store is not offered to another (sections 4, 5; row 33).
2. **Create without duplicates.** `agents.create`, the fallback write, the read-back by id, and the "look before retrying" rule (section 3).
3. **Settings as an extension.** The built `Settings.tsx` keeps its Gateway pane; the frame gains the section list, and Accounts and Integrations are added after it (section 7).

Then:

4. Accounts, read-only: rows, pages, states, "Kept by one bot", ids below admin.
5. Connect: the link-and-code kind first, then the pasted code, then the gateway's machine; the API key path; labels; the read-back after an unclean ending.
6. New bot with its Account step, "Let the gateway choose" and Create.
7. A bot's Settings tab, read-only: the frame, the account row and its states, model and effort with their catalogue line.
8. Changing model, effort and account, with the grey line.
9. The lock: the command, the order reads and every evidence state, Unlock, the re-check after a sign-in.
10. The failure card on an account, and the row's failed line.
11. The log follower, the notice and the row's warning, with "what this cannot see"; last of the account work, because it depends on the gateway's log configuration.
12. The T3 Code switch, as a preference, with nothing behind it, and the "nothing appears when off" check.
13. Adding the server (one write, read back); the command-line sign-in in full; "Last observed" from calls and from Clawtrate's own sign-in.
14. Each bot's switch (deny and skill), the found-with-tools report, turning off by tier.
15. Clawtrate's gateway plugin with the skill, the catalogue and the limits; then the limits page.
16. The app-started T3 Code sign-in, once a qualifying connection exists.
