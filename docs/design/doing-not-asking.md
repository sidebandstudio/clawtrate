# Doing, not asking

Every place Clawtrate stops a person to ask, judged against the product's rule (`docs/decisions.md`, "Doing, not asking"), with what each becomes and the order of the pull requests that convert what is already built. Facts with a file and line, or a gateway source, are **Established**. Everything else is **Proposed**. This design changes no product code.

## The page to decide from

### The rule

Clawtrate does the thing, shows what it did, and offers Undo. A card, a confirmation or any other "read this and approve" step stays only before something destructive. A change that can't be shown to be the person's own request is never presented as theirs: it is done with a visible note and Undo when the worst case is small and fully reversible, and otherwise it is not done, and Clawtrate says so.

### What still asks, and why

Five kinds, and nothing else:

| Kind                          | In Clawtrate today and in the designs                                                                                                                                                                                                                                       |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deleting something            | A bot, a task, a routine, a memory, a conversation's history, a tool server                                                                                                                                                                                                 |
| Anything that can't be undone | A message sent from the person's phone, a removal that loses a key the gateway never shows again, starting over with a new device identity                                                                                                                                  |
| Accounts and credentials      | Signing in or out of a model account or a Clawtrate account; pairing, a device's full control, approving another device or machine; trusting an SSH host key; handing over a secret; a device read of an app the person hasn't decided about, until its check is named (D4) |
| Spending money                | Nothing in Clawtrate spends money by itself today; a future paid step would ask                                                                                                                                                                                             |
| Changing OpenClaw itself      | Updating it, installing it, installing into it a program that isn't Clawtrate's own pinned code, changing how it starts or is reached                                                                                                                                       |

Each asks once, plainly, the same way however it is reached: a button in Settings, a bot's tool, or the person typing "delete it" in a conversation.

### What a person will notice first

1. **A bot that takes a name is renamed.** "Call yourself Juniper" changes the name at once: the conversation says "Renamed to Juniper · Undo". Today a card asks (F-552).
2. **The first run asks nothing between Connect and the first reply** except the command question, until section 3 is decided. No Save on the name card, no "bring what Juniper knows" sheet: the Main Bot starts from what the person's existing bot knows and says what it brought, each part with Undo (#493, #495).
3. **Bots know how Clawtrate works without a card in the sidebar** (#643, already open).
4. **Archiving a working task, stopping a bot in a task, and restarting to update just happen**, with the facts the confirmation used to carry shown in the line that follows.

### Commands on the person's computer

**What was found: today nothing asks before a bot runs a command on a gateway nobody configured.** With nothing set, both OpenClaw versions run every command a bot issues without asking, and New bot on `main` writes no command setting, so every bot made in Clawtrate gets that default. OpenClaw's approval stands between a web page and a command only where a person configured it.

**Recommended for a bot made in Clawtrate (Proposed, for its own security review and build):** where the bot would otherwise run every command without asking, Clawtrate sets OpenClaw's `auto` command mode. Commands on the gateway's allowlist run, OpenClaw's own reviewer judges every other command before it runs, and the person is asked only when the reviewer judges a command risky, can't judge it, or can't bind its review to what will run. Where the person already chose something stricter for the whole gateway, Clawtrate writes nothing and the bot keeps their choice (section 3). This is tighter than today.

**What it costs the person:** a model call on the bot's account for nearly every command, since almost every command is one the allowlist doesn't cover; and a reviewer that can be wrong, can be misled by what the bot read, and allows a local script it can't read, because it is shown the command and never the script. When it is wrong, something runs that the person would have refused, and it usually can't be undone. Nothing in this design changes any bot's command setting, and a person's own Ask or Never stays exactly as they set it. **No fact in section 3 has been confirmed by a run yet**: each comes from reading both versions' source and documentation, twice over, by two readers.

### Counted

**64 prompts** found across the built app, the plugins and the designs (section 2). **24 go**: 22 become done at once, shown, with Undo, and 2 become not done, said plainly. **30 stay** as a single plain confirmation of a destructive kind, 2 of them in a new form (full control is asked where it is needed rather than in a window that opens by itself, and pairing is one confirmation rather than two). **10 belong to the command question** and are unchanged until its own decision (section 3). The bot tools design (#669) has already converted its own earlier cards; they aren't counted. One more thing that never asked, forgetting a gateway, gains an Undo (B20).

Across the first run as designed and the most-met prompts already built, the conversions remove **10 clicks and 8 decisions** for someone who already runs OpenClaw: whether to take the bot's new name (1 click), whether to add the guides, and to which bots (2 clicks, and a section to read), the first-run card's Save (1), what to bring from the old bot (2 clicks, and a sheet), whether to keep the pasted facts (1), whether to stop a working task's run to archive it (1), whether to stop a bot in a task (1), and whether to restart now (1). The command question would remove one more choice and its sheet, once section 3 is decided.

### Not decided yet

- **Commands on the person's computer**: section 3, for its own security review.
- **A device read as the person's own ask** (D4): the signal on the device that shows a read of Calendar or Location is the person's ask. Until it is named, such a read keeps its permission step. With it, how a refusal given in words ("don't read my calendar") is enforced; until then only Don't allow and turning the app off are.
- **Putting unreadable settings back** (B18): whether Clawtrate offers a restore of the kept `state.json-kept-<date>` file, and what it does when that file still can't be read. Today it is put back by hand, so B18 keeps its confirmation; when a restore is built, B18 can become done at once, with the restore as its Undo.

## 1. How each prompt is judged

**Three outcomes, no fourth.** Each prompt is one of: **done at once, shown, with Undo** ("Done"); **not done, said plainly** ("Not done"); **destructive, asks** ("Asks", with its kind). No setting turns asking on or off. The command approvals of section 3 are the one family left as they are until their own decision.

**What the person presses is their request.** For a prompt Clawtrate itself shows after the person pressed something (Archive, Stop, Restart to Update, a switch), the press is the request, and the confirmation that followed it goes.

**A change a bot makes: one rule, in one place.** Whether a change a bot asks for is the person's own request, and what happens when it isn't, is `docs/design/bots-in-clawtrate.md` (#669) sections 3 and 4: the silent check sorts each call as **A** (the person's ask: typed by them in Clawtrate, in this conversation, on the device that applies it, with nothing read from outside before the call, and for a name or picture the value in their words), **B** (in their conversation, but the bot chose the value or read something first) or **C** (not from the person: another bot, a chat-app message, a routine's run, the gateway's own page), and its section 3 table gives each tool's outcome for each. For the tools a bot already had before Clawtrate, a request from **O**, the owner in a chat app (the channel is a chat app (not the gateway's own channel and not none), there is no message from another session or the system, and `requester.senderIsOwner` is true), with nothing read from outside in that run, keeps working as on plain OpenClaw, journaled and shown (its section 3.3). A's conditions are necessary, not proof: they show only that a change could be the person's request ("Don't rename yourself Juniper" contains the name too), so a line for A states what happened ("Renamed to Juniper") and never says the person asked for it, and every change done at once carries Undo. This design doesn't restate that table. Everything here that a bot causes, a name it writes into its own file on `main` included (B1), follows it.

**Undo is real.** "With Undo" means:

- **One record.** The record of changes is the bot tools plugin's journal on the gateway, written only through its admin method (#669 §5.2 and §5.4). Undo is offered for 7 days, or until the next change to the same field, in the line that announced the change and in the bot's settings under "Recent changes", on every device that shows the change, after any restart.
- **Until the plugin is on a gateway**, the gateway's per-user preferences (`users.prefs`, the store F-601 and #646 use) keep a bot's **name and picture only**, under the same 7-day window. Any paired device can write that store on 2026.11.10 (`users.prefs.set` needs only `operator.read` there and `operator.write` on 2026.10.6, read in both versions' method tables), so an entry there can be forged. Undo from it says what it puts back ("Undo: back to Pip"), checks the field still holds the value the entry says it changed to, and applies a name or picture only when it passes the same checks as a new one. Nothing else is ever restored from that store: a change that would need more (instructions, a model, a routine) isn't made by a bot on a gateway without the plugin, and the bot is told the person can make it in Settings. While a gateway has both stores, "Recent changes" shows entries from both.
- **For something the person did with a press** (archive, pause, allowing a model, forgetting a gateway, a switch), Undo is the line's own button on that device, and the opposite control in the same place on every device.
- **What Undo does.** It writes the value before, held to the gateway's precondition where there is one, and only while the field still holds the value after. A field changed again since says so and opens its editor. On 2026.10.6 a rename's Undo carries the race F-552 carries: an edit another admin makes between the read and `agents.update` can be overwritten.

**Where the bot's own question ends.** A bot asking its person something, in its words or with the gateway's question card (F-112, `packages/ui/src/cards/QuestionCard.tsx`), is the bot talking, not a prompt: the person can answer, ignore it or say something else, and nothing waits on Clawtrate. It becomes a prompt the moment Clawtrate tells a bot to ask permission before doing something that isn't destructive, as the task guide does today (row B16), or draws a card whose button applies a change.

## 3. Commands on the person's computer

Nothing in this section has been confirmed by a run. Each fact was read in the source and the bundled documentation of OpenClaw 2026.10.6 and 2026.11.10 as published on npm, by two readers separately.

### 3.1 What decides whether a command asks (Established, both versions)

- **The mode.** `tools.exec.mode`, for the gateway or one bot (`agents.entries.<id>.tools.exec.mode`), resolves to a security and an ask setting: `deny` (deny, off), `allowlist` (allowlist, off), `ask` (allowlist, on-miss), `auto` (allowlist, on-miss, with the reviewer), `full` (full, off) (2026.10.6 `dist/exec-approvals-core-s7tTQC_a.mjs:47-77`, `resolveExecPolicyForMode`; the same table in 2026.11.10's `dist/exec-approvals-core-BZ6-zeZE.mjs`; `docs/tools/exec.md`, "Modes", in both).
- **The default, with nothing set.** Security `full` and ask `off` for the gateway's machine and a node (2026.10.6: `DEFAULT_SECURITY = "full"` in `dist/exec-approvals-migration-gate-BdlHU4Xa.mjs:71`, and ask "Default is `off`" in `docs/tools/exec-approvals.md`, "`exec.ask`"; 2026.11.10: `DEFAULT_SECURITY` `full` and `DEFAULT_ASK` `off` in `dist/exec-approvals-config-BpoLzRe_.mjs`). So a gateway nobody configured runs every command without asking. The development gateway says the same of itself (`tools/dev-gateway/src/cli.ts:552`). A `sandbox` host defaults to `deny`. Commands run in the sandbox when a sandbox runtime is active and on the gateway's machine otherwise (`tools.exec.host: auto`, `docs/tools/exec.md`).
- **The layers, and which one wins.** The host's approvals defaults, then the gateway-wide `tools.exec`, then the bot's own `tools.exec`, then the turn's overrides; each layer that sets a mode replaces the one before it (2026.10.6 `dist/exec-defaults-6F-8vkMu.mjs:57-60`, `dist/exec-policy-DDPEdabr.mjs:3-9`; the same layering in 2026.11.10's documentation). So a bot's own mode replaces a gateway-wide one, a stricter one included.
- **The host's own approvals file is the one floor.** The effective policy is never looser than the approvals document on the machine that runs the command (`exec-defaults-6F-8vkMu.mjs:62-63`, `minSecurity` and `maxAsk`; `docs/tools/exec-approvals.md`, the opening note); a host-local `ask: "always"` keeps asking whatever the config says. The one exception is a session whose permission mode is full (`docs/tools/permission-modes.md`), which Clawtrate never sets.
- **The allowlist and safe bins.** Per bot, of resolved binary paths or command names, with optional argument patterns; a chain needs every top-level segment to match (`docs/tools/exec-approvals.md`, "Allowlist (per agent)"). Allow always adds an entry bound to the exact arguments and folder. The default safe bins, stdin-only tools that run without a match, are few: `cut`, `uniq`, `head`, `tail`, `tr`, `wc` (2026.11.10 `docs/tools/exec-approvals-advanced.md`). So nearly every command a bot runs is a miss.
- **Refused before any review.** Heredocs, unresolved executables and a script operand that can't be found are denied outright under `ask` and `auto` (`docs/tools/exec.md`, both versions), with a reason the bot sees.
- **The reviewer, in `auto`.** A miss goes to OpenClaw's native reviewer, a model call on the bot's own primary model and account unless `tools.exec.reviewer.model` names another, 30 seconds per stage (2026.10.6 `dist/exec-auto-reviewer-C7ldeGpx.mjs`, `DEFAULT_EXEC_REVIEWER_TIMEOUT_MS`; `dist/exec-auto-review-BFvTJS5y.mjs`; 2026.11.10 `dist/exec-auto-review-VmHNrjyT.mjs`). It answers allow (the command runs once), deny (a reason goes back to the bot) or ask (the person's approval card); an allow above medium risk becomes ask. A reviewer failure, a timeout, or three denials in a row in a session ask the person. Shell `-c` wrappers, `env` with assignments, login or interactive shells and any command whose whole dispatch chain can't be bound skip the reviewer and ask the person. Text in a command addressed to the reviewer is denied back to the bot.
- **What the reviewer allows, and what it sees.** Its instructions put running project scripts, installing packages from a lockfile, fetching well-known public resources and writing files inside the project among the commands it may allow (`exec-auto-reviewer-C7ldeGpx.mjs`, its instructions); deleting, sending data out, credentials, persistence, elevated rights, other hosts and publishing are high risk. It is given the command, its arguments, the resolved program path, the folder and the names of the environment's variables, and never the contents of a script. So a bot that writes `setup.sh` with its file tool and then runs `bash setup.sh` is in the class the reviewer allows; only its judgement of whether the command fits the person's request stands in the way. It also sees an excerpt of the conversation: redacted on 2026.10.6, "without secret masking" on 2026.11.10; with the default reviewer model that excerpt goes to the same provider as the bot's own turns.
- **Another runtime.** For a bot on OpenClaw's app-server coding harness, `auto` maps to that harness's own review and a workspace-write sandbox, not to OpenClaw's reviewer (`docs/tools/permission-modes.md`, both versions).
- **Inline code.** `tools.exec.strictInlineEval` (off by default) makes `python -c`, `node -e` and the like need the reviewer or the person even under `full`.
- **No one to ask.** `askFallback` decides when no approval client is reachable or the wait ends: `deny` by default. A routine's run asks only a connected approval client and is refused at once with none (`docs/tools/exec-approvals.md`, "Standing grants for automations").

### 3.2 What else can ask, and what goes round it

- **Plugin approvals**: a plugin can ask before any tool call (`plugin.approval.*`). Clawtrate's rules plugin uses it for Allow, Ask and Never on any tool, file writes and the browser included (`plugins/clawtrate-tool-rules/README.md`; development gateways only until its security review). OpenClaw 2026.11.10 also routes a coding harness's own permission requests and tool servers' approval requests through it (`docs/plugins/plugin-permission-requests.md`).
- **Without a plugin, nothing else asks.** File writes, network and the browser have no approval of their own; they are governed by the bot's tool lists and `tools.fs.workspaceOnly`, which keeps the file tools inside the bot's folder and does nothing for commands.
- **OpenClaw's own tool for scheduled jobs.** Local onboarding sets the `full` tool profile, the `coding` profile includes the scheduled-jobs tool (`automations`, alias `cron`), and `group:automation` is `automations`, `gateway`, `plugins` and `openclaw` (`docs/gateway/config-tools/tool-policy.md`, both versions). A bot with that tool can make a routine without Clawtrate's tools, and so round #669's routine rule.
- **Tool servers' standing grants** (Allow always for one tool of a configured server, any arguments) live in the same approvals document (`docs/tools/exec-approvals.md`, "MCP tool grants").

### 3.4 The options

**A. Ask for every command not on the allowlist or a safe bin (`ask`).** The person meets a card for every new command shape, often several per task, and a routine can't run any command that isn't listed or a safe bin. An attacker who steers the bot gets nothing run without the person's click, except what is on the allowlist and the gateway's safe bins (section 3.1); what remains is a person approving what they didn't read. Enforced on both versions by `tools.exec.mode: "ask"`. Fails by fatigue: Allow always or a switch to `full` follows.

**B. Ask for none (`full`).** The person meets nothing. An attacker who steers the bot with a page, a file or a message runs any command as the gateway's user: reading keys, sending files out, changing OpenClaw's settings and plugins, Clawtrate's rules store included, and leaving something that runs later. Enforced by `tools.exec.mode: "full"`; it is what a gateway nobody configured already does.

**C. Ask only for the destructive ones.** What can be recognised reliably before a command runs:

- the program that runs, by its resolved path and, for a writable program, its content (OpenClaw binds both before review and re-checks them before launch);
- its arguments, by pattern, when they are plain words;
- that a command can't be read: shell expansion, chains, redirects, heredocs, an inline interpreter, a login shell (the rules plugin then treats it as acting on everything; OpenClaw refuses some and its reviewer skips the rest and asks);
- that it runs elevated (`tools.elevated`), or is OpenClaw's own command line.

What can't be recognised: what a program does once it runs. `python build.py`, `npm install` with its lifecycle scripts, `make`, a script the bot wrote a minute ago, a binary it downloaded: any of them can delete, write outside the bot's folder, send data out, install or spend. So "destructive" can't be enforced as a list of commands to ask about; a list of that kind is advice against a bot that wants around it (the rules plugin says so itself). It can be enforced only the other way round: **everything asks unless it is known not to be destructive.** Two forms exist:

- **C1, a list of commands known to change nothing, `ask` for the rest.** Deterministic. Enforced on both versions with `ask` and a per-bot allowlist that Clawtrate writes (`exec.approvals.set`, admin), or with the rules plugin's Allow rules and "Ask when nothing else decides". A useful list is short (reading, listing, searching, `git status` and `git diff`), so most real work still asks.
- **C2, OpenClaw's reviewer for the rest (`auto`).** The allowlist and safe bins run; every miss is judged against what the person asked for; risky, unbindable and unjudgeable commands ask. Enforced on both versions by `tools.exec.mode: "auto"`, which OpenClaw's own documentation recommends as its default for agents that need host access without a prompt for every miss (`docs/tools/permission-modes.md`, "Recommended default"). Fails when the reviewer is wrong or misled, a model's failure rather than a rule's; when its model can't be reached (the person is asked, or, in a routine, the command is refused); and it adds a model call and up to 30 seconds per miss.

**D. A sandbox.** Commands run in a container, which can't reach the person's files or OpenClaw's settings, and nothing needs to ask inside it. It needs a sandbox runtime most computers don't have, so it can't be the default; it stays the strongest choice a person can make.

### 3.5 Recommendation (Proposed)

**For a bot made in Clawtrate, the Main Bot included, where the bot would otherwise run every command without asking:** `tools.exec.mode: "auto"` and `tools.exec.strictInlineEval: true` on that bot. "Otherwise without asking" means Clawtrate read the gateway's settings (`config.get`) and the host's approvals (`exec.approvals.get`) and found no gateway-wide `tools.exec.mode`, `security` or `ask`, or one that resolves to `full`, and no stricter host floor. **Where the person already chose `ask`, `allowlist`, `deny` or a stricter host floor, Clawtrate writes no command mode**, and the bot inherits their choice. For every bot made in Clawtrate, whatever its mode:

- the gateway's own `gateway`, `plugins` and `openclaw` tools denied, and `tools.fs.workspaceOnly: true`;
- OpenClaw's scheduled-jobs tool (`automations`) held to #669's routine row: where the bot tools plugin is on the gateway, its `before_tool_call` hook applies the same A, B and C outcomes to that tool as to `clawtrate_routine`; where it isn't, `automations` is denied to the bot, and its settings let the person turn it back on. A command can still reach `openclaw cron add` or `crontab`; the reviewer judges those, and persistence is high risk in its instructions;
- no allowlist of Clawtrate's own in the first version, and no reviewer model chosen: `tools.exec.reviewer.model` is offered as a setting in the bot's settings, not set.

**What the person meets.** No question in the first run or in New bot. A bot's page says "Runs commands: OpenClaw checks each new command and asks you when it looks risky", with the other choices there (Ask for every new command, Never run commands, Run every command without asking), or, where the bot inherits the person's gateway-wide choice, says that one. In an hour of ordinary coding work, roughly 60 to 150 commands, nearly all of them reviewed, each a few seconds and at most 30; roughly 0 to 3 approval cards for local work (a push, a publish, a `bash -lc` form, three denials in a row), and one for every command on another computer reached over `ssh`. A habit such as `cat > file <<EOF` is refused, with a reason, and the bot writes the file with its file tool instead.

**What an attacker gets.** A page or file that steers the bot gets a command run without a question in two ways: the command matches an allowlist entry or a safe bin, and the reviewer never sees it (allowlist entries exist only where someone added them, for example through Allow always); or the reviewer, seeing the person's request and the command, judges it low or medium risk, which includes running a script the bot wrote itself, since the reviewer never reads a script. Inline code goes to the reviewer even when it would otherwise match. With the settings above, the bot's direct tools can't reach OpenClaw's settings or plugins, or make a routine round Clawtrate's rule. Commands aren't limited that way, and that is the risk that remains: a script the bot writes with its file tool and runs through its command tool runs as the gateway's user, so it can change OpenClaw's settings or plugins, or add a scheduled job (`openclaw cron add`, `crontab`), whenever the reviewer or an allowlist entry lets that command run (sections 3.1 and 3.2; the reviewer never reads the script, and `tools.fs.workspaceOnly` does nothing for commands). In a routine, anything the reviewer would ask about is refused.

**The risk the person carries.** A command that matches the allowlist or a safe bin, or that the reviewer judges low or medium risk, runs without asking, as the gateway's user, on the computer running OpenClaw; a reviewer fooled or wrong runs something the person would have refused, and it usually can't be undone. Each reviewed command is a model call on the bot's account: up to about 16,000 characters of request and 24,000 of conversation, on the order of 5,000 to 10,000 input tokens, so on a large primary model the reviews can cost about as much as the bot's own turns.

**Compared with today.** Tighter than what `main` does now (nothing written, so a gateway nobody configured runs every command). Never looser than a choice the person made for the whole gateway. Looser than #257's and #493's "Ask before acting".

This is the input to a security review and a build of its own. Until both land, nothing in Clawtrate changes OpenClaw's approval for a command.

### 3.6 What it doesn't change

- A bot that already exists keeps its command setting.
- A person's Ask or Never for a bot or a tool, and a gateway-wide mode they set, stay exactly as they set them; the recommendation writes a mode only where a new bot would otherwise run every command unasked.
- The host's own approvals file stays a floor Clawtrate never lowers.
- The approval card (B17), the rules plugin's card (G1) and every row marked "Command question" stay as they are until this decision is built.

## 4. Where the rule is strained, and the form chosen

1. **A routine keeps acting.** A routine follows #669's routine row: made for the person's ask, made as the bot's own when it proposes one in the person's conversation with nothing read first, not made otherwise, except that one the owner asks for in a chat app after the bot read something is stored turned off until the owner says to start it or turns it on in Clawtrate (#669 §3.3), and each of its runs leaves a line with Pause and Edit (#669 §4.6). What isn't caught there: "find the cheapest flight and check it every morning" reads a page before the routine is asked for, so it is B after reading and isn't made, and the person asks again in a fresh turn. **Proposed, for #669 §3 to take up:** a routine is made as A even after outside content when three things hold: every sentence of its prompt appears in the device's own copy of what the person typed (the same test as a name's, whitespace and case folded); its results go to this conversation only; and it runs no more often than hourly. A page can then choose nothing that persists but the time.
2. **OpenClaw's own scheduled-jobs tool goes round that row** (section 3.2). Held to it by the plugin's hook, or denied where the plugin isn't installed (section 3.5).
3. **A bot's name is shown everywhere, and the test for the person's ask can be wrong.** A message that contains the name passes it even when it says not to rename ("Don't rename yourself Juniper"), so even "Renamed to Juniper" only says what happened, and Undo is always there. A page can make a bot call itself something misleading. The harm is small, visible and reversible, so it is done, shown as the bot's own doing, and limited to three a day and to names no other bot on the gateway has (B1). The device that sent the run applies it; for a run no device sent, the first device with admin to claim it in the gateway's per-user preferences (a compare-and-set on the value it read) does, and every other device only shows it. An undone name is kept there as declined for that bot, not per device, so the bot writing it into its file again doesn't rename it again.
4. **The Undo record without the plugin can be forged** (section 1). So it holds a name and a picture only, says what it puts back, and restores nothing else.
5. **Restart to update has no Undo.** It changes the app, not anything of the person's, and the one thing that could be lost, a message not yet sent, is waited for (B8). Asking again after the person pressed a button named "Restart to Update" protected nothing.
6. **Stopping can't be undone.** Stop makes a bot do less; what it ends is continued by a message. The composer's Stop never asked, and the computer view's Stop now matches it (B5, B7).
7. **A pause after a long absence was a protection, not a question.** It stays, done by itself, said on return, with Resume (D2). Where an opening can't be recorded on the gateway, absence on one device can't show the person was away, and the pause stops routines for the whole gateway, so it isn't done: the line says why and offers Pause all.
8. **Starting over with damaged credentials makes a new device.** That can't be taken back, so it keeps its confirmation (B19). The settings-only case (B18) keeps its confirmation too until a restore of the kept file exists; then it can start over by itself.
9. **Opening a link.** The question protected against words that say one place and an address that goes to another. Showing the host beside the words, and a label for a local address, does that before the tap (I1, D8). What remains: a look-alike host; the host is shown in its ASCII form, so a look-alike shows as one.
10. **Bringing in what another bot knows.** Copying memory can carry something an old page once planted in that bot's memory into the Main Bot. The harm stays on the same gateway and person, and each part is undone by one Remove, so it is done with a note. Scheduled jobs aren't moved by themselves (F6).
11. **Commands.** Section 3. The rule's own carve-outs cover it: a command usually can't be undone, so the approval stays where OpenClaw judges the command risky, and nowhere looser than the person set.
