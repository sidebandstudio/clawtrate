# Doing, not asking

Every place Clawtrate stops a person to ask, judged against the product's rule (`docs/decisions.md`, "Doing, not asking"), with what each becomes and the order of the pull requests that convert what is already built. Facts with a file and line, or a gateway source, are **Established**. Everything else is **Proposed**. This design changes no product code.

## The page to decide from

### The rule

Clawtrate does the thing, shows what it did, and offers Undo. A card, a confirmation or any other "read this and approve" step stays only before something destructive. A change that can't be shown to be the person's own request is never presented as theirs: it is done with a visible note and Undo when the worst case is small and fully reversible, and otherwise it is not done, and Clawtrate says so.

### What still asks, and why

Five kinds, and nothing else:

| Kind                          | In Clawtrate today and in the designs                                                                                                                                               |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deleting something            | A bot, a task, a routine, a memory, a tool server                                                                                                                                   |
| Anything that can't be undone | A message sent from the person's phone, a removal that loses a key the gateway never shows again                                                                                    |
| Accounts and credentials      | Signing in or out of a model account or a Clawtrate account; pairing, a device's full control, approving another device or machine; trusting an SSH host key; handing over a secret |
| Spending money                | Nothing in Clawtrate spends money by itself today; a future paid step would ask                                                                                                     |
| Changing OpenClaw itself      | Updating it, installing it, installing into it a program that isn't Clawtrate's own pinned code, changing how it starts or is reached                                               |

Each asks once, plainly, the same way however it is reached: a button in Settings, a bot's tool, or the person typing "delete it" in a conversation.

### What a person will notice first

1. **A bot that takes a name is renamed.** "Call yourself Juniper" changes the name at once: the conversation says "Renamed to Juniper · Undo". Today a card asks (F-552).
2. **The first run asks nothing between Connect and the first reply.** No Save on the name card, no "bring what Juniper knows" sheet: the Main Bot starts from what the person's existing bot knows and says what it brought, each part with Undo (#493, #495). The command question goes too, once section 3 is decided.
3. **Bots know how Clawtrate works without a card in the sidebar** (#643, already open).
4. **Archiving a working task, stopping a bot in a task, and restarting to update just happen**, with the facts the confirmation used to carry shown in the line that follows.

### Commands on the person's computer

OpenClaw's approval before a command is the one prompt that does a job nothing else does: it is what stops a web page, a file or a message from steering a bot into running a command, and most commands can't be undone. **Recommended for a bot made in Clawtrate (Proposed, for its own security review and build):** OpenClaw's `auto` command mode, which runs commands on the gateway's allowlist, has OpenClaw's own reviewer judge every other command before it runs, and asks the person only when the reviewer judges it risky, can't judge it, or can't bind its review to what will run (section 3). **What it costs the person:** a command the reviewer judges low or medium risk runs without asking, as the gateway's user, on the computer running OpenClaw; the reviewer is a model and can be wrong or misled by what the bot read, and when it is, something runs that the person would have refused. Each reviewed command is a model call on the bot's account. Nothing in this design changes any bot's command setting, and a person's own Ask or Never stays exactly as they set it.

### Counted

**74 prompts** found across the built app, the plugins and the designs (section 2). **40 go**: 36 become done at once, shown, with Undo, and 4 become not done, said plainly. **25 stay** as a single plain confirmation of a destructive kind, 2 of them in a new form (full control is asked where it is needed rather than in a window that opens by itself, and pairing is one confirmation rather than two). **9 belong to the command question** and are unchanged until its own decision (section 3). **1 is added**: forgetting a gateway, which removes a credential and asks nothing today. Seven more things look like prompts and aren't (section 2.7).

Across the first run as designed and the most-met prompts already built, the change removes **11 clicks and 6 decisions** for someone who already runs OpenClaw: the name card (1 click), the guides card and its sheet (2 clicks, and a section to read), the command question (a choice between two cards, and a sheet), the first-run card's Save (1), the bring-in offer and its sheet (2 clicks, and a sheet), the pasted facts' Save (1), archiving a working task (1), stopping a bot in a task (1), and Restart to update (1).

## 1. How each prompt is judged

**Three outcomes, no fourth.** Each prompt is one of: **done at once, shown, with Undo** ("Done"); **not done, said plainly** ("Not done"); **destructive, asks** ("Asks", with its kind). No setting turns asking on or off. The command approvals of section 3 are the one family left as they are until their own decision.

**The checks still run, silently.** What a design used to decide "apply or ask" is still computed and now decides between Done and Not done. For a request in a conversation, the checks are the ones `docs/design/bots-in-clawtrate.md` (#669) section 4 establishes: the gateway's record of what started the run, and Clawtrate's own record that this device sent that message in that conversation (Established there: `chat.send` runs under the client's idempotency key as its run id). A value the bot applies to itself, such as a name, must also appear in what the person typed.

**Done or Not done, for a change that isn't the person's own request.** Done with a note when the worst case is small, fully reversible and visible where the person looks (a name, a picture, a view switch, opening a pane, a task under the bot's own name). Not done when it would keep acting after the fact (a routine, the bot's instructions, its model), reach outside the conversation (another bot's settings, a new bot), or loosen what a bot may do. "After reading outside content" is a silent check of its own (**Proposed**): Clawtrate's bot tools plugin sees each tool call of a run before it runs (`before_tool_call`, both versions, #669 §4.1), so it records whether the run had already used a tool whose result is someone else's text (web search or fetch, the browser, a tool server's tools, another task's history, reading a file) before the bot asked for a standing change.

**Undo is real.** "With Undo" means:

- **What is kept.** The record of changes (**Proposed**): one list per gateway and person. With Clawtrate's bot tools plugin on the gateway, its journal, kept 90 days (#669 §5.2). Without it, one key in the gateway's per-user preferences (`users.prefs`, the store F-601 and #646 use), holding the last 16 changes, each with its field, the value before, the value after and the gateway's revision where the gateway gives one, kept 30 days or until 16 newer changes push it out.
- **Where Undo shows.** In the line that announced the change, and in the bot's settings under "Recent changes".
- **After a restart and on another device.** Both stores are on the gateway, so Undo is offered on every device that shows the change, after any restart.
- **What Undo does.** It writes the value before, held to the gateway's precondition where there is one, and only while the field still holds the value after. A field changed again since says so and opens its editor.
- **What it can't promise.** On 2026.11.10 any paired device can write `users.prefs` (#646, read in the source of both versions), so a forged entry could offer an Undo. Undo applies a value only when it passes the same checks as a new one, so the worst a forged entry does is offer a name that would have been accepted anyway. On 2026.10.6 a rename's Undo carries the race F-552 carries: an edit another admin makes between the read and `agents.update` can be overwritten.
- **When it can't be kept.** A change whose value before doesn't fit the record (an instructions change longer than 4,000 characters, say) is Not done at once: the bot is told the person can make it in Settings.

**Where the bot's own question ends.** A bot asking its person something, in its words or with the gateway's question card (F-112, `packages/ui/src/cards/QuestionCard.tsx`), is the bot talking, not a prompt: the person can answer, ignore it or say something else, and nothing waits on Clawtrate. It becomes a prompt the moment Clawtrate tells a bot to ask permission before doing something that isn't destructive, as the task guide does today (row B16), or draws a card whose button applies a change.

## 3. Commands on the person's computer

### 3.1 What decides whether a command asks (Established, both versions)

Read in OpenClaw 2026.10.6 and 2026.11.10 as published on npm.

- **The mode.** `tools.exec.mode`, for the gateway or one bot (`agents.entries.<id>.tools.exec.mode`), resolves to a security and an ask setting: `deny` (deny, off), `allowlist` (allowlist, off), `ask` (allowlist, on-miss), `auto` (allowlist, on-miss, with the reviewer), `full` (full, off) (2026.10.6 `dist/exec-approvals-core-s7tTQC_a.mjs:47-77`, `resolveExecPolicyForMode`; the same table in 2026.11.10's `dist/exec-approvals-core-BZ6-zeZE.mjs`; `docs/tools/exec.md`, "Modes", in both).
- **The default, with nothing set.** Security `full` and ask `off` for the gateway's machine and a node (2026.10.6: `DEFAULT_SECURITY = "full"` in `dist/exec-approvals-migration-gate-BdlHU4Xa.mjs:71`, and ask "Default is `off`" in `docs/tools/exec-approvals.md`, "`exec.ask`"; 2026.11.10: `DEFAULT_SECURITY` `full` and `DEFAULT_ASK` `off` in `dist/exec-approvals-config-BpoLzRe_.mjs`). So a gateway nobody configured runs every command without asking. A `sandbox` host defaults to `deny`. Commands run in the sandbox when a sandbox runtime is active and on the gateway's machine otherwise (`tools.exec.host: auto`, `docs/tools/exec.md`).
- **The host's own approvals file is a floor.** The effective policy is the stricter of `tools.exec.*` and the approvals document on the machine that runs the command (`docs/tools/exec-approvals.md`, the opening note, both versions); a host-local `ask: "always"` keeps asking whatever the config says. The one exception is a session whose permission mode is full (`docs/tools/permission-modes.md`).
- **The allowlist.** Per bot, of resolved binary paths or command names, with optional argument patterns; a chain needs every top-level segment to match (`docs/tools/exec-approvals.md`, "Allowlist (per agent)"). Safe bins (stdin-only tools) run without a match. Allow always adds an entry bound to the exact arguments and folder.
- **The reviewer, in `auto`.** A miss goes to OpenClaw's native reviewer, a model call (the bot's own primary model unless `tools.exec.reviewer.model` names another, 30 seconds per stage), which answers allow (the command runs once, for low or medium risk), deny (a reason goes back to the bot) or ask (the person's approval card). A reviewer failure, a timeout, or three denials in a row in a session ask the person. Shell `-c` wrappers, `env` with assignments, login or interactive shells and any command whose whole dispatch chain can't be bound skip the reviewer and ask the person. Text in a command addressed to the reviewer is denied back to the bot (`docs/tools/exec.md`, both versions; the reviewer is `dist/exec-auto-review-BFvTJS5y.mjs` in 2026.10.6 and `dist/exec-auto-review-VmHNrjyT.mjs` in 2026.11.10). One difference: 2026.10.6 gives the reviewer a redacted excerpt of the conversation, 2026.11.10 an excerpt "without secret masking". With the default reviewer model that excerpt goes to the same provider as the bot's own turns.
- **Inline code.** `tools.exec.strictInlineEval` (off by default) makes `python -c`, `node -e` and the like need the reviewer or the person even under `full`.
- **No one to ask.** `askFallback` decides when no approval client is reachable or the wait ends: `deny` by default. A routine's run asks only a connected approval client and is refused at once with none (`docs/tools/exec-approvals.md`, "Standing grants for automations").

### 3.2 What else can ask

- **Plugin approvals**: a plugin can ask before any tool call (`plugin.approval.*`). Clawtrate's rules plugin uses it for Allow, Ask and Never on any tool, file writes and the browser included (`plugins/clawtrate-tool-rules/README.md`; development gateways only until its security review). OpenClaw 2026.11.10 also routes a coding harness's own permission requests and tool servers' approval requests through it (`docs/plugins/plugin-permission-requests.md`).
- **Without a plugin, nothing else asks.** File writes, network and the browser have no approval of their own; they are governed by the bot's tool lists and `tools.fs.workspaceOnly`.
- **Tool servers' standing grants** (Allow always for one tool of a configured server, any arguments) live in the same approvals document (`docs/tools/exec-approvals.md`, "MCP tool grants").

### 3.3 What Clawtrate sets today

- **New bot on `main`** sends `agents.create {name, model, avatar}` and then writes the model's fallbacks and effort (`packages/core/src/accounts-engine.ts:1488`); it writes no command setting and no deny list. A bot made in Clawtrate today runs commands the way the gateway's default says, which, on a gateway nobody configured, is without asking.
- **#257** (draft) adds an Approvals step to New bot: "Ask before acting" (`ask`) or "Run without routine approvals" (`full`), nothing chosen, and a deny list of `gateway`, `plugins` and `t3code__*`.
- **#493** asks the same question once in the first run and denies the gateway's own `gateway`, `plugins` and `openclaw` tools to the Main Bot (`main-bot-onboarding.md` §12).
- **Issue #292** asks that people can hand work off without approvals unless they choose them.

### 3.4 The options

**A. Ask for every command not on the allowlist (`ask`).** The person meets a card for every new command shape, often several per task, and a routine can't run any command that isn't listed. An attacker who steers the bot gets nothing run without the person's click; what remains is a person approving what they didn't read. Enforced on both versions by `tools.exec.mode: "ask"`. Fails by fatigue: Allow always or a switch to `full` follows.

**B. Ask for none (`full`).** The person meets nothing. An attacker who steers the bot with a page, a file or a message runs any command as the gateway's user: reading keys, sending files out, changing OpenClaw's settings and plugins, Clawtrate's rules store included, and leaving something that runs later. Enforced by `tools.exec.mode: "full"`; it is what a gateway nobody configured already does.

**C. Ask only for the destructive ones.** What can be recognised reliably before a command runs:

- the program that runs, by its resolved path and, for a writable program, its content (OpenClaw binds both before review and re-checks them before launch);
- its arguments, by pattern, when they are plain words;
- that a command can't be read: shell expansion, chains, redirects, heredocs, an inline interpreter, a login shell (the rules plugin then treats it as acting on everything; OpenClaw's reviewer skips it and asks);
- that it runs elevated (`tools.elevated`), or is OpenClaw's own command line.

What can't be recognised: what a program does once it runs. `python build.py`, `npm install` with its lifecycle scripts, `make`, a script the bot wrote a minute ago, a binary it downloaded: any of them can delete, write outside the bot's folder, send data out, install or spend. So "destructive" can't be enforced as a list of commands to ask about; a list of that kind is advice against a bot that wants around it (the rules plugin says so itself). It can be enforced only the other way round: **everything asks unless it is known not to be destructive.** Two forms exist:

- **C1, a list of commands known to change nothing, `ask` for the rest.** Deterministic. Enforced on both versions with `ask` and a per-bot allowlist that Clawtrate writes (`exec.approvals.set`, admin), or with the rules plugin's Allow rules and "Ask when nothing else decides". A useful list is short (reading, listing, searching, `git status` and `git diff`), so most real work still asks, and most commands of a coding task are misses.
- **C2, OpenClaw's reviewer for the rest (`auto`).** The allowlist and safe bins run; every miss is judged against what the person asked for; risky, unbindable and unjudgeable commands ask. Enforced on both versions by `tools.exec.mode: "auto"`, which OpenClaw's own documentation recommends as its default for agents that need host access without a prompt for every miss (`docs/tools/permission-modes.md`, "Recommended default"). Fails when the reviewer is wrong or misled, a model's failure rather than a rule's; when its model can't be reached (the person is asked, or, in a routine, the command is refused); and it adds a model call and up to 30 seconds per miss.

**D. A sandbox.** Commands run in a container, which can't reach the person's files or OpenClaw's settings, and nothing needs to ask inside it. It needs a sandbox runtime most computers don't have, so it can't be the default; it stays the strongest choice a person can make.

### 3.5 Recommendation (Proposed)

**For a bot made in Clawtrate, the Main Bot included: `tools.exec.mode: "auto"`, `tools.exec.strictInlineEval: true`, the gateway's `gateway`, `plugins` and `openclaw` tools denied, and `tools.fs.workspaceOnly: true`.** No allowlist of Clawtrate's own in the first version: the reviewer decides misses, and a list can come once the decision records show which commands are asked about most.

- **What the person meets.** No question in the first run or in New bot. A bot's page says "Runs commands: OpenClaw checks each new command and asks you when it looks risky", with the other choices there (Ask for every new command, Never run commands, Run every command without asking). An approval card only when the reviewer escalates, can't judge, or can't bind the command, which is OpenClaw's own judgement of the destructive case.
- **What an attacker gets.** A page or file that steers the bot can get a command run only if the reviewer, seeing the person's request and the command, judges it low or medium risk. Inline code goes to the reviewer even when it would otherwise match. The bot can't reach OpenClaw's settings or plugins through its own tools. In a routine, anything the reviewer would ask about is refused.
- **The risk the person carries.** A command the reviewer judges low or medium risk runs without asking, as the gateway's user, on the computer running OpenClaw; a reviewer fooled or wrong runs something the person would have refused, and it usually can't be undone. Each reviewed command costs a model call on the bot's account.
- **Compared with today.** Tighter than what `main` does now (nothing written, the gateway's default, which is `full` where nobody configured one). Looser than #257's and #493's "Ask before acting".

This is the input to a security review and a build of its own. Until both land, nothing in Clawtrate changes OpenClaw's approval for a command.

### 3.6 What it doesn't change

- A bot that already exists keeps its command setting.
- A person's Ask or Never for a bot or a tool stays exactly as they set it; the recommendation applies only where nothing is set for a new bot.
- The host's own approvals file stays a floor Clawtrate never lowers.
- The approval card (B17), the rules plugin's card (G1) and every row marked "Command question" stay as they are until this decision is built.

## 4. Where the rule is strained, and the form chosen

1. **A routine nobody asked for keeps acting.** The case: a page read in the person's own turn tells the bot to add a routine that later sends files somewhere. The harm: it runs unseen, on a schedule. The form chosen: a routine is made at once only for the person's request in a run that had read no outside content before the call (section 1, O4); otherwise it is not made, and the bot and the person are told. The cost: "find the cheapest flight and check it every morning" reads a web page before it asks for the routine, so it isn't made; the bot says to ask again, and the second request, in a fresh turn, is made.
2. **Instructions and model change every later run.** The same check and the same form (O5, O6).
3. **A bot's name is shown everywhere.** A page can make a bot call itself something misleading. The harm is small, visible and reversible, so it is done with a note that says it wasn't the person's request, and limited to three a day and to names no other bot on the gateway has (B1).
4. **Restart to update has no Undo.** It changes the app, not anything of the person's, and the one thing that could be lost, a message not yet sent, is waited for (B8). Asking again after the person pressed a button named "Restart to Update" protected nothing.
5. **Stopping can't be undone.** Stop makes a bot do less; what it ends is continued by a message. The composer's Stop never asked, and the computer view's Stop now matches it (B5, B7).
6. **Opening a link.** The question protected against words that say one place and an address that goes to another. Showing the host beside the words, and a label for a local address, does that before the tap (I1, D8). What remains: a look-alike host; the host is shown in its ASCII form, so a look-alike shows as one.
7. **Bringing in what another bot knows.** Copying memory can carry something an old page once planted in that bot's memory into the Main Bot. The harm stays on the same gateway and person, and each part is undone by one Remove, so it is done with a note. Scheduled jobs aren't moved by themselves (F6).
8. **Forgetting a gateway asked nothing, and now asks** (B19): removing this device's pairing is a credential, and connecting again may need the gateway owner's approval.
9. **Commands.** Section 3. The rule's own carve-outs cover it: a command usually can't be undone, so the approval stays where OpenClaw judges the command risky.
