# Drafts, the Vault and secure input

Three things a bot can ask of the person: to look at a message before it goes (a draft), to keep a secret for it (the Vault), and to type a secret into Clawtrate's own field (secure input). This part follows `visual-language.md`, `conversation.md`, `bots.md`, `work-pane.md` and `controls.md`, in the same language and with the same tokens. The evidence for every state is `docs/research/drafts-and-vault.md` ("research" below, by section), run on a development instance of OpenClaw 2026.10.6 with a research plugin and stand-in send tools.

What must be true is in `docs/parity.md`: the draft rows F-181, F-182, F-341 to F-345 and F-453; the secure input rows F-183, F-184 and F-346; and the Vault rows F-261 and F-338. This document decides appearance, wording and input, and names the gateway fact each state rests on (section 11). Section 12 is what Clawtrate's drafts plugin (issue #89) would have to do: it is a **proposal**, and the section names which of its hooks were observed and which parts are proposed. Section 13 records each row's target, which stands, and what is available toward it.

Four facts shape everything here, and the design never draws past them:

- **An answer cannot carry an edit; a second hold can.** A held call's answer is Allow once or Deny, the request carries no arguments, and the gateway copies the arguments when a hold starts (research §1). A plugin can still apply the person's edit: after the first answer its ordinary hook swaps in the edit and holds the call again, and the second answer sends exactly the edit (research §1a). So an edited draft takes two answers on the same card.
- **Drafts need a plugin that doesn't exist yet.** No gateway setting holds a send for the person. Clawtrate's drafts plugin (#89) would, while it runs; it is proposed, and it would fail open like the rules plugin (`controls.md` section 2). Every draft example here uses that proposed plugin and stand-in tools, and the prototype says so on its page.
- **The Vault is the gateway's shared secret store.** One store for every bot on the gateway, admin only, named values with allowed hosts; nothing in an entry names a bot, and any bot offered the Secrets tool lists and can remove every entry (research §5). So the Vault never says an item is limited to a bot.
- **The gateway keeps a saved value in plain text** in its state database (research §4). No control or sentence claims more protection than that, and every field that saves a value says so before it is submitted.

The prototype shows all of it: `prototype/drafts.html`, with its states from the address (section 14). The styles are in `prototype/css/drafts.css` and the behaviour in `prototype/js/drafts.js`; `prototype/tools/checks/drafts.mjs` checks them.

### Input

- Neither card takes focus when it arrives. "Review" on the composer's shelf, or ⌘J, moves focus to the oldest pending card (`conversation.md` section 14).
- The draft card's tab order: Show full request, Show more, the attachments, Send, Edit, Discard, Raw; editing: the fields, the body, Send edited email, Cancel edit, Discard; "Disable drafts for Otto" is the last link of its foot. ⌘↵ inside the card is Send. Discard has no shortcut.
- The masked secret card's tab order: the field, Show, the hosts, Save to the gateway, Skip, Raw. Enter in the field saves when it has a value. Escape clears the field; it never skips.
- One polite live region announces: "Sent", "Not sent", "Discarded", "Edit taken", "Saved to the gateway", "Skipped", "Removed from the Vault", "Couldn't save", and the access request's phrases. A value is never announced, and the field is never named by its value.

### A masked value's path

On Clawtrate's submit path and its direct Vault-list path, a value typed into the Secure Form (the masked question's answer, or a new or replaced Vault value) exists in exactly three places and no others: the field that received it; the send path from the renderer to the host (Electron's bridge, or, in a web preview, the originating viewer's own command socket); and the host's request to the gateway. A later gateway tool result can independently contain an environment value. From the first render through a refusal, a timeout and a reload:

- on those paths it is never in the question card's sent record, the host's state, any viewer's snapshot, a fault or error report, a log, a notification, the clipboard or Raw;
- the field is cleared the moment the gateway answers, whatever the answer, and on "No answer" too; nothing of it is kept to retry, and "Try again" asks for the value again;
- the field is excluded from any state the app restores: reopening a task, a reconnect or a reload shows it empty;
- Raw shows the method, the question id or entry name, the hosts, and the record the gateway returned, which keeps `"stored"` for a masked answer (research §4); where the value would be, Raw reads "(not kept by Clawtrate)";
- on the phone the card is covered before the system takes the app switcher's snapshot (`work-pane.md` section 17).

Today's code would break this in three places, and section 14 says what replaces each.

## 3. The draft card

A draft is a send the bot made that the proposed drafts plugin holds for the person: a call of a tool on the plugin's list of sending tools (section 12), held by a plugin approval. The card is the approval card of `conversation.md` section 12 in a draft's form. **A draft belongs to its approval**: the card is drawn only for a held approval the gateway shows this connection, and its contents are the plugin's pinned arguments for that approval's call, read through the proposed `clawtrate-drafts.get {approvalId, toolCallId}`. It is never filled from the bot's call as the client saw it, because a hook can change arguments after that (research §1). The client's tool event is shown only in Raw.

**Joining a draft to its approval, and a reload.** The approval request carries `toolCallId`, `runId` and the approval `id`, and no arguments (research §1). After a reload, a reconnect or on a second admin device, Clawtrate lists the pending approvals (`plugin.approval.list`, approvals scope) and, for each whose `pluginId` is the drafts plugin, reads the plugin's record by approval id and call id. The record carries the run, the phase (first hold, or second hold after an edit), the pinned arguments and their revision. A second hold has a new approval id and the same call id (research §1a, §1b). When the record is missing or names another approval or phase, the card shows the request's own fields only, says "Couldn't read this draft. The gateway still lists it as waiting.", and offers Discard and "Check again", never Send.

**The email draft** (F-181):

- **Title** (17 px, semibold): "New email". The tag at the top right: "Ready to send" on `--warn-soft` with a dot.
- **Line under the title** (13 px, muted): "Otto wants to send this from its email tool, mail_send." The tool's name is the one in the request (`request.toolName`); `mail_send` stands for a connector's tool (issue #85).
- **Rows** (`.d-rows`): From, To, Cc and Subject, each only when the tool's mapping (section 12) names that argument and the call carries it. A recipient list wraps. When the mapping has no sender argument the row reads "From: the account Otto's email tool is set up with. The tool doesn't say which." (issue #85.)
- **Body** (`.d-body`), pre-wrapped, folded at eight lines with "Show more"; open, "Show less".
- **Attachments** (`.d-file`), one row each: name, size, and "Checked when Otto asked, 5:42 PM. Will be checked again after your first answer." (below, "A file that changed").
- **Buttons**: "Send email" (primary), "Edit" (default), and at the far right "Discard" (quiet). At the foot, "Disable drafts for Otto" (a text link; admin only) and the plugin's mark: "Held by Clawtrate's drafts plugin. It waits up to 10 minutes."
- **Show full request** opens an inset with the request's own fields: tool, bot, task, the time it was asked and when it expires, and the plugin's title and description.
- **Raw** (`.d-raw`): the approval request as the gateway sent it, the bot's call from the task's events, and the plugin's pinned arguments with their revision.

**The Slack draft** (F-345, F-453): the same card, titled "Slack message", with Workspace, To and Thread rows and "Send message". These rows are drawn only from a tool whose mapping accounts for every argument that decides where the message goes, and can name each one. The prototype's Slack draft is a connector's stand-in tool, `slack_post`, with exactly `workspace`, `to`, `thread` and `text`. The gateway's own `message` tool takes `target` or `targets`, `accountId`, `replyTo` and `threadId` (research §1b), and nothing yet names those as a workspace, a person or a thread; its card would show "Destination, as Otto's call gives it" with each argument in mono, and the line "Clawtrate can't name this destination."

**Decisions and their answers.** "Send email" is Allow once; "Discard" is Deny. Each follows `conversation.md` section 12's table: "Sending your decision…" until the gateway answers; the applied answer; "The gateway refused this decision." with its reason and "The draft is still waiting."; "Already answered on another device at 5:25 PM. Your decision was not applied."; and "No answer from the gateway. Your decision may or may not have been applied." with "Check again" and Discard. Discard stays visible in every pending state.

**Check again** reads the approval list and the run, and says what it found. A decision is offered only for a fresh matching pending approval, and Expired only for a recorded expiry:

| What it finds                                               | The card                                                                                                                                      |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| A fresh matching pending approval                           | The choices again: "The draft is still waiting."                                                                                              |
| A recorded expiry                                           | Expired (below)                                                                                                                               |
| The gateway refused the decision                            | Its refusal and "The draft is still waiting."                                                                                                 |
| The hold is gone and there is no terminal outcome to report | "Couldn't confirm what happened. The gateway no longer lists this draft, and Otto's email tool hasn't reported back." with "Check again" only |
| The tool's result arrived                                   | After Send (below)                                                                                                                            |

**After Send.** Allowing is not sending. The card reads what happened from the call's own result, never from the decision:

| What the gateway reports                                                                     | Tag                        | The sentence                                                                                                                                          |
| -------------------------------------------------------------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| A real connector result reports a send and its details (proposed; no real connector was run) | "Answered"                 | "Sent from otto@example.com to dana@example.com, cc lee@example.org, with report.txt (28 bytes), at 5:43 PM. Read back from the email tool's result." |
| A real connector result reports a send and its details (proposed; no real connector was run) | "Answered"                 | "Posted to #ops in Example Co, in the thread Disk alerts, at 5:43 PM. Read back from the message tool's result."                                      |
| The tool succeeded but reports nothing of what it sent                                       | "Answered"                 | "The email tool reported success at 5:43 PM. It doesn't say what it sent; this is what you approved."                                                 |
| The tool returned an error, with nothing showing that nothing went out                       | "Tool failed" (`--danger`) | "Tool failed. Sending could not be confirmed." and the tool's message                                                                                 |
| The plugin refused the call before the tool ran, or the tool's result says it sent nothing   | "Not sent" (`--danger`)    | Its reason (for example the file check, below) and "Nothing was sent."                                                                                |
| No result yet                                                                                | "Sending…"                 | "Sending. Otto's email tool hasn't reported back."                                                                                                    |

The resolved card folds to one line, 40 px: the tag, "New email to dana@example.com", the time, and a chevron; opened, it shows the rows, the body and the sentence as of that moment. (F-181's "Answered", F-342.)

**After Discard**: "Discarded" (neutral), "Discarded at 5:43 PM. Nothing was sent. Otto was told you discarded it." The gateway tells the bot "Denied by user. The tool call did not run." (research §1). (F-343.)

**Expired, closed, cancelled**: as `conversation.md` section 12, with "Nothing was sent." in place of "The command was not run.".

**When the run has ended.** Stopping a run cancels its hold, yet the gateway can list the hold for a moment afterwards; answering it is then refused (research §1b). Once the matching run is known to be over, hide approval actions even if the gateway still lists the hold. Keep a confirmed tool result. If there is no recorded refusal, expiry or cancellation that establishes the tool did not run, show "Otto's run ended. Couldn't confirm whether this was sent."

**A file that changed** (F-341). The proposed drafts plugin checks each attached file on the gateway's machine when the bot asks, and again after the person's first answer; if it changed, the plugin refuses the call and nothing runs (research §3). Clawtrate reads no file itself.

- Pending, each file's line: "Checked when Otto asked, 5:42 PM. Will be checked again after your first answer."
- After Send, when the plugin refused: tag "Not sent", and "report.txt changed after Otto asked (28 bytes then, 44 now), so nothing was sent. Otto was told why. If it asks again, the new draft appears below." The numbers are the plugin's, from its refusal. That request is over.
- **An edited draft's second hold**: the recheck runs before the second hold, and nothing runs between the second answer and the tool (research §1b). Each file's line then reads "Checked after the first answer. The file can still change while this draft waits." The plugin does not detect a change during the second hold. The connector decides which bytes it reads.
- A file the plugin could not read when the bot asked, or one outside the bot's workspace: "Couldn't check report.txt: the plugin couldn't read it. If it changes before it's sent, Clawtrate can't tell." Send stays offered.
- Which bytes a connector reads and when is the connector's (#85); a change while the tool runs is not caught.

**On a read-only connection** there is no card: the gateway gives that connection no hold. The conversation shows the access bar's "Request approvals access to see drafts", and nothing else of the draft.

## 4. Editing a draft

An answer can't carry new text, but the drafts plugin can apply an edit after the first answer by holding the call again (research §1a; confirmed independently: two holds, one call, and the exact edited arguments reached the stand-in). So an edited draft takes two answers on the same card, and the card says so before the first.

**Edit** turns To, Cc and Subject (or To and Thread) into fields and the body into a text area, with the held values. From and the attachments stay as they are: From is the tool's account, and the file check compares the files the bot attached. The tag stays "Ready to send". Under the fields, on `--bg-inset`: "Your edit goes to Clawtrate's drafts plugin, for this draft only. Sending it releases Otto's email to the plugin, which swaps in your edit. The gateway then asks once more, for the edited email, and that answer lets the tool run." Buttons: "Send edited email" (primary), "Cancel edit", and Discard at the far right. Cancel edit returns to the draft as it was; nothing has been sent anywhere. What the person typed stays in the fields exactly, spaces and line breaks included, until it is taken or the card closes.

**Send edited email**, in order, each step read back before the next:

1. **The edit to the plugin**: the proposed `clawtrate-drafts.edit {approvalId, toolCallId, runId, phase: "first", expectedRevision, params}`, at `operator.approvals` (a read-only connection is refused by the gateway, research §1a). The plugin takes it only from a connection the gateway would let decide that approval: the same current approval record, reviewer-device binding and session visibility checks as `plugin.approval.resolve` (research §1b). Clawtrate then reads the record back (`get`) and goes on only if it shows that approval, phase, the next revision, and fields equal to what the person typed. While it waits: "Giving your edit to the drafts plugin…".
   - Refused, with the record saying why: "This draft was already edited on another device." or "This draft was already answered." The gateway passes the client no reason of the plugin's ("gateway request failed", research §1a), so the card says why only from the record.
   - No answer, or the read-back is missing or differs: "Couldn't confirm the edit. Check the draft's current state." with "Check the draft", which reads the record and the approval list again. A new action is offered only when that fresh read says the draft still waits.
   - In each case the typed fields are kept, so sending again after "Check the draft" sends exactly what the person typed.
2. **The first answer**: Allow once on the bot's hold, with "Sending your decision…". The plugin rechecks the files first, so a changed file ends it here, as section 3 says, before any edit is held. A refused, unanswered or already-answered decision is section 3's, with "Your edit hasn't been used."
3. **The second hold.** The card offers its Send only when Clawtrate observes a newer pending approval for the same call: a new approval id, the same call id (research §1a). Until then it reads "Waiting for the gateway to ask again for the edited email." The card becomes **Edited email**, tag "Ready to send", with the line "You edited Otto's email. These are the edited arguments the tool will receive if you allow it." The rows and body are the plugin's record of the edit, which is what the person typed, each changed field marked "Edited" in words; "Show Otto's version" opens the bot's own version beside it. Each file's line is section 3's second-hold line. Buttons: "Send edited email" (primary, Allow once on this approval) and Discard (Deny). The foot: "The gateway asks again because you edited it. This answer lets the tool run."
4. **After the second answer**, the card resolves as section 3 says, read back from the tool's result, with "You edited this before it was sent. Show Otto's version." When the tool's result says nothing of what it sent: "You edited the approved draft."

**The action card.** The bot's own action card for that call (`conversation.md` §7) shows the bot's arguments, because the gateway's events and the task's history keep the bot's call, not the edit (research §1a). Clawtrate adds one line under it from the drafts plugin's record, never from a comparison of its own: "Edited before sending: To, Subject, Body. What was sent is on the draft card." When the tool's result says nothing of what it sent: "Edited before approval: To, Subject, Body. The tool didn't report what it sent." When the record can't be read: "Clawtrate can't tell whether this was edited: it couldn't read the drafts plugin's record."

**One edit, for one approval.** The plugin takes an edit only for the approval it is holding, only in its first phase, only at the expected revision, and only once (research §1a). An edit is never moved to another call; when Otto asks again, the new draft starts from Otto's version.

**How long the record lasts.** The plugin keeps a draft's record (the bot's arguments, the edit, which fields changed, who edited and when, and the result it read back) from the hold until 24 hours after the call ends, Clawtrate's choice, so a reload or a second device can still read what happened. After that the record is gone, and a resolved card the app no longer holds reads "The drafts plugin no longer keeps this draft's record."

**Another device.** An admin device sees the draft too (research §1b). It reads the plugin's record when the plugin announces a change, and shows "Edited on another device at 5:44 PM." above the edited rows, with "Edited" marks, "Send edited email" and Discard; Edit is absent there, since the approval already has its edit.

**When an edited draft doesn't go:**

| What happens                                                                                                                            | The card                                                                                                 |
| --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Discard, on either hold                                                                                                                 | "Discarded at 5:44 PM. Nothing was sent. Your edit wasn't used."                                         |
| Either hold expires                                                                                                                     | "Expired at 5:54 PM without an answer. Nothing was sent. Your edit wasn't used."                         |
| A file changed before the second hold                                                                                                   | Section 3's "Not sent", and "Your edit wasn't used."                                                     |
| The gateway restarts while it waits, and the call's recorded refusal is "Plugin approval required (gateway unavailable)" (research §1a) | Tag "Closed", "The gateway restarted before this was sent. Nothing was sent, and your edit wasn't used." |
| The gateway restarts, and that is all the client knows                                                                                  | Tag "Closed", "The gateway restarted. Couldn't confirm whether this was sent."                           |
| The run is stopped or ends                                                                                                              | Section 3's "When the run has ended"                                                                     |

**What can't be edited**: the tool, the bot, From and the attachments. Changing those is asking Otto in the conversation; no card does it.

(F-344, F-453.)

## 5. Disable drafts for a bot

"Disable drafts for Otto" (F-182) opens a confirmation (`role="alertdialog"`):

- Title: "Send Otto's emails and messages without drafts?"
- Text: "Otto's sends through mail_send and slack_post won't wait for you. They'll go under Otto's rules: what Otto may do (open). The gateway's automatic reviewer covers commands, not sends; a send can still meet an Ask or a Never rule. This is a setting of Clawtrate's drafts plugin; it holds only while the plugin runs."
- Buttons: "Send without drafts" (primary), "Cancel".

It saves one change to the drafts plugin's proposed settings (section 12) and is announced only when the plugin's read-back agrees: "Drafts off for Otto." If the save is refused or unanswered, the setting's current value is unknown until a read succeeds: "Couldn't confirm the setting. Read it again." with "Read again". The card that offered it stays pending: turning drafts off changes later sends, not this one ("This draft is still waiting for you."). Below admin, the link is absent. Drafts are turned back on in Settings, Drafts.

## 6. Settings, Drafts

## 8. Settings, Vault

The gateway's shared secret store, shown as it is (F-261's available part). Admin only: below admin, the section is the access bar with "Seeing the Vault needs admin access. The gateway shows its secret store to admin connections only." and its request, and nothing else.

**Names, values and refresh are three separate things.** A listing gives names and settings; a value is something the person sends; and a write or a removal is followed by the gateway refreshing the settings that use the name, which can fail on its own after the store changed (research §1b). The page never lets one stand for another.

- **The host drops every environment value** before it builds anything a screen, a snapshot or a diagnostic can see. `secrets.store.list` returns an `env` entry's value (research §1b); the view model carries its name, kind and dates only.

**The list.** A note first: "Values this gateway keeps for its bots and settings. Protected values are never listed. Environment values are returned to callers that can list them, and supplied to commands." Then "New item" (default) at its right, then one row per entry (`.d-vrow`), sorted by name:

- the name in mono; its kind: "Protected" or "Environment value"; for a protected entry its hosts ("api.example.com", or "No hosts"); "Updated Nov 19".
- **Empty**: "No secrets yet. A bot can ask for one in a conversation, or add one here."
- **Loading**: three skeleton rows. **Error**: "Couldn't read the Vault." and "Try again".

**An item's page** (a Settings page with a quiet round Back):

- Facts: Name (with copy), Kind, Allowed hosts (protected only), Updated, and "Reference: store · default · STORE_API_KEY" (with copy), the SecretRef settings use.
- Where it is kept: "The gateway keeps this value in its state database on its own machine and doesn't encrypt it there."
- **How it can be used**, as a note: "Settings can use this value through its reference. The bot's Secrets tool lists the name and can remove the entry where the gateway grants it access. The gateway doesn't limit an item to chosen bots." For a protected value only, after the first sentence: "When the gateway's egress proxy is enabled, it can substitute the value in supported requests to these hosts from commands on the gateway's machine." For an environment value, also: "The bot's Secrets tool can list this value." Below it, the bots offered the Secrets tool, by name, from what each was last offered (`tools.effective`), labelled with its date.

## 9. The Secure Form, password managers, and where a bot's secrets come from

**The Secure Form** is Clawtrate's own field for a value: the field of the masked secret card (section 7) and of the Vault's dialog (section 8). It is a single-line `password` input with `autocomplete="off"`, `spellcheck="false"` and `autocapitalize="off"`; "Show" reveals the typed value until the next keystroke or blur. Paste works. Its path is section 2's.

It is not a form that fills a website's sign-in. Nothing proven puts a typed value into a site without the bot being able to read it afterwards (research §8), so Clawtrate draws no such card (section 15).

**A password manager.** What the app can say, and does, on the field's help line ("About filling this field"):

- "Clawtrate's field is its own. Electron, the framework it is built on, documents no password-manager or system fill for an app's fields, and doesn't run browser extensions such as password managers. Copy the value from your password manager and paste it." (research §6, from Electron's documentation.)
- On the iPhone this line is absent until it is researched (section 15).

**Where a bot's secrets come from.** Under the Vault's list, a fixed note, "Where a bot's secrets come from":

- "This Vault: values the gateway keeps. Protected values aren't listed to bots or to Clawtrate."
- "A password manager the gateway offers a bot, such as its 1Password plugin: the value is given to the bot, which can see it."
- "Asking you: the bot asks in the conversation, and you type it into Clawtrate's field. It's saved here."
- Then: "Nothing on the gateway makes a bot try these in an order. Each bot chooses which to use." (research §6.)

## 12. Clawtrate's drafts plugin (#89, proposed)

Everything in this section is a **proposal**: issue #89 is open and its plugin unbuilt. What was observed is the research plugin's hooks on a development gateway: a trusted tool policy holding a call with `pluginId` set; the same plugin's ordinary `before_tool_call` hook running after that answer, rechecking files and returning an edit with a second `requireApproval`; `after_tool_call` seeing what the tool received; a gateway method registered at `operator.approvals` that sees its caller's scopes and device; and state shared on `globalThis` (research §1, §1a, §1b, §3). The plugin's status, settings, `get`, mapping, revisions, invalidation event and record retention below were not built or observed; each is marked "(proposed)". Like the rules plugin, it would fail open, so nothing it does is presented as a guarantee. Written from this list, each item checked by a test or a review, with its own security review before it is installed on any gateway that is not a development gateway.

**What it must do.**

- [ ] **Know the sending tools by name** (proposed mapping). A list of tool names, each with a mapping from its arguments to To, Cc, Subject, Body, Workspace, Thread, From and files. Match on `event.toolName` alone: the hook gets no owner (observed). A destination is named only where the mapping accounts for every argument that decides it; for the gateway's `message` tool that is `target`, `targets`, `accountId`, `replyTo` and `threadId`.
- [ ] **Hold from the trusted tier** (observed). A trusted tool policy for the listed tools, declared in `contracts.trustedToolPolicies`, with the plugin explicitly enabled, returning `requireApproval` with `pluginId` set, `allowedDecisions: ["allow-once", "deny"]`, `timeoutMs: 600000`, a title of at most 80 characters and a description of at most 512.
- [ ] **Pin what is shown.** Return the arguments it saw as `params` with the hold (observed with an ordinary hold), and keep that snapshot with its revision for `get` (proposed).
- [ ] **Check files** (observed). Hash each attached file inside the bot's workspace when it holds; in its ordinary hook after the first answer, hash again and `block` with a reason naming the file and both sizes when one differs. The production file check is proposed. Hash only readable attachments confirmed to be inside the workspace, with no symlink traversal or hard-link alias. Show every other attachment as unchecked. Nothing runs between the second answer and the tool, so a file changed during the second hold is not caught; until a connector binds the approved bytes to the send or checks them as it runs, say so.
- [ ] **Take one edit per approval** (proposed contract; the binding was observed). `clawtrate-drafts.edit {approvalId, toolCallId, runId, phase, expectedRevision, params}` at `operator.approvals`. Accept it only from a connection the gateway would let decide that approval: the same current approval record, reviewer-device binding and session visibility checks as `plugin.approval.resolve` (research §1b). Refuse another approval, another phase, a stale revision, an answered hold, and a second edit. Keep only the fields the mapping marks editable. Record which device edited it.
- [ ] **Apply the edit with a second hold** (observed). In the ordinary hook, after the trusted answer and the file recheck, return the edit as `params` with a second `requireApproval`. Never return edited `params` without it: the gateway refuses them.
- [ ] **Answer reads by approval** (proposed). `clawtrate-drafts.get {approvalId, toolCallId}` returns the record with its `approvalId` and `toolCallId`, the run, the phase, the pinned arguments, the edit and who made it, the revision, the file checks and, after the call, the read-back. It follows the same rules as `edit`: the same current approval record, reviewer-device binding and session visibility checks as `plugin.approval.resolve`. Once the gateway's native approval record has expired, the retained read is admin only (proposed) until a historical authorization contract is verified; a non-admin read gets section 3's missing-record copy. Both contracts are proposed.
- [ ] **Keep the record for 24 hours after the call ends** (proposed), then drop it; report a missing record as missing, never as empty.
- [ ] **Read the tool result** (hook observed, production read-back proposed). The stand-in proves only which arguments and attachment bytes the tool received. In `after_tool_call`, record whether the tool reported success and whatever its result says it sent; never infer success from a missing error.
- [ ] **Keep state where every evaluation finds it** (observed): one object for the hook, the trusted policy, the tools and the methods.
- [ ] Methods (proposed): `clawtrate-drafts.status` (read: version, whether the trusted policy and the hook are registered, the last call it saw); `get` and `edit` (approvals, as above); `clawtrate-drafts.settings.get` (read) and `clawtrate-drafts.settings.set {bots, expectedVersion}` (admin). An empty invalidation event; readers fetch again on receipt.

**What it must never do.** Change a held call's arguments except by the person's edit through a second hold; carry an edit to another approval; send anything itself; read or keep a file's content beyond its hash and size; carry recipients, subjects, bodies or paths in an event a broader audience can read; ask about any tool not on its list; make a standing permission from an answer.

**What it leaves to others, and what stays proposed.** Whether a bot may send at all is the bot's rules (`controls.md`). How the drafts plugin's trusted hold and the rules plugin's ordinary ask (#31) combine for one call — which runs first, and whether a send asks twice — is proposed until the two plugins are checked together on one gateway.

### A masked value: what replaces today's path

Today's question path keeps one copy in shared transcript state and exposes it through the web host's snapshots and Raw.

- `packages/core/src/client.ts`, `resolveQuestion`: it writes `sent: { method: "question.resolve", params }` into the question card before it sends, so the outgoing answers sit in transcript state. A masked answer uses its own command instead, whose value is passed straight to the request and never stored; the card's sent record holds the method, the question id and the hosts only.
- `apps/desktop/src/web-host/server.ts`: each viewer's snapshot carries the open transcripts as they are, so a second viewer of the task would receive whatever the card holds. With the masked command nothing is there to carry; the snapshot code needs no exception.
- `packages/ui/src/cards/QuestionCard.tsx`: Raw shows `card.sent`. It shows the method, the question id, the hosts and the returned record, with "(not kept by Clawtrate)" where a value would be.

The same applies to `secrets.store.set` for New item and Replace. For both a masked answer and a Vault set, hold the fake gateway's reply open. While the request is in flight, assert the fake gateway received the marker exactly once. Inspect the core store, the originating and second viewers' next snapshots for the open task, and opened Raw. Repeat the absence assertions after success, refusal, timeout and reload, including the visible fault and host log. Feed a different marker in an environment entry from the fake gateway's list and assert its absence from the core store, both snapshots, Raw and diagnostics.

### What the engine supplies

- For a plugin approval whose `request.pluginId` is the drafts plugin: the plugin's record by approval id and call id (proposed), the tool's mapping, and after the call its read-back; the approval itself as `conversation.md` section 22 already supplies it; the run's terminal state.
- For a question record with `isSecret`: the record, a fresh `question.get` after any error, and the call's result once it arrives (`currentPolicy`); never the value.
- The Vault: `secrets.store.list` on open and after every write, with each write's answer and its read-back kept apart, and every `env` value dropped before a view model; the settings that refer to a name, from `config.get`, read again before a removal is confirmed; the bots offered `secrets`, from `tools.effective` with its date.
- The drafts plugin's state, read on connect, on its invalidation event and every 60 seconds while a page that shows it is open (proposed).

## 15. Not covered here

- Connectors and their accounts (#85): which email and Slack tools exist, which account a send comes from, how their arguments map to a draft's rows, and which attachment bytes they send. This design needs from each a tool name and that mapping, and reads its result for what it sent.
- The approval and question cards themselves (`conversation.md` §12, §13), the rules and the Permissions page (`controls.md`), a bot's settings (`bots.md`): used as they are.
- Routines and check-ins, and links into the app: other designs. A routine's send can't wait for anyone (`controls.md` section 3, "When nobody can be asked"); what a draft does there is the routines design's.
- The iPhone's own permission requests, and whether the iPhone's AutoFill reaches the Secure Form: not researched, and the iOS app is not on `main`.

Not designed, because nothing proven supports them, each waiting for a capability the gateway doesn't have; their rows keep their targets:

- **A Secure Form that signs in to a website**, and saving a value for one use only: waits for a fill the bot cannot read back (F-183, F-346).
- **Editing the tool, the bot, From or the attachments of a draft**: the second hold applies changes to that call's own fields only.
- **A Vault item limited to chosen bots**, and an order among the store, a password manager and asking: wait for a bot-scoped store and an enforced order (F-261, F-338).
- **Logins, cards and contact details** as Vault kinds: the store keeps names and values only.
- **A file bound to its approval**: a check of attached files as the tool runs waits for a connector that binds or rechecks the approved bytes (F-341).
