# The model list: where it comes from and how it gets newer

Why a bot's Model menu can miss models a provider already offers, checked against OpenClaw 2026.10.6, the version `docs/decisions.md` names, and against OpenClaw 2026.11.6, the newest release on npm when this was written. It is the evidence behind parity rows F-478, F-533 and F-534 and the Model menu of `docs/design/bots.md` section 9.

How to read the citations, as in `steer-stop.md`:

- `<openclaw>/…` is a path inside the installed `openclaw` 2026.10.6 npm package, and `<openclaw-11.6>/…` one inside the 2026.11.6 package, unpacked with `npm pack openclaw@2026.11.6` and never installed. Bundled chunk names change with every release; search by the `//#region <source path>` marker given with each citation. Line numbers are of the 2026.10.6 chunks.
- `<protocol>` is `@openclaw/gateway-protocol` 2026.10.6, `dist/catalog-WA519PXd.mjs`.
- **Live** means it was run on a development instance, and the output is quoted. **Source** means it was read in shipped code or documentation only.

Where it was run: a named instance, `pnpm dev-gateway start --instance models --with-accounts --no-seed`, with the scripted providers `acme` and `globex`. The probe is [`dev-gateway/models/probe.mjs`](dev-gateway/models/probe.mjs). The instance was reset when the work ended. No real provider was used, so nothing here was checked against a real ChatGPT account.

## 1. Where Clawtrate's list came from

As found on `main` at `ba6f10fe`:

- The accounts engine read the catalogue once per refresh: `ctx.request("models.list", { agentId: defaultBot })`, with no `view` (`packages/core/src/accounts-engine.ts` lines 226-228).
- `readCatalog` kept at most `MAX_CATALOG_MODELS` rows, 128, across every provider (`packages/core/src/accounts.ts` lines 22-23 and 659). The gateway orders providers by id, so a provider late in the alphabet could lose rows on a gateway with many providers.
- The menu showed `modelsOf(accounts, provider)`, the rows of the bot's provider, in the gateway's order (`packages/ui/src/bots/words.ts` lines 268-270; `packages/ui/src/bots/ModelPair.tsx`).

Nothing else sorted or filtered the rows.

## 2. The gateway's views

### Source

`ModelsListParams` takes `agentId`, `sessionKey`, `authProfileId`, `provider`, `includeDetails`, `preparedOnly`, `refresh` and `view: "default" | "configured" | "provider-config" | "all"` (`<protocol>` lines 1355-1383). All of them are one method at `operator.read` (`docs/decisions.md`, "Read-only flows").

`prepareLogicalVisibleModelCatalog` (`<openclaw>/dist/model-catalog-visibility-Cpi0Jvw4.mjs`, region `src/agents/model-catalog-visibility.ts`):

- `view: "all"` takes every catalogue entry (line 67) and publishes it after ordering (line 133). The selection policies are skipped for it (`<openclaw>/dist/models-list-result-Dx7spcW4.mjs` line 686, region `src/gateway/server-methods/models-list-result.ts`). The operator role's own model policy still applies afterwards, in the handler (`<openclaw>/dist/models-qLzDNS0G.mjs` lines 104-108, region `src/gateway/server-methods/models.ts`).
- Any other view keeps the configured and allowed rows (lines 134-139), then drops a route-managed row unless it is configured or the account backs it (lines 156-160), and drops `deprecated` and `disabled` rows unless configured (lines 166-169). OpenAI's rows are route-managed (`routePolicy: openAIModelCatalogRoutePolicy`, `models-list-result` line 705).
- A configured row is one a provider entry in `models.providers` declares, or one named by the default model, the fallbacks or an allowlist (`agents.defaults.models`, `agents.<id>.models`) (`<openclaw>/dist/model-visibility-policy-HwJqwXi4.mjs` lines 14-29; `<openclaw>/dist/model-selection-shared-PnWvZr7n.mjs` line 626).

The order: "Provider catalogs declare models strongest-first. Preserve that owner order" (`<openclaw>/dist/model-catalog-order-CjmCH0dm.mjs` lines 6-9), with a provider's hosted `recommendedModels` first and the session's selected model before everything (lines 71-90). A row the hosted catalogue recommends carries `recommended: true` (`<protocol>` `ModelChoiceSchema`, lines 1435-1457). No field of a row gives a release date, so nothing a client receives says which model is newest; the picker and `view: "all"` share this one ordering (`model-catalog-visibility` line 131).

One answer holds the whole list: `ModelsListResultSchema` has `models`, the markers `refreshFailed`, `pendingProviders` and `providerOutcomes`, and no cursor (`<protocol>` lines 1458-1514), and `ModelsListParams` takes no page (lines 1355-1383). A client that keeps fewer rows than the gateway sends can only say so. An answer that carries `pendingProviders` naming the provider, or `refreshFailed`, is the rows the gateway had so far: Clawtrate shows them, says the list may not be complete, offers to ask again, and says the gateway lists no more models only after a complete answer. The full list is read each time "View more" is opened and held by that dialog alone, so nothing of it can outlive a gateway upgrade, a reconnect or another gateway.

The gateway's own documentation names `view: "all"` as the full list: "Use the Models page **Refresh** action (`models.list` with `view: "all"` and `refresh: true`) to publish the full catalog for the selected agent" (`<openclaw>/docs/plugins/codex-harness-reference/model-discovery.md`).

### Live

The scripted providers are declared in `models.providers`, so every one of their rows is configured, and the default view and `view: "all"` agree on a development instance, with an allowlist naming `acme/dev-1` alone as well. `provider` narrows `view: "all"` to that provider:

```
## models.list {agentId} (no allowlist)
[ "scripted/dev-1", "acme/dev-1", "acme/dev-2", "globex/dev-1" ]
## models.list {agentId, view:all, provider:acme}
[ "acme/dev-1", "acme/dev-2" ]
ok   with configured providers, the default view equals view:all
```

What the default view drops (an OpenAI row the account does not back, or one outside an allowlist) cannot be shown with the scripted providers.

### Live: the picker asked alongside other reads

On the end-to-end checks' development instance, `models.list {agentId}` sent while the same client's `config.get`, `users.prefs.get` and `models.authStatus` reads were still in flight was refused, twice, with `Chat metadata access changed while preparing its metadata. Retry the request.` Asked once those had answered, it was answered. So the account read asks for the picker last.

## 2a. Whose availability a read gives

### Source

- `models.list {agentId}` with no session resolves that agent's catalogue with automatic account selection: "`models.list {agentId}` listed every configured provider's models for every bot, all `available:true`, with `accountSelection: {kind:"automatic"}`" (`provider-accounts-and-t3-code.md` A.6, probe). A bot bound to one account (`<provider>/<model>@<account>`) reaches the projection only through a session (same section).
- `models.list {sessionKey}` projects the session's selected account into the catalogue (`resolveSessionCatalogProfiles`, `<openclaw>/dist/chat-metadata-session-projection-DuoPBWYl.mjs` lines 173-187; `prepareSelectedAccountCatalog`, `models-list-result` lines 446-474), also for `view: "all"`: the handler projects every view but `provider-config` (`<openclaw>/dist/models-qLzDNS0G.mjs` lines 98-103).
- `models.list {authProfileId}` selects a personal account only (A.6), so there is no read for a shared account a bot isn't on yet, such as the one chosen in New bot.

- Each answer names the account it was read for: `accountSelection` is `{kind: "automatic"}`, or `{kind: "personal" | "shared", authProfileId}` (`<protocol>` `ChatAccountSelectionSchema`, lines 1334-1353, "Configured preference only; provider failover can use a different account"), filled from the session's selection or the requester's (`models-list-result` lines 522-526). On a development instance a read for a bot answered `accountSelection` alongside `models` (probe, "result keys").

So a row's `available` is the gateway's verdict for the account its read was for, and nothing more. The Model menu keeps the picker's verdicts as they were before this work, the default bot's shown for every account (#407), and puts none on the full list's rows behind "View more": those say the provider decides. The OpenClaw documentation for Codex says the same of listings in general: "Listing does not prove account entitlement" (`<openclaw>/docs/plugins/codex-harness-reference/model-discovery.md`).

## 3. OpenAI's models in 2026.10.6

### Source

- The OpenAI plugin's manifest lists, in order, `gpt-daybreak-blue-latest`, `gpt-daybreak-red-latest`, `gpt-6-astra`, `gpt-6.1-sol`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5` and `gpt-5.5-pro` (both `deprecated`), and the `gpt-5.4` family (`<openclaw>/dist/extensions/openai/openclaw.plugin.json` lines 74-616). No `gpt-6.2-*` and no `gpt-6.1-terra`.
- A ChatGPT sign-in's models come from Codex: "By default, the Codex plugin asks the app-server for available models. Model availability is owned by Codex app-server, so the list can change when OpenClaw upgrades the bundled `@openai/codex` version" (`<openclaw>/docs/plugins/codex-harness-reference/model-discovery.md`). The bundled harness is `@openai/codex` 0.160.0, whose unauthenticated `model/list` the same page quotes: `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`. "Authenticated catalogs can differ."
- So a `gpt-6.1-terra` in a menu came from the account's Codex discovery, not the manifest.

## 5. A model id the catalogue doesn't list

### Live

`acme/dev-9` is in no catalogue. With an allowlist naming `acme/dev-1` only:

```
{ "ok": true, "agentId": "unlisted", ..., "model": "acme/dev-9@acme:work" }

ok   the bot's own unlisted model is not in its catalogue
## run on the unlisted model: terminal

## scripted model's record for that session
[ { "account": "acme:work", "credential": "api_key", "model": "dev-9", "session": "agent:unlisted:probe", "status": 200 } ]

## sessions.patch {model: acme/dev-9}
{ "ok": true, ... }
```

The gateway passed the id to the provider, which decides. The scripted model answers any id; what a real provider, or Codex in front of OpenAI, does with an id it doesn't serve was not observed.

### Source

For Codex: "Catalog membership does not reject arbitrary model overrides" (`<openclaw>/docs/plugins/codex-harness-reference/model-discovery.md`). Whether ChatGPT serves a model to an older Codex is ChatGPT's decision (section 4).

## 6. A model newer than the gateway's list

### Source

- A ChatGPT sign-in's list is the one Codex's app-server gives the gateway, and it follows the Codex build that runs turns: "ChatGPT-login model discovery reports the selected binary's version as its `client_version`, so the list matches the binary that runs turns" (`<openclaw-11.6>/docs/plugins/codex-harness-reference/model-discovery.md`; section 4).
- The gateway takes an id its catalogue doesn't list and passes it to the provider (section 5): "Catalog membership does not reject arbitrary model overrides" (`<openclaw>/docs/plugins/codex-harness-reference/model-discovery.md`).
- No gateway method reports the Codex version the gateway runs, or the version a model needs (section 7).

So Clawtrate shows the gateway's own lists and keeps no model list of its own: that would be Clawtrate saying what the gateway hasn't established.

## 7. Update signals

### Source

- `hello-ok` `snapshot.updateAvailable` is `{currentVersion, latestVersion, channel}` when the gateway's last update check found a newer OpenClaw, for any connection (`<openclaw>/dist/health-state-DDhO15ZI.mjs` lines 57-82, region `src/gateway/server/health-state.ts`; `<openclaw>/dist/events-ds0bML-H.mjs` lines 17-24). It is set from the check's saved state only when the latest version is newer than the running one (`<openclaw>/dist/update-startup-CW6kDiwm.mjs` lines 235-246, region `src/infra/update-startup.ts`).
- The `update.available` event carries `{updateAvailable}` when that changes, with no scope required (`<openclaw>/dist/server-start-D6vaUNGz.mjs` line 4299; `<openclaw>/dist/server-startup-post-attach-CAUsg7sV.mjs` lines 576-583, region `src/gateway/server-startup-update-check.ts`).
- `update.status` (`operator.admin`, `<openclaw>/dist/core-method-policy-DkntKRY_.mjs` lines 1132-1136) answers `{sentinel, updateAvailable, effectiveChannel, schedule, activeRun?, lastRun?}` (`<openclaw>/dist/update-DdfLxzzM.mjs` lines 792-799, region `src/gateway/server-methods/update-status.ts`).
- The command the gateway's documentation gives is `openclaw update` on the gateway's machine (`<openclaw>/docs/cli/update.md`). It is not every install's step: "For Docker, Podman, and Kubernetes image replacements, see Upgrading container images", and an app-owned package is updated through its app (`<openclaw>/docs/install/updating.md`, the opening section). So Clawtrate links to that page and names no command. It restarts the gateway by default: `--no-restart` is the option that skips "the updater's managed restart", and the interactive flow asks "whether to restart the Gateway afterward (defaults to restart)" (same page, the options table and "wizard"). A restart's drain "can interrupt ordinary work" once its budget runs out (same page, "--drain-timeout").
- The report's `channel` is the npm tag of the gateway's update channel: `latest` for stable, or `beta`, `dev`, `extended-stable` (`channelToNpmTag`, `<openclaw>/dist/update-channels-BLoHtGj7.mjs` lines 36-38; `update-startup` lines 241-245).
- `update.run` (`operator.admin`, a control-plane write; `<openclaw>/dist/core-method-policy-DkntKRY_.mjs` lines 1138-1143) takes only optional fields and answers `{runId, ok, result, message?, handoff?, ...}` (`<openclaw>/dist/sessions-B6HQw2nf.mjs` lines 1209-1221, 1425-1445). A Git checkout or a global npm, pnpm or bun install with a service manager, or a verified foreground gateway, hands the update to a detached updater and answers `ok: true`, `result.reason: "managed-service-handoff-started"`; any other install finishes the run at once as `skipped` or `failed` with a reason code such as `unmanaged-package-install`, `container-image-install`, `external-supervisor-update-required`, `restart-unavailable` or `managed-service-handoff-already-running`, and a host-owned or immutable install is refused with an error and no run (`<openclaw>/dist/update-DdfLxzzM.mjs` lines 283-352, 895-1314, region `src/gateway/server-methods/update.ts`). `update.status` says ahead of time only for an immutable install (`schedule.install.kind`) or through its `lastRun`.
- The run lives in the gateway's state database, so its id survives the restart. Each gateway process watches the active run every 2 s and sends `update.run.changed {runId, phase, status, updatedAtMs}` to admin connections; `update.runs.get {runId}` answers the record, or `{run: null}`, and `update.status` answers `activeRun` while one runs, whoever started it (`<openclaw>/dist/update-run-watcher-_KYgnzFk.mjs` lines 17-120; `sessions-B6HQw2nf.mjs` lines 1000-1207). Phases are `requested, staging, validating, repairing, activating, restarting, verifying, finished`; statuses `running, succeeded, failed, rolled-back, skipped` (`<openclaw>/dist/update-run-vocabulary-BuT3Q1bJ.mjs`).
- Before it replaces its code, the gateway stops admitting new work and waits for running work, within an outer bound the source sets. On Linux the updater drains through `gateway.suspend.prepare` until the gateway is idle or its step deadline passes: 30 minutes by default, 45 when the press takes over the gateway's own scheduled update (`trigger: "campaign"`) (`<openclaw>/dist/update-command-service-maintenance-CZYSQl3D.mjs` lines 717-724; `<openclaw>/dist/update-command-service-drain-CDNkVKq6.mjs` line 19; `<openclaw>/dist/update-run-timeouts-Byb-PlTk.mjs` line 4). Elsewhere the service stop uses the gateway's 325 s shutdown budget (`<openclaw>/dist/gateway-shutdown-budget-Ba5tqRyN.mjs` line 5). The 300 s `restartDrainTimeoutMs` in `update.run` is only the helper's wait for the old process to exit. The real runs below never came near those bounds. Under systemd, a turn in flight was drained for 20 s, then stopped and not picked up again, and the whole update took about 3.5 to 10 minutes. Clawtrate's confirmation says what the real runs showed, and the source's numbers are its outer bound.
- For models, `models.list` answers `refreshFailed: true` when the catalogue's last refresh failed and `pendingProviders` while a provider's discovery is still running (`models-list-result` lines 530-535). No field names the Codex version or which models a newer one would add.

### Live: a real update through `update.run`

The [OpenClaw update](../../.github/workflows/openclaw-update.yml) workflow ran a real update on GitHub-hosted Ubuntu runners: OpenClaw 2026.10.6 installed globally with npm, updated to 2026.11.10, npm's `latest` that day. The press came from an admin operator, as Clawtrate's does. The first four runs sent `update.run {}`. From the fifth on, the press sent Clawtrate's current request, `{requester: {channel: "webchat", senderId: "clawtrate-update:<id>"}}`, and some jobs sent the same press without the requester, to compare them. Runs: [1](https://github.com/sidebandstudio/clawtrate/actions/runs/45583975603) (both updates succeeded; the check misread its own record), [2](https://github.com/sidebandstudio/clawtrate/actions/runs/45585663422), [3](https://github.com/sidebandstudio/clawtrate/actions/runs/45587059859), [4](https://github.com/sidebandstudio/clawtrate/actions/runs/45590298865), [5](https://github.com/sidebandstudio/clawtrate/actions/runs/45593099501), [6](https://github.com/sidebandstudio/clawtrate/actions/runs/45595832650), [7](https://github.com/sidebandstudio/clawtrate/actions/runs/45597864415), [8](https://github.com/sidebandstudio/clawtrate/actions/runs/45599783119). The table's times are seconds after `update.run` was sent, from the third run.

| Case                                    | Handoff answer | Validating starts | Activating starts | Connection drops | New gateway starts | Reconnect | Finished |
| --------------------------------------- | -------------- | ----------------- | ----------------- | ---------------- | ------------------ | --------- | -------- |
| systemd user service, idle              | 1.6            | 31.7              | 218.2             | 254.6            | 386.5              | 396.2     | 409.5    |
| systemd, a chat turn in flight          | 1.6            | 27.7              | 183.0             | 234.5            | 355.1              | 372.7     | 376.4    |
| foreground process, idle                | 2.7            | 38.3              | not seen          | 237.7            | 359.8              | 380.9     | 383.0    |

- **The handoff.** For a global npm install, under a systemd user service (`openclaw gateway install`) and as a foreground `openclaw gateway run`, `update.run` answered `ok: true`, `result.reason: "managed-service-handoff-started"`, `handoff.status: "started"` and a UUID `runId`, in 0.9 to 3.7 s. `update.status` reported `schedule.install.kind: "package"`, `effectiveChannel: "stable"`, and `updateAvailable.latestVersion` 2026.11.10 about 13 s after the gateway started. The helper staged with `npm i -g --prefix <global root>/.openclaw.update-stage-… openclaw@2026.11.10` (18 s).
- **Phases.** `requested` (18 to 39 s), `validating` (103 to 187 s idle on systemd: candidate doctor, a candidate gateway start), `activating`, `verifying` and `finished`/`succeeded`. `update.run.changed` arrived on every phase change and also many times within a phase, whenever the record changed, so an event's phase is often not new. On the foreground gateway, `activating` and `verifying` were never seen: the old process stops during `activating`, and the run was finished by the first read after the reconnect.
- **Before the drop.** `update.run.changed` arrived before the connection dropped in every case, `activating` included on systemd. The gateway sent `shutdown` (`"gateway stopping"` on systemd, `"gateway restarting"` with `restartExpectedMs: 1500` in the foreground) and closed with 1012 or 1006.
- **The restart.** The gateway was gone for 71 to 150 s (the drop until the new process started, from the new `hello-ok` `snapshot.uptimeMs`). In that time the helper swapped the package and ran `openclaw doctor` (42 to 51 s) and its verification. The client's own reconnect added 7 to 36 s.
- **After the reconnect.** On systemd, the first `update.status` listed the run as `activeRun` in phase `verifying`, and `finished`/`succeeded` followed 4 to 13 s later. In the foreground the run was already finished. `update.runs.get` never answered `UNAVAILABLE` in any run: the first read after each reconnect answered the record.

The record's `verification.noticeDelivered` was `true` in some of these runs and `false` in others, so it does not say whether the message was posted. In two jobs out of about 75, the restarted gateway also ran two turns of its own in the main session, about 27 s after it started, from its scheduler (`taskKind=cron`, `source=cron`). At startup it had started its heartbeat and a memory upkeep job. One was a tagged foreground press in the fifth run, the other an untagged systemd press in a [later run](https://github.com/sidebandstudio/clawtrate/actions/runs/45610763205), so the requester does not cause them. - **How long it takes.** From the press to `succeeded`: 207 to 409 s idle, 300 to 469 s on systemd with a turn in flight, and 579 to 618 s with a turn the foreground gateway waited for. The connection was down for 87 to 178 s whenever the gateway came back. A job that updated, with its installs, took 5 to 13 minutes. These figures cover all eight runs.
- **First macOS evidence (one real install).** A real update of a gateway run by launchd succeeded. Its drain budget before the stop was 5,000 ms, against 20,000 ms on Linux. ## 8. Refresh: asking the gateway to look again

Checked against the 2026.10.6 package and on a named development instance with the scripted providers, with an admin and a read-only connection.

### Source

- `models.list` with `refresh: true` skips the prepared answer and, before answering, runs the catalogue's discovery again (`loadDeferredCatalog` with `refreshFullCatalog`), for `provider` alone when it is given (`providerDiscoveryProviderIds`) (`<openclaw>/dist/models-list-result-Dx7spcW4.mjs` lines 277-290; handler `<openclaw>/dist/models-qLzDNS0G.mjs`). It works with any `view`, and takes read access like every `models.list`. After answering, it re-applies the copy of OpenClaw's hosted model list that the gateway already downloaded (`applyRemoteModelCatalogUpdate`; `readRemoteModelCatalogAsync` reads the gateway's state database, `<openclaw>/dist/remote-store-BmbsqXiC.mjs` lines 16-28): no request leaves the gateway.
- The gateway downloads that hosted list (`https://catalog.openclaw.ai/models/v2/catalog.json`) at start and every 6 hours, unless `models.catalogRefresh.enabled` is false (`update.remote-model-catalog`, `<openclaw>/dist/update-startup-CW6kDiwm.mjs` lines 607-622; `<openclaw>/dist/remote-overlay-Bpv95iW5.mjs` lines 288-291). A hosted list newer than the build, within its `minVersion`, replaces a provider's list that comes with OpenClaw (`source: "runtime-refresh"`, `<openclaw>/dist/manifest-planner-DVQg3qlB.mjs` lines 27-60). So a list that comes with OpenClaw gets newer models from a newer OpenClaw and from that download, not only from an update. A refresh doesn't fetch it.
- Asked again are only the providers whose plugin discovers its list live and has a credential to ask with (`runLiveProviderCatalog`, `<openclaw>/dist/provider-catalog-live-runtime-BgJMvSyc.mjs` lines 329-356); OpenRouter, for example, asks nothing without a key (`<openclaw>/dist/extensions/openrouter/index.js` lines 240-243). A plugin's static list and the models `models.providers` declares are not asked: they change with a newer OpenClaw or plugin, or the config. A ChatGPT sign-in's list comes from the bundled Codex app-server (section 3).
- Each provider asked gets an entry in `providerOutcomes`: `{provider, profileId?, status}`, with `ready`, `auth-rejected` (its discovery got HTTP 401 or 403) or `unavailable` (any other failure, a timeout included). No reason text reaches the client (`<protocol>` lines 1449-1457). Discovery waits up to 5 seconds per paged list (`timeoutMs ?? 5e3`), 15 for an upstream provider catalogue, and 10 for Codex (`model-discovery.md`).
- No row and no field says that a provider's list comes with OpenClaw: `ModelChoiceSchema` has no origin. A provider with rows and no outcome was not asked again; its list is OpenClaw's or a plugin's, the config's, or one the gateway had no credential to ask for.
- With `models.mode: "replace"`, as on a development instance, the gateway resolves no plugin provider at all (`<openclaw>/dist/models-config-FpTGoQoq.mjs` line 289), so a refresh there asks no one. In the default merge mode a provider's models declared in `models.providers` are listed before OpenClaw's and plugins' own, which stay (`mergeProviderModels`, `<openclaw>/dist/models-config.merge-QDUUWnKY.mjs` lines 41-119): the config's list is the whole list only when every model listed is one it declares.
- The models a bot may use come from one list, resolved in this order (`resolveConfiguredModelPolicyAllow`, `<openclaw>/dist/model-selection-shared-PnWvZr7n.mjs` lines 886-918): the bot's own `agents.entries.<id>.modelPolicy.allow` when its policy has an `allow`; else `agents.defaults.modelPolicy.allow`; else the old `agents.defaults.models`, but only while there is no `agents.defaults.modelPolicy` and the config has no `meta.migrations.modelPolicyAllowlist` marker (`computeModelPolicyAllowlist`, `<openclaw>/dist/agent-scope-config-CtLA1__T.mjs` lines 64-81). Every config write OpenClaw makes sets the marker and moves an old list into `modelPolicy.allow` (`materializeModelPolicyAllowlist`, same file lines 83-120; `<openclaw>/dist/io.meta-C_ryXAjc.mjs` line 47). An empty list limits nothing. `<provider>/*` allows a provider whole; `*` and `*/*` are not wildcards. 2026.11.10 resolves it the same way (`resolveConfiguredModelPolicyAllow`, `computeModelPolicyAllowlist`). What the list then limits, run on a development instance of each version with `agents.defaults.modelPolicy.allow: ["acme/dev-1"]` (below), is the picker and a task's switch, not a bot's own model or the default, as long as the list has no wildcard. `resolveSelection` keeps a configured model the list doesn't name only when the list has exact names and no wildcard entry (`<openclaw>/dist/model-selection-shared-PnWvZr7n.mjs`, `resolveSelection`, `configuredDefault`; 2026.11.10 the same). What a wildcard is differs by version. 2026.10.6 (`parseModelPolicyWildcardRef`, `<openclaw>/dist/agent-scope-config-CtLA1__T.mjs` line 26) reads one whose last segment, trimmed, is `*` after at least one valid segment, and matches at a segment's end (`isModelKeyAllowedBySet`, `model-selection-shared-PnWvZr7n.mjs` line 945): `globex/*` and `openrouter/anthropic/*` are wildcards, `*`, `*/*` and `acme/dev-*` aren't, and its config check refuses `acme/dev-*` ("invalid model policy ref"). 2026.11.10 (`parseModelPolicyWildcardRef`, `<openclaw>/dist/model-policy-allowlist-migration-BDJYmlL9.mjs` line 3) also reads an entry that ends in `*` after a prefix of its last segment, such as `acme/dev-*`, and matches it by prefix (`modelPolicyWildcardMatches`: the model's reference starts with the entry less its `*`; `isModelKeyAllowedBySet`, `model-selection-shared-PDwe2GYm.mjs` line 13). Both trim segments, so `openai/ *` and `openai / *` allow OpenAI whole on both. So the menu reads wildcards by the version the gateway reports. With one anywhere in the list, a bot's own model and the default that it doesn't name run on the first model the list allows. The source's refusals are for a run's explicit override and a task's stored choice: "Model override … is not allowed for agent …" (`<openclaw>/dist/agent-command-DFdm3k6d.mjs` lines 2222-2231) and "… reverted to …" (`<openclaw>/dist/get-reply-wuu1XOh_.mjs` lines 751-756). So a model a newer OpenClaw or the hosted list adds stays out of the picker, and out of a task's switch, until the list names it or `<provider>/*`; a bot's own model can be set to it, and runs on it only while the list has no wildcard.

## What follows for Clawtrate

- Show the gateway's picker as the menu did before, its unavailable models disabled. Behind "View more", read the provider's full list (`view: "all"`) when it is opened, and show the models the picker lacks in the gateway's order, never called newest first, with no availability verdict. Say when it is loading, failed or longer than kept, and offer no "View more" on a gateway that refuses `view: "all"` (F-478).
- Ask for the picker after the account reads, never alongside them: the gateway refuses it while they prepare the bots' metadata.
- Let a person type a model id the catalogue doesn't list, and leave the decision to the provider (F-533).
- When the gateway reports `updateAvailable`, say near the Model menu that a newer OpenClaw is out, with the channel when it isn't stable, and link to OpenClaw's own update instructions rather than name a command: `openclaw update` skips container installs (`<openclaw>/docs/install/updating.md`) (F-534).
- Offer "Update OpenClaw" in Settings › Updates, with one line and a link there from where Clawtrate says a newer OpenClaw is out and from Settings › Gateway (#590): one confirmation, then `update.run` bound to the gateway shown, its run followed across the restart, and "updated" said only when the record says succeeded and the same gateway reports the new version (F-589). The confirmation says what the real runs below showed: an update usually takes 5 to 15 minutes, some installs take longer, bots can't be reached for part of it, and work running at the restart is stopped and may not be picked up again. It promises nothing about what runs after the restart. The press carries a tag as its requester on the gateway's internal channel (`webchat`), which the run record keeps (`origin.requester`) and the updater ignores (`<openclaw>/dist/update-managed-service-handoff-DwoAWYgB.mjs` line 2277). A press whose answer is lost is matched to its run by that record, and where nothing carries the tag, Clawtrate says it can't tell. A gateway away longer than 10 minutes, past the longest absence measured on Linux (150 s) and macOS (about 6 minutes), is said to be taking longer than usual, and one started by hand may need starting again. `update.status` is asked only when Settings › Updates or the confirmation opens, or when something needs settling, never on each connect. A real `update.run` was not run from this machine: its source does not show that every write stays inside a scratch folder. The runs below were made on throwaway hosted runners.
- For OpenAI's newest models on a ChatGPT sign-in: update OpenClaw to 2026.11.6 or newer and keep a current `codex` on the gateway's `PATH`. That is what the documentation establishes; it was not run against a real account.
