# Connect on this Windows computer: what can be proved

Issue #655 asks for one-click Connect to OpenClaw on the same Windows computer, with a design first for a gateway inside WSL and for one run by a Scheduled Task. The decision here: one-click Connect stays off on Windows. A gateway that runs natively gets it only once the acceptance checks below pass and the product owner accepts what remains. A gateway inside WSL stays on the address-and-token form.

Written 2026-11-26 from sources only, and checked again on 2026-11-27 against `ac6d2cb3`, the head of #930. The one measurement is the start-time probe of 2026-11-27 under "A native gateway". No OpenClaw program, gateway, task or WSL distribution was started, and no profile was read. Installing OpenClaw into private folders and the shape of its Scheduled Task are in §6.6 of `../setup-flow.md` on the unmerged branch `research/windows-private-openclaw`. Secure storage on Windows is #654.

How to read the citations, each linked to its file and lines:

- `openclaw@<tag>:<path>` is `github.com/openclaw/openclaw` at that tag. Clawtrate pins 2026.10.6 (`apps/desktop/src/setup/openclaw-pins.ts`).
- `hub@8d31176d:<path>` is OpenClaw's Windows Hub, `github.com/openclaw/openclaw-windows-node`, at commit `8d31176d3ad4`, its `main` on 2026-11-26.
- `wsl@f753835d:<path>` is `github.com/microsoft/WSL` at commit `f753835d5464`.

## What Windows does today

At `ac6d2cb3`, every step refuses before it reads or sends anything:

- The look answers `windows` before any program runs (`apps/desktop/src/setup/look.ts` line 255).
- The settings reader refuses before it resolves or opens a home (`apps/desktop/src/setup/settings-reader.ts` line 275).
- The proof refuses with `platform` before the home guard or the helper (`apps/desktop/src/setup/local-prove.ts` line 148).
- No shipped host turns local connect on. `LOCAL_CONNECT` in `apps/desktop/src/main/index.ts` is set only on macOS. Windows keeps no credentials in secure storage (`usesSecureStorage` in `apps/desktop/src/main/secret-box.ts`), so a first pairing asks for read only.

So a person types an address and a token. Two tests hold these refusals. CI's Windows job runs "reads nothing on Windows, and looks up, resolves and opens no home first" in `apps/desktop/test/settings-reader.test.ts`. "on Windows the proof refuses before it looks at a home or a helper, and the socket carries no byte" in `apps/desktop/test/local-connect.test.ts` sends a real socket through `provedRouteFor` to a listener of the test's own. It counts the bytes that arrive before the connection closes, and checks that `verify`, run just before the frame that carries a credential, refuses too. It passes `platform: "win32"` to the proof, so CI's Linux and macOS jobs run it too. The Windows job's step "Check the settings reader and the local proof on Windows" selects it by name as well.

## A native gateway

On macOS the proof checks the exact connection Clawtrate opened: who holds its server end, and that the holder matches this account's OpenClaw profile (`docs/design/setup-effortless.md` §3, "The send gate"). That doesn't establish which program is running (`docs/decisions.md`, "Local connect's proof"). On Windows, part of it can be read whichever way the gateway was started:

- The TCP connection table names, for this connection, the process that issued its context bind ([`MIB_TCPROW_OWNER_PID`](https://learn.microsoft.com/en-us/windows/win32/api/tcpmib/ns-tcpmib-mib_tcprow_owner_pid)). That is one process, the one that bound the socket, not a list of every process that may hold it.
- That process's token gives its account by SID. Reading the token of another account's process needs a debug privilege ([`OpenProcessToken`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocesstoken)).
- Its creation time comes as a FILETIME, a count of 100-nanosecond intervals since 1 January 1601 ([`GetProcessTimes`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)).
- OpenClaw's compatibility lock is `tmp/openclaw/gateway.state.lock` in the profile on Windows, which has no `process.getuid` ([`openclaw@v2026.10.6:src/config/paths.ts` lines 311-318](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/config/paths.ts#L311-L318), [`src/infra/gateway-lock.ts` line 284](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/infra/gateway-lock.ts#L284)). Its payload has `pid`, `port`, `role`, `stateDir` and an optional `startTime` ([`openclaw@v2026.10.6:src/infra/gateway-lock-payload.ts` lines 143-158](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/infra/gateway-lock-payload.ts#L143-L158)).

**The lock's start time is Unix epoch milliseconds when it is there.** The gateway reads its own start when it writes the lock ([`gateway-lock.ts` lines 466-474](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/infra/gateway-lock.ts#L466-L474)), on Windows through `readWindowsProcessStartTimeSync` ([`src/shared/pid-alive.ts` lines 316-317](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/shared/pid-alive.ts#L316-L317)), and records `startTime` only when that returns a finite number ([`gateway-lock.ts` line 491](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/infra/gateway-lock.ts#L491)). That function turns the FILETIME into milliseconds since 1970 and drops the sub-millisecond part ([`src/infra/windows-process-start.ts` lines 37-38](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/infra/windows-process-start.ts#L37-L38)). Its PowerShell and WMIC fallbacks return milliseconds too ([lines 109-110 and 117-127](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/infra/windows-process-start.ts#L109-L127)), and any failure gives `null`. So the lock holds a coarser value than `GetProcessTimes` reports. OpenClaw's own ancestry check keeps native ticks for that reason ([line 257](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/infra/windows-process-start.ts#L257)). Whether the pinned gateway writes `startTime` on Windows, and what tolerance the comparison allows, are for native acceptance to measure. A lock without it doesn't pass, as on macOS (`apps/desktop/src/setup/local-prove.ts` line 190).

**What a probe measured on 2026-11-27.** On one Windows x64 host, whose Windows build wasn't recorded, a Node 24.20.0 probe imported `src/infra/windows-process-start.ts` from the tag and called its exported `readWindowsProcessStartTimeSync`, the function the gateway calls, not a copy of its arithmetic. It ran on koffi 3.3.2, the exact version [`openclaw@2026.10.6`](https://registry.npmjs.org/openclaw/2026.10.6) lists, extracted from registry tarballs that matched their `dist.integrity`, with no install script run. Each call had no time budget and named a Windows folder that doesn't exist, so neither fallback could start a program ([lines 142-150](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/infra/windows-process-start.ts#L142-L150)), and a guard on `spawnSync` caught no calls. Over three runs the probe started 18 Node children that each exit after 60 seconds, and it held a handle to each from its start until after the last read. For every child:

- Twenty calls, before and after the other reads, all returned one value: the creation FILETIME divided by 10,000 with the remainder dropped, minus 11,644,473,600,000. Seven children had a remainder of 5,000 ticks or more and still mapped down, so the function truncates and doesn't round.
- That FILETIME came from `GetProcessTimes` on the probe's handle. A second reader, Windows PowerShell calling `GetProcessTimes` through P/Invoke with `PROCESS_QUERY_LIMITED_INFORMATION`, ran twice per child and gave the same FILETIME to the tick.
- The sub-millisecond part the lock drops was never zero. It ran from 61 to 8,444 ticks.
- In the last two runs, all 12 creation times fell between two `GetSystemTimePreciseAsFileTime` reads taken around the spawn. The creation time is on the system's UTC clock, and the function's value is Unix epoch milliseconds.
- After a child exited on its own, with the probe's handle still open, the function returned the same value again, while Node's `process.kill(pid, 0)` reported the process gone. A matching start time alone doesn't show that a process is still running.

The probe isn't in this repository, and CI doesn't run it. It didn't run the PowerShell or WMIC fallback, or the copy of this function bundled in the published package. It didn't measure a real gateway or the lock it writes, another account's process or an S4U task's, Windows on Arm, or whether a PID and this value pick out one process.

**How the gateway was started** decides whether these reads succeed and which account the gateway runs as. It never stands in for the account check.

- **By hand, or from the Startup folder.** The gateway runs in the person's own logon session. OpenClaw falls back to the Startup folder when it can't register a task ([`openclaw@v2026.10.6:docs/platforms/windows.md` lines 171-172](https://github.com/openclaw/openclaw/blob/v2026.10.6/docs/platforms/windows.md#L171-L172)).
- **The task OpenClaw generates.** OpenClaw takes a user name from the installing process's `USERNAME` and `USERDOMAIN` ([`src/daemon/service-process-env.ts` lines 39-53](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/daemon/service-process-env.ts#L39-L53)). With a name, the gateway's task runs as that user with an S4U logon. With no name, its principal is the built-in Users group, `S-1-5-32-545`. Either way the run level is `LeastPrivilege` ([`src/daemon/schtasks-xml.ts` lines 16, 21-23 and 39](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/daemon/schtasks-xml.ts#L16-L39)). Microsoft documents that an S4U task runs on a non-interactive desktop, without network or encrypted-file access ([`TASK_LOGON_TYPE`](https://learn.microsoft.com/en-us/windows/win32/api/taskschd/ne-taskschd-task_logon_type)). That says where the task runs. It doesn't say whether the person's app, with the same SID on the interactive desktop, may open the task's process.
- **A Password task already there.** When a task with the `Password` logon type exists, the installer keeps it and refreshes only its launcher files, as an "operator-managed account and triggers" ([`src/daemon/schtasks-install.ts` lines 210-233](https://github.com/openclaw/openclaw/blob/v2026.10.6/src/daemon/schtasks-install.ts#L210-L233)). It runs as whatever account its operator chose, which may be another account.
- **Windows Hub's isolated package.** It runs the gateway under an agent account of its own ([`hub@8d31176d:docs/ARCHITECTURE.md` lines 599-600 and 774-775](https://github.com/openclaw/openclaw-windows-node/blob/8d31176d3ad407cf264472f48f82c1b6daa8b362/docs/ARCHITECTURE.md#L599-L600)).

So the check reads the token SID of the process that bound the connection and compares it with Clawtrate's own. A different SID refuses, and so does a token that can't be read. The check never infers the account from the task's logon type, its user name, the session or the desktop.

**Before one-click Connect is offered for a native gateway**, each item below must pass on a Windows runner, against a gateway and a profile the test creates:

1. Secure storage on Windows (#654). Without it a first pairing asks for read anyway.
2. The account check: the process that bound the connection has Clawtrate's SID, and a different or unreadable account refuses. This is measured for a gateway started by hand, from the Startup folder and by the generated S4U task. For the S4U task it includes whether the person's app can open the process at all; if it can't, that gateway stays on the form. A preserved Password task or a Users-group task passes only when its process has Clawtrate's SID.
3. The lock's `startTime`: that the pinned gateway writes it on Windows, and the tolerance against the process's creation time in milliseconds. macOS compares whole seconds, within 1 s (`judge` in `apps/desktop/src/setup/local-prove.ts`). A lock without it stays on the form. The rest of the lock check applies as on macOS, including the settings file the lock names in `configPath`. A lock without one doesn't pass, and one that names any file but this profile's `openclaw.json` is refused with `config` (`apps/desktop/src/setup/local-prove.ts` lines 194 and 198).
4. The module pin, as on macOS, where it is a consistency check that authenticates nothing (`docs/decisions.md`, "Local connect's proof"). `apps/desktop/src/setup/openclaw-pins.ts` pins the Windows x64 module of OpenClaw 2026.10.6, `@openclaw/fs-safe-win32-x64-msvc@0.25.0`, by the SHA-256 of the published file (#930). Only a test compares that pin, with an installed package's bytes on disk, and CI points that test at an install only in its Linux `check` job. Clawtrate has nothing yet that reads which modules a process has loaded on Windows, so no running gateway has been compared with it. [`@openclaw/fs-safe@0.25.0`](https://registry.npmjs.org/@openclaw/fs-safe/0.25.0) lists a Windows package for x64 only in its `optionalDependencies`, so there is no Arm pin, and 2026.11.10's table pins only macOS.
5. A listener on the same port that isn't the gateway gets nothing, as #655's packaged check requires.

Two things would remain beyond the macOS residue in `docs/design/setup-effortless.md` §13. The table names only the process that bound the socket, where the macOS scan lists every holder this account can see. And the pages read describe no way to confirm from outside that the gateway holds the profile's lock and database open, which macOS checks.

## Why a gateway inside WSL stays manual

Windows Hub's local setup provisions an app-owned `OpenClawGateway` distribution ([`openclaw@v2026.10.6:docs/platforms/windows.md` lines 55-56](https://github.com/openclaw/openclaw/blob/v2026.10.6/docs/platforms/windows.md#L55-L56)). Inside it the gateway runs as the Linux user `openclaw`, and its settings live on the distribution's disk ([`hub@8d31176d:docs/WSL_GATEWAY_ADMIN.md` lines 3, 11 and 33](https://github.com/openclaw/openclaw-windows-node/blob/8d31176d3ad407cf264472f48f82c1b6daa8b362/docs/WSL_GATEWAY_ADMIN.md#L3-L33)). That isn't a file of this Windows account, which is all the settings reader reads.

- **NAT, WSL's default.** Microsoft documents that `localhostForwarding` defaults to true, so that ports bound to wildcard or localhost in the VM can be reached from the host at `localhost:port` ([WSL settings](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)). It doesn't say which Windows process holds that endpoint. In the WSL source at the pinned commit, `wslrelay` binds the Windows loopback listener and relays each accepted connection into the VM over a Hyper-V socket ([`wsl@f753835d:src/windows/wslrelay/localhost.cpp` lines 260-282 and 321-329](https://github.com/microsoft/WSL/blob/f753835d546473f75c813c99093c6afd398cb7e4/src/windows/wslrelay/localhost.cpp#L260-L329)). That is how this implementation behaves, not a guarantee Microsoft documents for every NAT endpoint. Either way the gateway's process runs in the Linux VM, so whatever Windows process holds the endpoint isn't it.
- **Mirrored.** Microsoft documents that Windows and the VM then reach each other on 127.0.0.1 ([WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking)). The pages read don't say which Windows process, if any, owns such a connection. Windows Hub can turn this mode on ([`hub@8d31176d:src/OpenClaw.SetupEngine/WslGlobalConfigManager.cs` lines 15-23 and 57](https://github.com/openclaw/openclaw-windows-node/blob/8d31176d3ad407cf264472f48f82c1b6daa8b362/src/OpenClaw.SetupEngine/WslGlobalConfigManager.cs#L15-L57)), and it accepts a mirrored endpoint only when its own Windows listener snapshot is empty ([`hub@8d31176d:docs/CONNECTION_ARCHITECTURE.md` line 945](https://github.com/openclaw/openclaw-windows-node/blob/8d31176d3ad407cf264472f48f82c1b6daa8b362/docs/CONNECTION_ARCHITECTURE.md#L945)). That is the Hub's acceptance rule, not a statement by Microsoft. Clawtrate's check needs a named holder that is the gateway, and neither source gives one.

Windows Hub proves its own WSL gateway by running `systemctl` and `ss` inside the distribution ([`hub@8d31176d:src/OpenClaw.Connection/ManagedLocalGatewayPortProvenanceService.cs` lines 138-141](https://github.com/openclaw/openclaw-windows-node/blob/8d31176d3ad407cf264472f48f82c1b6daa8b362/src/OpenClaw.Connection/ManagedLocalGatewayPortProvenanceService.cs#L138-L141)). Its authors write that this check "does not prove the Windows listener forwards to that distro" ([`hub@8d31176d:docs/CONNECTION_ARCHITECTURE.md` line 947](https://github.com/openclaw/openclaw-windows-node/blob/8d31176d3ad407cf264472f48f82c1b6daa8b362/docs/CONNECTION_ARCHITECTURE.md#L947)). Clawtrate would have to start programs in the distribution and would still lack that link. So one-click Connect isn't offered for a gateway in WSL, in either mode, and the address-and-token form stays.
