# Addresses a gateway hands the client: what they are and what each app does

Every address an OpenClaw gateway can put in front of Clawtrate, who writes it, what the desktop app, the web preview and the iPhone app do with it today, and what Electron, the browser and iOS can enforce. It is the evidence behind the rule in `docs/decisions.md` ("Addresses a gateway hands the client", issue #70); enforcing the rule is #71.

How to read the citations, as in `gateway-capabilities.md` and `setup-flow.md`:

- `<openclaw>/…` is a path inside the installed `openclaw` 2026.10.6 npm package, the one the `openclaw` wrapper script runs. Bundled chunk names carry a build hash that changes with every release; search by the `//#region <source path>` marker at the top of each chunk instead. Line numbers are of the 2026.10.6 chunks.
- A path with no prefix is in this repository on `main` (`0882ea0b`). A path after a branch name, as in `m42-artifacts:packages/core/src/artifacts.ts`, is read with `git show` on that branch's tip: `m42-artifacts` `617b7884`, `m310-t3-thread-card` `6b46b01b`, `m61-ios-foundation` `6caf8044`, `m511b-accounts-b` `8d4ebd68`, `d6-bots-lifecycle-design` `cc39b52f`. None was checked out.
- **Tried** means it was run here and the output is quoted. **Source** means it was read in shipped code only. **Docs** means it was read in a platform's documentation: Electron's comes from the `electron.d.ts` that ships with Electron 45.3.2, Node's from the `@types/node` the workspace installs (24.19.2; the project runs Node 26), React Native's and Apple's from their published pages, read through a search for this note. **Not established** marks what could not be settled here, with the reason.

Where things were run: three probes, all offline. The third, a browser on loopback, is in §4.3. One ran the `m42-artifacts` link previewer under Node 26.0.0 with a stand-in `fetch` that records the address and answers itself, so nothing left the machine. The other ran Electron 45.3.2, unpacked from the release archive already in the machine's Electron download cache, with a temporary profile, a `file://` page and an HTTP server of its own on loopback. No gateway was started: every gateway fact here is read from source or from the capability map, which marks its own live results.

### 1.1 A bot's picture

- `agents.list` on a connection that is not the Control UI builds each identity from the configured entry only, `entry.identity?.avatar` (`<openclaw>/dist/session-utils-store-C-0MBZ3E.mjs` lines 213-235). The gateway's own avatar route is used only when `client.id` is the Control UI's (`<openclaw>/dist/agents-DAPW-UCQ.mjs` line 584).
- The value becomes `avatarUrl` by `resolveAgentAvatarUrlFromSource` (`<openclaw>/dist/identity-avatar-file-B7GwXSk3.mjs` lines 143-155): an address matching `/^https?:\/\//i` (`<openclaw>/dist/avatar-policy-DiIdI6oM.mjs` line 32) is returned as written, with no host check; a renderable image `data:` address is returned; any other scheme is dropped; a path is read inside the workspace, up to 2 MB, and returned as `data:<type>;base64,…`, including `image/svg+xml`. The bundled docs agree: "`identity.avatar`: workspace-relative path, `http(s)` URL, or `data:` URI" (`<openclaw>/docs/gateway/config-agents/entries-and-multi-agent.md` line 87).
- `agent.identity.get` resolves the configured avatar, else the one in the workspace's `IDENTITY.md` (`<openclaw>/dist/identity-avatar-ItnIZk3C.mjs` line 32; `<openclaw>/dist/assistant-avatar-Br9YHCxQ.mjs` line 96). It answers `avatarStatus` with the kind of source: `remote` for an address, `local` for a workspace file, `data`, or `none` with `avatarReason` (`missing`, `outside_workspace`, `unsupported_extension`, `too_large`, `unreadable`, and `unsupported_data_url` or `unsupported_uri` for an unusable `data:` address or another scheme) (`<openclaw>/dist/agent-identity-BjpSY6Dp.mjs` lines 33-50; `<openclaw>/dist/assistant-avatar-Br9YHCxQ.mjs` lines 150-175). For a remote picture `avatar` is the address itself, and `avatarSource` says only "remote URL". A configured value that is already the gateway's own avatar route comes back as that route with no `avatarStatus` (`assistant-avatar-Br9YHCxQ.mjs` lines 199-207).
- `agents.list` also sends the configured value as written, as `identity.avatar`, beside `avatarUrl` (`<openclaw>/dist/session-utils-store-C-0MBZ3E.mjs` lines 218-234). The gateway's check on a `data:` value reads its label and its encoded length only: `/^data:image\//i`, at most the length of 2 MiB in base64 (`<openclaw>/dist/avatar-limits-2506OuP3.mjs` lines 8-19); the 2 MiB limit on a workspace file is a separate check on the file.
- The authenticated Control UI avatar route serves workspace files and can generate thumbnails from workspace or inline image data. It returns remote URLs as metadata and does not fetch them (`<openclaw>/dist/control-ui-DtLaS2Te.mjs` lines 687-729). `agent.identity.get` can return a recognized gateway avatar route without a status. Unusable values can also report `unsupported_data_url` or `unsupported_uri`.
- Clawtrate keeps an `avatarUrl` only if its label says PNG, JPEG, WebP or GIF `data:` with base64, or it starts with `https://` (`packages/core/src/mapping.ts` lines 36-42). The check reads the label only: it neither decodes the base64, nor bounds the decoded size, nor looks at the bytes, so malformed or mislabeled data reaches the image decoder on every platform. It does not call `agent.identity.get`. The bot lifecycle design writes pictures only as PNG `data:` addresses (`d6-bots-lifecycle-design:docs/design/bots-lifecycle.md` line 135).

### 1.2 Media a reply hands over, and what `artifacts.download` answers

- The reply directive accepts a public `https` address in a `MEDIA:` line, and refuses others as `invalid-reference` (`<openclaw>/dist/reply-payload-BOcGzEWl.mjs` line 47; `<openclaw>/dist/reply-directives-s-Q6bOJ0.mjs` lines 33-42). WebChat's managed media then fetches such an address into the gateway's own media store (`saveRemoteMediaForStore`, `<openclaw>/dist/managed-image-attachments-D3mpm5lG.mjs` lines 869-880), so the block names the gateway's route, not the remote address. The display block's `url` and `openUrl` are that route with no ticket; a document's sit under `attachment` (same file, lines 500-530).
- `artifacts.download` answers in one of three ways. A managed item gets the route with a fresh `mediaTicket` and `expiresAt` (same file, lines 266-290 and 697-725; `<openclaw>/dist/artifacts-CVcZMNpQ.mjs` lines 452-485). Asked with `transport: "http"`, an item the gateway can read gets a grant, `/api/artifacts/download/<connection>/<ticket>`, valid for five minutes and only on that connection, with `expiresAt` (`<openclaw>/dist/artifact-download-grants-tzwDxk5o.mjs` lines 21-55; `artifacts-CVcZMNpQ.mjs` lines 574-617). Otherwise it answers inline bytes, or `url` alone: the first of the block's `url` or `openUrl`, `source.url`, `image_url` and `audio_url` that starts with `/api/` or is `http` or `https` (`<openclaw>/dist/artifacts-content-C0x4QGox.mjs` lines 15-69; `artifacts-CVcZMNpQ.mjs` lines 619-633). An answer marks an address the gateway issued only by `expiresAt` and its path.
- The artifacts branch asks with `transport: "http"` and fetches whatever address the answer names if it is a path under `/api/` or on the gateway's origin (`m42-artifacts:packages/core/src/artifacts.ts` lines 172-192 and 454-498). That check establishes where the request goes, not who wrote the path or whether it is a grant: a path a bot wrote into a block reaches the host's fetch the same way.

## 3. What the platforms can enforce

Versions from the `package.json` files: Electron 45.3.2 and React 19.3.1 (`apps/desktop/package.json`), react-markdown 10.1.0 (`packages/ui/package.json`); on `m61-ios-foundation`, Expo 58.0.25 and React Native 0.88.1 (`apps/mobile/package.json`).

### 3.1 Electron 45.3.2

- **The page's content security policy** limits what the renderer loads by kind: `img-src`, `media-src`, `connect-src`, `frame-src` (from `default-src`). It holds a scheme or a host, not a person's choice. **Source** (`index.html`).
- **The request filter**, `session.webRequest.onBeforeRequest`, is called "when a request is about to occur" with its address and `resourceType`, and can cancel it (**docs**). It is called again for each redirect hop of an image, and cancelling a hop stops the load (**tried**, §4.2). It covers the renderer's requests through the session; it does not see Node's `fetch` in the main process, which does not use Chromium's network stack (**not established** by a run; the filter's documentation names only the session's requests).
- **Headers.** `onBeforeSendHeaders` can replace a request's headers and `onHeadersReceived` a response's (`BeforeSendResponse.requestHeaders`, `HeadersReceivedResponse.responseHeaders`) (**docs**). Whether `Cookie` is visible there to remove is **not established**: the cookie half of the probe did not run (§4.2).
- **Navigation.** `will-navigate` covers the main frame and `will-frame-navigate` every frame; `preventDefault()` stops either (**docs**). Only `will-navigate` is handled today. A subframe's load to an address outside the app is a request the filter cancels; one to the app's own files passes it.
- **New windows.** `setWindowOpenHandler` is called for `window.open()`, a `target="_blank"` link, a shift-click and a form with `target="_blank"` (**docs**). Today it hands the address to `openExternally` and denies the window.
- **The system browser.** `shell.openExternal(url)` opens "the given external protocol URL in the desktop's default manner" (**docs**): any scheme, so the scheme check is the app's, in `openExternally`.

### 3.2 Node, for fetches the host process makes

`net` and `http` connection options take a `lookup` function (`@types/node` `net.d.ts` line 60, `http.d.ts` line 223) (**docs**). A check made there sees the address the connection actually uses; a `dns.lookup` before `fetch`, as `link-preview.ts` did at the pinned commit, sees an address the later connection may not use. A `lookup` does nothing for an address written as an IP literal, which is never resolved, nor for a request sent through a proxy, which resolves the name itself: a literal is checked before the request, and the connection is made directly.

### 3.3 The web preview

The viewer's browser applies the page's policy and the web host's headers, and opens a `target="_blank"` link itself. The page can choose what it renders, and nothing else: no request filter, and the browser's own cookies for a picture's host go with the picture unless the image element is `crossorigin="anonymous"`, which also makes a picture without CORS headers fail. The web host sends `referrer-policy: no-referrer` for its page. **Source** for the headers; the cookies are the browser's documented behavior.

An `<img>` follows a redirect by itself: the page gets no event for the hop and cannot cancel it, and a policy of `img-src https:` admits any `https` host it leads to. The hop went to a third origin in the probe, with the cookie (§4.3, **tried**).

The web host's access cookie is set with `HttpOnly; SameSite=Strict; Path=/` and no `Domain` (`apps/desktop/src/web-host/server.ts` lines 339-345), so it belongs to the host name alone: cookies do not tell ports apart, and a picture on another port of the same host carries it (§4.3, **tried**).

### 3.4 iOS (React Native 0.88.1, Expo 58)

- **App Transport Security** applies to URLSession and the APIs built on it, and requires TLS for public host names. `NSAllowsLocalNetworking` (set on `m61-ios-foundation`, `apps/mobile/app.json`) lifts that for unqualified names and `.local` hosts; Apple's pages and its forum answers disagree about IP addresses. **Docs** (Apple's `NSAllowsLocalNetworking` and "Preventing insecure network connections"). So a plain-`http` picture on a public host fails on iOS whatever the app does, and one on a local name loads.
- **Images.** `Image` takes `source {uri, method, headers, body, cache}`; `cache` is iOS only (**docs**, React Native's Image page). None of these refuses a redirect, and the app sees no hop, so an `Image` cannot be held to the address it was given. Whether it sends or stores cookies is **not established**.
- **App Transport Security and pictures.** It refuses plain `http` to a public host name, but not to a local name, because the iPhone branch sets `NSAllowsLocalNetworking`. It also says nothing about which `https` host a redirect reaches. It does not hold the desktop's `img-src https:` line.
- **Links.** `Linking.openURL(url)` hands any address to the system, whatever app handles it (**docs**, React Native's Linking page). The scheme check is the app's, as `openableUrl` does.
- **Fetch.** No option that checks the address a request connects to was found for React Native's `fetch`, and its redirect handling was not established.
