## Connecting to the gateway

- **Client identity.** `connect` sends `client.id: "gateway-client"` and `client.mode: "ui"`, with a `displayName` of "Clawtrate Desktop" or "Clawtrate Web". The gateway accepts only ids from its registry, and the other ids name OpenClaw's own products. `gateway-client` with mode `backend` is a reserved trust path for internal helpers, so we use mode `ui`.
- **Scopes, in tiers.** A device starts read-only: every `connect` requests exactly `operator.read`, and reading bots, tasks, transcripts and live streams needs nothing more. The first time the user sends, stops or answers something, the client asks once, through `device.scopes.requestUpgrade`, for the interactive tier: `operator.read`, `operator.write`, `operator.approvals` and `operator.questions`. Write does not imply the other two, and a read+write device receives no question events and is refused every `question.*` call, so they are asked for together and the gateway's owner approves once. `connection.upgrade` shows the pending request id and the approve command, chosen by the host as for pairing. On approval the client stores the rotated device token from `device.scopes.waitUpgrade` (through the pinned `GatewayScopeUpgrade`) and reconnects. `operator.admin` and the narrower `operator.sessions.*` scopes are never requested.
- **Requested is not granted.** The token record keeps the gateway's grant in `grantedScopes` and what the client means to hold in `heldScopes`. Only `heldScopes`, normalized to read plus whichever interactive scopes were granted, is ever requested; a record without it means read. The pinned device-auth lifecycle would otherwise reuse a stored token's grant as the request, so the token store reports the held scopes to it, and the client refuses to send a plan whose scopes differ.
- **Capabilities.** `caps` is `["tool-events"]`, without which the gateway sends no tool lifecycle events. A connect that asks for `operator.approvals` adds `approvals`, `exec-approvals` and `plugin-approvals`: without the first two the gateway auto-denies exec approvals as `no-route`, and the third routes plugin approvals. A read-only connect claims none of them, so the gateway never waits for a connection that cannot see approvals. Question events need a scope, not a cap.
- **Pairing.** The core waits for `connect.challenge` and signs the v3 device payload through the host's signer. It sends `connect` with the shared gateway token as bootstrap auth. On `PAIRING_REQUIRED` it shows the request id and an approve command chosen by the host: `pnpm dev-gateway approve` for the development gateway, otherwise `openclaw devices approve <requestId>` with a line saying the gateway's owner runs it on the gateway's machine. An unqualified `openclaw` command is never shown for the development gateway, because it would address the default profile. It retries every 3 seconds, which keeps the same request id, so the app connects by itself once someone approves. After approval it stores `hello-ok.auth.deviceToken` and stops sending, and stops storing, the bootstrap token.
- **Device tokens are scoped to one gateway URL.** The token store key includes the URL, so a token issued by one gateway is never offered to another.
- **A credential never crosses gateways.** Each connection gets its own token store and device-auth lifecycle, bound to its gateway URL and connection generation. Every read and write names that URL, and every write, including the rotated token of an approved step-up and the dropping of a bootstrap token after pairing, is checked again after each wait and dropped once the connection is no longer current. A handshake or step-up that finishes after a switch writes nothing.
- **Losing access.** A call refused for a missing scope, an action or a list read, drops that scope from the connection's effective scopes, and `canWrite`, `canAnswer` and `canApprove` follow from them together; the next use asks for access again rather than repeating the refused call, and read access is kept. A dropped connection clears all three until the next hello. When the gateway stops accepting the device, or reconnecting stops, every operation waiting for access is refused, and one started after that fails at once, since no hello will come: a send fails visibly with retry and delete, a Stop goes back to how the run was, a question or approval keeps its error and stays answerable. The user's retry reconnects. At most `MAX_ACCESS_WAITERS` (512) operations wait for access at once.
- **A viewer that goes away takes its requests with it.** Each bridge session names itself to the client; on dispose, every task creation, Stop, answer or approval resolution it started that is still waiting for access is withdrawn at once, before the gateway is asked, and nothing of it is kept. The viewer's token is checked once more just before each of these asks the gateway, so one whose access was already held, or settled a moment before, is withdrawn too. Outgoing messages belong to the task, not the viewer, and are not withdrawn. A second answer to the same question or approval while one is on its way is refused.
- **Session list.** `sessions.subscribe` with list parameters gives the subscription and the snapshot in one call, and is re-established after every reconnect. The list is read in pages of 200 (`hasMore`, `nextOffset`) until the gateway reports no more, up to 50 pages; reaching that ceiling sets `discovery.partial` and the task list says so. Changes that arrive while the snapshot is in flight trigger a trailing re-read. `sessions.changed` deltas are merged field by field into cached rows: present fields replace, `null` clears, omitted fields stay. Event rows follow the same membership rules as the list query (`excludeCron`, `excludeSubagents`, archived), mirrored from the gateway's own filter: a known row that stops qualifying is dropped, and an unknown row is never inserted from an event, because its payload cannot prove membership; the filtered list is re-read instead. Nothing polls.
- **Discovery.** After hello, bots and tasks load independently. A failed read sets `discovery.status: "error"` with a message, keeps whatever loaded before, and the status strip offers a retry, which reloads without reconnecting.
- **Reconnecting.** Once a connection has reached hello, every later drop and failed attempt is `reconnecting`, never `connecting`, and reopening the same gateway keeps the cached bots, tasks and transcripts. The interface keeps the shell mounted whenever it has data.
- **Viewers.** The host keeps one client; each Electron window and each browser tab gets its own bridge session. Transcripts are reference-counted across sessions, so one viewer closing a task does not close it for another, and a closed tab releases what it held. A browser that reconnects is a new viewer to the host; its bridge (`createRemoteBridge` in core) remembers the tasks it has open and opens them again after every hello.
- **Closing a task keeps the user's words.** When the last viewer closes a task that still holds unsent, accepted-but-unconfirmed or failed messages, or a run this client started, the task is kept and followed until that work is done, confirmed or deleted; reopening shows the same queue. Switching gateways drops it: a message is never sent to another gateway than the one it was written for.
- **Transcripts.** Opening a task subscribes with `sessions.messages.subscribe` and reads `chat.history` (200 rows). `session.message`, terminal `chat` events and the `agent` lifecycle end reload history. Earlier pages (`hasMore`) are not loaded yet.

## Live runs

- **One engine, pure.** `packages/core/src/runs.ts` turns `chat` and `agent` events, `question.*` events, the user's own sends and stops, and `chat.history` into each open task's `runs`, `outbox` and `questions`. Run states and transitions follow the table in `docs/research/grok-bot-flows.md` §5.6. The client feeds it and owns the timers and requests.
- **Text from one projection per run.** The capability map says a run's text comes as `chat` deltas or as `agent` assistant events and that consuming both double-counts it. Each run takes its text from whichever arrives first and ignores the other. `chat` deltas, which carry the whole message or only what to add (`deltaText`, `replace`), are followed by the client's own `ChatTextBaselines` (`chat-text.ts`), which keeps only each streaming run's text, not the client package's `GatewayChatStreamProjection`, which kept the whole message.
- **Steps.** A step is a tool call (`tool:<toolCallId>`, the gateway's own id) or a reasoning segment, which has no gateway id. A live segment is `reasoning:<runId>:<n>`, with `n` from one counter for the whole client that never goes back, so no id is used twice within a task while the client runs, whatever retention dropped. A segment read from history is named by its row and block, `reasoning:<runId>:h<row>.<block>` (the row's id, else `#<seq>`, else `@<index>`), a namespace of its own. A resync pairs history segments with live ones in order: each history segment takes the first live segment after the last one paired whose whole text has the same length and digest, or, when both have the same number of segments, the live one at its own place if that comes after the last one paired, and keeps the live id. Ids never cross, and repeated text pairs in order. So ids are stable while the task stays open, through streaming and resyncs of the same history window. Closing a task and reopening it from a different window can name the same segment differently; that is not promised, and `Step.id` says so. A segment ends at a `lifecycle` `model` phase, at a tool item, at reply text, or at a cumulative frame that does not continue it. Bot-to-bot sends and MCP tools are ordinary tool steps with their exact names. Titles are derived from the tool name, the same live and from history; the gateway's English `item.title` is not used. Text on a step is cut to `MAX_STEP_BODY_CHARS` (2,048 JSON characters), and the cut is named in its `cut` at the first cut, whichever cap made it. The exact payloads stay in a raw table in the host process, inline on the step only when their JSON is at most `MAX_INLINE_RAW_CHARS` (2,048), otherwise read with the bridge command `readStepRaw`. That keeps the 16 ms state snapshots small however long a tool's output is.
- **What `readStepRaw` promises.** A step's whole text is read from the raw table while it fits there (`MAX_RAW_ENTRY_CHARS`, 262,144, and the table's total, oldest first), and otherwise from the gateway's history once that step is in history. Until then the read answers `{status: "not-available-yet"}` with a reason the interface can show; it answers null only for a step the task does not have. Nothing claims a text is recoverable before it is: a payload too long for the table, for a run history does not yet hold, cannot be read until it does. History holds what the gateway stored, which may itself be cut by the gateway (`__openclaw.truncated` on the row).
- **Sending.** `chat.send` always carries a `queueMode`: `followup` for a new run, `steer` into the active run. With none the gateway steers. A steer's own run id is settled at once by the gateway with an empty final, so it is remembered as an alias and its events are ignored while the run it joined is active. The idempotency key is the message id; a retry reuses it. A refusal from the gateway fails the optimistic run as "Couldn't start"; a send whose outcome is unknown drops it, and its events or history bring it back if it did start. Deliveries for one task go out one at a time in the order they were made. Messages leave the outbox only when an identifier ties them to a history row: the row's idempotency key (under `__openclaw` or on the row), or the `messageSeq` `chat.send` returned when the row carries no contradicting key. Text is never evidence. Acceptance is not confirmation: a `sent` message whose run has ended, and that the history read after it does not tie to a row, becomes `unconfirmed`, with a note that it may not have been delivered, and can be retried with its own idempotency key (so the gateway delivers it at most once) or deleted. Its files are kept until history confirms it or the user deletes it. An acknowledgement that names no run assumes none: the optimistic run is dropped, and the next history read confirms the message or finds it unconfirmed. A `/stop` the gateway handles as a command answers `{ok, aborted, runIds}` before any run or turn is recorded (`chat-send-handler` in OpenClaw 2026.10.6); the message is then `handled`, starts no run, is never made unconfirmed, and can be dismissed. A request nobody answers is given up locally after `REQUEST_TIMEOUT_MS` (60 s), and its outcome is unknown, never failed: the message becomes `checking`, its optimistic run is dropped, and history reads decide it, tying it to a row or, once nothing does, making it `unconfirmed`, to retry with the same key. Only a refusal from the gateway, or a request that never left, fails it. Nothing is sent again on the client's assumption. Waits the gateway answers late by design (`device.scopes.waitUpgrade`) take no deadline.
- **Creating a task.** `sessions.create` is idempotent per device and key with the same parameters: the gateway keeps a success for 300 s, a repeat waits on work still in flight, and a refusal frees the key (OpenClaw 2026.10.6). The request is kept with its key, counted against `MAX_CREATIONS` and holding its task slot from the moment it is asked, before anything is awaited (access included), in `state.creations`; the same request asked meanwhile joins it, and one withdrawn or refused before it was sent takes those who joined with it. A refusal makes it `failed`, offered again with the same key (`retryCreation`) or dismissed. No answer makes it `checking`, never failed. It is asked again automatically, with the same key and parameters, only of the gateway start that holds the key, and only within `CREATION_KEY_WINDOW_MS` (240 s) of sending: the hello's `server.bootId` is a random id the gateway draws at each start (2026.10.6 sets it in `createGatewayKernel`), and the idempotency record lives in that start's single request context, so the same `bootId` means the same record. The client keeps the `bootId` the request went to and asks again, with backoff and at once after a reconnect, only while the current hello carries the same one; the gateway then brings back the original outcome, the task is kept with its first message in its outbox, and the creation shows `created` with its key. Start times estimated from `snapshot.uptimeMs` are not used: a fast restart can match them after the record was lost. A hello without a `bootId`, another `bootId`, or the end of the window makes it `unknown`: nothing establishes whether the task exists, so it is never sent again automatically. Its `error` says that retrying may create a second task; the user can dismiss it once they have checked the task list, or retry it (`retryCreation`, the same key), which is their own decision. The same request asked while one is out or being checked joins it; asked once it was created, it opens that task; asked while unknown, it is refused with that warning.
- **Queue and hold.** "Queue after this turn", and any send while a run is stopping, is held by the client and sent when the run is terminal; the gateway's own queue is not used. A send while a question is pending is held too: the gateway would take a plain message as the answer and fail the asking run. It goes out as a steer once the question is answered or dismissed. Whether a question is pending is read from the question records as well as the run's cards. When it settles, every held message is claimed at once and delivered once each, in the order sent.
- **Pending cards and steering.** A steer does not close cards or move a waiting run back to running; the map shows a steer leaving approvals pending. This is where the engine departs from §5.6, which closes approval cards on a steer.
- **Reasoning segments are best effort.** The `thinking` stream has no segment id. A segment ends at a model call, a tool item, reply text, or text that does not extend the last; the last of these cannot tell a rewrite from a new segment. So a reload never adds history reasoning to a run still in flight, and once history holds the finished run its `thinking` blocks replace the live segments. A fresh opening of a run in flight whose last persisted content is a `thinking` block keeps that segment open, as the live view has it. Whether the next cumulative frame continues it is judged against the length and digest of the segment's whole text so far (`continuation`), live or persisted, not against the text kept, which may be cut, nor the raw payload's shape: a frame continues it only when it is at least that long and its prefix of that length has the same digest. One that does not starts the next segment and leaves the earlier one done, with its text and raw payload. A segment without that evidence starts a new one rather than being assumed to continue. No reasoning text is shown twice or dropped.
- **Run endings.** A lifecycle `error` ends a run only when the gateway marks it definitive (`executionSettled`, `fallbackExhaustedFailure`, or a classification other than a plain failure); otherwise it is an attempt error kept in `attemptErrors`, and the run goes on to its fallback. Terminal events are classified as the gateway does (completed, cancelled or aborted, timed out, blocked, failed). A run keeps the terminal event's own `stopReason`, `timeoutPhase`, `providerStarted` and `status`, and a `chat` error's `errorKind`; nothing is read from error text. In history, the gateway's injected aborted-partial row (`openclawAbort`) means stopped; only a final reply row establishes completion, and a run history shows ended without one has `outcomeKnown: false`. The gateway's own run timeout pauses while waiting for an approval; Clawtrate's turn limit is wall-clock time from the send.
- **Tool results.** Both shipped shapes are read: `result: {content, details}`, and the native one with the text in `output` and the details in `result`. Command output is matched by its `toolCallId`, or by exec's `command:<toolCallId>` item. A result marked `replaceable` takes a later `replace` frame for the same call, even after the run ended, and history's copy wins over it on reload; either bumps the step's `correction`, so a view that keeps state across renders starts again from the facts. Errors are capped like other step text.
- **Timers.** Timers are capped at 2³¹−1 ms, which `setTimeout` cannot exceed, and re-armed when they wake early.

## Approvals

- **Origins.** An approval keeps who asked: agent, session, run and tool call. It is shown once, in one task: where it already is; its own session's task; the task holding its run; the task that spawned its session, a helper (`spawnedBy` on events, `relation: "helper"`); or the task whose `sessions_send` result named its run, or, for an approval naming no run, its session (`relation: "messaged"`). Messaging an existing bot does not make it a helper, so only the send's own result ties the two. Either kind carries `parentSessionKey`, and `runEnded` follows the asking run, which the client follows as a foreign session. One that arrives before any of these ties is known is kept in `unroutedApprovals` (at most `MAX_UNROUTED_APPROVALS`, 16; past it new ones are counted in `unroutedApprovalsOmitted`, not kept) and placed once its spawn, its send result or its own task appears. A helper's spawn is known only from its events, so after a fresh opening its approval waits there until the helper's next event.
- **Sources.** On opening a task and after every reconnect, `exec.approval.list`, `plugin.approval.list` and `openclaw.approval.list` load what is pending for it; `exec.approval.*`, `plugin.approval.*` and `openclaw.approval.*` requested and resolved events keep it current. All three kinds' requests and list items are `{id, request, createdAtMs, expiresAtMs}` envelopes (the requested event adds `approvalKind`); a system-agent request carries `title`, `description`, `command`, `proposalHash`, `allowedDecisions`, `agentId`, `sessionKey` and `runId`. Only `approval.get` and `approval.resolve` return an `ApprovalSnapshot`. Each list is read against a revision per task and kind and against the task's opening: a response older than one already applied, or from an earlier opening or connection, changes nothing. A failure, a timeout or a refusal is that revision's answer too: it changes only what it establishes (the kind's access is `error`, or a lost scope), and an older list arriving after it adds or settles nothing. A pending approval no longer listed after a reload is `closed` (`no-longer-listed`), but only if it was already pending when the list was asked for. Question lists follow the same rules. Each kind's access is kept in `approvalSources`; `approvalAccess` is `ready` only when all three loaded and `partial` when some failed. Without `operator.approvals` it is `unavailable`, which the interface must not show as "no approvals".
- **Outcomes are kept apart from the cards.** Every resolution the gateway reports is kept by id (at most `MAX_APPROVAL_OUTCOMES`, 512, oldest first; cleared when switching gateways), whether or not a card has arrived. A request or list entry that arrives after its resolution, or is replayed after its settled card was trimmed, shows settled, never actionable. A closure this client inferred (`expired` at the expiry time, `closed` when no longer listed) is marked `inferred`, and the gateway's own outcome replaces it, decision, reason and resolver included. Once the gateway has settled an approval, nothing reopens it; only a later application result is added.
- **Legacy denials are not assumed to be denials.** Exec and plugin resolved events read `deny` whether a reviewer denied the approval or the gateway cancelled it when its run was stopped or let it expire (`publishAppliedApprovalResolution` adds `terminalStatus` only for system-agent approvals). Such a deny is a lossy outcome: the approval shows `closed` with `outcomeUnknown` and reason `settled-cause-unknown`, never as a denial, and the client reads its snapshot with `approval.get`, under the `operator.approvals` it already holds (at most `MAX_OUTCOME_LOOKUPS`, 16, at once). The snapshot's exact outcome (`cancelled` with `run-aborted`, `expired`, or `denied` with its reason and resolver) replaces the lossy one; an exact outcome, this client's own included, is never replaced by a lossy one. If the snapshot cannot be read the approval stays closed with its cause unknown.
- **What it carries.** Every field the map and schema give: for exec the command, argv, cwd, host, node, security, ask, resolved path, warning and command analysis; for plugin approvals the title, description, detail, severity, plugin and tool; for the generic kind its title, description and proposal hash. Also the scope, the session, agent, run and tool call, created and expiry times, and the record as received. What an interactive exec approval will run is its request's `command` and `cwd`; a node's run plan (`systemRunPlan`) is kept apart, and `runsOn` says whether the command runs on the gateway or a node, whose own rules govern it. `allowedDecisions` holds exactly the decisions the request offers, plus `deny`. Without a list each kind takes the gateway's own default: exec requests always list theirs, so allow once less any `unavailableDecisions` is the safe reading; a plugin request gets the plugin default of allow once, allow always and deny; system-agent changes offer allow once and deny. A terminal snapshot's typed `resolver` (`device`, `channel`, `runtime` or `system`, with its id) is kept apart from the legacy events' `resolvedBy` label, and its `source` gives its session and agent. A system-agent resolution's `terminalStatus` (`cancelled`, `expired`) is the outcome, not the deny its decision field projects, and its later `applicationStatus` is kept as `applicationStatus`. A saved rule does not bypass a host that always asks, so an approval for an already allowed command is not an error.
- **Cut text.** A field cut to its bound is named in the card's `cut`, a diagnostic list of at most eight paths in which later cuts can displace earlier ones, so it is never the safety fact. That is `decisionCut`, set on each card when it is admitted (bounded) if what the reviewer is asked to allow was cut (an exec command, its argv or cwd, a plugin or system-agent approval's text), and never cleared. While it is set only deny is accepted, except from a viewer the host itself gave the whole text to: `readApprovalText` lists the approvals again, returns that text with its digest, keeps nothing of the text, and records per approval and per viewer the digest it gave (at most `MAX_APPROVAL_READERS`, 8, viewers per approval, only while the approval is pending). An allow is accepted only from a viewer with that record, naming that digest (`shownDigest`); the digest alone, which every snapshot carries, proves nothing. A viewer whose channel cannot carry the whole text (the web host's result cap) is not given it, so nothing is recorded and that approval stays deny-only there. The check is made again after waiting for access, against the approval as it then is. The digest is over the whole text as the gateway sent it, so an approval changed under the same id is not allowed as the one shown. Deny is always accepted.
- **A step's waiting status.** An approval naming a tool call is that step's own `waiting` status while the step runs, and links to it by `stepId`; one that names no step is its own card. The run's state follows only the run's lifecycle events: exec can return an `approval-pending` result and wait on its own, so a pending approval does not mean the run is blocked. An approval is never settled because its run ended. It stays pending, with `runEnded`, until the gateway resolves it, it expires, or a reload no longer lists it; withdrawing it means denying it.
- **Resolving.** Allow once, deny, or a standing allow (`allow-always`) through `exec.approval.resolve`, `plugin.approval.resolve` or `approval.resolve` for the generic kind. The legacy methods answer `{ok: true}` once the decision is applied, and the card settles as asked. `approval.resolve` answers `{applied, approval}` with the approval as it actually ended, which is what the card shows, even when another reviewer settled it first (`applied: false`, with a note). A standing allow may carry `grantExpiresInDays` (1 to 3650) for exec and the generic kind; plugin approvals take no duration. No protocol field says which bots a standing allow covers, so the engine offers none.
- **Expiry.** A pending approval expires at its `expiresAt`, and the lists are re-read to confirm. The expiry is an inference; the gateway's outcome, if it differs, replaces it.

## Message cards

- `selectMessageCards` (`packages/core/src/cards.ts`) is a view over steps; it changes nothing in the store. It draws a Messaged card for each `sessions_send` call and an MCP card for each external MCP call. Two events belong to one card only when they share the call's id.
- **Delivery is not inferred from a start.** A tool start, or a `toolCall` in history, is the model's request; the gateway may never execute it. A started call is `started`, delivery not established. A Messaged card reaches Sent and later states only from the result's own `details.status`; an MCP card is `returned` once its result arrives, which does not mean the external work is done. A call that closed without a result is `unknown`. A returned error stays `failed` with its text, before, during or after Stop, on Messaged and MCP cards alike; only a result that itself says it was aborted (`details.aborted`, or for MCP `details.status` `aborted` or `cancelled`) makes the card `unknown`, still with its error. `deliveryUncertain` says whether the recipient or external server got it. A Messaged result with a delivery status (`sentBeforeError` included) keeps the delivery it establishes. "Work may continue" is shown only after an MCP call returned.
- **Times.** `requestedAt` is the tool's start, the model's request, which may precede approval or execution by minutes. `resultAt` is when this connection saw the result. The gateway reports no delivery time, so `sentAt` is always null.
- **Recipient.** From the result's `sessionKey`, else the arguments' `sessionKey`, `agentId` or `label`. Its run state comes from the recipient run's events when this connection receives them: the client follows a few recent runs of sessions no viewer has open, and copies the ones a task's results name into `linkedRuns`, with `outcomeKnown`. A recipient run that ended without saying how is `recipient-outcome-unknown`, never "no reply yet" or "recipient stopped".
- **Late replies are not attached.** An inter-session reply names its source session and tool, not the send it answers, and several sends to one bot can be outstanding. Such rows are returned as incoming messages.
- **MCP names are opaque.** The gateway sanitizes, shortens and de-duplicates MCP tool names, so they are never parsed. A call is recognized from its result's `details.mcpServer` and `details.mcpTool`, or before a result from a caller-supplied map of exact tool names. A configurable list of server names marks the coding agent; no product name is built in.
- States move only forward, with the precedence of §6.1 and §6.2, when the caller passes the previous cards, except after an explicit correction of the call's result (`correction` differs), which starts again from the facts.

## Attachments

- Files do not travel in bridge commands: the web bridge's frames are capped at 64 KB. A renderer adds a file first and `sendMessage` names it by id. The web host takes it on `POST /attachments?name=…&type=…`. The path is treated as internet-facing: it needs the access cookie (the access link's `?token=` only establishes the cookie and is not accepted here) and an `Origin` that is exactly this plain-HTTP listener's own scheme, host and port; a browser always sends one with a POST, so one without it is refused, and the host terminates no TLS, so an `https` origin is refused too. It needs a declared length, refuses one over the ceiling for that type before reading the body, closes the connection on any refusal, and answers 408 to a body that has not arrived within `UPLOAD_DEADLINE_MS` (60 s), giving its room back. The Electron host takes the file's bytes over IPC, never a path, so a renderer cannot make the main process read a file of its choosing.
- Both put files in one host-side `AttachmentStore`: 6 MiB per image and 20 MiB per other file, checked before the bytes are encoded or kept, at most 20 files per message, at most 64 files and 32 MiB waiting in total, kept 15 minutes. An upload reserves its room before its body is read, so uploads arriving together cannot exceed those bounds. The whole `chat.send` frame is checked against `hello-ok.policy.maxPayload` (25 MiB) before it reaches the socket. Base64 grows a file by a third, so a single file near 20 MiB already exceeds the frame. A refused message leaves its files available, so the user can send fewer. Once a message takes its files they leave the store (`take`, with `restore` if the message is refused) and are kept by the client, counted against `MAX_RETAINED_ATTACHMENT_BYTES` (32 MiB across every outbox), until history confirms the message or the user deletes it; a cancelled message's files are dropped at once. A file is counted in one place at a time. A message past any of these is refused before anything is kept.
- **Stop.** `chat.abort {sessionKey, runId}`. The run is `stopping` until the gateway reports how it ended; a normal end first gives `completed` with `finishedBeforeStop`. Cards pending at Stop are held aside, closed when the stop takes. If the stop request itself fails, the run goes back to how it was, `waiting` with those cards restored if it had any, with `stopError`: the one transition outside the table. Questions of a run that ended are closed, and a late or repeated question event for an ended run is ignored.
- **Turn limit.** A run this client started fails after 50 minutes (`turnLimitMs`), and the client aborts it.
- **Size ceilings.** Before anything reaches the socket, a send is refused with `SendTooLargeError` when an image exceeds 6 MiB, a file 20 MiB, or the request frame `hello-ok.policy.maxPayload`; the gateway would otherwise close the socket with 1009 and no answer. The bridge does not carry attachments: its web frame limit is 64 KB.
- **Resync.** The protocol client closes the socket on a frame sequence gap; the reconnect reloads open tasks and sets `caughtUp: {reason: "gap"}`. Any other reconnect sets `reason: "reconnect"`, except the one that follows an approved step-up. A jump in a run's own `agent` seq is not loss: the gateway numbers frames before it coalesces assistant and thinking frames. A repeated or older frame for a run is dropped.
- **Reloads.** Reads of one task run one at a time, a further request runs once after, and a response is applied only to the same connection and the same opening of the task, so a slow read never overwrites newer state. History is rebuilt aside and merged by run id and step id; only the steps the merge takes from history bring their raw payloads, so a step and its raw lookup always agree, and the same history read twice gives the same state. The in-flight run is rebuilt from its rows plus its `inFlightRun` snapshot: the snapshot's progress events (tool, item and status events; it carries no thinking) are replayed into the run by step id, so a step the rows already finished is not repeated and the current step shows even when earlier iterations were persisted. The same snapshot applied twice changes nothing. A run that was active before the read and that the gateway no longer has in flight, with no row, has ended without saying how: it settles with `outcomeKnown: false`.
- **Retention is bounded by construction.** Every value the host keeps in its state has a named maximum and every collection a named count, declared once in `packages/core/src/state-bounds.ts` against the state's own types: a field added to a retained type without a bound does not compile. The unit throughout is the JSON character, the length in UTF-16 code units of a value's `JSON.stringify` form, quotes and escapes included, so a `"` counts two. The store applies the bounds to every write (`enforceState`): a string past its cap is cut and its path recorded in the nearest `cut` list; an id past its cap is replaced by a digest of itself; a value kept as received (a raw payload, an avatar) is kept whole or not at all; a list keeps its newest items; a value of the wrong shape is dropped. The engine applies first the counts that need judgment, oldest finished first, and says what it dropped (`omittedSteps`, `runsOmitted`, `questionsOmitted`, `unroutedApprovalsOmitted`). A question past `MAX_PENDING_QUESTIONS_PER_TASK` is not shown, and stays pending on the gateway. Nothing cut is kept anywhere else: the whole value is read again when asked for and returned without being kept (`readStepRaw`, within the promise above, `readApprovalText`, `readHistoryItem`), and an answer names an option by its original place, never by the text shown: it is sent as that option's `value`, else its label, read whole from `question.list` at that place, and refused if the option there no longer begins with what was shown. A question keeps its first `MAX_QUESTION_OPTIONS` options, each with its place and the gateway's `value`; the rest are counted in `optionsOmitted`. Outside the state, every map, set and array the client, a viewer's bridge session and the waiting files keep is named in one registry (`packages/core/src/owners.ts`) with its count and the most each entry holds; `owners.test.ts` reflects over the live objects' own properties and fails for any collection the registry does not name or that is past its count, and the host table below is arithmetic over the registry. Each of those keeps only the bounded representation, from the moment it is admitted: an unrouted approval and a task creation are the very objects the state holds, nothing whole beside them; ids used as map keys pass the id cap (`capId`), and a task key, bot id, label or file name past its cap is refused, never cut; the task list is cut to the rows and fields kept as each page arrives; only `hello-ok.policy`'s two ceilings are kept, and a foreign session's step payloads not at all. The worst case is then arithmetic, count × cap, computed by `worstCase` over the same schema, and `bounds.test.ts` checks the numbers here against it and drives the client with oversized and wrongly shaped input. `state.retention` estimates use against the total as a secondary alarm (`near` past 80 %); nothing relies on it.

## Core layout

- Core builds on `@openclaw/gateway-client/browser` (`GatewayProtocolClient` and `GatewayBrowserDeviceAuthLifecycle`), not on the Node `GatewayClient`. The browser entry takes an injected socket and uses no Node built-ins, so it can run in Electron, Node and Expo.
- The host passes in a WebSocket factory, a key/value store, a device signer and its client identity (`packages/core/src/host.ts`). The only globals core uses are `setTimeout`, `clearTimeout` and `URL`, declared in `src/globals.d.ts`.
- The Node implementations live behind a separate entry point, `@clawtrate/core/node`, instead of a separate package. They are a JSON file store, an Ed25519 key in a 0600 PEM file, and the built-in WebSocket. Electron's main process and the web host share them. ESLint stops shared core code from importing `node:*` or using Node and DOM globals.
- Hosts and the renderer talk through one bridge contract (`packages/core/src/bridge.ts`). The host pushes whole state snapshots, coalesced to one per 16 ms. The renderer sends a few validated commands; `invoke` also returns a command's answer (a sent message's id, a created task's key, a step's raw payload). Commands that act on a task are accepted only for tasks that viewer has open. Selection lives in the renderer.

## Apps

- `apps/desktop` holds the Electron main process, the preload script, the renderer entry and the web host. The interface itself is in `packages/ui`, so the desktop renderer and the browser load the same components.
- Electron runs with `contextIsolation` and `sandbox` on. The preload script is CommonJS because sandboxed preloads must be, and it exposes three functions. The window never navigates, and links open in the system browser.
- `CLAWTRATE_SCREENSHOT=<path>` makes Electron render offscreen, save a PNG and quit. It is there so the app can be checked on a machine nobody is looking at.

## Web preview host

- The host binds `0.0.0.0:5310` by default and keeps the gateway connection, the device key and pairing in Node. Browsers on other machines usually reach it over plain `http`, which is not a secure context, so signing could not happen in the browser anyway.
- Access token: 24 random bytes, generated at each start and printed once. A request carrying the valid token gets a `HttpOnly; SameSite=Strict` cookie and a redirect that removes the token from the URL. Every asset request and the `/bridge` WebSocket need the cookie. The WebSocket also checks that `Origin` matches `Host`. Comparisons are constant time. Static files are confined to the build directory.
- The development endpoint belongs to the selected dev-gateway instance (`--instance` or `CLAWTRATE_DEV_INSTANCE`, default instance otherwise), and only while it is proven (`tools/dev-gateway/src/endpoint.ts`): the instance's folder is the tool's own and not a link, its marker is valid and names the instance, the marker's run id, instance and checkout agree with this checkout's run file, the run file's port is the instance's (19001 for the default instance), the connection file is a regular file naming the same URL, instance and run id, and the recorded gateway is the live process the tool spawned, by PID and start time. Two files agreeing is never enough: a stale pair whose port another process has since taken is refused. The hosts import the tool's own name validator and proof, so they apply the same rules.
- `--no-access-token` is accepted only when that proof holds at startup. The client is then told to open nothing but the selected instance's endpoint, and the proof is run again before every connection, saved, typed or retried. It runs where the socket is created (`createSocket` in `packages/core/src/client.ts`), because `GatewayProtocolClient` schedules its own retries without going back through `connect`. A refusal there opens no socket, shows `GATEWAY_NOT_ALLOWED` and ends the retries, so a gateway that stops, is restarted with a new token, or whose process cannot be checked, is not reopened without a token. The desktop app and a web host with a token apply the same proof to the development gateway's address; connections the user makes to other gateways are not affected. The default instance's endpoint is refused like any other when a named instance is selected. If the host's data directory remembers another gateway, the host refuses to start rather than resume it without a token. The pairing screen shows `pnpm dev-gateway approve --instance <name>` for a named instance.
- Unauthenticated upgrade requests are untrusted input: a malformed cookie is an invalid credential, and any parsing failure is answered with 400 or 401 instead of reaching the process.
- **Viewers are bounded.** At most `MAX_WEB_VIEWERS` (8). A viewer's snapshot carries only the tasks it has open. A snapshot is written only once the socket has accepted the one before (`bufferedAmount` back to 0), and only while fewer than `MAX_SNAPSHOTS_IN_FLIGHT` (2) viewers hold one unaccepted; until then the viewer keeps a reference to the newest state, not a copy, so no older snapshot is held. A socket that does not accept its snapshot within `SNAPSHOT_DRAIN_TIMEOUT_MS` (30 s) is dropped at once with what it left buffered, not left to flush. A command result is at most `MAX_RESULT_CHARS` (262,144 JSON characters); a longer one is answered with an error, so text too long for it is read whole only in the desktop app, and an approval it belongs to can still be denied. A viewer that leaves more than `MAX_UNACCEPTED_RESULTS` (16) results unaccepted is dropped the same way.
- The development gateway's bootstrap token stays in the host. **Use the development gateway** sends a command, never the token.

## Development gateway

- **Instances.** `openclaw --dev` means one state folder and one port per machine, but a long-lived preview and several end-to-end runs in other worktrees need gateways at the same time. So every `pnpm dev-gateway` command addresses one instance. With no name it is the default instance: `--dev`, `~/.openclaw-dev`, ports 19001 and 19091, as before. With `--instance <name>` or `CLAWTRATE_DEV_INSTANCE=<name>` it is `--profile clawtrate-dev-<name>`. Names are 1 to 24 lowercase letters, digits and inner hyphens, `default` and `dev` are refused, and the check runs before any path is built, so no name reaches the default profile, the `--dev` profile or a profile without the `clawtrate-dev-` prefix. Both set to different names is an error.
- **How a profile maps to a folder and a port.** Read from the installed OpenClaw 2026.10.6: `--profile <p>` sets `OPENCLAW_PROFILE=<p>` and resolves the state folder to `$HOME/.openclaw-<p>` (`resolveProfileStateDir` in `profile-utils`), with the config at `openclaw.json` inside it. The gateway port is `OPENCLAW_GATEWAY_PORT` if set, then `gateway.port` in the config, then a hash of the profile name (`resolveGatewayPort`); only `--dev` defaults to 19001. The tool sets the environment variable, writes `gateway.port`, and passes `gateway run --port`, all to the same recorded port. The gateway's lock lives inside the state folder, so instances do not share one. OpenClaw derives its sandbox host (port + 1) and browser control (port + 2) ports from the gateway port, so those are kept free too.
- **Ports for named instances** come from 19200 to 19999 in blocks of 20: the gateway on the first port and the scripted model ten above it. `start` picks the first block, starting from one derived from the name, whose ports are free and not recorded by any instance folder, and records them in the new folder's marker, all under the machine-wide port lock, so concurrent starts never pick the same block. The run file records the same ports, and the runner refuses a marker whose ports are outside the range or differ from the run file's.
- **Profile.** Every OpenClaw command passes the instance's profile option (`--dev` or `--profile clawtrate-dev-<name>`), and also sets `OPENCLAW_PROFILE`, `OPENCLAW_STATE_DIR`, `OPENCLAW_CONFIG_PATH` and `OPENCLAW_GATEWAY_PORT` for that instance. Callers cannot pass `--dev` or `--profile` themselves. `reset` deletes only the instance's own folder, after checking the path is exactly `~/.openclaw-dev` or `~/.openclaw-clawtrate-dev-<name>`.
- **State is never reused.** OpenClaw loads a profile's own `.env` and auth stores at startup, after the environment allowlist has been applied, and keeps credentials in SQLite stores (`agents/<agent>/agent/openclaw-agent.sqlite`, `state/openclaw.sqlite`) that a clean profile also has with empty tables. No inspection of an old folder could prove it clean, so there is one way to start the gateway: `start` (and its alias `up`) stops the gateway this checkout started, deletes the instance's folder, creates it again empty with a `.clawtrate-dev-gateway` marker holding a new random run id, then configures, starts and seeds. The folder counts as the tool's own only if, checked without following links, the path is a real directory and the marker is a regular file written by the tool. Anything else is refused untouched; the tool never deletes a folder it does not own.
- **Process identity.** The marker records the instance name, its ports, the checkout whose tool created it and every process a start spawned on it: the start command itself, the scripted model and the gateway, each by PID and by its start time from `ps -o lstart`. The marker is always written whole and renamed into place. A look at a process has three outcomes. It is alive with a start time; it has exited, which needs positive evidence (the kernel answers `ESRCH` to signal 0, or `ps` shows it as a zombie); or it is unknown, which is every other result: `ps` could not be run, timed out, exited non-zero or printed something unreadable, or signal 0 failed for another reason. A recorded process counts as gone only when it has exited or a live process has its PID with another start time (a reused PID). Unknown is never gone: it refuses every signal and every deletion and is reported with its reason. A record missing either half, or naming a PID below 2, cannot identify a process, so the marker is not trusted. The run file in this checkout records only the run id, instance, checkout and ports.
- **Recorded before it can run.** A spawn followed by a file write is not atomic against the spawner being killed. So `start` first writes to the marker that it is about to spawn the scripted model (`providerPending`), then spawns it behind a gate: `/bin/sh` waiting for a line on a pipe from `start`, which then `exec`s the real command under the same PID and start time. `start` records the PID and start time, and only then opens the gate. If `start` dies before that, the pipe closes, the shell exits without running anything, and the pending record remains. A pending process therefore counts as running while its `start` runs, unknown while that is unknown, and gone once that `start` has exited. The gateway is spawned the same way, and so is the e2e preview host (`hostPending` in the run record).
- **Signals need proof.** Run files are per checkout and can be stale or edited, so `stop` signals a process only when the folder is the tool's own, its marker is valid, the marker's run id, instance and checkout agree with this checkout's run file, and the live process has the recorded PID and start time. The identity is checked again right before every SIGTERM and SIGKILL. If a process's state is unknown, `stop` signals nothing. After SIGTERM it waits for proof of exit, also through lookups that fail for a moment while the process exits (macOS `ps` shows such a process as `?E`), sends SIGKILL only to a process still proven alive, and if it cannot confirm that a process ended it keeps the run file and says so. A gateway's direct children are listed, with their start times, while it is still the proven parent, and each is signalled only if it is still that process. Anything that disagrees is refused and reported, and nothing is signalled. A run file whose folder is gone or holds another run proves nothing and is discarded without signalling. No PID of 0, 1, a negative PID or a process group is ever signalled.
- **Deletion needs proof that nothing runs.** `start`, `reset` and `prune` delete a folder only when its marker is valid and names the instance and folder it sits in, every recorded process is proven gone, and nothing listens on the instance's ports (19001 and 19091 for the default instance). Before deleting, `start` and `reset` also refuse, name the instance and the other checkout, and change nothing when something on the folder may run and this checkout's run file does not prove the run is its own. This is what protects a long-lived preview from builders in other worktrees. A marker without a recorded start time was written by an older version of the tool. It is never trusted, whether or not its processes still run, and the tool never deletes or adopts it. The README gives the one-time manual migration: stop the old processes by PID, rename the old folder aside, delete the old run file, then `start` on the now absent folder.
- **Locks.** Each instance has a lifecycle lock, held by `start`, `stop`, `reset` and `prune` from before their ownership checks until after the change they make, and port choice has a machine-wide lock. `start` holds it through the health check, the exec policy check and seeding, so no other of these commands acts on an instance that is still starting; they wait up to ten minutes. `status`, `seed`, `approve` and `list` take no lock. A lock is an exclusive SQLite transaction on a file in `~/.clawtrate-dev-gateway/locks/`, through Node's built-in `node:sqlite`. SQLite takes an operating-system file lock, so ownership is atomic, the lock is released when its holder exits however it exits, nobody ever judges another process's lock stale, and release closes only the holder's own connection. Lock files are never deleted, since deleting one while a waiter has it open would let two processes hold it; named instances share 64 lock files by a hash of the name, which can only serialise two instances, never mix them. The lock folder and its parent must be real directories and a lock a regular file; a link there is refused. A command interrupted by SIGINT or SIGTERM ends at its next step; a command killed outright leaves only gated processes it never released, which exit on their own, or recorded ones.
- **One boundary for OpenClaw.** Every `openclaw` subprocess, including the health check behind `status`, `seed` and `approve`, goes through one runner in `tools/dev-gateway/src/env.ts`. Before spawning it checks that the state folder is the tool's own and either was created by the start in progress or belongs to this checkout's run, by the marker and the run file, whose recorded gateway must still be the live process the tool spawned. Otherwise it reports why and spawns nothing. OpenClaw always runs with the state folder as its working directory, so no `.env` in the caller's directory is read.
- **Environment.** OpenClaw and the scripted provider run with an allowlist: `PATH`, `TMPDIR`, `LANG`, `LC_ALL`, `TZ` and `USER`, plus `HOME` and the dev profile variables. Everything else is dropped, including provider keys, auth tokens, base URLs and `NODE_OPTIONS`. A unit test checks this against a shell that sets them.
- **The scripted model** (`tools/dev-gateway/src/fake-provider.ts`) speaks the OpenAI Chat Completions streaming API on `127.0.0.1:19091`. It is registered as a custom provider:

  ```json
  "models": {
    "mode": "replace",
    "providers": {
      "scripted": {
        "baseUrl": "http://127.0.0.1:19091/v1",
        "api": "openai-completions",
        "apiKey": "scripted-dev-provider",
        "models": [{ "id": "dev-1", "reasoning": true, "input": ["text"], "contextWindow": 128000, "maxTokens": 8192 }]
      }
    }
  },
  "agents": { "defaults": { "model": { "primary": "scripted/dev-1" }, "thinkingDefault": "low" } }
  ```

  `models.mode: "replace"` keeps bundled and discovered providers out. The `apiKey` is a placeholder; the scripted server ignores it. Reasoning is streamed as `reasoning_content` deltas, which the `openai-completions` adapter shows only when thinking is not `off`, so seeded turns use `--thinking low`. Tool calls are standard streamed `tool_calls`. Replies are chosen by the user's prompt and the number of rounds since it, so the same conversation always produces the same output. The gateway prefixes user text with a timestamp and sometimes appends a runtime block; the planner strips both before matching.

- **Seeding** goes through the real gateway with `openclaw --dev agent --agent <id> --session-key agent:<id>:<task> --message …`. The command waits for the run's terminal outcome. The seeder requires `status: "ok"`, `summary: "completed"`, no abort, a `stop` stop reason and a final text that matches the script exactly. After each task it reads `chat.history` and checks the number of user turns, that every scripted tool call has a result and none failed, and that the session ends on a completed reply. Any mismatch fails the seed. Task titles are set with `sessions.patch` labels. Every start seeds its new gateway; running `seed` again verifies the existing sessions instead of duplicating them.
- **Bots.** Four invented bots: Juniper (research), Otto (home server operations), Marlow (editing) and Pip (planning). Juniper is the gateway's built-in `main` agent, restyled rather than replaced. Every gateway has one, it is the system and heartbeat agent, and deleting it fights the gateway. Each bot gets its own `AGENTS.md`; the interface draws its avatar as a character. The scripted tool calls use only `ls`, `read` and `write` inside each bot's workspace.
- **Sandbox config.** In addition to the provider settings above:
  - `gateway.nodes.pairing.autoApproveLocal: false`: loopback devices are approved like any other, so the pairing flow is exercised for real.
  - `tools.exec.mode: "deny"`: global, so every bot inherits it, including bots created later. Without a policy the gateway resolves `security: "full", ask: "off"`. The mode cannot be combined with `security` or `ask` in the same object; the gateway rejects that.
  - `tools.toolSearch: false`: tools are offered directly rather than behind `tool_search` and `tool_call` wrappers. The seeded tools were already offered directly, but later flows such as bot-to-bot messages need it.
  - `memory.search: { enabled: false, provider: "none" }`: memory search sits outside `models` and defaults to hosted embeddings.
  - `discovery.mdns.mode: "off"`, `update.checkOnStart: false` and the memory plugin's dreaming job off.
- **Enforcement.** `start` writes the config fresh and refuses to run if any of these guarantees is missing. `start` and `seed` both read the gateway's effective exec policy with `openclaw --dev approvals get` and fail unless every bot's effective exec security is `deny`. Unit tests cover the generated config.
- **Processes.** `start` writes its run file, `tools/dev-gateway/.run/state.json` for the default instance and `tools/dev-gateway/.run/instances/<name>/state.json` for a named one, git-ignored, next to the logs and the connection file. `stop` sends SIGTERM to the proven processes, waits up to 15 seconds, then sends SIGKILL, and does the same for any proven direct child the gateway left behind. Nothing is ever stopped by name.
- **Housekeeping.** `list` finds instances from their state folders under the home (`~/.openclaw-dev` and `~/.openclaw-clawtrate-dev-*` with the tool's marker) and shows each folder, its ports, whether its gateway is running and which checkout started it. `prune` is deliberate machine-wide maintenance: it removes every named instance, whichever checkout created it, that the deletion rule proves idle, each under its lifecycle lock with the marker read again after the lock is taken, plus this checkout's run folder for it. It never removes the default instance. `list` and `prune` refuse `--instance` and `CLAWTRATE_DEV_INSTANCE` rather than ignore them, and every command validates the selector before it does anything.
- **End-to-end runs use their own instances.** `pnpm e2e` names one instance `e2e-<run id>` and a sentinel `e2e-<run id>-other`, and gives each a dev-gateway run id of its own (`start --run-id`). It starts the sentinel unseeded (`start --no-seed`), so another instance's gateway is always listening, then its own seeded instance, builds the web renderer into a temporary folder and starts a preview host on a system-chosen port. It checks it never uses 19001, 19091, 5310 or 5311, and that the default instance, non-e2e instances and its sentinel are still running with the same PIDs and ports. It keeps a run record in `tools/dev-gateway/.run/e2e/`: the runner's identity, each instance with its run id (written before that instance's `start`), each temporary folder (written as it is created) and the preview host, which is written as pending before it is spawned behind a gate and completed with its PID and start time before the gate opens (`e2e/run-record.ts`). Cleanup removes exactly those, resetting each instance with `--run-id`, and never runs `prune`. The host's folders are removed only once the host is proven to have exited. Cleanup runs from the teardown, from a setup failure, on SIGINT and SIGTERM and at process exit, synchronously, after letting an interrupted dev-gateway command exit. A run killed outright leaves its record, and the next run in the same checkout cleans it up once that run's runner has exited. If the runner or the host is alive or unknown, the record and the folders stay and the reason is printed. Each run also has its own Playwright output folder, so runs in one checkout do not delete each other's traces.
- **What the tool trusts.** It trusts its own local records, written by the same user account: the state folder's marker, this checkout's run file and connection file, and the e2e run records. A recorded start time protects against a PID the system has given to another process since. It does not prove which program started a process: someone who can rewrite the marker can point it at any process of theirs whose PID and start time they read from `ps`, and `stop` would signal it. The tool does not defend against that, since such a writer could signal the process directly. It does defend against stale and mismatched records: a run file alone, or a run file and a connection file that agree, never authorise a signal, a deletion or a token-free connection. The state folder, its marker, the run file and the lock folder are never read through a link, and neither is the connection file when an endpoint is proven.
- **Ports.** Default instance: gateway 19001, scripted model 19091. Named instances: 19200 to 19999, chosen at start. Web previews 5310 and 5311. The e2e preview host uses a port the system picks (loopback only). The fixture mode serves on 5341 (loopback only).

## Brand

- `assets/brand/logo.png` is the only hand-placed brand file. `pnpm brand:icons` (`tools/brand/src/make-icons.ts`) derives everything else from it with a small PNG codec, so no native image dependency is needed. The outputs are the Electron icons (`apps/desktop/resources/icon.png`, `icon-mac.png`, `icon.icns`, `icon.ico`), the favicons, and the in-app mark (`packages/ui/src/assets/logo-mark.png`). `assets/brand/generated.json` records the logo's hash, and a unit test fails when the icons are older than the logo.
- The logo must not carry provenance, text or camera metadata (`caBX`, `tEXt`, `iTXt`, `zTXt`, `eXIf` chunks). `pnpm brand:strip` removes them in place and copies every other chunk byte for byte, so the pixels do not change. `pnpm brand:icons` refuses a logo that still has them, and a unit test checks the committed file.
- Accent tokens come from the mark's mint. Dark theme: `--accent` `#3ee6c1`, hover `#6cf0d3`, text on accent `#04261f`. Light theme, where the raw mint is only 1.6:1 on white: `--accent` `#0a6e5c` (6.2:1 on white), hover `#06624f`, indicator line `#0d8f77` (above the 3:1 minimum for non-text).
- **Palette.** The chrome is neutral grey with no tint (`docs/design/visual-language.md`, section 2): two surfaces, the rail and the stage, and one raised fill for bubbles and cards. Selection and primary buttons are neutral too. The accent appears only on your own bubbles (`--bubble-user`, its own token so it can later be switched to neutral), on unread dots, on a working mark, on focus rings and on links. Colour otherwise belongs to the bots' avatars.
- **Avatars.** A bot without a picture is drawn as a character, a flat body and colour with a dark visor, chosen from a stable hash of its id (`packages/ui/src/Avatar.tsx`), so it looks the same on every device. A bot whose gateway identity has a picture shows the picture cropped to a circle. The development gateway no longer generates pattern pictures for its seed bots, so the preview shows characters.
- **Where the mark appears.** Inside the app the mark appears only on the connection and pairing screens, at 56 px. The rail has no product name.
- **Type.** One family, Figtree (`@fontsource-variable/figtree` 5.3.0), in two weights, with JetBrains Mono (`@fontsource-variable/jetbrains-mono` 5.3.0) for code. Both are under the SIL Open Font License 1.1, which allows bundling them in an MIT app as long as the fonts are not sold alone and their notice travels with them; the font packages carry it. The bundler includes the fonts from the packages, so the app loads no fonts from the network and no font file is committed. Instrument Sans and Instrument Serif are removed.

## Interface: the visual language

The shell follows `docs/design/visual-language.md`, built in the order of its section 14. What a later builder should know:

- **One test for each layout switch, shared with the stylesheet.** `packages/ui/src/layout.ts` holds the two widths: one pane below 688 px of `.app`, and Work docked from 960 px of `.main-pane`. The stylesheet's container queries use the same numbers, and the code measures the same elements with a `ResizeObserver`, so the layout and the behaviour that depends on it (the drawer's dialog role, focus, `inert`) cannot disagree.
- **Selection.** `packages/ui/src/selection.ts` keeps the selected bot, the remembered task for each bot (it wins over the most recent), the bots unfolded by hand and whether the open bot was folded by hand; the last two persist. A bot's row summarises all of its tasks with three independent signals (latest activity, unread, run state, failed before working).
- **May this connection write?** `canWrite` in `packages/ui/src/access.ts` returns false: the client asks for `operator.read` and the bridge has no command that writes. Nothing that creates or sends is rendered; the composer is the read-only pill.
- **The strip.** `packages/ui/src/StatusStrip.tsx` derives every state from what the shell already has. After a connection problem the shell is "dropped" until bots, tasks and the open task have loaded again, then "Synced" shows for four seconds. The core stamps each connect (`connection.connectedAt`) and each successful history load (`transcript.loadedAt`), so a transcript kept from before the drop, which still says "ready", does not count as in sync until it has reloaded; a reload that fails is "Couldn't sync this task", never "Synced". "Try again" for one task sends `closeSession` and then `openSession`.
- **Following the end of a transcript.** The view follows new output while the reader is at the end. A scroll the reader did not make, such as content growing when fonts arrive, keeps following; only the reader moving up stops it. Otherwise width changes keep the text at the reading line, just under the protected band, where it was: the character there when the engine's caret API can say which, or else the top of its paragraph, list item or row. The browser's own scroll anchoring is off on the transcript.
- **Focus.** On one pane, opening a conversation moves focus to its heading and Back moves it to the row that opened it. Closing Work returns focus to the control that opened it, if that is still visible and focusable, or else to the Work toggle. "Check now" stays focusable while it checks.

Where the build departs from the specification, and why:

- **Task rows show their time.** The specification says "With no mark, the title has the whole row." and puts the time of last activity only in the row's accessible description (`docs/design/visual-language.md`, section 7). `F-425`, the designer's corrected prototype screenshots and the review of this work ask for it in the row. Each task row shows it, right-aligned in 12 px tabular figures, followed by one fixed 12 px slot for its mark or unread dot, so times line up whether or not a row has a mark. The row stays 34 px, the title gives way with an ellipsis, the full title is still on hover and focus, and the time is still in the accessible description.
- **The title pill opens Work and does not close it**, as the specification says; the panel button toggles. Its name always ends "Show details."
- **A failed discovery in the strip** reads "Couldn't load bots and tasks" ("Couldn't load bots" on the phone), with the gateway's message as the explanation after the dot; "Can't reach <gateway>" becomes "Can't reach the gateway" on the phone. The strip's state may shorten after its explanation has, and never runs under its action; the whole line stays in the strip's text, which its live region announces, and in its tooltip.
- **A task with no messages** says "Messages between you and <Bot> in this task will appear here." The specification's "Say what you need" invites typing, which a read-only connection cannot do.
- **The development gateway's hint** ("127.0.0.1:19001, started with `pnpm dev-gateway up`") moved into the button's tooltip, so the connect screen has the one hint the design gives it.
- **A connection error** is titled "Could not connect"; the error's code stays visible, small, under the sentence, for support.
- **System messages** are centred event lines outside `.turn`, as before, so `transcript-turn` still counts user and assistant items only.
- **The gateway's name** is its address (host and port): the gateway does not report a name.
- **A task with nothing saved, while the gateway is away** (after a reload, for example) shows "Waiting for the gateway" instead of loading skeletons that could never finish.
- **The task-title tooltip** shows on any focus, not only keyboard focus, so a test can focus a row and see it.
- **Pins, sections, search, "+" and New task** are not rendered (section 14 says so). The `.pin*` and `.rail-section` rules, the composer's field and send button and the extra state marks were not brought over, On a read-only connection the rail's top holds no controls. The specification allows only a 12 px drag band there and keeps the product's mark and name out of the rail ("There is no product name in the rail and no heading above the bots."). The band is the full header height instead (56 px, 60 on touch), the same band the conversation's floating controls sit in, so both panes share one top edge and the list starts where it will sit once search and "+" exist; on macOS it also clears the window controls.

## Fixture mode and visual tests

- **Fixture mode.** `apps/desktop/src/fixture/` is a separate Vite entry (`apps/desktop/vite.fixture.config.ts`, output `out/fixture`) that renders the shared `App` through a `ClawtrateBridge` holding fixed state: five bots (one with a picture, one with one task, one with fourteen, a long name), a long transcript with reasoning and tool calls in every state, and scenes for pairing, reconnecting, catching up, synced, a task that failed to sync or load, an empty gateway and more. It cannot reach a packaged app: neither the Electron build nor the web preview's build refers to it, and `apps/desktop/test/fixture-isolation.test.ts` fails if one does. Its page sets `connect-src 'none'`, and a visual test checks that it requests nothing but its own files. `pnpm fixture` serves it on `127.0.0.1:5341`.
- **Visual tests.** `pnpm visual` (`playwright.visual.config.ts`, tests in `visual/`) builds and serves the fixture and runs three things: screenshots of the connect, pairing and main views, Work closed and open, in light and dark at 1440, 1100 and 800 px and at phone width (390 × 844 with a touch pointer), plus the phone's bot list; a legibility audit over fourteen states in both themes at 1440 px and phone width that measures every rendered text node's size (at least 12 px) and its contrast against its composited background (at least 4.5:1), skipping only what is inert behind the drawer's scrim; and behaviour checks for the rail, the Work pane, the strip and the phone. The clock is fixed and the time zone is America/New_York, so times are stable.
- **Tolerance.** A pixel differs when its colour moves more than Playwright's 0.2 threshold; a screenshot passes with at most 0.2% of pixels different. Animations are stopped and the caret hidden.
- **The baselines are specific to macOS.** Font rasterising differs between operating systems, so the baselines live under `visual/baselines/darwin/` and only that platform can compare against them. They are not part of the CI workflow. They were approved by the builder's own review, not yet by the owner.
