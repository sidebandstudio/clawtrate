# Roadmap

What is left to build in Clawtrate, in what order, and how to take a part of it. Read this first if you want to contribute.

## The product, and what done means

Clawtrate is a desktop (Electron) and iOS client for an OpenClaw gateway you already run. It puts your bots in a sidebar with tasks under each bot, shows what a bot did as plain-words cards beside the conversation, and gives you fine-grained control over each bot: its model, account, tools, memory and machine. The agent runtime is the gateway; Clawtrate is the client, and where the gateway lacks something, the project adds an OpenClaw plugin under `plugins/`.

Done is defined row by row in [`docs/parity.md`](parity.md). Each row is one behavior with a stable id (`F-012`), a platform (`desktop`, `iOS` or `both`), a target, what the gateway gives it, and a status. A row is `done` only when an automated check whose title begins with its id passes and would fail if the behavior broke; a `both` row whose desktop check passes is `desktop done` until its iOS check exists; a row the gateway cannot support becomes `gap` with the evidence.

Three rules hold for every part of the plan:

- **Design before build.** Where an area has a document in [`docs/design/`](design/), that document governs how it looks, reads and moves, and `docs/parity.md` governs what must be true. An area without one gets its design document and a clickable prototype (`docs/design/prototype/`, with a check file under `docs/design/prototype/tools/checks/`) before it is built.
- **Nothing is claimed that the gateway does not do.** Each row's gateway cell names the methods it relies on; [`docs/research/gateway-capabilities.md`](research/gateway-capabilities.md) is the map. A screen says what the gateway established and no more.
- **Everything is developed against a development gateway** with a scripted model (`pnpm dev-gateway`, see the [README](../README.md) and `tools/dev-gateway/README.md`): no real provider, no real key, loopback only. Add scenarios there when a row needs gateway behavior on demand.

Status lives in `docs/parity.md` and in the issues, not here. This document says what each segment is, what it needs and who has it.

## How the plan is cut

The plan is divided into milestones and each milestone into segments. A segment is one GitHub issue: a set of rows that one pull request series can finish, or a design, a plugin, or a piece of engine or packaging work that rows depend on. Every row that is not yet done appears in exactly one segment for each platform it still lacks. Each milestone has a tracking issue that lists its segments.

In the tables below, **Rows** lists the rows a segment owns (for an iOS segment, their iOS side). **Needs first** names the segments that must land before it. **Designed** says whether the design that governs it exists. **Who** is `maintainers` (being done now; please don't start it), `naman0r` (that contributor's section), or `open` (anyone may take it once what it needs is done; `help wanted` marks the ones best suited to a first contribution). The code in parentheses after a segment's name is its stable short name in the project's planning.

## Plugins the gateway needs

A plugin runs inside the gateway with the gateway's own access, so each one is written from a list of requirements, tested on development gateways (`pnpm dev-gateway start --instance <name> --with-plugin <plugin>`, with a `clawtrate-dev-contract.json` the tool's guard checks), and reviewed before it is offered for real gateways.

## The iOS app

The iOS app is an Expo app in `apps/mobile` that runs the same `packages/core` as the desktop app, with the host supplying the WebSocket, storage and signing. Its work is ordered this way:

1. **The foundation** ({{issue:ios-foundation}}), being built now: the app itself, how its checks run against a development gateway and in a fixture mode, and the iPhone and iPad shell. Then the iOS side of milestone 2 ({{issue:ios-shell-sidebar}}), also being built now.
2. **The iOS side of each later feature follows its desktop side.** Each iOS segment waits on the foundation and on the desktop segment for the same rows, and takes the phone layouts from the design documents (`docs/design/visual-language.md` section 12, and each document's phone section). Nothing on iOS asks the gateway for more than the desktop app asks for the same behavior.
3. **Rows only the phone has** (the share sheet, Siri and Shortcuts, Live Activities, the phone as a node, push) sit in the iOS segment of their feature.

The iOS half of a `both` row is proven the same way as its desktop half: by an automated check on the iOS app, run as the foundation sets out and against a development gateway or the fixture mode, whose title begins with the row's id. A `both` row moves from `desktop done` to `done` only when both checks pass. An iOS-only row is `done` with its iOS check.

## Taking a segment

1. **Pick an issue that is `open`.** Start with one marked `help wanted` if this is your first contribution. Leave issues marked "in progress, maintainers" alone, and comment on them if your work needs something from them.
2. **Comment on the issue** to say you are taking it, with a short plan: the order you will build in and any question about the design or the gateway. A maintainer assigns it to you. If you stop, say so on the issue so that someone else can take it.
3. **Keep to your files.** So that two streams of work do not collide, a segment has its own files and touches shared files only in small, additive ways:
   - **Yours** (create these; nobody else edits them): the segment's design document and prototype pages if it is a design; new engine modules under `packages/core/src/` and new interface folders under `packages/ui/src/` named for the feature, with their tests; its plugin folder under `plugins/`; its checks, as new files under `e2e/` and `visual/`, with their baselines; its development-gateway scenarios, in modules of their own under `tools/dev-gateway/`; and the status cells of its rows.
   - **Shared** (keep each change small and additive, and rebase often; `main` moves several times a day): `docs/parity.md` (only your rows), `docs/decisions.md` (a section of your own), `README.md` and `CONTRIBUTING.md`; the entry points where the sidebar and Settings link to your pages, the bridge's command list, and the engine's registry of retained state (`packages/core/src/state-bounds.ts` and the documented totals in `docs/decisions.md`: everything the engine keeps is bounded and registered); and the scenario list of `tools/dev-gateway`.
   - **Not yours for now**: anything a segment marked "in progress, maintainers" is changing. Open an issue first if you need something there.
4. **Open a pull request to `main`** that names the issue. Several small pull requests are better than one large one.

A pull request is judged on these points:

- `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm e2e` and `pnpm visual` pass, and so do CI's three jobs ([CONTRIBUTING.md](../CONTRIBUTING.md) has the commands).
- Each row it marks `done` or `desktop done` has a check whose title begins with the row's id, and the check would fail if the behavior broke. A row that cannot be done is left `todo` with the exact reason, or made `gap` with the evidence, in its gateway cell.
- It follows the design that governs it, at 1440, 1100 and 800 px and the 390 px one-pane layout, in light and dark, by keyboard and with a screen reader.
- It claims nothing the gateway does not do, asks for the smallest scope that works (read first, the interactive tier on first use, admin only on an explicit request), and records in `docs/decisions.md` what a later contributor needs to know, including what the gateway really returned where it differs from the map.
- It develops only against development gateway instances, never a real provider, key or your own OpenClaw profile.
- Commits are small and in plain sentences, and the change carries no secrets, private host names, addresses, user names, home paths or third-party images: the repository is public.
