# @clawtrate/account-protocol

The signing, device list and join of a Clawtrate account, as the account design (`docs/design/accounts.md`, #641, §4.2, §4.4 steps 1 to 5a, §4.5, §4.6 and §8.4) has them: the keys and what each may sign, the device list, the join with its three words and decoys, the gateway's sealed card, the list secret, and the session request a device signs for the account service. The connector, the account service and the apps will build on it. Nothing imports it yet.

**It has had two rounds of independent cryptographic review, each with a confirming review; this version makes the changes the second round listed, and the design's additions that came with them.**

It does no I/O and has no clock or random source of its own: every time and every random byte comes in as an argument, so it runs the same in Node, Electron, a Worker and the phone app, and every test is deterministic. Where a random value matters to the sealing or a secret, the package derives it, or hedges the caller's bytes with secret key material, so a repeated or predictable argument can't weaken it. The join is the exception: a new device's commitment comes from its keys and the caller's bytes, so the same keys with the same bytes give the same commitment, and the one-reveal rule holds only because the package refuses a second join from one list key in a running program and the caller never rebuilds an attempt (below, "The rules the words rest on"). It uses `@noble/curves`, `@noble/hashes` and `@noble/ciphers` at the versions the repository pins, `TextEncoder` and `TextDecoder` (with `fatal: true` and `ignoreBOM: true`) and nothing else. It imports nothing from `packages/relay-protocol`.

The rule it exists for: signing in never admits a device; only a signature from one of the person's own devices does, and the account service holds nothing that can sign. Here that means: the list grows only by an entry signed with a device member's list key after a person's pick; no function signs bytes a caller hands it whole, each builds its object's bytes from that object's fields; and every signed object starts with a label of its own, so a signature made for one kind never verifies as another.

### Values the package derives or hedges

Each is one HKDF-SHA256 call or one HMAC-SHA256 call; "the key's random bytes" are the 32 bytes the key was made from, which only this package reads.

- **N's nonce:** HKDF-SHA256 with N's list key's random bytes as input, the caller's 32 random bytes as salt, and as info the `join new nonce` tag, the gateway and account ids and N's encoded record.
- **A's answer nonce:** HKDF-SHA256 with A's list key's random bytes as input, no salt, and as info the `join answer nonce` tag, the gateway and account ids, the commitment and the hash of the head A answers from. No caller randomness: the same commitment at the same head always gets the same answer, and at any other head an answer no one without A's key can predict.
- **The decoys:** 1,024 bytes of HKDF-SHA256 with A's list key's random bytes as input, the transcript hash as salt and the `join decoys` tag as info.
- **N's word-back words:** 256 bytes of HKDF-SHA256 with N's list key's random bytes as input, the transcript hash as salt and the `join word back decoys` tag and A's confirmation signature as info.
- **A confirmation's HPKE ephemeral input:** HKDF-SHA256 with A's list key's random bytes as input, the caller's 32 random bytes as salt, and as info the `join ephemeral` tag, the delivery's HPKE `info` (which holds the transcript hash) and the SHA-256 of the payload it seals.
- **A rotation share's, or the first secret's, HPKE ephemeral input:** HKDF-SHA256 with the connector key's random bytes as input, the caller's 32 random bytes as salt, and as info the `rotation ephemeral` tag, the share's HPKE `info` (which holds the epoch, or the first entry's hash, and the recipient) and the SHA-256 of the secret it seals.
- **Each list secret:** as in the table above.
- **The list seal's nonce:** the first 24 bytes of HMAC-SHA256, keyed with HKDF-SHA256 of the list secret (no salt, `list seal nonce` tag as info), over the `list seal nonce` tag, the version, kind and epoch, the gateway and account ids, the caller's 32 random bytes and the plaintext.

A hedged value can't be predicted by anyone without the key, whatever the caller's bytes are; with fresh caller bytes it can't be predicted even by someone who learns the key. A repeated random reuses an HPKE ephemeral only for an identical plaintext to the same recipient.

## Keys

Each key and purpose is its own class, so one can't be passed where another is expected. A public key class checks its bytes when it is made; a secret key class is made from 32 random bytes the caller supplies, derived for its purpose (above), and its secret is reachable only by this package's own signing, opening and derivation functions (never printed, serialised or exported). Every key, secret and state object is frozen, and the package's internal files can't be imported from outside it (a lint rule for the whole repository).

| `ListSecretKey`, `ListPublicKey`       | Ed25519   | each device, and the connector | List entries, refusals, the join's reveal and confirmation, and its half of a fresh start or a re-link (a device); the first entries, the card, the head, removals and withdrawals, its half of a fresh start or a re-link, the list secret's rotations and first message, and on a server its first join's answer and confirmation (the connector). |

## Encoding

One encoding for everything signed, hashed or sealed:

- `u8`, `u16`, `u32`: unsigned big-endian integers of 1, 2 and 4 bytes. `u64`: 8 bytes big-endian, at most 2^53 − 1.
- `bytes[n]`: exactly `n` bytes.
- `var`: a `u16` length, then that many bytes, within the field's bounds.
- `text`: a `var` holding UTF-8, decoded strictly (no overlong forms, no surrogates), holding no control character (`\p{Cc}`), no bidirectional formatting character (`\p{Bidi_Control}`) and no invisible one (`\p{Default_Ignorable_Code_Point}`, which includes a byte-order mark and zero-width characters).
- `label`: the object's label, exactly, as ASCII. The same kind's label with another version is refused as `unsupported_version`.
- `context`: the gateway's random id, `bytes[16]`, then the account's id, `bytes[16]`. Every object carries it or is sealed under it.

Nothing is optional and nothing is skipped; a decoder refuses bytes cut short or left over, an unknown enum value, a length over its bound and a key that isn't one, so a value has exactly one encoding. Every public function copies its byte arguments once on entry and works on the copy.

## Objects, byte for byte

`sig(K)` is a 64-byte Ed25519 signature by `K` over every byte of the object before it (for a first entry, before the first of its two signatures).

**Device record** (`record`): `bytes[32]` list key, `bytes[32]` seal key, `bytes[32]` TLS pin, `bytes[32]` gateway device key, `u8` platform (1 macOS, 2 Windows, 3 Linux, 4 iOS), `text` name (1 to 64 bytes). The name is what the device says; nothing checks it, so members show it as "says it is". Only the list key is proven, by the reveal's signature; the TLS pin, the gateway device key and the seal key are claimed here and proven later, by the TLS handshake, the connector's door and use.

**List entry**: `label`, `context`, `u32` position (0 for a first entry), `bytes[32]` previous entry's hash (zeros for a first entry), `u8` type, then:

| Type           | Fields                                                                                                                                                                                                                                                                                                                                                                                                                | Signatures                                |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 1 first        | `bytes[32]` connector key, `record` of the linking device                                                                                                                                                                                                                                                                                                                                                             | `sig(connector)`, `sig(linking device)`   |
| 2 add          | `record`, `bytes[32]` join transcript hash, `bytes[32]` signer                                                                                                                                                                                                                                                                                                                                                        | `sig(signer)`                             |
| 3 remove       | `u8` origin (1 a member, 2 the account page, 3 a withdrawal), `bytes[32]` target, `bytes[32]` signer                                                                                                                                                                                                                                                                                                                  | `sig(signer)`                             |
| 4 restore      | `bytes[32]` target, `bytes[32]` signer                                                                                                                                                                                                                                                                                                                                                                                | `sig(signer)`                             |
| 5 server first | `bytes[32]` connector key, `record` of the first device, `bytes[32]` join transcript hash                                                                                                                                                                                                                                                                                                                             | `sig(connector)`, `sig(first device)`     |
| 6 fresh start  | `u32` generation, `bytes[32]` connector key, `u32` old list's length, `bytes[32]` old list's latest entry hash, `record` of the gateway's own device, `u8` count (0 to 31), each current device's `record` and `bytes[32]` its nearest current ancestor (zeros for none), then `u8` count (0 to 32), each account-page removal that can still be put back, as a `record` and `bytes[32]` its nearest current ancestor | `sig(connector)`, `sig(gateway's device)` |
| 7 re-link      | `bytes[32]` the device that takes the gateway device's role                                                                                                                                                                                                                                                                                                                                                           | `sig(connector)`, `sig(that device)`      |

An entry's hash is `taggedHash(entry hash, the whole entry with its signatures)`. The list as one byte string, for sealing: `u16` count, then each entry as a `var` (the first up to 14,799 bytes, a fresh start; every other up to 488).

**Removal notice** (the account page's removal, unsigned): `label`, `context`, `bytes[32]` target.

**Head**: `label`, `context`, `u32` generation, `u32` the list's length, `bytes[32]` its latest entry's hash, `u32` the secret's epoch, `bytes[32]` the card's hash, `u32` the card's serial, `sig(connector)`. Its hash is `taggedHash(head hash, the whole head)`. In code a head is a `Head`, a frozen object only `verifyHead` makes; a reader persists `head.bytes` and verifies them again when it reads them back.

**Refusal**: `label`, `context`, `bytes[32]` the list's latest entry hash, `bytes[32]` the join's commitment, `u8` reason (1 a wrong set picked, 2 none match, 3 not started by me, 4 two joins at once), `bytes[32]` signer, `sig(signer)`. Its hash, by which the connector takes it once, is `taggedHash(refusal hash, the whole refusal)`.

**Card**: `label`, `bytes[16]` gateway id, `u32` serial, `bytes[32]` connector key, `bytes[32]` the connector's TLS pin, `u8` address count (1 to 8), each address a `text` host and a `u16` port (1 to 65535), `text` the gateway's name (1 to 64 bytes), `sig(connector)`. A host has one form: an IPv4 dotted quad with no leading zeros; a lowercase DNS name whose every label starts with a letter (1 to 63 bytes of letters, digits and inner hyphens); or an IPv6 address in brackets in its shortest lowercase form (RFC 5952). No port goes in a host. A device builds the address as `wss://<host>:<port>/`. Its hash is `taggedHash(card hash, the whole card)`. A card is checked against the connector key the reader already trusts (the list's, from its first entry), never against the key the card names, and is taken only as the card the newest head names.

**Join messages**: `label`, `u8` step, `context`, then:

| Step      | From | Fields                                                                                                                                         |
| --------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 commit  | N    | `bytes[32]` commitment                                                                                                                         |
| 2 answer  | A    | `bytes[32]` commitment, `bytes[32]` A's list key, `bytes[32]` the list's latest entry hash, `bytes[32]` the card's hash, `bytes[32]` A's nonce |
| 3 reveal  | N    | `record`, `bytes[32]` N's nonce, `bytes[32]` transcript hash, `sig(N's list key)`                                                              |
| 4 confirm | A    | `bytes[32]` transcript hash, `var` the entry (up to 488 bytes), `bytes[32]` HPKE `enc`, `var` HPKE ciphertext, `sig(A's list key)`             |

On a server's first join, A is the connector, the answer's list head is 32 zero bytes, and the confirmation's entry is the server's first entry carrying only the connector's signature.

The HPKE plaintext in a confirmation: `u32` epoch, `bytes[32]` list secret, `var` the signed card. Its `info`: `device seal` tag, `u8` 1, gateway id, account id, transcript hash. No associated data.

**Rotation of the list secret**: `label`, `context`, `u32` generation, `u32` the list's length and `bytes[32]` its latest entry hash (the head it follows), `u32` epoch, `u8` count (1 to 32), each share `bytes[32]` recipient's list key, `bytes[32]` HPKE `enc`, `bytes[48]` HPKE ciphertext of the 32-byte secret; `sig(connector)`. Each share's `info`: `device seal` tag, `u8` 2, gateway id, account id, `u32` epoch, recipient's list key.

**First secret**: `label`, `context`, `bytes[32]` the first entry's hash, `bytes[32]` the linking device's list key, `bytes[32]` HPKE `enc`, `bytes[48]` HPKE ciphertext of the epoch-0 secret, `sig(connector)`. Its `info`: `device seal` tag, `u8` 3, gateway id, account id, first entry hash, recipient's list key.

**Sealed with the list secret**: `u8` version 1, `u8` kind (1 the list, 2 the card, 3 an entry), `u32` epoch, `bytes[24]` nonce, then the XChaCha20-Poly1305 ciphertext with its 16-byte tag. The key is HKDF-SHA256 of the secret, no salt, `info` the `list seal key` tag, 32 bytes. The nonce is synthetic (above). The associated data is the `list sealed` tag, the 30-byte header, the gateway id and the account id.

**Session request**: `label`, `text` audience, `bytes[32]` session key, `bytes[32]` the service's challenge, `u64` the device's time in milliseconds, `u8` method (1 GET, 2 POST, 3 PUT, 4 DELETE), `text` path (`/` then printable ASCII, up to 512 bytes), `bytes[32]` `taggedHash(session body, body)`, `sig(session key)`. The audience is the service's origin, `https://host[:port]` in lowercase with a DNS name or IPv4 address as host (no IPv6 literal) and a port of 1 to 65535; `http:` on loopback is accepted only when the caller says it is a development build, because on a shared machine another user could listen on that port first. It relies on two things the service keeps: each session key belongs to exactly one account (no account id is signed), and each challenge is taken once and issued to this device alone.

## The list

`ListState` is what a verifier knows after an entry: the list's generation, the current members with their roles (`connector`, `gateway-device` for a first entry's device or a re-link's, `device`), who added or put back each, the removed ones and how, and every key and pin the list has held. A list starts with one of three first entries, each signed by the connector and its device: the linking app's first entry; a server's first entry, after the server's terminal confirmed its first device (that device holds the gateway device's role); or a fresh start. `ListState.fromGenesis` checks a first entry and `state.append(entry)` the next one, as the connector builds its own list; a reader uses `verifyList(context, entries, head, held)`, which also checks the connector's head and the head held (below). Each append runs these checks in this order and stops at the first failure: the bytes; the signature (so any change to a signed field is `bad_signature`); the gateway and account; the position and previous hash (`bad_chain` for a reordered, repeated or forked entry); for an add or a restore, the growth limit (`list_full`); the signer is a current member (`not_member`, `removed_member`); then the rules:

| Entry                       | Who may sign it                                                                     | What it needs                                                                                                                                                                                                                                                                            |
| --------------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a first entry               | the connector and its device                                                        | position 0, zero previous hash, no key appearing twice; a fresh start's generation at least 1                                                                                                                                                                                            |
| add                         | a device member, never the connector                                                | no key of the record appears twice in it, and no key or pin of it is or was on the list in any role, the connector's key included, except an OpenClaw key a withdrawal freed, which comes back only as an OpenClaw key (`duplicate_key`); fewer than 32 devices. Built only by the join. |
| remove, by a member         | any device member (`signRemoval`), or the connector (`signRemovalOnGatewayMachine`) | the target is a current member, not the connector (`protected_member`); the gateway machine's own device only by itself or the connector (`protected_member`)                                                                                                                            |
| remove, by the account page | the connector alone (`signRemovalNotice`)                                           | as above, and the target is not the gateway's own device (`protected_member`)                                                                                                                                                                                                            |
| withdrawal                  | the connector alone (`signWithdrawal`)                                              | the target is a device an add made a member, never put back and in no first entry, that has signed no entry (`bad_target`); only its OpenClaw key is freed, and only for that role                                                                                                       |
| restore                     | a device member, never the connector                                                | the target's latest removal came from the account page (`bad_target`); fewer than 32 devices. It comes back with its record as it was, put back by the signer.                                                                                                                           |
| re-link                     | the connector and the device taking the role (`signRelink`, `assembleRelink`)       | no current device holds the gateway device's role, and the target is a current device member (`bad_target`)                                                                                                                                                                              |

The connector is removed only by unlinking, which ends the list; no entry removes it. Adds and restores are refused once a list holds 1,024 entries (`GROWTH_LIMIT`); a removal or a re-link is never refused for the list's size, so no device can make itself impossible to remove, and a list holds at most 1,089 entries (`MAX_ENTRIES`: the growth limit, a removal of every device, a re-link before each removal of the gateway's own device, and one more re-link). Before the bound matters, the connector starts the list afresh (`FRESH_START_AFTER`, 900 entries, or whenever the gateway's machine asks; the connector's to decide). `state.addedBy(key)` names the devices an entry by `key` added; `state.causedBy(key)` names what removing `key` offers to remove too: every current member that descends from it through adds or restores (a device it added, a device that one added, a device it put back, and on), walking through removed devices too, so removing a device in the middle doesn't hide what came after it. For a device put back, the member that put it back is the one it descends from. `state.rotationPoint` says whether the latest entry is a removal or a restore, the only places a rotation follows.

The sign functions return only the entry: whether it is on the list is the connector's to decide when it appends it. Who appends: a member sends its entry (sealed with the list secret) through the service to the connector, which appends it with `openEntry` or `append` to the list it holds; the connector's list is the one that counts. The connector may refuse an entry a member signed (its list moved, a pause, a full list), so "Confirmed" on a member can come before the connector's refusal; the new device then holds the list secret and card without being a member, and gets no pass.

**A withdrawal** takes out an entry that never paired (design §4.4 step 5a): the connector signs it when an added device doesn't pair within `WITHDRAW_AFTER_MS` (10 minutes, the connector's to time). It frees only that entry's OpenClaw key, and only as an OpenClaw key, so the same device, with its same OpenClaw identity, can join again with new list and seal keys; its list key, seal key and TLS pin stay burned, and the freed OpenClaw key is refused as any other kind of key. Every other removal burns every key: the list refuses them for good.

**A fresh start** is a new first entry (generation one higher) carrying the old list's length and latest entry hash, its current devices, and its account-page removals that can still be put back (the latest 32), each with its nearest current ancestor for "what it caused". `signFreshStart(key, state)` builds it from the state for the connector or the gateway machine's own device to sign, and `assembleFreshStart` puts it together; a list with no device in the gateway device's role can't start afresh. A member takes it with `state.freshStart(entry)` only when it is the next generation, signed by its list's connector and its gateway device, and names its head or a newer one; naming its very head, it must carry exactly its devices and its restorable removals. A reader checks the same through `verifyList` with its held head (below). A removal carried this way can be put back on the new list. The new list remembers only its members' and carried removals' keys: the set of keys and pins a list has ever refused, across generations, is the connector's to keep (What the caller owes).

**A re-link** gives the gateway device's role back when it was lost while the list went on (design §4.6): Clawtrate on the gateway's machine was reinstalled with new keys and joined as an ordinary device, or a server's first device was removed at the terminal. It is an entry signed by the connector and the device that takes the role, and only on the gateway's machine (over the local channel between the connector and the app) or at the server's terminal; the package can't see where it was made, so that is the caller's.

## The head

The connector signs a head with every change to the list or the card (`signHead(connector, state, secret, card)`): the generation, the list's length and latest entry hash, the secret's epoch, and the card's hash and serial. `verifyHead` checks it against the list's connector key and context and returns a `Head`; `verifyList`, `openList`, `catchUp`, `openCard`, `requireNotOlder` and the seal functions refuse anything else as a head (`bad_argument`). A reader:

- reads a list only with its head: `verifyList` and `openList` refuse a list that doesn't end exactly at its head (`bad_chain`), and take `held`, the newest head the reader holds, as a required argument, `null` only for a device's first read. Against it they refuse a head older than it (`stale_head`: an earlier generation, fewer entries, a lower epoch or card serial), a list on which the held head's own entry isn't found (a fork of any length, `bad_chain`), and, one generation on, a list that doesn't start with a fresh start naming the held head or a later one (`stale_head` for an older list, `bad_chain` for another list of the same length); a reader more than one fresh start behind is refused (`bad_chain`), since it can't check the gap;
- takes a card only as the card the head names (`openCard`, `card_mismatch`);
- seals nothing under a secret older than the newest head's epoch (`sealList`, `sealCard`, `sealEntry`, `stale_secret`);
- answers a join only from its list at its head, with that head's card and secret (`MemberJoin.answer`).

## The join

N is the new device, A a device member. Each side is an object with one-shot state kept inside the package; the service carries every message.

**The rules the words rest on.** The figure of one chance in 2^33 (about 8.6 billion) for someone in the middle holds only while N reveals at most once per commitment and A answers a commitment once. After one reveal, anyone who saw it can compute N's words for any answer, so a second reveal would let the service grind an answer offline until N shows the words a member is showing for the service's own device. So:

- `NewDeviceJoin` holds N's nonce privately and takes exactly one answer. The same answer again gets the same reveal, byte for byte (resuming after a dropped connection, within this one live object); any other answer ends the join for good (`join_spent`), and nothing more is revealed or finished. A second `NewDeviceJoin.start` from a list key a join has already started from in this running program is refused (`join_spent`): a new object from the same keys and random bytes would have the same commitment and would never have revealed. Across a restart the package can't see, so the caller owes it: an attempt never outlives its object, and nothing of it (its keys' seeds or its random bytes) is stored before the join has finished.
- `MemberJoin` derives A's answer nonce from A's key, the commitment and the head A answers from, so the same commitment at the same head always gets the same answer, byte for byte, and never a second, different one. It takes one reveal (the same reveal again gets the same sets) and confirms once. One join is open per member key in a running program: a second commitment while one is open ends both (`join_spent`, design §4.4 step 2); answering the same commitment at the same head again gets the same object back. `end()` closes a join without a pick.
- A `finish` that fails ends the attempt: the service gets no second try at that join.

The steps:

1. **`NewDeviceJoin.start(device, context, random, clock)`** (N): the commitment to N's record (every public key, the TLS pin, the name and platform) and N's derived nonce; `commit` is the message. Refused (`paused`) while `clock.nowMs` is before `clock.pausedUntilMs`.
2. **`MemberJoin.answer(member, commit, clock)`** (A): A must be a current device member at its newest head, holding that head's card and secret; refused while A's own pause lasts. The answer holds A's list key, the list's latest entry hash, the card's hash and A's derived nonce. A has not seen N's keys.
3. **`reveal(answer)`** (N): checks that the answer answers its commitment, computes the transcript hash over the gateway id, account id, commitment, A's key, the list head, the card hash, A's nonce, N's record and N's nonce, and signs it with its list key, which also proves it holds that key. Returns the reveal and N's three words.
4. **`choices(reveal)`** (A): checks that the reveal opens the commitment (`commitment_mismatch`), that its transcript hash is the one A computes (`transcript_mismatch`), that its signature verifies, and that N's keys are new to the list and the list has room for N (`list_full`). Returns five sets: the right one at a uniformly random place, and four decoys A derives, sharing no word with the right set or each other.
5. **`confirm(pick, random, nowMs)`** (A): `pick` is the three words of the set the person picked, compared with the transcript's own words, or "none-match" or "not-started"; words that weren't among the five sets shown are refused. A right pick signs the entry adding N (with the transcript hash), seals the list secret and the card to N's seal key inside A's signed confirmation, and returns the word back to show. Anything else signs a refusal and tells A to answer no join until `pauseUntilMs` (an hour). `refuseJoin(member, commit, reason, nowMs)` signs a refusal without a pick: "I didn't start this" before the sets, or two joins at once, which pauses nothing (`pauseUntilMs` null). For "I didn't start this" the member's app ends its open join, sends the refusal to the connector (directly when it is connected to the gateway, through the service otherwise), keeps `pauseUntilMs` as its own pause, and tells the person to secure their Google or GitHub account.
6. **`finish(confirm, sealedList, head, held)`** (N; `held` the newest head N holds, `null` when it holds none, as on a first join): makes every check, in this order, before anything else: (1) the confirmation answers this transcript and is signed by the member key the words covered; (2) its entry adds exactly N's record, carries this transcript and follows the head the words covered; (3) the delivery opens, and the card's hash is the one the words covered; (4) the sealed list opens with the delivered secret, verifies from its first entry against the connector's head that came with it and against `held`, holds the covered head with N's entry (byte for byte the confirmation's) right after it, and has N as a current member; (5) the confirming device is a current device member of that list; (6) the card verifies against the connector key in that list's first entry, is for this gateway, and is the card the head names. Anything that fails throws and ends the attempt. It returns only the word back's prompt: N's three words, once, and five words.
7. **`pickWord(pick, nowMs)`** (N, the word back): `pick` is the word the person picked together with the three words it was shown under, which must be N's own, or "none-match" or "not-confirmed". The right word hands back the result: the list secret, the card, the list and its head, and the confirming device's name. Anything else discards everything N was sent and ends the attempt, and tells N to start no join until `pauseUntilMs` (an hour). It picks once.

**The word back** (design §4.4 step 5a). A's confirmation word is the first 11 bits of `taggedHash(join confirmation word, transcript hash, A's confirmation signature, card hash)`, shown always under N's three words and N's name, for at most `WORD_BACK_MS` (two minutes). N's five words are that word at a uniformly random place and four others, none equal to it, to each other or to N's own three words above them, drawn as the decoy sets are from 256 bytes of HKDF-SHA256 with N's list key's random bytes as input, the transcript hash as salt, and the `join word back decoys` tag and A's confirmation signature as info. The word's bits protect nothing against the service, which sees every real confirmation and can steer a fake one's word; what protects N is that a real device of the person's shows a word for this join, now, under N's own three words. A fake join beside a real one shows other three words, which match only once in 2^33.

**A server's first join** (design §8.4). `ServerFirstDeviceJoin.open(install)` takes the connector's key, the context, the card and the epoch-0 secret, and no list: it can't be used on a list that exists; the connector opens one only from the install's own one-time state. It answers one commitment (the same again gets the same answer; another ends it, `join_spent`), shows the sets for the terminal, and on the right number signs the server's first entry with its key alone and seals the first secret and the card to N. N's `finish` recognises the first entry (its prompt's mode is `first-device`, so the device names the server's terminal), makes the same checks with the first entry as the whole list, and on the right word adds its own signature: `result.firstEntry` is the complete first entry, which N returns to the connector, which starts its list from it. Any refusal at the terminal ends it.

Against someone in the middle: N commits before seeing A's nonce and A answers before seeing N's keys, each only once, so a party that swaps either side's keys gets matching words only with probability 2^-33 per try, and can't try in advance. An old confirmation fails against a new transcript, and an entry appended twice fails the chain. Someone who picks one of the five sets without looking at the new device is right one time in five; someone who presses any of the seven choices at random, one time in seven. Someone who compares only the first word, or two words, is protected only to 2^-11 or 2^-22. Anyone who can talk to the person can tell them the right set; the decoys don't help against that. A first pick made without looking leaves the word back nothing to add.

## Refusals and the pause

`verifyRefusal(state, refusal, replacedWithinHour)` is the connector's check (design §4.5): signed by a current device member, for this gateway and account, naming the latest entry hash of a head that was current at any time within the last hour: always the current one (`state.head`), however long the list has been quiet, or one of `replacedWithinHour`, the latest entry hashes of the heads replaced in the last hour, which the connector keeps with their times (`stale_head` otherwise). So neither a quiet list nor moving the head first voids a refusal. It returns the refusal's hash, by which the connector takes each refusal once, keeping that mark for as long as the head the refusal names stays current, plus an hour, so a replay can't start a new pause; and whether it pauses joins: every reason but two joins at once.

## The list secret

Every secret is derived inside the package (above), never handed in. At linking, `sealFirstSecret(connector, state, random)` derives the first secret (epoch 0, at the first entry), seals it to the linking device alone and signs it, naming the first entry, and returns the message and the secret; the message goes over the local channel between the two, never through the service, and `openFirstSecret` opens it. On a server, `ServerFirstDeviceJoin.open` derives the first secret from the install's random bytes (at generation 0, length 0 and a zero entry hash, since no list exists yet), and it travels in the first join's confirmation. Each joining device gets the current secret in its confirmation.

After a removal or a restore, and only then (`bad_target` from any other state), `rotateListSecret(connector, state, held, random)` derives the next secret (the held one's epoch plus one, at the removal or restore), seals it to each current device member alone, signs the whole naming the position it follows, and returns the rotation and the new secret. Since every secret's derivation names its own position and a strictly higher epoch, no secret the list has used is issued again (and the new one is checked against the held one, `stale_secret`): a removed device still has the old bytes. The connector then signs a head with the new epoch and reseals the list and the card under the new secret. A removed device has no share, and its old secret opens nothing sealed after: the epoch is in the header and the associated data, and the key is another.

A device takes a rotation with `catchUp(member, held, newest)` (design §4.2.1), one change behind or several, needing nothing in between. `held` is what it holds (its list, its newest `Head` and its secret); `newest` is the newest rotation naming it, the newest sealed list and the newest head. In this order: (1) the rotation is the held list's connector's, for this gateway and account, newer than the held secret (`stale_secret`), and the device's own share opens; (2) the newest list opens with that secret; (3) it verifies against the newest head, whose epoch must be the rotation's (`stale_secret`), and against the held head, as `verifyList` does; (4) the rotation's position is on that verified list, is a removal or a restore, and its recipients are exactly the devices there, in order (`bad_chain`); (5) the secret differs from the one held (`stale_secret`). It returns the secret, the verified list and its head together, or throws and returns nothing.

A stored secret is read back with `ListSecret.restoreStored(bytes, epoch)`, only from what its holder stored with `exportForStorage()`.

`openList`, `openCard` and `openEntry` only open and verify together: a list comes back as its verified state at its head, a card checked against the list's connector key, gateway and head, an entry appended to the given state.

## Errors

Every refusal throws `AccountProtocolError` with a `code` (see `src/errors.ts`). Messages are fixed text: no key, secret, nonce or value from the input is ever in one.

## What is stated rather than enforced

- **Timing.** Secret bytes are compared in constant time where they are compared at all (`equalBytes`), and the AEADs compare their own tags. Every other comparison is of public values. Noble's Ed25519 and X25519 run on JavaScript's BigInt, and JavaScript can't promise constant-time scalar arithmetic. An HPKE opening runs only after a signature check, so no unauthenticated peer drives a seal key's Diffie-Hellman.
- **Derivations from a list key.** Each takes the key's random bytes as HKDF's input and, where there is one, a salt an attacker may influence (the caller's random, the transcript hash). That rests on HMAC being a PRF keyed by either input (its dual-PRF property), the usual assumption for HKDF used this way.
- **The pair on the new device is the person's reading.** That the word back's word appears under N's own three words, on a real device of the person's, now, is what the person sees and checks; the package can make the word and the decoys right, not make the person look.
- **What a caller gets back.** The byte arrays inside returned heads, cards, refusals, results and states are the caller's own copies: changing one changes nothing the package holds.
- **The internal-import fence.** A lint rule for the whole repository refuses an import, export or `import()` of the package's `src/` files from outside it, in every spelling of the path (repeated slashes and `./` segments included).
- **Strict signatures.** A signature whose R is the identity point is refused here although OpenSSL accepts it (`ed25519-edges.json` records both answers): the accepted set is inside what every common implementation accepts.
- **Neither AEAD commits to its key** (the list seal's XChaCha20-Poly1305 and HPKE's ChaCha20-Poly1305). No setting here needs it: everything sealed is a signed object checked again after opening, each opening tries exactly one key, and the keys are 256-bit random. If a sealed object ever carries meaning its signature doesn't cover, use a committing AEAD or prepend an HMAC of the key.
- **The words' numbers.** The words are bits 0 to 10, 11 to 21 and 22 to 32 of the words hash; the decoys and the place are uniform and secret to A. From its traffic the service learns only whether a pick was right, or which refusal reason came back.
- **Crossing protocols with OpenClaw's device signatures.** The package never signs with a gateway device key, every message it signs begins with `clawtrate account `, and no key may hold two roles on a list (an OpenClaw key a withdrawal freed comes back only as an OpenClaw key). Whether OpenClaw's own signed hello could ever begin with those bytes is not established here.
- **Only the list key's possession is proven at the join.** A member could list another device's OpenClaw key under its own entry; "says it is" and "what it caused" cover that.
- **What a head leaves.** A device that can't reach the connector can be kept at the newest head it has, though never shown an older one; a device restored from a backup forgets the newest head it had seen and starts again from what it reads.

## What the caller owes

One list, for the connector, the service and the apps:

- Fresh random bytes for every key and every `random` argument, from the system's random source; fresh keys and a fresh `NewDeviceJoin` for every attempt (the same keys with the same random bytes give the same commitment, which a service may already have seen opened).
- An attempt never outlives its object: resuming means resending within one live `NewDeviceJoin`; after a restart of the app before the word back, the app discards that attempt's keys and starts again with new ones; it never stores an attempt's random bytes or key seeds before the join has finished. The package refuses a second start from one list key only within a running program.
- One `MemberJoin` per commitment, never a second built from other bytes to get around one's refusal; `end()` when the person closes a join or it times out.
- The pauses: keeping each `pauseUntilMs` and passing it back as `clock.pausedUntilMs` (N's after a refused word back, a member's after its refusal); for "I didn't start this", also sending the refusal to the connector and telling the person to secure their Google or GitHub account.
- The connector's pause: keeping, with their times, the latest entry hashes of the heads it replaced in the last hour, and passing them as `replacedWithinHour`; taking each refusal once by its hash, keeping that mark for as long as the head it names stays current plus an hour.
- Clearing the confirmation word by `showUntilMs` or when the join ends, and showing it always under N's three words and name; showing N's prompt in `first-device` mode as "the word your server's terminal shows".
- Keeping the newest head as its signed bytes (`head.bytes`), verifying them again with `verifyHead` when read back, and passing the `Head` as `held` (`null` only for a device's first read) and to the seal functions; keeping a stored secret only through `exportForStorage` and `ListSecret.restoreStored`.
- The connector signing a head with every change to the list or the card, and never reloading its list or head from the service; the service keeping the newest list, card and head, and for each device the newest rotation naming it, which is all `catchUp` needs.
- The connector's decisions: rotating after every removal and restore, then signing a head and resealing the list and card; withdrawing an entry that doesn't pair within ten minutes; starting a list afresh past 900 entries; never calling `signRemovalOnGatewayMachine` for a request that came through the service; making a re-link only over the local channel on the gateway's machine or at the server's terminal; opening a `ServerFirstDeviceJoin` only from the install's one-time state, and closing it when the terminal closes or after 30 minutes.
- The connector's burned set: the keys and pins its list has ever refused, kept locally across every generation, and an add naming one refused. A fresh start carries only current members and restorable removals, so the new list's own checks no longer know the rest.
- The service's part: one account per session key, each challenge taken once.
- What the package can't wipe: JavaScript can't promise that a secret leaves memory.

## What the package does not do

- No I/O, no storage, no clock and no randomness of its own.
- It doesn't make or check passes, TLS certificates, the direct listener, or anything the gateway is asked.
- It checks a name's characters, not its meaning: two devices may say the same name, and look-alike letters remain possible.

## Checks

`test/` holds: known-answer vectors (`test/vectors/account-v1.json`, every signed object, the transcript, the words, the word back and each sealed thing, from fixed keys and randomness, with every signature also checked by Node's own Ed25519); vectors from the standards (`test/vectors/standards.json`: RFC 8032's Ed25519 tests, RFC 9180's A.1.1 key encapsulation and A.2.1, the XChaCha20-Poly1305 draft's A.3.1) and the Ed25519 edge cases (`test/vectors/ed25519-edges.json`), each accepted here only when OpenSSL accepts it too, with OpenSSL's own answer recorded; the word list's published hash; a cross-kind check of every pair of seventeen signed kinds under one key, and of each kind signed without its label; a field-by-field tamper check of every message; the one-shot and per-key rules, the derived values and secrets, the word back and the pauses; hand-built, validly signed counter-examples for each of N's checks, the connector's refusal check, and each catch-up check; the head against cut, forked (of any length) and older lists and cards, and across a fresh start; every list refusal, the growth limit with removals past it, the withdrawal, the fresh start, the re-link, "what it caused", the secret's rotation, catch-up and first message and a removed member's blindness; a server's first join; tests of each construction that the vectors alone would otherwise guard; and seeded fuzzing of every decoder and of list verification. Each rule's test was checked by undoing the rule alone and seeing the test fail.
