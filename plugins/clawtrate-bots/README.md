# clawtrate-bots

Clawtrate's plugin for bots. Two designs: `docs/design/main-bot-onboarding.md`, sections 5 to 10 (the records), and `docs/design/bots-in-clawtrate.md` (#669: where a run came from and the read tools).

So far:

- **The records**, and **the journal and Undo**. It keeps proposals and agent grants, decides admission, decline and revocation, and holds the claim, journal, crash settling and Undo that Apply needs. It writes nothing to any bot. On OpenClaw 2026.10.6 no stored request can be applied (section 17), so accept and Undo always refuse, and the journal stays empty. Apply runs only in the unit tests, through a stand-in for the gateway's missing conditional writes (`test/harness.ts`, `standInApply`); `index.js` gives the plugin none, and a test checks that.
- **Where each run came from**, and whether it has read anything from outside (`lib/origins.js`); and **three read tools**, `clawtrate_here`, `clawtrate_tasks` and `clawtrate_bots` (`lib/here.js`, `lib/runs.js`). Its `before_tool_call` (`lib/hooks.js`) records each call and decides none: the holds on the tools a bot already has come next. Below, from "Where a run came from".

No gateway gets this plugin yet: Clawtrate installs it in a later step of #669. Until Clawtrate's own record of the messages it sent exists (that design's step 1 and 3), the plugin never treats a call as the person's ask (A): a run typed on the gateway's own chat is at most B.

Every method but the reads needs a person's own connection: a direct operator request over the gateway's socket. An in-process call, such as a turn with no operator (research finding R6), is refused with `operator-required`, even when it reuses a client.

`relay.propose` trusts the authenticated admin connection that sends it to say which grant and generation it acts for. Another admin could send the same pair, and neither value proves which helper sent the request. So the app's relay must take the pair from the helper it authenticated, and keep its own gateway connection out of the helper's reach.

The event `plugin.clawtrate-bots.changed` is empty, at `operator.read`, and fires when a proposal or grant changes, including through expiry or retention. The plugin calls `agents.list` and `config.get`, and `config.patch` only from `managers.set`, for its own entry's `managers`. The plugin declares that path a dynamic read (`registerReload`, `noopPrefixes`) and reads managers with `config.get` when it needs them, so writing them keeps its instance: replacing it would wait on the `managers.set` call that made the write.

## Records

Three keyed stores in the gateway's database (`lib/records.js`): the ledger in a retained namespace, so a decision can always be stored; the versions in a bounded one (512 rows, `overflowPolicy: "reject-new"`), which refuses new records with `records-full` when full; and the journal in a retained one of its own.

- **Versions** are immutable and written once: a proposal's details, or a grant's.
- **The ledger** is one row. It is the only record that decides anything (`lib/ledger.js`), and it changes only through `compareAndApply`. Admission enforces 200 open proposals, 20 per source, and one open proposal per bot and field (a newer one supersedes). Revoking a grant moves its generation on and withdraws its open suggestions in the same update. A claim checks the digest and the grant's generation.
- **Persist first, then publish.** Readers use only versions the ledger refers to.
- **Cleanup** runs at startup and hourly. Proposals expire after 24 hours. The ledger retains settled proposals and revoked grants for 30 days. A stored version can be reclaimed once the sweep has observed it without a ledger reference for a full hour.
- **The journal** (`lib/apply.js`, design §9) holds one immutable entry per confirmed effect, keyed by proposal or Undo, claim attempt and field, written right after the gateway confirms the write and then attached to the claim in the ledger. A claim reserves one space per field (at most 1,000, entries and reservations together), and settling releases the rest. A step is applied only when its entry is attached; one that may have been written without an entry is `unknown`, and the steps after it aren't written. At startup, recovery settles claims a stopped process left `committing`: it finds their entries by key and attaches them, before retention runs. Entries leave after 90 days, or sooner, oldest first, when a claim needs room and their Undo is no longer offered. The orphan sweep scans only the versions, so it never sees an entry still waiting for its reference.
- **Undo** has its own version, by an id derived from the entry it undoes, so a retry finds the first. It reads the field once and writes the journaled value back under that read's token only when the field still holds the journaled result. It's offered for 7 days, until the next change to the same field.
- **When the store fills,** new records are refused with `records-full` until cleanup frees a slot. Active grants can keep the store full beyond 30 days. The cleanup protocol and capacity estimates are in [design §9](../../docs/design/main-bot-onboarding.md#9-for-the-avatar-studio-describe-and-proposal-records).

## Where a run came from

From the gateway's hooks, per run, in memory (`lib/origins.js`). `before_prompt_build` gives the run's id, session, bot, trigger, channel, workspace, its routine (`jobId`) and the provenance of its input; `before_model_resolve` whether its message came with files; `before_message_write` a message that joined a run under way; `before_tool_call` each call's run id, call id and requester; `agent_end` that the run ended. The first three need `plugins.entries.clawtrate-bots.hooks.allowConversationAccess: true`; without it no run is known, and every call is C, a run recorded before access was turned off included: the plugin no longer sees what joins it. A record kept across a change of access, or across any config write (which may have turned access off and on again unseen), is no longer vouched for: every run held then counts as C with something lost, and so do the task sessions, the spawns waiting for one and what their starters had read.

A run is one of: **typed** (the gateway's own chat channel, `webchat`, trigger `user`, no provenance but a person's: necessary for the person's ask, never enough), **chat-app**, **bot-message** (another bot's `sessions_send`), **task**, **report** (a task reporting back), **routine**, **check-in**, **command-line** or **unknown**. A **task** is every run in a session a bot's own call made: a hidden task by its session's form (`agent:<bot>:subagent:…`), on both versions; a visible one by its provenance on 2026.11.10, and on either version because the plugin saw the `sessions_spawn` (or, on 2026.11.10, `sessions_create`) that made it. A task's first run can start before that call's result names its session, and nothing on a visible task's first prompt ties it to the spawn on 2026.10.6, so a wait is matched to a session only by the result that names it, never by arrival order: while a spawn of its bot waits, a new run of that bot in any session but its main one is **pending**, C with something lost, and becomes the task when the result names its session, or what it otherwise is once no wait it could belong to is left. A person's run in another session is never left recorded as a task. A task carries what the run that started it had read, and "something Clawtrate lost track of" when the plugin doesn't hold that run. A spawn stops waiting for its task's first run once its result names the session or the call fails, including a result whose status is `error` or `forbidden`; the wait ended is the one that call made from that session. A task takes what its starter had read when the call passed, not later; with no record of that, it counts as having read something lost. A run's spawns that never named a task stop waiting when the run ends. At most 64 spawns wait at once across every bot; when a live one is dropped to make room, every new run in the minute after (but a bot's main conversation) is pending until that minute is over. Every run in a task's session is a task, the ones a person types in it later included, until Clawtrate's own record can tell them apart. A call's origin, as the holds will read it: **B** for a typed run (A needs Clawtrate's own record, a later step), **O** for a chat-app run whose requester OpenClaw resolved as its owner (`requester.senderIsOwner`, on the run's own channel), and **C** for everything else: another bot, a task, a routine, a check-in, the command line, a chat-app sender who isn't the owner. A run the store doesn't hold, and a gateway whose version this build doesn't know (it knows 2026.10.6 and 2026.11.10), are C and count as having read something from outside.

A tool finds its own run by its run id on 2026.11.10, and on 2026.10.6, whose tools aren't told it, by the session key and call id `before_tool_call` saw.

**Bounds.** At most 512 runs. When full, an ended run leaves first; with none ended, a new run isn't held: it is remembered as lost, so its calls are C. A run unseen for 24 hours leaves, also when its next prompt is the one that finds it; one that hadn't ended is remembered as lost too. So is a run first seen at a call or a result rather than at its first prompt: one under way when the plugin was loaded, enabled or given conversation access. A lost run is C and is never admitted as new while it is remembered: the plugin remembers the last 512 lost runs, oldest first out. Once it has forgotten one to make room, it can no longer tell a new run from a forgotten one, so for a day after that every run it hasn't seen is admitted as having read something it lost track of. The call lookup keeps 2,048 entries and the task sessions 512, oldest first out. After a gateway restart the store is empty: every call is C until a new run's first prompt.

## Read from outside

A run is marked, once, with the first source, when (design 4.3): a call passes the hook, for every tool but `ask_user`, `progress_card`, `sessions_spawn`, Tool Search's `tool_search` and `tool_describe`, and the wrappers `tool_call` (`dispatch_action` on 2026.11.10) and Code Mode's `exec` cell, whose calls each reach the hook themselves; its message came with files; a message no person typed (another bot's, the system's) joined it; or any message joined a chat app's run. Tool Search's controls return the catalog's own names and descriptions, which a run without Tool Search has in its tool list and which mark nothing there either, so an MCP server's or another plugin's description is a standing residual in both modes, not outside content. A call is marked as it passes, not when its result comes back, so a later call in the same Code Mode cell already sees it. Clawtrate's own read tools mark it when their answer holds text a bot may have written (below).

**Steers (design 4.3).** A message that joins a run already under way is outside content when no Clawtrate device sent it. The plugin alone can't tell which messages a device sent: for a typed run it counts them for Clawtrate's own record (#669's step 3) and marks nothing yet; for a chat app's run, where no record will ever tell the owner's message from another sender's in a shared chat, any message that joins marks the run (source `steer`).

## The read tools

Each answer is at most 8 KiB and only about this bot.

- **`clawtrate_here {}`**: whether this conversation is in Clawtrate: "can't tell yet" for a typed run, since the plugin alone can't tell Clawtrate from the gateway's web page or another app, and "no", with why, for every other origin; whether the run has read anything from outside; this conversation (main or a task, and who started it); what the person sees in Clawtrate; the bot's model, effort, how it runs commands and its check-ins. It returns no name or title: until Clawtrate's record says who set each field, any of them could be a bot's, so nothing it returns is outside content.
- **`clawtrate_tasks { state?, limit? }`**: the bot's tasks (not its main conversation) and the ones it started under other bots, newest first, with the gateway's state. A title may be a label a bot gave, so an answer with a title marks the run.
- **`clawtrate_bots { find? }`**: with `find`, the bots whose name is that name among every other bot, by id, whether this bot can reach each now, and its account; no name text, so it marks nothing. Without it, every other bot with its name, which marks the run, since a bot may have chosen its own name.

## Failing safe

The hook only records, and never throws: both OpenClaw versions block a call when a `before_tool_call` handler throws or takes 15 seconds (their global hook runner runs it fail-closed), so a recording failure is caught and logged, and the call goes on. A run the store doesn't hold, conversation access turned off, and a version this build doesn't know all leave a run unknown: C, and counted as having read something from outside.

## Tests

```sh
pnpm exec vitest run plugins/clawtrate-bots
node plugins/clawtrate-bots/test/gateway-check.ts   # starts and resets its own development instances
pnpm dev-gateway start --instance bots --with-plugin clawtrate-bots
node tools/dev-gateway/src/bots-checks.ts --instance bots
```

The checks leave behind the tasks and routines they make, and some use fixed labels a gateway accepts once, so run them on a fresh instance, or `pnpm dev-gateway reset --instance bots` before running them again. `pnpm scenarios` runs the same checks (`tools/dev-gateway/src/bots-checks.ts`) on an instance of their own.
